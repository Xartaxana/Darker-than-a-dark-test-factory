# BUG-072 — обещание «retry Undo после отказа на потолке» не реализуемо в UI

## Окружение

Найдено критик-входом приёмки верификации BUG-016 (fix-verifier, D1),
2026-08-16, сборка `aa377e0ec9664fcd5439fec9391638fabf94f448`
(dev-local, versionCode 12). Не воспроизведение экшена пользователем —
находка чтением кода `app-under-test/` (read-only, ни одного изменения
в код приложения не внесено).

## Суть дефекта

Фикс BUG-016 (`aa377e0`) переписал `BrowserViewModel.restoreClosedTab`:
чтение снапшота `closedTabSnapshots[token]` БЕЗ немедленного удаления,
проверка потолка `if (state.tabs.size >= MAX_TABS)` ДО удаления —
цель, по KDoc метода (`BrowserViewModel.kt:362-363`): «so the user can
close a tab and retry Undo instead of silently losing the tab».
`app-under-test/PROJECT.md:31` несёт то же обещание: «keeps the
snapshot (nothing is silently lost)».

Фактически `restoreClosedTab` имеет **ровно один вызов** во всём
приложении — `MainActivity.kt:325`, внутри
`if (result == SnackbarResult.ActionPerformed)` обработчика снекбара
«Tab closed / Undo». Нажатие `Undo` **потребляет** этот снекбар
(стандартная семантика Android `Snackbar` — одно действие на показ);
повторного снекбара с тем же токеном показано не будет. У пользователя
физически нет UI-пути повторно вызвать `restoreClosedTab` с тем же
`token` после первого отказа на потолке — сохранённый снапшот
недостижим, вкладка теряется безвозвратно, отличие от исходного бага
только в том, что теперь пользователю ЯВНО показан диалог «Tab limit
reached» вместо молчания.

## Верификация находки (критик-вход BUG-016)

- `grep -rni restoreClosedTab app-under-test/` → ровно 1 вызов
  (`MainActivity.kt:325`), плюс определение и KDoc.
- Живая проба: после отказа на потолке (диалог показан) снекбар Undo
  отсутствует на экране — независимо перепрогнано критиком, зелёная
  (сценарий подтверждает недостижимость).
- `git -C app-under-test log --oneline -- PROJECT.md` — класс
  «код↔документация разошлись» уже чинился в этом репозитории
  коммитом `27d5cfd` («Correct two PROJECT.md claims that contradict
  the code»); этот случай — рецидив того же класса, не новый (D-0043).

## Критерий готовности (рекомендация для разработчика)

Одно из двух (решение — за разработчиком/product-владельцем):
1. **Реализовать обещанное:** дать пользователю реальный способ повторно
   вызвать Undo для сохранённого снапшота при потолке (например, снекбар
   с Undo переиспользуется/перепоказывается вместо потребления при
   отказе по потолку).
2. **Поправить обещание:** переписать KDoc `BrowserViewModel.kt:362-363`
   и `PROJECT.md:31` под фактическое поведение («снапшот больше не
   сжигается впустую, пользователю явно объяснена причина отказа»,
   БЕЗ утверждения о возможности retry) — тогда это не дефект, а
   документационная правка.

QA не занимает позицию по выбору — баг заведён, чтобы решение было
осознанным, а не молчаливым расхождением.

> 
> Выбран третий вариант — не «реализовать retry» и не «поправить обещание», а убрать саму ситуацию, в которой retry нужен: снекбар «Tab closed» теперь **скрывается при открытии новой вкладки**. Открытие вкладки — явный сигнал, что пользователь ушёл от отмены, поэтому предложение Undo снимается, и устаревший Undo больше не может встретить занятый потолок.
> 
> Как сделано:
> 
> - `BrowserUiState.tabOpenSeq` инкрементируется на каждом пользовательском `openTab`; `LaunchedEffect(tabOpenSeq)` в `MainActivity` закрывает видимый снекбар, если его текст — «Tab closed» (другие снекбары, например «Opened in background», не трогаются).
> - Внутренний `openTab` (домашняя вкладка, заменяющая закрытую последнюю) помечен `userInitiated = false` и снекбар не гасит.
> - Ветка потолка в `restoreClosedTab` оставлена как защитная: снапшот по-прежнему не сжигается, но дойти до неё из UI больше нельзя.
> 
> KDoc `restoreClosedTab` и `PROJECT.md` переписаны под фактическое поведение — обещания «retry Undo» там больше нет.
> 
> Проверено на эмуляторе с контролем по времени (снекбар живёт ~4 с, а один `uiautomator dump` стоит ~2.4 с, поэтому в каждой пробе ровно один дамп на одинаковом смещении): контроль — снекбар виден на T+0.7 с; проба — на том же T+0.7 с после открытия вкладки снекбара уже нет. Undo без открытия вкладки по-прежнему восстанавливает вкладку.
> 
> Побочное наблюдение: закрыть **последнюю** вкладку из UI нельзя — `TabStrip` рендерится только при `tabs.size > 1`, а `restoreClosedTab` вызывается только из обработчика снекбара. Так что ветка `userInitiated = false` защитная, а не рабочая.
