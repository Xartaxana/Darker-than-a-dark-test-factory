# AT-BUG-063 — device-liveness recovery игнорирует GPU-конфиг live-прогонов

## Окружение
- Эмулятор emulator-5554, WHPX-гипервизор, Appium 2 + UiAutomator2.
- Live-прогон `@pytest.mark.live` с явной предпосылкой `AO3_EMU_GPU=host` 
  (TC-078.md, решение Lead 2026-07-19).
- Прогон: dev-local (source_commit cc201f789f0fb123722bbba7b29b8e0c6412dac1, 
  versionCode 12).

## Суть долга

`framework/core/driver_factory.py:64-67` реализует device-liveness recovery 
(восстановление среды при падении эмулятора); восстановление запускается 
строкой:

```python
cmd = [
    "powershell", "-NoProfile", "-ExecutionPolicy", "Bypass", "-Command",
    f". \"{_TASKS_PS1}\"; Start-Emulator -WritableSystem",
]
```

Команда **не пробрасывает параметр `-Gpu`**, обязательный в TC-078.md 
(решение Lead 2026-07-19): `Start-Emulator -Gpu host`.

**Следствие:** если live-прогон начат под `AO3_EMU_GPU=host` (параметр при 
подъёме), первый же сбой эмулятора триггерит recovery guard (класс 
AT-BUG-026), который **молча перезапускает эмулятор дефолтным 
`swiftshader_indirect`** (tasks.ps1:189, когда `-Gpu` не указан явно).

Этап TC-078 после recovery падает с **той же сигнатурой qemu-краша 
(`0xc0000005`)**, которую предпосылка `host`-конфиг должна смягчить 
(диагностика AT-BUG-021).

**Живое подтверждение в RUN-20260811-0405:** 
- Прогон стартован с явным `Start-Emulator -Gpu host` (PID 15100, 
  командная строка `-gpu host`).
- TC-078 упал в 00:30:51Z–00:31:06Z (WebDriverException: 
  `disconnected: not connected to DevTools`).
- Событие Event Log: `qemu-system-x86_64.exe` краш `0xc0000005` в 00:30:59Z 
  (совпадает с окном TC-078).
- Recovery-guard срабатывает, эмулятор поднят заново (PID 1088, 
  командная строка `-gpu swiftshader_indirect` — БЕЗ host).
- Перепрогон TC-078 с тем же guard'ом окончен: `broken`, crash PID 1088 
  в Event Log в 02:36:10Z (новый краш того же класса на восстановленном 
  эмуляторе).

**Дополнительный контекст (пункт (б) из RUN-20260811-0405, 
раздел "Дефекты-собратья"):** 
Паллиатив 2026-08-04 (из HANDOFF.md, решение Lead в AT-BUG-021): 
"до механизма — повторить предпосылку runbook-строкой в HANDOFF" — 
runbook-строка исчезла из текущего HANDOFF.md. Это третье 
воспроизведение класса:
- 2026-07-19 (заведение AT-BUG-021, fail-fast диагностика).
- 2026-08-04 (RUN-20260804-1317, воспроизведение при Verified, 
  поправка+runbook-решение Lead).
- 2026-08-11 (этот прогон, runbook позабыта).

## Гипотеза причины (механизм, не дефект приложения)

`framework/core/driver_factory.py::_recover_device` восстанавливает 
эмулятор, но берёт команду подъёма из **жёсткого шаблона**, без 
наследования переменной окружения `AO3_EMU_GPU` или другого хранилища 
текущего GPU-режима.

**Почему не помогает переменная окружения:** параметр `-Gpu` явно 
передаётся начальному `Start-Emulator` в канонической форме 
(`Start-Emulator -Gpu host`); переменная `$env:AO3_EMU_GPU=host` наследуется 
дочерним PowerShell-процессом и влияет на дефолт `tasks.ps1:189`, но 
переменная окружения НЕ сохраняется **внутри состояния эмулятора** и 
**не восстанавливается** из него при recovery.

## Кандидат фикса (предложение, не реализация)

Recovery-ветка `driver_factory.py` должна:

1. **Опция 1 — читать из переменной окружения:** при подъёме recovery 
   пробросить `AO3_EMU_GPU`, если задана — 
   ```python
   gpu_arg = os.environ.get('AO3_EMU_GPU', '')
   gpu_flag = f"-Gpu {gpu_arg}" if gpu_arg else ""
   cmd = [...f". \"{_TASKS_PS1}\"; Start-Emulator -WritableSystem {gpu_flag}",]
   ```
   **Минус:** переменная может быть позабыта в конкретном прогоне 
   (прецедент: HANDOFF-runbook).

2. **Опция 2 — читать из состояния живого эмулятора:** если эмулятор 
   ещё жив (не полностью упал), снять GPU-режим из `hardware-qemu.ini` 
   (`Get-CimInstance Win32_Process ... qemu-system-x86_64.exe` и парсить 
   `-gpu <VALUE>` из командной строки), затем пробросить при recovery.
   **Минус:** требует позитивной сверки живости эмулятора перед смертью.

3. **Опция 3 — хранить GPU-режим на диске/переменной уровня сессии:** 
   сохранить выбранный GPU-режим в `state/` или другом статусном месте 
   при инициализации; recovery читает оттуда.
   **Минус:** требует синхронизации состояния, риск несогласованности.

Выбор и реализация — решение Lead/test-maintainer.

## Частота
**Каждый раз**, когда:
1. Live-прогон начат с явным `AO3_EMU_GPU=host` или `-Gpu host`.
2. Во время этого прогона эмулятор упадёт (класс AT-BUG-021/026, 
   вероятностный, но систематический).
3. Device-liveness guard сработает и восстановит эмулятор.

Результат: перезаписанный GPU-режим молча нарушает env-предпосылку.

## Обсуждение

Диагноз failure-analyst (раздел RUN-20260811-0405.md, 
пункт ESC-024 сиблинг (а)): класс ПОДТВЕРЖДЁН, кандидат-фикс предложен.

**test-maintainer, 2026-08-11 — реализация.** Выбрана Опция 1 (кандидат
failure-analyst, наиболее простая, без зависимости от состояния живого
эмулятора/дисковых сторов). Прочитан `_restart_emulator_writable_system`
целиком в контексте `DeviceLivenessGuard` (`framework/core/driver_factory.py`)
— функция вызывается ОДИН раз, из `ensure_ready()`, сразу после того, как
guard решил, что recovery нужен; `timeout`/error-handling вокруг нужного
участка не требовали изменений, правка ограничена сборкой команды.

Изменение:
```python
gpu_arg = os.environ.get("AO3_EMU_GPU", "")
gpu_flag = f" -Gpu {gpu_arg}" if gpu_arg else ""
cmd = [
    "powershell", "-NoProfile", "-ExecutionPolicy", "Bypass", "-Command",
    f". \"{_TASKS_PS1}\"; Start-Emulator -WritableSystem{gpu_flag}",
]
```

**Почему это закрывает баг, а не маскирует.** `subprocess.run(cmd, ...)`
(без `env=`) по умолчанию наследует ПОЛНОЕ окружение python-процесса —
если pytest-сессия была запущена с `$env:AO3_EMU_GPU = "host"` на уровне
PowerShell-сессии (канонический способ по `docs/environment-setup.md:257-258`
и `docs/HANDOFF.md:279-280`), эта переменная видна и python-процессу
(`os.environ`), и порождённому recovery-подпроцессу PowerShell. До фикса
recovery никогда явно не передавал `-Gpu`, поэтому `tasks.ps1::Start-Emulator`
(tasks.ps1:189, `if (-not $Gpu) { $Gpu = if ($env:AO3_EMU_GPU) {...} else
{"swiftshader_indirect"} }`) сама решала, что делать — но ТОЛЬКО если
переменная унаследовалась ЧЕРЕЗ ВЕСЬ путь до неё; данные RUN-20260811-0405
показывают, что на практике этого не произошло (эмулятор был поднят явным
`-Gpu host` отдельной командой, а не через переменную сессии — то есть сама
переменная окружения `AO3_EMU_GPU`, вероятно, не была выставлена на уровне
процесса pytest вовсе). Явный проброс делает намерение НЕЗАВИСИМЫМ от того,
унаследовалась ли переменная случайно транзитивной цепочкой процессов — но
он всё ещё зависит от того, что переменная СУЩЕСТВУЕТ хоть где-то в
окружении python-процесса на момент recovery.

**Известный остаточный операционный риск (НЕ дефект этого фикса, тот же
риск, что называл failure-analyst для Опции 1).** Если операторская сессия
подняла эмулятор ТОЛЬКО явным флагом (`Start-Emulator -Gpu host`) БЕЗ
`$env:AO3_EMU_GPU = "host"` на уровне сессии — переменная не существует ни
в python-процессе pytest, ни, соответственно, в recovery-подпроцессе;
`gpu_arg` будет пустой строкой, `gpu_flag` — пустым, и recovery снова
откатится на дефолт `tasks.ps1`. Runbook (`docs/HANDOFF.md:279-287`) прямо
предписывает переменную окружения на сессию именно для того, чтобы этот
путь работал; операционная дисциплина (не забыть выставить переменную) —
вне скоупа кодового фикса.

**Красная проба (откат чист).** Байтовая копия
`framework/core/driver_factory.py` до пробы снята в scratchpad (permission-
hygiene п.8); `-Gpu`-проброс временно убран (возврат к жёсткому шаблону из
диагноза), новый unit-тест `test_recovery_propagates_gpu_env_var` упал
осмысленно:
```
assert "-Gpu host" in ps_command
E   assert '-Gpu host' in '. "D:\\AO3_tests\\scripts\\tasks.ps1"; Start-Emulator -WritableSystem'
```
— т.е. тест ловит РОВНО диагностированный дефект (отсутствие `-Gpu` в
собранной команде), не что-то постороннее; `test_recovery_no_gpu_flag_when_env_unset`
остался зелёным на сломанном коде (ожидаемо — эта ветка не менялась).
Diff порченого файла против байтовой копии показал ровно 2 удалённые
строки и 1 изменённую (сама GPU-логика) — файл восстановлен из копии,
идентичность подтверждена `diff` (пусто).

**Верификация.** Реальный краш+recovery цикл на живом эмуляторе
непропорционально дорог/рискован для детерминированной проверки в рамках
этой задачи (класс инфраструктурного фикса, который failure-analyst
заранее пометил как "трудно детерминированно триггернуть" — то же
ограничение сформулировано в DoD задачи). Использован **unit-уровень**:
два новых device-free теста в
`framework/tests/test_device_liveness_guard_unit.py`
(`test_recovery_propagates_gpu_env_var`,
`test_recovery_no_gpu_flag_when_env_unset`) монки-патчат ТОЛЬКО
`subprocess.run` (не саму функцию `_restart_emulator_writable_system`, как
остальные пробы файла) и проверяют РЕАЛЬНУЮ собранную командную строку:
`AO3_EMU_GPU=host` в окружении -> `-Gpu host` присутствует в команде;
переменная не задана -> `-Gpu` отсутствует, команда оканчивается на
`Start-Emulator -WritableSystem`. Это доказывает корректность СБОРКИ
команды (единственная новая логика этого фикса), НЕ доказывает, что
`tasks.ps1::Start-Emulator` фактически поднимет эмулятор с этим GPU-
бэкендом на реальном хосте (та часть уже покрыта существующей
диагностикой AT-BUG-021 — `hw.gpu.mode=host` в `hardware-qemu.ini`
подтверждён живым фактом при явном `-Gpu host`) — уверенность средняя:
код-путь доказан юнитом, интеграция с реальным recovery-циклом НЕ
воспроизведена живым крашем в рамках этой задачи (честно, по аналогии
с калибровкой предыдущего воркера AT-BUG-062 — не переоцениваю
доказанность).

Прогоны (все дословные, PYTEST_EXIT=0):

## Обсуждение — rework attempt 2 (test-maintainer, 2026-08-11)

**Почему attempt 1 отклонён.** Critic-вердикт FAIL, эмпирический:
`tasks.ps1:188-189` УЖЕ фолбэчится на `$env:AO3_EMU_GPU`, когда `-Gpu` не
передан явно, и `subprocess.run` БЕЗ `env=` и так наследует полное
окружение python-процесса дочернему PowerShell (критик проверил напрямую:
`os.environ['AO3_EMU_GPU']='host'; subprocess.run([...,"$env:AO3_EMU_GPU"])`
→ `CHILD_SEES=[host]`) — то есть правка attempt 1 была поведенчески
ИДЕНТИЧНА коду до фикса для ЛЮБОГО значения `AO3_EMU_GPU`. Реальный
воспроизведённый сценарий (`-Gpu host` явным CLI-параметром НАЧАЛЬНОМУ
`Start-Emulator`, БЕЗ переменной окружения на сессию — сам диагноз,
`runs/RUN-20260811-0405.md:420-421`) остался НЕ закрыт; attempt 1
процитировал это как «остаточный риск» в `fixed_in`, не осознав, что это
и есть НЕзакрытый баг. Плюс два новых дефекта самой правки: **F3**
(injection) — сырое значение `AO3_EMU_GPU` интерполировалось напрямую в
строку `-Command`: пробел ломал биндинг параметра (сам recovery падал
жёстко — ровно то, чего guard должен избегать), `;` исполнялся отдельной
командой (инъекция), кавычка валила PowerShell-парсер. **F4** (класс
шире) — recovery терял и `-AvdName` (у него не было даже env-фолбэка) —
`framework/tests/test_compatibility.py` (TC-109, AT-BUG-028) требует
второго AVD `ao3_test_api29`, recovery на этом прогоне молча поднял бы
ЧУЖОЙ AVD.

**Реализация (Опция 3, а не 2).** Опция 2 (снять GPU-режим из
командной строки ЖИВОГО qemu-процесса через `Get-CimInstance
Win32_Process`) отброшена — зависит от того, жив ли процесс на момент
краха (часто НЕТ, именно краш и триггерит recovery), и не даёт
`-AvdName` вовсе (AVD не виден в командной строке qemu тем же прямым
способом, что GPU). Опция 3 — `state/emulator-session.json`
(гитигнорится, `.gitignore` дополнен) — `scripts/tasks.ps1::Start-Emulator`
пишет РАЗРЕШЁННЫЕ (пост-фолбэк, параметр > env > дефолт) значения `$Gpu`/

recovery-подпроцессу.

**F3 закрыт МЕХАНИЗМОМ передачи, не только валидацией.** Значения кладутся
в `env=` дочернего процесса (`AO3_RECOVERY_GPU`/`AO3_RECOVERY_AVD_NAME`) —
сама `-Command`-строка ФИКСИРОВАННЫЙ литерал
(`$seArgs = @{ WritableSystem = $true }; if ($env:AO3_RECOVERY_GPU) {...}; ...
Start-Emulator @seArgs`), без f-string подстановки непроверенных данных.
PowerShell резолвит `$env:AO3_RECOVERY_*` как ОБЪЕКТ-значение параметра при
байндинге через переменную — не перепарсивает содержимое как скрипт
(фундаментально отличается от подстановки в исходный текст `-Command`,
который парсер видит и исполняет). Пробел/`;`/кавычка внутри значения
инертны структурно, не благодаря экранированию. Белый список
GPU-бэкендов (`host`/`swiftshader_indirect`/`angle_indirect` —
tasks.ps1:178-182, docs/environment-setup.md, bugs/AT-BUG-021.md) и regex
для AvdName (`^[A-Za-z0-9_.-]+$`) — санитизация мусора (не звать qemu с
выдуманным `-gpu`/`-avd`), НЕ защита от инъекции (та уже закрыта
механизмом передачи).

**Красная проба поймала РЕАЛЬНЫЙ баг (не тестовую придумку).**
Real-PowerShell тест (`test_tasks_ps1_set_emulator_session_state_writes_resolved_params`

## Остаточные риски (границы фикса, честно — не маскировка)

Три оси. Первая была названа failure-analyst ещё в исходном диагнозе как
минус Опции 3; вторая и третья ВСКРЫТЫ критиком attempt 2 и до attempt 3
нигде не были записаны.

**Р1. Протухание state-файла: TTL отсутствует, `updated_utc` не проверяется
(НОВОЕ направление отказа, которого не было ДО фикса).**
`Set-EmulatorSessionState` пишет `updated_utc`, но НИКАКОЙ код на него не
опирался. Если текущий эмулятор поднят НЕ через `Start-Emulator` этой сессии
— пережил прошлый прогон, либо оператор вручную переключил AVD (штатный
сценарий TC-109: `framework/tests/test_compatibility.py:48-66` прямо
предполагает ручное переключение оператором) — recovery применит параметры
ПРОШЛОЙ сессии. До фикса recovery брал безопасный дефолт `ao3_test_api34`;
теперь он может уверенно поднять НЕ ТОТ AVD/GPU. Направление отказа новое,
хотя вероятность ниже исходного бага (который срабатывал ГАРАНТИРОВАННО при
каждом recovery live-прогона).
*Решение attempt 3:* реализована только НАБЛЮДАЕМАЯ половина — `updated_utc`
теперь читается и попадает в диагностическую строку возрастом
(`state записан <ts> (возраст N.N ч)`); битый/отсутствующий `updated_utc`
деградирует до `возраст state неизвестен` и НЕ роняет recovery (покрыто
пробой). ПОВЕДЕНЧЕСКАЯ половина (TTL-отсечка: игнорировать state старше N,
либо сверять его с фактическим `Get-CimInstance` живого qemu) СОЗНАТЕЛЬНО
ОТЛОЖЕНА — это новая граница/лимит, которая по правилу 11 CLAUDE.md требует
собственных проб НА границе и ЗА ней и меняет семантику ядра, снятого
критиком с переработки в этой итерации. Явная известная граница, в очередь
Lead (кандидат: отдельный test_debt либо доработка этого бага после
приёмки).

**Р2. Инверсия приоритета: state ПЕРЕКРЫВАЕТ `AO3_EMU_GPU` текущей сессии.**
`driver_factory._restart_emulator_writable_system` читает state ПЕРВЫМ и
опускается до `AO3_EMU_GPU`, только если state ничего не дал. Между тем
runbook (`docs/HANDOFF.md:280`, `docs/environment-setup.md:257-258`) называет
переменную окружения сессии КАНОНИЧЕСКИМ способом заявить предпосылку
прогона — то есть протухший state теперь может погасить актуальную
env-заявку оператора.
*Почему порядок НЕ перевёрнут в attempt 3:* оба порядка защитимы, и выбор
неоднозначен. `tasks.ps1::Start-Emulator` имеет собственный приоритет
`параметр > env > дефолт`; state отражает УЖЕ РАЗРЕШЁННОЕ значение реально
поднятого эмулятора, то есть по смыслу это «параметр», и env-first сломал бы
случай «env=host, но эмулятор поднят явным `-Gpu angle_indirect`». Инверсия
приоритета — семантическое решение по ядру, которое эта итерация по условию
эскалации не переделывает.
*Решение attempt 3:* реализована наблюдаемая половина — при РАСХОЖДЕНИИ
(state несёт одно, `AO3_EMU_GPU` сессии другое) печатается явный
`WARNING: КОНФЛИКТ источников GPU — ... Применяется <state>` с подсказкой
(поднять эмулятор канонической формой заново либо удалить
`state/emulator-session.json`). Молчаливого гашения env больше нет; сам
порядок — известная граница, вопрос приоритета в очередь Lead (при решении
менять — это затрагивает runbook/предпосылки live-прогонов, т.е. нужен
проход test-strategist, не только test-maintainer).

**Р3. Файл машинного, а не сессионного уровня (перенос из attempt 2,
подтверждается).** Чужой `Start-Emulator` на той же машине МЕЖДУ подъёмом
этой pytest-сессии и её recovery будет унаследован. Проект дисциплинирует
однопоточное использование эмулятора на хосте
(`docs/environment-setup.md`) — риск операционный, вероятность низкая, но не
ноль.
