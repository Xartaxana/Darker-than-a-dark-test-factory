# BUG-082 — Снекбар «Continue reading at N%?» (Resume) предъявляется поверх чужой вкладки и его действие невидимо пользователю

## Окружение
- Версия приложения: source_commit fdd3f728 (versionCode 12)
- Режим: replay и live-тестирование
- Найдено: exploratory charter CH-011 (2026-08-20), гипотеза Г4 (четвёртый носитель позиции скролла — Room WorkRating.readProgress*)

## Контекст (архитектурный класс)

Снекбар «Continue reading at N%?» рождается из Room-таблицы WorkRating.readProgress*, вызывается через `BrowserViewModel.maybeOfferResume:583` и записывает ГЛОБАЛЬНОЕ поле `uiState.resumeOffer` **БЕЗ guard'а** по активной вкладке. Это четвёртый независимый носитель позиции чтения (сверх трёх известных: нативный WebView-скролл, HistoryEntry.scrollY в prefs, производный FAB `_activeScrollY`). 

Классовый сиблинг: BUG-068 (архитектурный паттерн «колбэк пишет ГЛОБАЛЬНОЕ поле БЕЗ guard'а»). Отличие: BUG-080 — guard ЕСТЬ, но пересчёта на дверях смены вкладки нет; здесь guard'а НЕТ ВОВСЕ.

## Шаги воспроизведения (Given-When-Then)

### Сценарий (а): Оффер предъявляется поверх ЛИСТИНГОВОГО экрана при релонче

**Given**
1. Приложение запущено, экран Browse с листингом (маркерная страница)
2. Активная вкладка на листинге
3. Некий work открывался и был прочитан на 76%

**When**
- Kill + релонч приложения (`app_steps.restart_app_via_adb_asserting_new_process`)
- Первые 10 секунд после стартовки: активная вкладка остаётся листингом
- Room-восстановление срабатывает и генерирует `maybeOfferResume`

**Then (ожидалось)**
- Снекбар может предъявиться, но только если на экране обозреватель со скачанным work'ом (вкладка-владелец)
- Тап «Resume» скроллит ВИДИМую вкладку или переключается на соответствующую

**Actual (фактически)**
- Снекбар «Continue reading at 76%?» появляется на 7.9 с и ВИДИМ пользователю, но он смотрит на листинг
- Тап кнопки «Resume» не производит НИЧЕГО наблюдаемого (8 замеров / 12 с: активная вкладка остаётся листингом, URL не меняется, все позиции статичны, полоска прогресса без изменений)
- По коду `acceptResumeOffer:611` исполняет скролл в НЕВИДИМОЙ вкладке-владельце (та, что содержит work с 76% progress)
- Пользователь думает, что функция не сработала

### Сценарий (б): Оффер всплывает поверх экрана Library при фоновом открытии

**Given**
1. Приложение запущено, Library открита
2. Некий work в библиотеке уже читался ранее на позиции >= 5% (порог MIN_PROGRESS_PERCENT)

**When**
- Пользователь видит экран Library (браузер не видна)
- Long-press на карточку work → «Open in background tab»
- Фоновая вкладка грузится, Room повторно записывает readProgress*, генерирует `maybeOfferResume`
- Снекбар появляется на 4.95 с

**Then (ожидалось)**
- Оффер предъявляется ТОЛЬКО на экране, где пользователь может его использовать (Browse)

**Actual (фактически)**
- Снекбар видим поверх Library, пока пользователь листает карточки
- Пользователь может тапнуть «Resume», но действие бьёт по фоновой вкладке

### Сценарий (в): Оффер предлагает перейти туда, где пользователь УЖЕ стоит

**Given**
1. Приложение запущено, холодный старт
2. Во время восстановления вкладок: одна вкладка содержит work, восстанавливается на позицию 0.76 scroll-progress

**When**
- Вкладка-владелец восстанавливается пиксельно в ту же позицию (контроль: полоска показывает 0.76)
- `maybeOfferResume` срабатывает и предлагает 76%

**Then (ожидалось)**
- Если вкладка УЖЕ на целевой позиции — оффер не предъявляется (сверка `offer.url != currentUrl` + текущая позиция >= целевая)

**Actual (фактически)**
- Оффер всё равно предъявляется пользователю: «Continue reading at 76%?» на позиции, которая УЖЕ 76%
- Пользователь видит пустое действие

## Частота
(а) Наблюдено в первом же прогоне; (б) 4.95 с в одном из прогонов CH-011; (в) Контроль: полоска 0.76 + оффер.
Всегда воспроизводится (0/3 отклонений в трёх дверях).

## Анализ

Корень — `uiState.resumeOffer` пишется из Room-обновления, срабатываемого `onReadingProgress` (пишется ПЕР-ВКЛАДОЧНО) и `maybeOfferResume` (`:1340-1355`), но нет проверки:
1. **Активна ли вкладка-владелец** в момент предложения (guard `tabId == activeTabId`)
2. **Видимый ли экран** (guard `currentScreen == BROWSE`)
3. **Уже ли пользователь на целевой позиции** (guard `currentScrollY >= targetScrollY - tolerance`)

Три независимые двери:
- На дверях смены активной вкладки (closeTab / switchTab / openTab / deep-link / фоновое открытие) оффер переживает смену и предъявляется новой активной вкладке, которая не имеет отношения к исходному work'у
- На дверях смены экрана (Library, Settings) оффер остаётся видимым, хотя браузер скрыт, и пользователь не может выполнить действие или не понимает, к какой вкладке оно относится
- Если целевая позиция УЖЕ восстановлена (`acceptResumeOffer:611` вызывает `ao3ScrollToPercent`, `:1076`, но проверка запроса ≠ guard'у на предложение), пользователь видит бесполезное действие
