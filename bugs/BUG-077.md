# BUG-077 — Прогресс чтения не сохраняется и не синхронизируется; нарушает требование R-18 (мультиустройственная синхронизация)

## Окружение
- Версия приложения: dev-local (versionCode 12)
- Сборка: debug, source_commit aa377e0e (2026-06-28)
- Тип анализа: code inspection WorkRating.kt, LibraryJson.kt, SyncRepository.kt

## Требование владельца (R-18, docs/01-test-strategy.md §5)
> Должна работать так, как будто человек читает одну и ту же книжку на всех устройствах.

Конкретизация для прогресса чтения:
> Прогресс чтения переносится [между устройствами]

## Проблема

**WorkRating.kt (данные)** не содержит ни одного поля для отслеживания прогресса чтения:
- WorkRating имеет 11 полей (строки 7-19): `ao3Id, title, author, url, rating, timestamp, fandom, wordCount, comment, downloadPath, tags`
- **Отсутствует:** `readProgress`, `scrollPosition`, `readingPosition`, `progressPercent`, `currentChapter`, `pageNumber`, или любой другой маркер прогресса чтения

**LibraryJson.kt (синхронизация)** не публикует и не принимает прогресс:
- `workToJson()` (строки 18-32) не сериализует никаких полей прогресса
- `workFromJson()` (строки 35-54) не десериализует никаких полей прогресса

**SyncRepository.kt (движок синка)** не имеет маршрута для перемещения прогресса:
- При публикации (строка 206): `LibraryJson.workToJson(it, includeDownloadFile = false)` публикует только базовые поля
- Merge (последняя запись побеждает) не может работать с несуществующим полем

**Grep-подтверждение** (позитивный контроль поиска):
```
Grep по readProgress|scrollPosition|readingPosition|progressPage|currentChapter
→ 0 совпадений по всему app/src/main
```

## Шаги воспроизведения (Given-When-Then)

**Given** пользователь открыл работу (скачанный файл или WebView) на устройстве A

**When** пользователь читает несколько страниц/прокручивает на позицию 35% работы

**Then (ожидалось по R-18)**
1. Прогресс сохраняется локально (app-side, не просто WebView state)
2. Синхронизируется на устройство B при следующем синк-проходе
3. Устройство B открывает работу на той же позиции (35%), где пользователь остановился на A

**Actual (фактически)**
Прогресс не сохраняется в базу, синхронизация его не передаёт, устройство B открывает работу с начала (0%)

## Анализ

Класс дефекта: расхождение с требованием владельца R-18 (§5 docs/01-test-strategy.md). 

Требование говорит: "прогресс чтения переносится [между устройствами]". Это архитектурное требование к синхронизации, не вопрос о дизайне или интерпретации. Отсутствие поля прогресса в data model и полного пути синхронизации — прямое нарушение требования.

Пути реализации:
1. **Хранить локально в Room:** добавить поле `readProgress: Int?` (процент) или `lastReadPosition: Long?` (миллисекунды в аудио-работе) в `WorkRating`
2. **Синхронизировать:** добавить поле в `LibraryJson.workToJson/workFromJson`
3. **Merge:** усложнить merge-логику — для прогресса может быть нужна стратегия отличная от last-write-wins (например, максимум из двух позиций, или последний из двух пользовательских действий)

Фича «последняя известная позиция» особенно критична для:
- Дальних путешествий (человек читает на планшете дома, продолжает на телефоне в дороге)
- Многоустройственных домов (два человека читают одну работу, каждый на своём устройстве, но полученная с синка позиция переносится корректно)

**[gitlab:dyakagreen @ 2026-08-19T17:21:59.267Z]** > **Реализовано в `33918fe`** (main).
> 
> Решение владельца: делаем для чтения **внутри приложения**; позиция в скачанном файле, открытом во внешней читалке, не отслеживается и не синхронизируется (подробности ниже).
> 
> Что сделано:
> 
> - `WorkRating` получил `readProgressUrl`, `readProgressPercent`, `readProgressChapter`, `readProgressChapterTotal`, `readProgressAt` (миграция Room 8→9, проверена на заполненной БД).
> - Позиция хранится **в процентах**, а не в пикселях, чтобы переносилась между устройствами с разным экраном и размером шрифта.
> - Пишется с дебаунсом и только после `MIN_PROGRESS_PERCENT` страницы — иначе строка появлялась бы у каждой мельком открытой работы, а «возобновить» предлагало бы позиции, до которых никто не дочитывал. У работы без рейтинга появляется строка только с прогрессом: во вкладках Library она не видна (они фильтруют по рейтингу / `downloadPath`), но синхронизируется.
> - `readProgressAt` — **отдельные часы от `timestamp`**. Прогресс меняется на каждом скролле, и если бы он двигал `timestamp`, читающее устройство выигрывало бы каждый merge и затирало бы рейтинг или заметку, поставленные на другом. `SyncRepository.withNewerProgress` мержит группу полей прогресса отдельно, независимо от того, чья строка победила в row-level LWW.
> - **Возобновление предлагается, а не применяется**: при открытии работы с сохранённой позицией показывается снекбар «Continue reading at ch N, X%?», и страница двигается только по нажатию «Resume». Сделано так осознанно — это тот же R-17, по которому заведены BUG-019/020/073.
> 
> Уточнение по телу бага, которое может пригодиться при дизайне TC: grep по `readProgress|scrollPosition|readingPosition|progressPage|currentChapter` действительно даёт 0 совпадений, но прогресс чтения в приложении **уже измерялся** — `ao3_bridge.js` шлёт `Android.onReadingProgress(chapterCurrent, chapterTotal, scrollPercent)`, значения лежали в `TabInfo.readingScrollPercent` / `readingChapterCurrent` и рисовали индикатор «Ch 1 / 10» в нижней панели. Не хватало именно хранения на работу и переноса между устройствами, а не измерения.
> 
> **Явное ограничение (решение владельца, не дефект):** работа, скачанная и открытая во внешней EPUB-читалке, ничего не сообщает приложению — её позиция не отслеживается и не синхронизируется, и это не планируется. Записано в `PROJECT.md`, раздел «Reading progress». То есть R-18 в части прогресса выполняется для чтения в приложении и сознательно не выполняется для внешней читалки.
> 
> Проверено на эмуляторе (локальные фикстуры, без обращения к AO3): скролл записывает главу 1/3 и 19% без изменения `timestamp`; повторное открытие работы показывает предложение и **не** двигает страницу; нажатие «Resume» прокручивает к сохранённой позиции.
> 
> **Не проверено:** собственно перенос между устройствами и полевой merge (`withNewerProgress`) — для этого нужны два устройства с настроенным GitLab-синком. Прошу закладывать TC именно сюда: сценарий «на A дочитали до X %, на B открыли ту же работу» и сценарий «на A читают, на B в это же время ставят рейтинг» (последний проверяет, что рейтинг не затирается прогрессом).
