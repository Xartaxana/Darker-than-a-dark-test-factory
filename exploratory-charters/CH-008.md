# CH-008 — Двери записи одной строки

## Mission

CH-007 нашёл **BUG-021** (major, Open): правка заметки скачанной работы через
overlay листинга обнуляет `downloadPath` — файл остаётся на диске сиротой.
Сам чартер назвал это ЭКЗЕМПЛЯРОМ класса и оставил класс неразобранным
(дословный `mission_leftover` CH-007: «Изоляция второй двери находки 1: правка
ТЕГА (и панель work-страницы) при `downloadPath != null` — в пробе R1 поле уже
было обнулено заметкой» и «Поле `title` при пере-сохранении существующей строки
из overlay/панели: наблюдалась замена локального заголовка скрейпом при
пере-рейтинге — отдельно не изолировано (тот же класс)»). Класс формулируется
так: **одну и ту же строку Room пишут несколько дверей, и часть из них
СТРОИТ строку заново из данных страницы, а часть ПРАВИТ существующую.**

Разница видна в коде и проверяема поштучно (полный след поиска по символу
`upsertWorkRating` по пакету `app-under-test/app/src/main/java/com/example/
ao3_wrapper` — **12 вызовов**: `BrowserViewModel.kt:532, 698, 722, 746, 807,
822, 840, 1027, 1205`; `SettingsScreen.kt:355`; `DownloadRepository.kt:112`;
объявление `RatingRepository.kt:16`; плюс не-upsert писатели того же поля:
`updateDownloadPath` `RatingRepository.kt:28` ← `DownloadRepository.kt:72,126,
146`, `deleteWorkRating` ← `LibraryViewModel.kt:115`/`DownloadRepository.kt:148`,
`updateWorkMetadata` ← `SettingsScreen.kt:244`):

- **пересобирают** (`WorkRating(...)` конструктором, `downloadPath` в списке
  аргументов ОТСУТСТВУЕТ ⇒ дефолт `null`, `WorkRating.kt:17`;
  `title/author/fandom/wordCount` берутся из скрейпа страницы):
  `:807-813` и `:840-853` (overlay листинга, `applyRating`), `:1027-1040`
  (панель, ветка «строки ещё нет»), `:1205-1218` (`onWorkFinished`),
  `:532-543` (stub-строка перед скачиванием), `DownloadRepository.kt:112-122`
  (stub от orphan-скана);
- **правят существующую** (`existing.copy(...)` ⇒ `downloadPath` и `title`
  сохраняются): `:698-705`, `:722`, `:746-753` (панель work-страницы,
  `savePanelRating`, ветка `existing != null`), `:822` (overlay, очистка
  заметки), плюс `RatingRepository.removeRating:33-40` (снятие рейтинга
  оставляет строку, если есть комментарий, теги ИЛИ `downloadPath`).

Гипотеза сессии: **дверей несколько, инвариант «пользовательское состояние
переживает сохранение» держится не у всех, и ни один кейс не смотрит на это
поле после правки** (CH-007 находка 2: TC-114/TC-115 ассертят ОБРАТНОЕ — что
файл НЕ появляется у нескачанной работы, и остаются зелёными при BUG-021).
BUG-021 закрывает ровно ОДНУ клетку матрицы «дверь × поле» (overlay × заметка ×
`downloadPath`) — остальные клетки не проверял никто.

Вторая половина миссии — **последствие**, а не сам факт потери. Имя файла на
диске строится из `title` строки Room (`LibraryViewModel.kt:91` →
`DownloadRepository.kt:51` → `buildFilename:155-159`), а связь «файл ↔ строка»
восстанавливается сканом по хвосту `_(\d+)\.html$` (`:163`). Значит после
«невинной» правки заметки (title перезаписан скрейпом, `downloadPath` обнулён)
повторное скачивание кладёт ВТОРОЙ файл того же `ao3Id` под другим именем — это
состояние CH-007 наблюдал побочно (протокол п.2.11: `ao3_Зимняя песнь…
_900000001.html` и `ao3_A Loved Test Work_900000001.html` в одной папке), но
скан по нему не гонял и вердикта не выносил. По коду цикл скана
(`DownloadRepository.kt:108-130`) идёт по КАЖДОМУ файлу и для каждого с тем же
`ao3Id` берёт ветку `existing.downloadPath != path` → `updateDownloadPath` +
`relinked++`: два файла = `relinked 2` на ОДНУ работу, а победителем становится
последний в порядке `dir.listFiles()`. Ни один кейс не имеет двух файлов с
одним id (TC-037 — скан на нуле файлов, TC-038 — релинк одного, TC-039 —
восстановление одного синтетического `orphan_<id>.html`).

Рисковый якорь — **R-05** (TECH, счёт 6: «Скачивание: cookies, SAF-папки,
orphan-скан, relink»; расширение surface 2026-07-28 — «семантика правила»).
Пути пересекают R-01 (потеря пользовательских данных), R-10 (заметки/теги),
R-16 (молчаливая потеря состояния без сообщения) — эти риски называются в
самих находках, как в CH-003/004/005/006/007.

## Риски и гипотезы

- **Г1 (флагман). Матрица «дверь × поле»: инвариант держится не везде.**
  Ожидания ПО КОДУ (каждое — фальсифицируемое, расхождение = находка):
  | дверь | точка кода | `downloadPath` | `title/author/fandom/wordCount` | `comment/tags` |
  |---|---|---|---|---|
  | overlay листинга, рейтинг ≠ null | `:840-853` | **теряется** (BUG-021, не находка) | перезаписываются скрейпом блёрба (`getWorkData`, `ao3_bridge.js:~320-336` → `:353`) | из полей overlay |
  | overlay листинга, «Save note» без рейтинга | `:807-813` | **теряется** | перезаписываются | из полей overlay |
  | overlay листинга, очистка заметки (`comment == ""`) | `:822` | сохраняется | сохраняются | comment → null |
  | панель work-страницы, `existing != null` | `:698-705`, `:746-753` | **сохраняется** | сохраняются | из полей панели |
  | снятие рейтинга (обе двери) | `:730`/`:831` → `RatingRepository:33-40` | сохраняется, строка живёт | сохраняются | сохраняются |
  Предмет проверки — не «баг ли это», а СУЩЕСТВОВАНИЕ асимметрии: если панель
  действительно сохраняет, у BUG-021 есть готовый образец починки внутри того же
  файла (материал для bug-reporter/владельца, «чини класс, а не экземпляр»);
  если панель ТОЖЕ теряет — класс шире, чем описан в BUG-021, и это новая
  строка в баг. Оба исхода информативны, поэтому оба обязаны быть измерены,
  а не выведены.
- **Г2. Метаданные-скрейп — не баг, но ОРАКУЛ у пользователя ломается.**
  Перезапись `title/author/fandom/wordCount` из страницы сама по себе
  соответствует коду и намерению («освежили метаданные»); вердикт по ней —
  `ok`, если ничего не сломалось. Но у пользователя эти поля — рабочие оси
  библиотеки: `library-filter-fandom` (TC-029), `library-sort-wordcount`
  (TC-030/031/063), дефолтная `library-sort-last-read` (TC-062, сортировка по
  `timestamp`, который каждая дверь двигает). Проверка: засеять Room
  значениями, ОТЛИЧАЮЩИМИСЯ от страницы (`fandom`, `wordCount`, `title`), затем
  тронуть работу дверью и посмотреть, **сдвинулась ли работа под пользователем**
  — выпала из активного фильтра по фандому, переехала в сортировке, прыгнула
  наверх списка. Класс находки — `risk`/UX-развилка, вердикт человеку
  (критерий владельца: есть сообщение — норма).
- **Г3. Снятие рейтинга у скачанной работы (ветка `downloadPath` в
  `removeRating`).** `RatingRepository:33-40` держит строку живой, если есть
  комментарий, теги ИЛИ `downloadPath`. Скачанная работа без рейтинга и без
  заметки — легальное состояние, но Download-иконка карточки рисуется только на
  вкладках Favorite/Liked/Pending (`LibraryScreen.kt:254`), а работа с
  `rating = null` не видна ни на одной из них. Вопрос: где пользователь её
  теперь находит (вкладка FILES?), и достижимо ли обратное действие. Ожидание
  положительное (`downloadedWorks` — отдельный Flow, `RatingRepository:14`);
  расхождение = находка R-16-класса.
- **Г4. Два файла на один `ao3Id` — что скажет скан.** Цепочка достижима без
  единого искусственного файла: скачать → тронуть дверью-пересборщиком (title
  сменился, `downloadPath` обнулён) → скачать снова (Download-иконка вернулась,
  `LibraryScreen.kt:881`) → в папке два файла с хвостом `_900000001.html`
  (`downloadWork:55/:67` удаляет только файл с НОВЫМ именем). Ручной «Scan for
  downloads» по коду (`:108-130`) обработает ОБА: `relinked` = 2 на одну
  работу, победитель — последний в порядке `listFiles()`. Наблюдаем: дословный
  текст диалога и счётчики; какой путь оказался в `downloadPath` (проба);
  СТАБИЛЕН ли победитель при повторном скане (второй скан по коду должен дать
  `relinked` 0 или 1 — по тому, совпал ли `downloadPath` с последним файлом);
  что открывается из карточки. Вердикт — человеку: пользователь не имеет ни
  одного способа узнать, что файлов два и какой из них «его».
- **Г5. Удаление скачанного файла при двух файлах.** `deleteDownload`
  (`:138-150`) удаляет ровно `path` из строки и обнуляет поле (при наличии
  другого состояния). Второй файл остаётся, и следующий скан ВОСКРЕСИТ работу
  как скачанную — файлом, который пользователь считал удалённым. Ожидание по
  коду; живое подтверждение = находка R-16/R-05-класса. Контроль: TC-035
  (Automated) знает только сценарий с ОДНИМ файлом.
- **Г6. Проба недостижимости авто-READ (5 минут, обязательна как СТРОКА).**
  Открыть `/works/900000001` в replay, снять
  `!!document.getElementById('chapters')` — ожидание `false` (см. Scope/Out);
  прокрутить работу до конца и убедиться, что рейтинг READ не появился
  (позитивный контроль ОТСУТСТВИЯ эффекта, а не только чтение кода); повторить
  проверку на СКАЧАННОМ локальном файле, где `#chapters` есть, но `pathname` не
  матчит `^/works/(\d+)` (`ao3_bridge.js:1118`). Итог — одна строка протокола
  «дверь `onWorkFinished` недостижима корпусом: <измеренное>» + запрос фикстуры
  к test-automator. Это НЕ находка приложения.
- **Г7 (по остатку таймбокса). Что уносит в бэкап испорченная строка.**
  `exportToUri` кладёт `downloadFile = work.downloadPath?.let { File(it).name }
  ?: NULL` (`SettingsScreen.kt:425`) ⇒ бэкап, снятый ПОСЛЕ правки заметки,
  теряет и запись о файле, хотя файл на диске есть. Дешёвый ассерт-якорь для
  будущего кейса формата (кандидат CH-007 «формат бэкапа как контракт»).
  Требует SAF-экспорта (~10 мин) — берётся только если seed 1-3 закрыты.
- **Г8. Амплификация: «Save note» ×5 (остаток CH-007, Г7а — выполнено 1 из 5).**
  Каждая итерация по коду ПЕРЕСОБИРАЕТ строку (`:840`) и двигает `timestamp` ⇒
  при дефолтной сортировке Last read работа прыгает наверх после каждого
  сохранения, а соседи перетасовываются. Наблюдать агрегированный опыт:
  очередь тостов/перерисовок, залипание overlay, не дублируются ли теги, не
  накапливается ли задержка. Известный инструментальный барьер (CH-007 п.2.10):
  после «Save note» поле сворачивается в превью — между итерациями нужен тап по
  превью; барьер — не находка.

## Эвристики / туры

**Правило генерации пути (обязательное, наследует CH-003/004/005/006/007):**
путь = персона × цель × 4-7 шагов из РАЗНЫХ фич; на каждый пройденный seed —
минимум одна вариация (перестановка двух шагов / прерывание между шагами /
повтор шага дважды). **НОВОЕ для CH-008:** каждый шаг, который ПИШЕТ в
`work_ratings`, обязан быть окружён снимком ВСЕЙ строки (до/после) — шаг без
парного снимка не засчитывается; наблюдение «через UI» снимок не заменяет
(текст карточки — ненадёжный оракул, см. Ловушки).

После КАЖДОГО шага — инвариант-чек:
- полная строка `work_ratings` целевой работы (все поля) — собственным
  SELECT пробы; `seed_db.read_work_ratings()` НЕ отдаёт `title/author/
  downloadPath` (`framework/data/seed_db.py:190`), расширять фреймворк — не
  задача сессии (строка отчёта для test-designer/test-maintainer);
- состав файлов папки загрузок — `adb shell ls`, имена дословно в протокол;
- карточка Library: какая иконка — Download или Open (`LibraryScreen.kt:881`
  vs `:884`), на какой вкладке видна работа;
- prefs `ao3_settings.xml` (`run-as cat`): `auto_download_saved` — обязан
  оставаться выключенным (ловушка BUG-014);
- активная вкладка/URL не изменились, если шаг не навигационный;
- каждый диалог (Scan complete / удаление / ошибка) — ДОСЛОВНЫЙ текст ДО
  закрытия.

**Амплификация-тур** — применимость оценена: применим (Г8, «Save note» ×5 на
одной работе). Неприменимость на других сидах — явной строкой «н-п: причина».

**Визуальный-свип-тур** — применимость оценена: применим ЧАСТИЧНО. Новые
экранные состояния этой сессии — карточка Library до/после потери файла
(Download-иконка вместо Open), вкладка FILES, диалог ручного скана, карточка
работы с `rating = null` и файлом (Г3). Скриншоты — в
`exploratory-charters/attachments/CH-008/`, суждение глазами по чек-листу
шаблона. **Тёмная тема — обязательна хотя бы на одном состоянии** (остаток
CH-007: «визуальный свип в ТЁМНОЙ теме — не снималась»). Пороговые метрики
(WCAG, 48dp) — не этим туром.

**Seed-пути (стартовый набор, НЕ исчерпывающий; 1 и 2 — обязательные, 3 и 4 —
по остатку таймбокса).**

1. **«Ревизор дверей» (replay `listing_basic.mitm`; Г1, Г2, Г3, Г8-вариация).**
   Персона: читатель, который держит одну работу скачанной и наводит порядок в
   заметках. Предусловие: `clean_state` → `seed_with_download` для
   `900000001` (rating SAVE) + `seed_with_comment` для 2-3 фон-работ; целевая
