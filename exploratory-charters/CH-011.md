# CH-011 — Скролл: одно состояние, три носителя, два индикатора

## Mission

Позиция скролла — единственное пользовательское состояние этого приложения,
которое одновременно живёт в ТРЁХ носителях и предъявляется ДВУМЯ независимыми
индикаторами:

1. **нативная позиция WebView** каждой вкладки (WebView'ы всех вкладок живы
   одновременно — `MainActivity.kt:542` «Browser is always rendered to keep
   WebViews alive»);
2. **`HistoryEntry.scrollY` → prefs `open_tabs_urls`** (персистентность через
   смерть процесса: `BrowserViewModel.saveTabsToPrefs:389/395-398`,
   восстановление — `pendingScrollRestores` + `peekScrollRestore`,
   `:1200-1201`, допуск `SCROLL_RESTORE_TOLERANCE = 100`, `:1363`);
3. **два производных индикатора**: ГЛОБАЛЬНЫЙ `_activeScrollY` (`:139-140`),
   единственный потребитель которого — гейт FAB «Scroll to top»
   (чтение `MainActivity.kt:349`; гейт — конъюнкция ПЯТИ условий, `:512-516`:
   `selectedTab == AppTab.BROWSE` `:512`, **`activeTab?.isWorkPage == false`
   `:513`**, `activeScrollY > 600` `:514`, `!navExpanded` `:515`,
   **`!uiState.showRatingOverlay` `:516`**; сам узел — content-desc
   `Scroll to top`, `:532`), и ПЕР-ВКЛАДОЧНЫЙ
   `readingScrollPercent`/`readingChapterCurrent`/`readingChapterTotal`
   (`TabInfo.kt:24-26`, пишется `Ao3JsBridge.onReadingProgress:1336-1346`,
   рисуется полоской и подписью «Ch N / M» в нижней панели
   `BottomBar.kt:66-81`).

Обе индикаторные фичи имеют **НОЛЬ кейсов**: `browse-scroll-to-top-fab` и
`bridge-scroll-reporting` стоят в секции «Фичи без единого кейса»
`state/coverage-map.md:185-187`. Обе СОЗНАТЕЛЬНО оставлены без дизайн-метки
(`docs/01` §9, строки 1812-1824 и 1875-1884: «вспомогательная навигация…
данных не задевает, отказ виден мгновенно»; «репорт скролла — restore покрыт
TC-025, reading-% — минор»). Дизайн-вердикт по гейту FAB (`docs/01` §9,
строки 622-634, критик-трассировка + Lead 2026-07-19) разобрал РОВНО ОДНУ
дверь — `switchTab` — и ровно одну сторону эффекта: «побочный эффект „FAB
может мигнуть после переключения“ — косметика ниже порога кейса».

Предмет чартера — то, чего в этом вердикте нет. Полный инвентарь мест ЗАПИСИ
`_activeScrollY` (поиск по символу `activeScrollY` по всему
`app-under-test/`, перечислены ВСЕ найденные вхождения): объявление
`BrowserViewModel.kt:139-140`; запись `:309` (`switchTab` → 0), `:1216`
(транзиентная ветка `onScrollChanged`, под guard'ом
`_uiState.value.activeTab?.id == tabId`), `:1223` (штатная ветка, тот же
guard); чтение — `MainActivity.kt:349`, потребитель — гейт `:512-516`. **Ни
`closeTab` (`:331-357`), ни `restoreClosedTab` (`:360-369`), ни `openTab`, ни
`openOrNavigateDeepLink`, ни восстановление вкладок при холодном старте
(`init:191-230`) в этом инвентаре не фигурируют** — то есть все двери смены активной вкладки,
кроме `switchTab`, оставляют глобальный индикатор от ПРЕДЫДУЩЕЙ вкладки, а
`switchTab` — наоборот, стирает верную величину, ничего не меряя заново
(JS-репортер шлёт только по событию `scroll`, троттл 200 мс,
`ao3_bridge.js:37-44`). Обе стороны рассинхронизации — про АФФОРДАНС
(«кнопки нет там, где она нужна» / «кнопка есть, но ничего не делает»), а не
про «мигнуло».

Миссия собрана из трёх источников сразу: **(а)** остатки миссий Done-чартеров
— `mission_leftover` CH-010 «home + возврат БЕЗ смерти процесса» (дважды
отложен: CH-009 → CH-010) и «релонч с 3-4 открытыми вкладками, пройден только
с ОДНОЙ», плюс остаток CH-006 «персистентность ПОСЛЕ эвикции окна (kill+
релонч, клампится ли `scrollY`)»; **(б)** непокрытые клетки матрицы
PERTURBATIONS — «Прерывания МЕЖДУ шагами пути» на новом состоянии и
«Серийность/амплификация» на переключении вкладок; **(в)** seam-пара двух
0-кейсовых фич (`browse-scroll-to-top-fab` × `bridge-scroll-reporting`),
которая до сих пор не была даже названа парой. Рисковый якорь — **R-08**
(«Состояние табов (10 шт., undo, персистентность, **скролл**)», `docs/01`
§5). Пути пересекают **R-16** (граница/режим молча отбирает функцию — критерий
владельца «есть сообщение — норма» здесь неприменим: сообщения не
предусмотрено вовсе, отказ чисто аффордансный) и **R-03** (механизм
`pendingScrollRestores`/`peekScrollRestore` построен ради bot-check
interstitial — в replay он проверяется на «страница стала короче»).

## Scope

  полоской прогресса), вкладки (создание/переключение/закрытие/Undo/deep-link/
  фоновое открытие из Library), kill+релонч, home+возврат без смерти процесса,

  ПРОГРАММНЫЕ двери скролла (условно — см. Data setup). Оракулы: наличие
  нативного узла FAB (content-desc `Scroll to top`), заголовки чипов вкладок,
  prefs `open_tabs_urls` (URL + `scrollY` каждой вкладки) и `active_tab_index`,
  наличие/значение полоски прогресса и подписи «Ch N / M».
- **Out:**

## Риски и гипотезы

Каждая гипотеза фальсифицируема; расхождение с ожиданием ПО КОДУ = находка,
совпадение — строка «инвариант держится» (тоже результат).

- **Г1 (флагман). Глобальный индикатор против N носителей — обе стороны.**
  Инвентарь записи `_activeScrollY` — три места, перечислены в Mission.
  - **(а) «Кнопки нет там, где она нужна».** `switchTab:306-312` ставит
    `_activeScrollY = 0` и НЕ трогает WebView вкладки-цели (`scrollTo` в этой
    функции нет; целевая позиция жива нативно — эмпирика CH-003 находка 3).
    Ожидание: после переключения на ГЛУБОКО прокрученную вкладку FAB
    отсутствует, хотя страница прокручена на тысячи пикселей, и появляется
    только после того, как пользователь сам прокрутит (событие `scroll`,
    троттл 200 мс). Фальсификация: если пересборка/переприкрепление WebView
    порождает событие скролла, FAB вернётся сам за ~0.2-1 с — измеряем окно
    внешними часами.
  - **(б) «Кнопка есть, но ничего не делает».** Закрытие АКТИВНОЙ прокрученной

    активной соседнюю; ни `closeTab`, ни `restoreClosedTab` в инвентаре записи
    `_activeScrollY` не значатся ⇒ стакан остаётся полным: FAB продолжает
    висеть над вкладкой, стоящей в начале страницы, а тап по нему выполняет
    `scrollToTop:314-317` (`window.scrollTo(0,0)` на АКТИВНОЙ вкладке) —
    видимого эффекта нет.

    вкладку И делает её активной (`activeTabIndex = insertAt`, `:367`), а её

    пальцем, когда восстановленная позиция достигнута (`onScrollChanged`

    возврата индикатора нет; измеряем окно внешними часами.
  - **(в) Чужие двери создания активной вкладки:** deep-link

- **Г3. Персистентность на нескольких вкладках и «залипшая» pending-ветка.**

## Эвристики / туры

**Правило генерации пути (наследует CH-003..CH-010):** путь = персона × цель ×
4-7 шагов из РАЗНЫХ фич; на каждый пройденный seed — минимум одна вариация

**НОВОЕ для CH-011:** каждый шаг, который может изменить АКТИВНУЮ вкладку или
высоту документа (переключение, закрытие, Undo, deep-link, фоновое открытие,

После КАЖДОГО шага — инвариант-чек:
- **FAB — нативный оракул глобального состояния**: наличие узла с
  content-desc `Scroll to top` (`MainActivity.kt:532`). Оракул ОДНОСТОРОННИЙ:

  выполнены; «FAB нет» ⇒ ЛЮБОЕ из пяти (`:512-516`) не выполнено, поэтому
  каждый снимок «FAB нет» обязан нести строку, какие из четырёх побочных
  условий проверены (не work-page `:513`, панель погашена `:515`, нет
  оверлея рейтинга `:516`, вкладка BROWSE `:512`) — иначе вывод про
  `activeScrollY` из него не следует. Помощника в фабрике
  НЕТ — поиск по строке `Scroll to top|scroll_to_top|scrollToTop` по всему
  репозиторию (case-insensitive, `*.py`/`*.md`/`*.yaml`) даёт только
  `docs/01:1816-1818`, `docs/feature-registry.yaml:1001-1009` и

  фабрику), держать в scratch-скрипте;
