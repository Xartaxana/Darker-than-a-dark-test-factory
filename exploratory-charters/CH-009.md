# CH-009 — Очередь фоновых вкладок из Library

## Mission

Сборка `6f884d97` (versionCode 12) принесла ДВЕ продуктовые фичи, обе — в зоне,
где exploratory уже находил молчаливые потери состояния: **#26** «Open in
background tab» из overlay длинного нажатия по карточке Library (коммит
`6e43b14`) и **#28** «скролл-позиция каждой вкладки Library переживает
переключение» (коммит `6f884d97`). Реестр после переинвентаризации даёт им
четыре записи, и у ВСЕХ четырёх ноль кейсов: `library-card-open-background-tab`,
`browse-background-open-snackbar`, `library-tab-scroll-retained`,
`library-sort-change-offscreen-reset` (`state/coverage-map.md`, секция «Фичи без
единого кейса»).

Scripted-дизайн этих областей УЖЕ заказан (`docs/01` §9, две области `needs-design`
P1 от 2026-08-09/10) — сессия его НЕ повторяет. Предмет чартера — **пересечения,
по которым scripted-кейс по одной фиче не ходит**:

1. **Один канал обратной связи, два производителя.** «Tab closed / Undo» и
   «Opened in background (N tabs)» пишут в ОДИН `SnackbarHostState`
   (`MainActivity.kt:243`, рендер `:441`; производители — ровно два: `:250-254`
   и `:276`; полный поиск по символам `snackbarHostState|showSnackbar` по
   `app/src/main/java/com/example/ao3_wrapper` даёт только эти места, позитивный
   контроль формы — та же альтернация нашла и хост, и оба вызова). У первого
   есть ДЕЙСТВИЕ (Undo), у второго — счётчик и заявленная семантика ЗАМЕНЫ
   (`LaunchedEffect(uiState.backgroundTabOpen)`, ключ — весь сигнал
   `BackgroundTabOpen(seq, tabCount)`, `BrowserViewModel.kt:100`, `:283`).
   Что происходит, когда оба производителя говорят одновременно, не проверял
   никто, а именно эта комбинация теперь достижима штатно.
2. **Потолок MAX_TABS достигается НОВОЙ дверью, не уходя из Library.**
   Разработчик сам назвал этот путь третьим способом занять освободившийся слот
   при живом Undo («Вариант В» в Обсуждении `bugs/BUG-016.md`). Кейсы потолка
   (TC-022 — кнопка `+`; TC-131..135 — deep-link; TC-136/137 — тап по телу
   карточки, который экран ПЕРЕКЛЮЧАЕТ) новую дверь не знают, а её Then прямо
   противоположен: экран остаться обязан.
3. **Скролл-позиции вкладок Library против общей сортировки пейджера.**
   `effectiveSort` считается ОДИН раз от текущей вкладки (`LibraryScreen.kt:
   226-229`) и раздаётся ВСЕМ страницам пейджера (`:252`), а сброс скролла живёт
   в самой странице (`:906-912`, saveable `lastSort`). Значит при выбранной
   Files-only сортировке (Rating) **само переключение вкладок меняет `sort`,
   приходящий на страницы, где сортировку никто не трогал** — фича #28 в этой
   комбинации может не держаться. Критик-вход `docs/01` §9 назвал эту грань
   «кодом возможно, прогоном не проверено, баг не завожу» — сессия её ИЗМЕРЯЕТ.

Рисковый якорь — **R-08** (TECH, многотабовость и состояние вкладок; сегодня
покрыт кейсами tabs/TC-022..026, TC-084, TC-131..135, ни один из которых не
знает фонового открытия из Library). Пути пересекают **R-16** (молчаливая
потеря/неприменение пользовательского ввода без сообщения), **R-06**
(корректность списка Library) и **R-05** (локальный файл как цель вкладки).

## Риски и гипотезы

Каждая гипотеза фальсифицируема; расхождение с ожиданием ПО КОДУ = находка,
совпадение — строка «инвариант держится» (тоже результат).

- **Г1 (флагман). Два производителя — один канал.** Material3
  `SnackbarHostState.showSnackbar` — сериализующий ресурс, а наблюдатель
  фонового открытия — `LaunchedEffect`, который при новом сигнале ОТМЕНЯЕТ
  предыдущий вызов (в т.ч. ещё не показанный). Сама сериализация — **уже
  измеренный факт фабрики, не открытие сессии**: докстринг
  `browser_screen.swipe_dismiss_snackbar` (`framework/screens/browser_screen.py:
  418-422`, разведка TC-024 2026-07-18) фиксирует, что `showSnackbar`
  сериализует показы через `Mutex` и 6 закрытий подряд без явного смахивания
  оставляют часть сообщений недостижимыми. Ново здесь другое — что в этой
  очереди стоят ДВА РАЗНЫХ производителя, один из которых несёт ДЕЙСТВИЕ, а
  второй — счётчик, устаревающий, пока ждёт. Отсюда четыре подпробы:
  - **(а)** Фоновое открытие ПРИ ЖИВОМ «Tab closed / Undo»: что на экране
    в первые 3-4 с (CH-006 измерил жизнь «Tab closed» ≈3.3-3.8 с), когда
    приходит «Opened in background (N tabs)», и какой в нём счётчик к моменту
    показа. Пользовательский эффект, ради которого проба делается: живой Undo
    остаётся на экране, хотя слот уже занят, а подтверждение занятия слота
    приходит ПОЗЖЕ — это и есть «Вариант В» BUG-016 с точки зрения канала.
  - **(б)** Обратный порядок: закрыть вкладку СРАЗУ ПОСЛЕ фонового открытия
    (пока висит «Opened in background») — успевает ли «Tab closed» с его
    ДЕЙСТВИЕМ на экран, и остаётся ли Undo нажимаемым столько же.
  - **(в)** N быстрых фоновых открытий подряд: сколько сообщений реально
    показано и какие счётчики (заявлено — ЗАМЕНА новым счётчиком, не очередь).
  - **(г)** Открытие в ПЕРЕДНЕЙ вкладке гасит сигнал: `:283` при
    `background=false` пишет `backgroundTabOpen = null`. Проба: фоновое
    открытие → сразу тап по **ТЕЛУ карточки** — это `onOpenWork`
    (`LibraryScreen.kt:928` → `MainActivity.kt:331-334`, переключает экран на
    Browse) → исчез ли снекбар и что видно на Browse. Вариация той же подпробы
    — вторая передняя дверь того же экрана: **иконка локального файла**
    `onOpenFile` (`LibraryScreen.kt:934-935` → `MainActivity.kt:522-526`).
  Инвентарь дверей (полный поиск по символу `openTab(` по `app/src/main`, все
  места перечислены): фоновые — РОВНО ДВЕ, `MainActivity.kt:529` (наша, из
  overlay длинного нажатия Library) и `BrowserScreen.kt:647` (long-press по
  ссылке в WebView, TC-026); передние — `MainActivity.kt:332` (`onOpenWork`,
  тап по телу карточки), `:414` (New tab на TabStrip), `:523` (`onOpenFile`,
  иконка локального файла), `BrowserViewModel.kt:336` (авто-HOME при закрытии
  последней вкладки), `:653` (deep-link). `restoreClosedTab` вызывается ровно
  из одного места — `MainActivity.kt:256` (действие Undo).
- **Г2. Потолок новой дверью.** `openTab:272-275` возвращает false ДО записи
  сигнала ⇒ ожидание: вкладка не создаётся, снекбара НЕТ, поднимается диалог
  «Tab limit reached» (`MainActivity.kt:619-637`). Наблюдаем: диалог поверх
  экрана **Library** (все прошлые наблюдения диалога — поверх Browse), успел ли
  закрыться bottom-sheet (`:323` обнуляет `pendingActions` ПОСЛЕ вызова),
  дословный текст, что с листом Library и его позицией после закрытия диалога,
  и — главное — **экран НЕ переключился** (отличие от TC-136/137, где тап по
  телу карточки на потолке диалог показывает и экран МЕНЯЕТ). Критерий
  владельца «есть сообщение — норма» здесь выполняется, поэтому вердикт по
  самому отказу — `ok`; находкой может быть только расхождение.
- **Г3. Место в списке переживает фоновое открытие.** Смысл фичи дословно
  записан в коде (`MainActivity.kt:527-528`: «Stays on Library deliberately —
  the point is to queue up several works without losing your place in the
  list»). Проба: прокрутить вкладку Library глубоко → зафиксировать первый
  видимый элемент → long-press → «Open in background tab» → тот же элемент
  первый? Далее — то же под снекбаром (не сдвигает ли Scaffold список, не
  перекрывает ли снекбар следующую цель long-press).
- **Г4. Крест #28 × Files-only сортировка (грань, названная критиком §9).**
  По коду: `effectiveSort` (`LibraryScreen.kt:226-229`) считается от ТЕКУЩЕЙ
  страницы и передаётся во ВСЕ страницы (`:252`); в каждой странице
  `LaunchedEffect(sort)` при `sort != lastSort` делает `scrollToItem(0)`
  (`:906-912`). Ожидание: при выбранном Rating (допустим только на Files)
  переход Files → Favorite меняет `sort`, приходящий на страницу Files, и её
  скролл сбрасывается БЕЗ действия пользователя; возврат на Files сбрасывает
  ещё раз; зеркально страдает и соседняя страница, пока Rating активен.
  Измеряем ОБА направления и фиксируем, какие страницы вообще композированы
  (пейджер держит соседние). **Предусловие измеримости:** обе участвующие
  вкладки должны быть ПРОКРУЧИВАЕМЫ — для Files это значит 10-12 строк с

- **Г6. Судьба недопустимого выбора** (`library-sort-invalid-pick-fallback`):

- **Г7. `file://` как содержимое фоновой вкладки (R-05 × R-08).** На вкладке

  открытии (`saveTabsToPrefs`, `:286`). Пробы: (1) kill+релонч с
  `file://`-вкладкой среди прочих — восстановилась ли, каким URL, рендерится ли
  при переключении; (2) удалить скачанный файл из карточки (путь TC-035), пока
  фоновая вкладка на него уже открыта → переключиться на неё / релонч — что
  показано (страница ошибки приложения? пусто? старый рендер?). Ни один кейс
  вкладок не имеет `file://`-вкладки: TC-025 проверяет persist HTTP-вкладок.
- **Г8. Дедупликации вкладок нет.** `openTab` (`:270-288`) не сверяет URL с
  существующими вкладками (полный инвентарь вызовов — в Г1). Следствие:
  повторные открытия ОДНОЙ карточки дают N вкладок с одинаковым URL. Это и
  удобный рычаг (набрать потолок записанными страницами, см. Data setup), и
  предмет наблюдения: что показывает счётчик снекбара, различим ли пользователь
  свои вкладки. **Оговорка об оракуле:** дубли доказываются ТОЛЬКО списком

- **Г9 (амплификация, обязательна к оценке).** 5-7 «Open in background tab»
  подряд с интервалом ~300 мс по РАЗНЫМ карточкам: агрегированный опыт —

## Эвристики / туры

**Правило генерации пути (наследует CH-003..CH-008):** путь = персона × цель ×
4-7 шагов из РАЗНЫХ фич; на каждый пройденный seed — минимум одна вариация
(перестановка двух шагов / прерывание между шагами / повтор шага дважды).
**НОВОЕ для CH-009:** каждый шаг, меняющий число вкладок ИЛИ позицию списка,
обязан быть окружён снимком ПАРЫ «число вкладок ПО PREFS + первый видимый элемент
активной вкладки Library» (до/после); шаг без парного снимка не засчитывается.
Снекбар фиксируется ДОСЛОВНО и с временем (внешние часы) — сообщение, увиденное

После КАЖДОГО шага — инвариант-чек:

  удерживаемый весь бюджет — для «вкладка НЕ создана» на потолке). Парсер —
  честный JSON (`_parse_persisted_tabs`, `:325-370`), не substring-подсчёт.

- ни один вывод о вкладках не берётся из WEBVIEW-контекста (sticky-ловушка ниже);
- **активный экран** (Library/Browse/Settings) и активная вкладка браузера;

   продолжив набирать работы из Library.
   Предусловие: 10 вкладок (конец seed 1 либо пере-сев).
   **Способ закрытия вкладки при 10 открытых (обязателен, позиционные локаторы
   тут не работают):** тап по САМОЙ видимой иконке `Close tab`

   СКОМПОНОВАННЫХ чипов, `browser_screen.py:361-368`, надёжно до ~7), а

   списка `open_tabs_urls` ДО и ПОСЛЕ (`assert_persisted_tab_url_at` по
   позициям), а не по видимому чипу.
   Шаги: закрыть вкладку описанным способом (снекбар «Tab closed / Undo» жив,
   засечь время; `wait_persisted_tab_count(9)`) → **не дожидаясь его
   исчезновения** уйти в Library и сделать фоновое открытие (снова 10 по

   (**BUG-016 — известен, НЕ находка**; фиксируем ровно то, что видел
   пользователь: живая кнопка, отсутствие любого сообщения после нажатия) →

   бессмысленны).** После шагов выше сессия стоит РОВНО НА ПОТОЛКЕ (10), а на
