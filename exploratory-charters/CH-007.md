# CH-007 — Круг жизни пользовательских данных

## Mission

Пять чартеров подряд ходили по ПОВЕДЕНИЮ приложения (тема, рейтинги-как-журней,
настройки-как-возмущение, ввод/геометрия, пагинация) и ни разу — по ДАННЫМ,
которые пользователь в приложение кладёт. Матрица PERTURBATIONS держит две
клетки, не тронутые НИ ОДНИМ чартером: **«Данные-экстремумы в журнеях»** и
**«Backup/restore ПОСРЕДИ сессии»** (последняя планировалась CH-004 и не была
исполнена — дословный `mission_leftover` CH-004: «seed 4 "Уборка": backup →
смена настроек → restore ПОСЕРЕДИНЕ (SAF-драйв, содержимое backup-JSON vs
prefs) — не тронут (SAF тяжёлый)»). Инструментальное основание блокера
«SAF тяжёлый» с тех пор ослабло: SAF-инфраструктура достроена и обкатана
(`framework/steps/saf_steps.py`, `framework/screens/documents_ui.py`,
`framework/steps/backup_steps.py`, проба `framework/tests/test_saf_infra_probe.py`,
TC-021 Automated) — экспорт/импорт/выбор папки доводятся до конца тем же
UiAutomator2-сеансом.

Гипотеза сессии: **самое непокрытое здесь — не «бэкап работает», а СЕМАНТИКА
СЛИЯНИЯ и СУДЬБА КРАЙНИХ ЗНАЧЕНИЙ на круге «экспорт → жизнь → импорт».**
Единственный scripted-кейс зоны (TC-021) гоняет стерильный круг
backup → **Clear all** → restore, то есть импорт в ПУСТУЮ базу и на «нормальных»
данных. Реальный пользователь восстанавливается в базу, которая с момента
бэкапа ИЗМЕНИЛАСЬ, и данные у него живые: эмодзи в заметке, длинный заголовок
работы, тег с пробелами, комментарий на нескольких строках. Код импорта
(`SettingsScreen.kt:321-405`, функция прочитана целиком) знает ровно одну ветку
разрешения конфликта — `val existingIds = repo.getAllIds()` (`:341`) и
`if (id in existingIds) { skippedCount++; continue }` (`:348`): ветки
«обновить», «слить поля», «спросить пользователя» в функции нет, а результат
сообщается ЧИСЛОМ без единого имени работы («Restored X works, Y filters
(Z works already existed).», `:1187-1188`). Второй край того же круга —
downloads-зона, которой не касался ни один журней: экспорт кладёт в JSON имя
файла (`obj.put("downloadFile", …)`, `:425`), а импорт создаёт строку с
`downloadPath = null` (`:366`) и ключ `downloadFile` не читает вовсе — связь
файла со строкой восстанавливает только последующий скан
(`downloadRepo.scanForOrphanedDownloads()`, `:395`), который узнаёт работу по
ИМЕНИ ФАЙЛА (`WORK_ID_PATTERN = Regex("""_(\d+)\.html$""")`,
`DownloadRepository.kt:163`), а имя строится из ЗАГОЛОВКА строки Room —
несущая цепочка целиком: `LibraryViewModel.kt:91`
(`downloadRepo.downloadWork(work.ao3Id, work.url, work.title)`) →
`DownloadRepository.kt:51` (`val filename = buildFilename(workId, title)`) →
`buildFilename` `:155-159` (замена `[\\/:*?"<>|\r\n\t]` на `_`, `.trim()`,
`.take(80)`). То есть **крайние данные и восстановление данных встречаются в
одной точке**.

Базовый релинк после restore уже покрыт scripted — **TC-039** (Automated):
пустая Library, backup с одной работой, orphan-файл под СИНТЕТИЧЕСКИМ именем
`orphan_<ao3_id>.html`, положенный adb (`app_steps.place_file_in_download_folder`),
диалог «Restored 1 works, 0 filters. Also relinked 1 and added 0 downloaded
file(s).». Непокрыто ровно ДВА отличия от него, и они и есть предмет сессии:
(1) имя файла построено САМИМ приложением из ЭКСТРЕМАЛЬНОГО заголовка Room
(`buildFilename`), а не подложено фикстурой в заведомо матчащей форме;
(2) restore идёт в **непустую** базу, где скип по `ao3Id` (`:348`) и релинк
сканом (`:395`) спорят за одну и ту же строку.

Рисковый якорь — **R-01** (DATA, счёт 6: «Потеря пользовательских данных при
backup/restore/clear/delete»); пути дополнительно пересекают R-05 (downloads),
R-10 (заметки/теги) и R-16 (молчаливая потеря функции/состояния — принят с
очень низким приоритетом, §5), эти риски называются в самих находках, как в
CH-003/004/005.

## Scope

- **In:** replay-режим целиком. Круг данных: seed Room (экстремальные значения)
  → правка из UI (заметка/теги через overlay листинга и панель work-страницы)
  → **экспорт бэкапа через SAF** (`exportToUri`, `SettingsScreen.kt:407-452`) →
  изменение состояния ПОСЛЕ бэкапа (правка/снятие рейтинга, удаление работы,
  переименование и удаление фильтр-профиля, смена 3-4 настроек) → **merge-restore
  через SAF** (`importFromUri`, `:321-405`) → сверка Room
  (`seed_db.read_work_ratings()`, `read_filter_profiles()`) и UI. Downloads как
  часть круга: ручное скачивание из карточки Library (путь TC-033) — только
  `ao3_id 900000001`, единственный записанный download-flow (см. Data setup,
  «Ограничение корпуса»), ИМЯ файла на диске, релинк сканом после restore
  (`:395`, `scanForOrphanedDownloads`).
  Библиотечные фильтры/сортировки по экстремальным значениям как наблюдатель.
  Визуальный свип экранов с экстремальными данными.
- **Out:**
  - **Ретроактивность auto-download / edge-vs-level (BUG-014, BUG-015)** — зона
    уже РАЗМЕЧЕНА дизайном: TC-112..TC-117 (docs/01 §9 «settings/downloads:
    семантика тумблера auto-download-favorite (edge-vs-level)»), плюс два Open-бага.
    Тумблер `auto_download_saved` в этой сессии держится **выключенным** и не
    включается ни на одном шаге, чтобы скачивания были только явные (ручные) —
    иначе сессия перепройдёт scripted. Следствие, важное для разбора находок:
    репро BUG-014 требует ВКЛЮЧЁННОГО тумблера, поэтому в этой сессии он
    воспроизвестись не может (см. ловушки).
  - **Авто-клик kudos** (BUG-015, R-17) — live-только по существу и стоит в
    очереди дизайна; сюда не берём.
  - **Вкладки/undo/снапшоты и парад снекбаров закрытия (BUG-016, BUG-017,
    CH-006 seed 5)** — чужая зона; амплификация в этой сессии направлена на
    ДРУГИЕ поверхности (серия сохранений заметки, серия скачиваний, повторный
    Restore), не на закрытие вкладок.
  - **Пагинация/эвикция/плотность и tap-зоны на скачанном файле** — зона CH-006
    (seed 1/2/3/6), даже пока он Blocked.
  - **Геометрия/ввод/panel_side/поворот** — зона CH-005 (пройдена), поворот
    заблокирован драйвером.
  - **Гонка «смена папки загрузок → немедленный Restore» (BUG-011, Open)** — это
    известный баг; воспроизводить его сессия не должна и сдавать как находку не
    имеет права (ловушка ниже). Наша ветка скипа — СВОЯ строка, изменённая
    пользователем, без участия скана.
  - Live-режим (AT-BUG-026: краш qemu на тяжёлом живом рендере) и всё, что
    требует живого AO3 (метаданные `fetchAo3WorkPage`, `SettingsScreen.kt:259`).
  - Прямые пути одиночных фич с чистого экрана (TC-021, TC-033..039, TC-087..091,
    TC-060/061) — ассертить только шов.

## Риски и гипотезы

- **Г1 (флагман). Merge-restore молча уступает локальной правке.** Импорт
  сравнивает ТОЛЬКО по `ao3Id` (`:341`, `:348`) и на совпадении не обновляет
  ничего — прибавляет к `skippedCount`. Значит после «бэкап → пользователь
  изменил рейтинг/заметку/теги → restore того же файла» бэкапная версия
  **не возвращается**, а пользователь получает одну строку с числом
  (`:1187-1188`), без имён работ и без выбора «перезаписать/оставить».
  Ожидание пользователя от кнопки «Restore from backup» — вернуть то, что было.
  Проверка: три ветки на трёх работах одним импортом — (а) работа изменена после
  бэкапа (ждём: скип, локальное значение выжило); (б) работа УДАЛЕНА из Library
  после бэкапа (ждём: восстановится, `imported++`); (в) работа появилась ПОСЛЕ
  бэкапа и в файле её нет (ждём: осталась нетронутой). Числа диалога обязаны
  сойтись с составом Room. **Вердикт класса — человеку** (R-16/дизайн-развилка,
  критерий владельца «есть сообщение — норма»): сообщение ЕСТЬ, но не называет,
  ЧТО именно не восстановлено — это и есть предмет вердикта, а не автоматический
  баг.
- **Г2. Бэкап обещает больше, чем содержит.** `exportToUri` (`:407-452`, функция
  прочитана целиком; поиск по символу `fun exportToUri` по всему
  `app-under-test` даёт ровно одно вхождение — другого экспорта в приложении нет)
  кладёт в JSON ровно три ключа: `version`, `works`, `filterProfiles`
  (`:441-443`); поля работы перечислены `:415-425`, профиля — `:433-436`.
  Ни одной настройки (`theme_mode`, `tap_to_scroll`, `panel_side`,
  `auto_download_saved`, `download_folder_uri`, шрифт, яркость) в файле нет.
  Проверка: экспорт → сменить 3-4 настройки → restore → настройки НЕ вернулись
  (ожидание ПО КОДУ — это не баг реализации), а текст «Backup restored» об
  ограничении объёма не предупреждает. Класс находки — `risk`/UX-заметка
  («имя функции шире формата»), не баг; вердикт — человеку. Дополнительно
  сверить фактическое содержимое файла глазами (`adb shell cat`) — это же
  ассерт-якорь для будущего scripted-кейса.
- **Г3. Скачанный файл не переживает круг как ССЫЛКА, только как ИМЯ — и имя
  делает не фикстура, а приложение.** Экспорт пишет `downloadFile` =
  `File(it).name` (`:425`); в цикле импорта (`:345-371`) читаются
  `ao3Id/rating/tags/title/author/url/fandom/wordCount/comment/timestamp`,
  а `downloadPath` жёстко `null` (`:366`) — ключ `downloadFile` не читается
  вовсе. Единственный восстановитель связи — `scanForOrphanedDownloads()`
  (`:395`), опознающий работу регуляркой по хвосту имени
  (`_(\d+)\.html$`, `DownloadRepository.kt:163`).
  **Дельта к TC-039 (Automated, базовый случай уже покрыт — см. Mission),
  ровно две:** (1) файл на диске создан САМИМ приложением из экстремального
  `title` строки Room (`LibraryViewModel.kt:91` → `DownloadRepository.kt:51` →
  `buildFilename` `:155-159`), а не подложен фикстурой в заведомо матчащей
  форме `orphan_<id>.html`; (2) restore идёт в **НЕпустую** базу (у TC-039
  Library пуста по Given) — и это даёт ветку, которой у TC-039 нет вовсе:
  скип работы по `ao3Id` (`:348`) и релинк файла сканом (`:395`) внутри
  ОДНОГО импорта.
  Общий сетап: папка загрузок = SAF-подпапка вне app-private каталога;
  скачать работу (id `900000001`, единственный записанный download-flow — см.
  Data setup) с экстремальным заголовком → бэкап → `Clear all ratings`
  (`clearAllRatings` бьёт только `work_ratings`, файл в SAF-папке остаётся —
  тот же факт, что использует TC-021; фон-работы остаются на экране как
  «база непуста» только если сидятся заново — иначе непустоту даёт ветка Б).
  Дальше — ДВЕ ветки, обе обязательны:
  - **(А) строки НЕТ, файл ЕСТЬ** → Restore: работа импортируется
    (`imported++`, `downloadPath = null`, `:366`), затем тот же импорт зовёт
    скан и релинкует файл по ИМЕНИ, построенному приложением;
  - **(Б) строка ЕСТЬ (создана заново из UI: поставить рейтинг после Clear
    all), `downloadPath = null`, файл ЕСТЬ** → Restore: работа СКИПАЕТСЯ
    (`skippedCount++`, `:348`), но файл всё равно обязан быть релинкован
    сканом. Именно эта ветка — шов merge × downloads, не тронутый ни одним
    кейсом.
  **Ожидания счётчиков — ФОРМУЛОЙ, не литералом (правка по критик-вердикту
  attempt 3: в бэкапе круга лежат и фон-работы, литералы «Restored 1» /
  «Restored 0» не сойдутся):** `Restored X` = число работ бэкапа,
  ОТСУТСТВУЮЩИХ в Room на момент импорта (целевая в ветке А + фон-работы,
  которым рейтинг НЕ вернули после Clear all); `Z already existed` = число
  присутствующих (ре-рейтингованные фон + целевая в ветке Б);
  `relinked 1` — файл круга. Ассерт ветки Б — по паре «целевая в скипе
  (локальные поля нетронуты) ∧ relinked 1», не по дословной строке диалога;
  инвариант Г1 (числа сходятся с составом Room до/после) — арбитр.
  Кандидат «файл, положенный adb заранее» СНЯТ: это буквально сетап TC-039,
  повтор покрытого. `delete work` тоже не годится (удаляет и файл, и строку —
  TC-036); `delete downloaded file` наоборот оставляет строку (TC-035).
  Наблюдаем: счётчики диалога (`:1189-1191`) и вкладка Downloads — есть ли
  работа и открывается ли файл. Ожидание положительное; расхождение — находка
  на данных, а не на коде.

## Эвристики / туры

**Правило генерации пути (обязательное, наследует CH-003/CH-004/CH-005):**
путь = персона × цель × 4-7 шагов из РАЗНЫХ фич; на каждый пройденный seed —

**круговой шов данных** — значение, записанное на шаге k, обязано быть
предъявлено обратно на шаге k+n через ДРУГУЮ дверь (Room → JSON-файл → Room,
или Room → имя файла на диске → Room через скан, или UI-ввод → карточка Library
→ фильтр по этому же значению). Без предъявления обратно шаг не засчитывается.
