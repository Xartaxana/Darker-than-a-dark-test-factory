# /next-task — следующая задача очереди Lead (+ параллельные фоновые диспатчи)

Скилл отвечает на команду «возьми следующую Lead-задачу»: выбирает
верхний пункт очереди Lead, исполняет его по политике маршрутизации и
параллельно отдаёт фоновым воркерам задачи очереди, уже готовые к
делегированию и не пересекающиеся путями. Правила CLAUDE.md здесь не
дублируются — скилл фиксирует только порядок их применения.

## Границы (жёстко)

- **Очередь фабрики не трогать**: задача под when-условием
  state/rules.yaml (строки «очередь следующего прохода /qa-loop» в
  HANDOFF) диспатчится ТОЛЬКО проходом /qa-loop (слово оператора
  2026-07-10). Детектор нарушения — чек 15 еженедельной калибровки OS.
- **Порядок словом владельца не перескакивать**: owner-ordered блоки
  механизмов исполняются в объявленном порядке.
- Пункты «awaiting dev/human» и «по evidence рецидива, превентивно не
  трогать» — не готовая работа: не брать, пропуском не считать.
- `app-under-test/` не трогать.

## Шаг 0 — сверка яруса (п.4а CLAUDE.md)

Очередь Lead — Lead-tier работа. Семейство Lead-привязки
(`delegation.config.yaml` roles.lead; после D-0099 — Opus) и выше
(Fable-резерв) — полный режим. Ярус ниже —
матрица «Роль ≠ ярус»: механизменные коммиты и статусы не делать
(tier-гейт отклонит — задача остаётся в очереди), доступны
инвентаризация, диспатчи и приёмка по матрице; вход в окно — событием
`lead_degraded`, явная строка в сводке.

## Шаг 1 — собрать очередь

Источники (точечные известные носители, порядок сбора):
1. `python scripts/log_append.py open-dispatches` — незакрытый диспатч
   с готовым результатом = приёмка; она и есть «следующая задача».
2. `state/escalations.md` — секции без resolved-метки (глубокий поиск
   по ВСЕЙ секции до следующего `## ESC-`, класс F-34).
3. docs/HANDOFF.md — очередь механизмов Lead (owner-ordered блоки),
   «Открытые хвосты» (входящие OS, кросс-репо решения), «Возвращённые
   живые остатки».

## Шаг 2 — выбрать следующую

Приоритет: (1) приёмка готового результата открытого диспатча;
(2) нерешённая эскалация; (3) owner-ordered механизм; (4) прочие
механизмы в порядке носителя; (5) кросс-репо хвосты и мелочь.
Задача, конфликтующая путями с работающим воркером, пропускается с
явной строкой (легальная причина отсрочки 8а) — берётся следующая.

## Шаг 3 — исполнить

По типу задачи, существующими правилами:
- **Механизм**: четыре вопроса F-11 письменно → спека → критик-на-план
  (реализация дороже ~30 мин) → builder по спеке → критик диффа →
  коммит с осевым блоком и `tier:` (отдельный коммит).
- **Решение Lead / кросс-репо ответ**: принять, зафиксировать в
  носителе тем же ходом (resolved-блок / HANDOFF / кросс-коммит OS по
  правилу 4б).
- **Разведка** → scout; **реализация по готовой спеке** → builder;
  самоисполнение — только с `dispatch_skipped` (правило 8).

Каждый диспатч: DoD + манифест (owns/non-goals/handoff), сверка
DoD-шагов с `tools:` роли, `delegated` ПОСЛЕ фактического запуска с
worker_ref, фон по D-0040 с лейблом «модель: …».

## Шаг 4 — параллельные фоновые диспатчи

Сразу после запуска основной задачи — скан остальной очереди на
задачи, готовые к делегированию БЕЗ нового Lead-решения (scout с явным
вопросом; builder по уже принятой спеке; critic на уже сданный дифф).
Для каждой:
- пересечение owns-путей с основной задачей и друг с другом — ДО
  запуска (правило 4); пересекается — не запускать;
- device-задачи на общий эмулятор не параллелить (прецедент 07-29/30);
- свой DoD+манифест, свой `delegated`, запуск фоном.

Задача, требующая сначала Lead-решения, в параллель не уходит — она
кандидат «следующей» на будущий вызов.

## Шаг 5 — закрытие

1. Приёмка ВСЕХ запущенных воркеров по матрице ярусов (critic-вход по
   правилу 3 где положено). Воркер не завершился к концу сессии —
   открытый диспатч остаётся виден open-dispatches, передача следующей
   сессии по чеку 2 session-handoff.
2. Носитель очереди обновлён ТЕМ ЖЕ ходом (пункт вычеркнут / статус в
   HANDOFF / resolved-блок эскалации) — ось 9: результат без записи в
   носитель не существует.
3. Сводка оператору: что исполнено (witness/ссылки), что запущено
   фоном (worker_ref), что следующее в очереди, что пропущено и почему.

Детекторы отказа скилла — существующие: чек 15 калибровки OS
(фабричная задача вне /qa-loop), чек 3а session-handoff (готовая
работа отложена без причины из списка 8а), чек 5 калибровки OS по
транскриптам (самоисполнение без skip-события, ярусные декларации).

сверх существующих правил не создаёт.
