# session-handoff — проверка переноса сессии (D-0050, порт из OS-репо)

Принцип: handoff проверяет вечером ровно то, что следующая сессия
прочитает утром. Утренний путь AO3: `CLAUDE.md` (автозагрузка) →
`docs/HANDOFF.md` («Читать первым при старте», resume-заметки +
таблица «что где») → `state/factory-status.md` (ГЕНЕРИРУЕТСЯ
`scripts/queue_snapshot.py`, ручные числа запрещены — правило A4,
docs/09-improvement-plan.md). Journal: `logs/routing-log.jsonl`,
пишется ТОЛЬКО через `scripts/log_append.py`.

## Шаги

1. **Git.** `git status --short` пуст — незакоммиченное коммитится
   сейчас (узким явным списком путей, не `git add -A`); незнакомые
   untracked-файлы не заметать в коммит молча — разобраться, чьи они
   (возможна параллельная сессия, D-0060 OS-репо / F-23 AO3). Затем
   `git log origin/master..master --oneline` пуст — иначе `git push`.
   Если сессия трогала OS-репо (`D:\Improving_AI\Operating-System-for-LLMs`)
   — та же проверка там (ветка `main`).
2. **Журнал закрыт** (`logs/routing-log.jsonl`): прогнать
   `python scripts/log_append.py open-dispatches` — каждый показанный
   открытый `delegated` сверить с реальностью (D-0076 OS-репо / F-44
   ЗДЕСЬ): воркер по `worker_ref` жив или результат ждёт приёмки —
   иначе фантом (запись без запуска); фантом закрывается токеном
   `closes-phantom:<task_id>` в notes следующего события (проза не
   читается сканером) и, если работа нужна, честным ре-диспатчем.
   `lead_degraded` без `lead_restored`
   допустим ТОЛЬКО как ПОСЛЕДНЕЕ событие журнала (деградация,
   переживающая сессию, D-0039 OS-репо) — иначе следующая сессия
   стартует ошибочно на полном Lead. Гейт чартеров (2026-07-21,
   регистрация детектора N3 вердикта critic): каждый чартер,
   перешедший Proposed→Planned за сессию (`git log -p` по
   `exploratory-charters/CH-*.md` или дифф сессии), имеет в журнале
   критик-событие по своему task_id И заполненный `plan_review:
   critic:PASS:...` — Planned без критик-вердикта = самосертификация
   гейта (F-22), FAIL хендоффа. События сессии написаны
   `scripts/log_append.py`, не ручной правкой файла (permission
   hygiene, CLAUDE.md п.4).
3. **Живое состояние.**
   - `docs/HANDOFF.md`: блок «Где мы» и resume-заметки отражают
     фактическое закрытие сессии (не хвост предыдущей).
   - **3а. Инвентаризация готовой работы (правило 8а CLAUDE.md,
     2026-08-03; детектор класса «отсрочка без причины» — три
     прецедента одного дня).** Скан статусов по ТЕКУЩЕМУ состоянию
     (Grep frontmatter, как шаг 3 qa-loop): каждая ГОТОВАЯ пара
     «правило/обязанность × артефакт» (срабатывание rules.yaml,
     follow-up Done-чартера, эскалация с исполнителем — без лока, не
     Blocked/wip, не ждёт человека) обязана быть ЛИБО в открытом
     диспатче (open-dispatches чека 2), ЛИБО строкой HANDOFF-очереди
     с причиной из закрытого списка правила 8а (лимит / конфликт
     путей / занятое устройство для device-класса) — «следующей
     сессии» без причины из списка = FAIL хендоффа: работа
     диспатчится до закрытия либо причина дописывается честно.
     Сверка дешёвая: свежий `state/escalations.md` (sla_sweep уже
     считает charter follow-up) + Grep по Open|Fixed багам и
     Approved-кейсам против занятости устройства на закрытии.
   - **3б. Сторож жив (детектор M4 ВЫВЕДЕН для СТАРОЙ ПАРЫ — spec-
     factory-window v6 К5а, 2026-08-16; ПРАВКА Д1, 2026-08-16 вечером —
     обёртка снова пишет M4-строки, см. ниже).** Прежний чек «парность
     heartbeat-строк» (`logs/heartbeat.log` start ↔
     `state/orchestrator-log.md` heartbeat-обёртка) БОЛЬШЕ НЕ
     ПРИМЕНЯЕТСЯ и остаётся выведенным: `logs/heartbeat.log` по-прежнему
     никем не пишется (шапка `scripts/heartbeat.cmd` без echo НЕ
     менялась) — детектор был парой «файл ↔ строка», а файла нет, пары
     физически не из чего собрать. **НО обоснование «M4-строки были
     детектором child-spawn ЭТОЙ обёртки, обёртка не запускается» —
     УСТАРЕЛО (Д1, консолидированная секция spec-factory-window v7):**
     `scripts/heartbeat_wrap.py::run_pass` (прежний production-контракт)
     действительно не вызывается, НО `run_fallback_pass` (ночной резерв,
     `scripts/factory_watchdog.py`) — ЖИВОЙ вызыватель, и он ПИШЕТ M4-
     строку `heartbeat-обёртка/heartbeat_wrap` НА КАЖДЫЙ резервный
     проход (busy/spawned/spawn_failed/timeout_kill), с артефакт-
     колонкой `logs/fallback-YYYYMMDD.log` (НЕ `logs/heartbeat.log`).
     Эти строки — легитимный аудиторский след ночных резервных
     проходов (Grep `orchestrator-log.md` по `heartbeat_wrap.*
     logs/fallback-` при разборе ночи), НЕ детектор старой пары —
     новый парный детектор для НИХ не заводится (нет соответствующего
     «start»-файла, как не было и раньше; сам факт наличия строки уже
     самодостаточен как М4-артефакт). На месте выведенного детектора —
     НОВЫЙ чек-импликация (Б-6):
     **ЕСЛИ** задача `AO3-QA-Heartbeat` в состоянии `Ready` И
     `LastRunTime` < 2ч, **ТО** `state/factory-watchdog.json` не старше
     `LastRunTime + 30 мин`; задача `Disabled` → н/п (не FAIL). Форма
     неравенства ЯВНАЯ: `LastRunTime − mtime(factory-watchdog.json) ≤
     30 мин` (сторож пишет state-файл В МОМЕНТ своего запуска —
     «не старше LastRunTime+30» в буквальном чтении дало бы FAIL
     ВСЕГДА, т.к. mtime всегда ПОЗЖЕ LastRunTime).
     **Источник состояния задачи — ЕДИНЫЙ ридер**
     (`python scripts/scheduled_task_reader.py AO3-QA-Heartbeat` —
     `Get-ScheduledTask(.State)` + `Get-ScheduledTaskInfo(.LastRunTime)`,
     локале-независимо; `schtasks`-парсинг ЗАПРЕЩЁН — вывод
     локализован, cp866 «Состояние: Отключено» на русской Windows;
     `NextRunTime` у Disabled-задачи врёт). Тот же ридер использует
     `doctor.py`. «Запрос не удался» (`error=...`, exit 1) → н/п +
     строка в резюме сессии (F-30 CLAUDE.md — env-негатив без сверки не
     факт; детектор фолбэка — строка в `state/factory-watchdog.json`
     сторожа + этот же чек).
     **Плюс чек mode-файла:** `state/factory-mode.json` СОГЛАСОВАН с
     намерением оператора — если `mode: "active"`, `updated_ts` не
     старше 2ч (окно реально ведётся, не забыто открытым без пульса);
     `mode: "stopped"` или файла нет — н/п. Расхождение (`active`,
     `updated_ts` протух) — находка, не FAIL хендоффа: зафиксировать в
     журнале и в HANDOFF (детектор дрейфа mode — та же строка, что
     упомянута в матрице сторожа К3 п.2).
     **Driver-оговорка (Д1 ночной резерв, spec-factory-window v7,
     2026-08-16):** поле `driver` mode-файла различает, КТО пульсировал
     последним — `"factory-skill"` (окно) или `"watchdog-fallback"`
     (резерв сторожа). `mode: "active"` со свежим `updated_ts` И
     `driver: "watchdog-fallback"` — ШТАТНОЕ ночное вождение резервом
     (окно закрыто/умерло, резерв самостоятельно довозит очередь до
     `budget_total`/two_empty) — это НЕ «оператор забыл окно открытым»,
     дрейф-находка выше НЕ применяется в этом случае; зафиксировать в
     резюме сессии факт «ночь вела резерв» (кто/сколько проходов, если
     виден `passes_done`), не как отклонение. `driver: "factory-skill"`
     со свежим `updated_ts` при отсутствии видимого открытого окна на
     этой машине — вот это остаётся дрейф-находкой (несогласованность).
     Сверка дешёвая: `Get-Item state/factory-watchdog.json`
     (`.LastWriteTime`) + `Get-Content state/factory-mode.json` (или
     их отсутствие — оба файла gitignored, легитимно отсутствуют вне
     активного окна/после чистого клона).
   - **3в. Обратный канал GitLab чист (детектор мёртвого канала,
     2026-08-09).** `python scripts/gitlab_inbound.py --check`: «чист»
     (exit 0) — ок; «деградация» (нет токена/сети/частичный отказ,
     exit 0) — строкой в резюме сессии, не FAIL; exit 1 — строка
     HANDOFF-очереди, находка, не FAIL хендоффа: либо необработанные
     ноты разработчика ждут переноса, либо (E7) строка `QAREADY-<iid>`
     без resolved — фича разработчика ждёт диспатча test-strategist
     (обязанность держится видимой до resolved-пометки).
   - **3г. Вопросы владельцу видимы (слово оператора 2026-08-19).**
     Резюме сессии несёт строку «вопросы владельцу: N (старейший —
     …)» — тем же грубым Grep-счётом, что шаг 6 qa-loop (носители:
     пакеты §10 `docs/01` без «РЕШЕНИЯ ВЛАДЕЛЬЦА», незакрытые «Что
     нужно от человека» выше-Lead-класса в `state/escalations.md`,
     строки «Владельцу:» HANDOFF, Blocked-по-человеку в `bugs/`).
     Строки нет — дописать сейчас (находка, не FAIL). Полная
     человеческая форма вопросов — мандат /lead-review шаг 5а, не
     хендоффа.
   - `state/factory-status.md`: перегенерирован
     `scripts/queue_snapshot.py` ПОСЛЕ последнего изменения
     артефактов сессии — сверить `generated_at` со временем последних

     HANDOFF/докках запрещены (A4). Расхождение счётчиков —
     FAIL, чинится регенерацией скриптом, не руками.
   - `state/coverage-map.md`: перегенерирован `scripts/coverage_map.py`
     ПОСЛЕ последнего изменения `test-cases/**` — если нет, перегенерировать
     сейчас; шапка файла не несёт строку «⚠ реестр фич протух» без причины

4. **Boot-бюджет.** Суммарный размер в байтах `CLAUDE.md` +
   `docs/HANDOFF.md` + `docs/09-improvement-plan.md` (в бут-перечне с
   2026-07-17; его нарративы обязаны уходить в docs/09-history.md —
   рост плана = кандидат свипа). Сравнить с прошлым замером (в сообщении
   прошлого handoff-коммита; при смене состава перечня прошлый замер
   несравним — новый baseline, явно пометить в коммите). Флаги:
   рост >10% за сессию без объяснимой причины; суммарно >100 КБ →
   пункт «boot-диета» в `docs/09-improvement-plan.md`, если его там
   ещё нет. (Ось платного автозагружаемого контекста — чек 10
   еженедельной калибровки OS-репо, WEEKLY_CALIBRATION_PROTOCOL.md.)
   Порядок реакции на пробой (порт OS-репо 2026-07-10, D-0068):
   СНАЧАЛА архивный свип — закрытое/нарративное уводится в архивный
   дом (HANDOFF-история, docs/) со сверкой, что урезанная версия не
   разошлась с полной и указатели живы; глубокие срезы оперативных
   домов (CLAUDE.md, действующие правила) — НЕ в ходе handoff, а
   отдельным решением координатора+человека пунктом очереди.
5. **Живость утренней цепочки.** Существуют: `CLAUDE.md`,
   `docs/HANDOFF.md`, `state/factory-status.md`, `state/rules.yaml`
   (переименование любого без правки HANDOFF.md = сломанное утро
   следующей сессии).
6. **Итог.** Короткий отчёт по пунктам 1–5 (OK/FAIL и что сделано).
   FAIL чинится ДО закрытия сессии, не записывается «на потом».
   Финальный коммит (в сообщении — замер п.4 как baseline для
   следующего handoff) и push — последнее действие сессии.

## Детектор пропуска

Утреннее правило Session Start в `docs/HANDOFF.md` (первые строки
после «Читать первым при старте»): `git status --short` и
`git log origin/master..master --oneline` на старте новой сессии.
Грязное дерево или расхождение с origin в этот момент = прошлая
сессия закрылась без handoff-проверки — фиксируется находкой через
`log_append.py` (по словарю событий CLAUDE.md; минимум — пометка в
notes ближайшего события журнала; `defect_found` — только если
находка ссылается на конкретную ПРИНЯТУЮ задачу, его `ref`
обязателен), не поглощается молча. Внешняя сеть — еженедельная
калибровка OS-репо читает журналы ОБОИХ репо (routing-log.jsonl
здесь и в OS-репо), так что несловленный пропуск здесь виден и там.
