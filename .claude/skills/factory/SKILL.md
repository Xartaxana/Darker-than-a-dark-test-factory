# /factory — окно-фабрика: вождение проходов /qa-loop (spec-factory-window v7 = v6 + Д1 ночной резерв)

Архитектура «окно-фабрика + сторож» (слово оператора 2026-08-16: «в
идеале heartbeat просто подталкивает фабрику в открытом окне»). Эта
сессия — ВОДИТЕЛЬ: она сама выполняет процедуру `/qa-loop` (та же
самая, что описана в `.claude/skills/qa-loop/SKILL.md` — **ты, эта же
сессия**, идёшь по её шагам напрямую, НЕ через субагента, тем же
принципом «оркестрацию выполняешь ТЫ», что и у самого `/qa-loop`)
СЕРИЕЙ проходов, с паузами между ними и с самопробуждением через
`ScheduleWakeup`, пока не исчерпан бюджет или не пришло слово
оператора «остановись». Снаружи, из планировщика, тикает НЕЗАВИСИМЫЙ
сторож (`scripts/factory_watchdog.py`, каждые 30 мин) — ОН ШТАТНО не
ведёт проходы (только проверяет, что окно живо, и поднимает тревогу,
если нет), НО класс «фон не ведёт» здесь БОЛЬШЕ НЕВЕРЕН БЕЗ ОГОВОРОК
(Д1, консолидированная секция spec-factory-window): если STALLED
держится ≥15 мин при активном mode (`night_fallback` не выключен,
бюджет ещё не доехал, серии поломок чисты) — сторож САМ спавнит ОДИН
резервный `/qa-loop 5`. Это ЕДИНСТВЕННЫЙ путь, которым фон когда-либо
запускает `/qa-loop`; окно-фабрика остаётся штатным, предпочтительным
водителем — резерв подхватывает ТОЛЬКО мёртвое вождение и молчит, пока
окно живо (пульс §1 закрывает любой резервный эпизод немедленно).

## Команды

- `/factory N` — **бюджетный режим**: провести N СОСТОЯВШИХСЯ проходов
  (BUSY-попытки в счёт не идут). N — целое ≥1.
- `/factory` (без аргумента) — **безлимит**: вести проходы, пока не
  придёт слово оператора «остановись» (или другой терминальный путь,
  см. §6).
- «остановись» (в любой момент диалога, пока окно ведёт) —
  **грациозный стоп**: закончи ТЕКУЩИЙ проход штатно (не обрывай
  диспатч воркера на середине), затем `stopped_reason: operator_stop`.

## §0. Старт — владение по nonce (CAS)

**Владение вождением — compare-and-swap по `session_nonce`.**
`state/factory-mode.json` несёт `session_nonce`; ЛЮБАЯ запись в
mode-файл легальна ТОЛЬКО если nonce в файле на момент записи ==
собственный (перечитать перед КАЖДОЙ записью, не полагаться на
значение из прошлого чтения). Чужой nonce в файле → прекратить
вождение (см. §1).

1. **Сгенерируй свой nonce** (один раз за инвокацию, до первой записи):
   `python -c "import secrets; print(secrets.token_hex(4))"`.
   Держи его в контексте этого хода — он же уйдёт в текст
   wakeup-prompt (см. §7, якорь nonce вне контекста сессии).

   **Исключение — это ПРОБУЖДЕНИЕ, не явный вызов оператора**: если
   тебя разбудил `ScheduleWakeup` с нейтральным текстом, несущим токен
   `factory-nonce=<nonce>` (см. §7), — это ТВОЙ собственный nonce
   ПРОШЛОГО хода. Восстанови его ИЗ ЭТОГО ТЕКСТА (не из файла — после
   компакции контекста файл может показывать чужой/более новый nonce,
   а разбудившее сообщение — единственный надёжный носитель твоей
   личности между ходами). Дальше действуй как «продолжение», не как
   «старт» (ниже) — НЕ генерируй новый nonce, НЕ считай это «первым
   проходом после явного вызова» (ключ `passes_done == 0` из
   `state/rules.yaml` применяется ТОЛЬКО к СВЕЖЕМУ старту, не к
   wakeup-продолжению).

   **Нет своего nonce ни в контексте, ни в wakeup-тексте** (сессия
   потеряла его — компакция/неизвестный триггер) — **усыновление
   nonce из файла ЗАПРЕЩЕНО**: не веди молча, перейди сразу к ветке
   «чужой активный mode-файл» ниже (спроси оператора).

2. **Прочитай `state/factory-mode.json`.**
   - **Файла нет** → бутстрап: пиши свежий mode-файл (см. схему §2)
     с `mode: "active"`, `budget_total: <N|null>`, `passes_done: 0`,
     `session_nonce: <твой>`, `session_started_ts: <now>`,
     `updated_ts: <now>`, `heartbeat_note: "старт"`,
     `stopped_reason: ""`. Иди к §2.
   - **Нечитаем** (битый JSON) → **НЕ писать поверх** (пересоздание со
     своим nonce вернуло бы двойное вождение, если старый писатель ещё
     жив) — спроси оператора, что делать (файл битый, чей это был
     nonce — неизвестно), жди слова.
   - **Читается, `mode: "stopped"`** → **ПЕРЕД бутстрапом (Д1, п.9/11а)
     прочитай `stopped_reason`/`driver`/`passes_done`** из ЭТОГО (ещё не
     перезаписанного) файла:
     - **`driver` != `"watchdog-fallback"`** (штатный дневной/вечерний
       стоп самим окном, как в v6) → предыдущее окно завершилось штатно;
       НЕ конфликт — бутстрап свежего состояния (как «файла нет» выше), с
       НОВЫМ `session_started_ts`/`passes_done: 0`.
     - **`driver` == `"watchdog-fallback"`** (ночь: резерв довёз
       `two_empty`, ты просыпаешься первым после ночи резерва) →
       **РАССКАЖИ оператору ночь** ДО бутстрапа (см. общий формат
       рассказа ниже), **СПРОСИ выбор** (см. ниже), жди слова. Только
       ПОСЛЕ выбора — пиши mode-файл (с твоим новым `session_nonce`,
       `driver: "factory-skill"`) и иди к §3.
   - **Читается, `mode: "active"`, `session_nonce` СОВПАДАЕТ с твоим**
     (случай пробуждения — см. п.1) → продолжение: НЕ трогай
     `passes_done`/`budget_total`, иди к §3 (следующий проход).
   - **Читается, `mode: "active"`, `session_nonce` ЧУЖОЙ** (или ты
     сюда попал из ветки «нет своего nonce» выше) → **чужой активный
     mode-файл**: назови оператору владельца (по возможности — из
     `heartbeat_note`/`session_started_ts`) и `updated_ts`. **Если
     `driver` файла == `"watchdog-fallback"`** (п.9 спеки: «mode active
     ИЛИ stopped/two_empty» — ОБА случая рассказа+выбора, симметрично
     ветке `mode: "stopped"` выше — takeover здесь НЕ особый случай) —
     **РАССКАЖИ оператору ночь** ДО takeover (см. общий формат ниже),
     **СПРОСИ выбор** (см. ниже) — жди слова. Иначе (driver ==
     `"factory-skill"`, живое чужое окно) — просто СПРОСИ, что делать
     (без рассказа/выбора, обычный конфликт вождения). В любом случае
     жди слова:
     - **«перехвати» (takeover)** — ЕДИНСТВЕННОЕ легальное исключение
       из CAS-запрета записи чужого nonce: пиши mode-файл с НОВЫМ
       nonce (твоим), `driver: "factory-skill"`; `passes_done`/
       `budget_total` — по ВЫБОРУ оператора, если он был (driver=
       watchdog-fallback ветка выше), ИЛИ **НАСЛЕДУЮТСЯ** без вопроса
       (driver=factory-skill ветка, обычный takeover живого окна,
       поведение v6 без изменений) — `passes_done == 0` НЕ считается
       «свежим стартом» ни в одном из этих случаев (ключ rules.yaml не
       срабатывает повторно на этом же бюджете).
     - иначе (оператор не сказал «перехвати») — НЕ веди, останови
       работу этим ходом.

   **Общий формат «рассказа ночи»** (Д1 п.9, обе ветки выше — `mode:
   "stopped"` и `mode: "active"`+чужой driver=watchdog-fallback):
   назови оператору `passes_done` (спавнов ВСЕГО за эпизод — Н1:
   читай `fallback_runs` ИЗ `state/factory-watchdog.json`, он честнее
   `passes_done` mode-файла — считает и НЕрезультативные попытки busy/
   spawn_failed/fast-timeout, не только успешные; `fallback_runs_24h`
   ИЗ ТОГО ЖЕ файла — скользящее 24ч-окно, для быстрой сверки «не
   разогналось ли»), результативных (`passes_done` mode-файла —
   ТОЛЬКО завершившиеся с `rc==0`), `stopped_reason`/причину (если
   `mode: "active"` — ночь ещё НЕ остановилась, назови текущий streak-
   контекст из notes сторожа, если он там есть), ссылку на
   `logs/fallback-*.log` для деталей.

   **Общий формат «выбора оператора»:** «продолжить общий бюджет»
   (наследуешь `passes_done`/`budget_total` из файла, НЕ обнуляешь) ИЛИ
   «начать новый счёт» (бутстрап как обычно — `passes_done: 0`, новый
   `budget_total` по введённому `/factory N`) — **НЕ выбирай молча**.

## §1. Пульс (CAS-запись при КАЖДОМ обновлении)

Перед КАЖДОЙ записью в `state/factory-mode.json` (и на пульсе, и на
терминальном пути) — **перечитай файл** и сверь `session_nonce`:
- совпадает с твоим → пиши (обнови `updated_ts` = now,
  `heartbeat_note` = короткая строка «что сейчас», `driver:
  "factory-skill"` — **НА КАЖДОЙ своей записи БЕЗ ИСКЛЮЧЕНИЯ, включая
  КАЖДУЮ BUSY-попытку/паузу** (Д1: писателей у mode-файла ДВОЕ — этот
  скилл и ночной резерв сторожа, `driver` — единственный способ
  различить, кто вёл последним; пропуск поля на одной BUSY-записи ломает
  guard two_empty резерва — см. `scripts/factory_watchdog.py` docstring
  `_run_reserve_pass`), остальные поля по контексту записи).
- НЕ совпадает → **прекрати вождение НЕМЕДЛЕННО**: чужая сессия/окно
  перехватило (или переиграло) владение этим же интервалом пульса.
  Строкой в сводке («вождение прекращено — чужой nonce в mode-файле»),
  **погаси СВОЙ wakeup-таймер** (§7, `stop: true` — не оставляй
  фантомное пробуждение), **НЕ пиши `mode: "stopped"`** (это НЕ
  терминальный путь из enum §6 — сама запись запрещена CAS; молчание
  файла — единственный след).

**Пример-«юнит» CAS «чужой nonce → прекращение вождения»** (проверочный
сценарий этой ветки — прогони ЭТИМ рассуждением при ревью правки
скилла, раз кода для pytest здесь нет — вся механика прозовая, К1
владеет ТОЛЬКО этим файлом): твой `session_nonce = "aaaa1111"`, ты
собираешься записать пульс `heartbeat_note: "диспатч test-runner:..."`.
Перечитываешь `state/factory-mode.json` ПЕРЕД записью — там
`session_nonce: "bbbb2222"` (другая сессия взяла лок на этот же
интервал пульса, например — оператор запустил `/factory` в ДРУГОМ
окне поверх твоего, не сказав «перехвати»). Ожидаемое поведение: ТЫ
**не пишешь** запланированный пульс НИКАКИМ содержимым (ни
`heartbeat_note`, ни, тем более, `mode: "stopped"` — CAS запрещает
саму запись), сообщаешь в сводке «вождение прекращено — чужой nonce
`bbbb2222` в mode-файле», гасишь СВОЙ `ScheduleWakeup`-таймер, ход
заканчивается БЕЗ дальнейших проходов qa-loop. Второе окно (`bbbb2222`)
продолжает вести НЕЗАВИСИМО — двойного вождения НЕ возникает именно
потому, что проигравшая сторона молча замолкает при первом же
расхождении, не переигрывает и не ждёт.

**Пульс — КЛАССОВОЕ определение: каждый шаг качественного изменения
состояния прохода.** Ниже — исчерпывающий список веток ВНУТРИ
процедуры `/qa-loop` (шаги нумерации из `.claude/skills/qa-loop/
SKILL.md`), помеченных «пульс» либо «без пульса (обоснование)» —
беспульсовая ветка, для которой обоснование НЕ приведено, — дефект

Пульс — это Edit ОДНОГО JSON-файла (копейки токенов), КАЖДОЕ
срабатывание перечитывает-и-пишет по правилу CAS выше.

**Пример-«юнит» driver на BUSY-пульсе (Д1, держи актуальным при правке
таблицы выше):** лок занят, ты пишешь пульс `"ждём лок holder=<h>
ts=<t>"` — эта запись ОБЯЗАНА нести `driver: "factory-skill"` наравне с
любой другой (диспатч воркера, приёмка, коммит). Если её пропустить
(«это же просто ожидание, не настоящая работа») — резерв, увидев
устаревший `driver: "watchdog-fallback"` от СВОЕГО прошлого прохода
вместо свежего `factory-skill`, ошибочно решит, что окно всё ещё мертво,
и (при двух пустых резервных проходах подряд) запишет
`mode: "stopped"/two_empty` ПОВЕРХ живого, просто ожидающего лок окна —
класс инцидента «резерв усыпил живое окно». Единственная защита —
дисциплина: driver пишется ВСЕГДА, без исключений.

## §2. Схема `state/factory-mode.json`

**Писателей ДВОЕ (Д1, изменение относительно v6):** этот скилл (владелец
— пишет ЛЮБЫЕ поля, CAS по nonce, §1) И ночной резерв сторожа
(`scripts/factory_watchdog.py::_run_reserve_pass`, ОГРАНИЧЕННЫЕ поля под
loop-lock, non-throwing) — модель записи «честная»: last-writer-wins по
некритичным полям (`updated_ts`/`heartbeat_note`/`driver`/
`last_fallback_ts` — окно пульсирует и на BUSY-попытках, даже пока лок у
резерва), критичные (`passes_done`, `mode`/`stopped_reason` НА
two_empty-финише) защищены CAS-перечиткой резерва (см. докстринг
`_run_reserve_pass`). Файл gitignored (`.gitignore`). Поля:

```json
{
  "mode": "active",
  "budget_total": 5,
  "passes_done": 2,
  "session_nonce": "a1b2c3d4",
  "session_started_ts": "2026-08-16T10:00:00Z",
  "updated_ts": "2026-08-16T10:41:12Z",
  "heartbeat_note": "диспатч test-runner:Новая сборка/state/app-under-test.yaml",
  "stopped_reason": "",
  "driver": "factory-skill",
  "night_fallback": "on",
  "last_fallback_ts": null
}
```

`budget_total: null` — безлимитный режим (`/factory` без аргумента).
`stopped_reason` — пусто, пока `mode: "active"`; на терминальном пути
— одно из enum §6 (резерв добавляет СВОЁ единственное легальное
значение `two_empty` — см. §6 ниже). `driver` — `"factory-skill"` ИЛИ
`"watchdog-fallback"`, ставится КАЖДОЙ записью ОБОИХ писателей (§1).
`night_fallback` — `"on"` (дефолт, в т.ч. отсутствие ключа) | `"off"`
(оператор явно выключил ночной резерв на эту сессию/бюджет — пиши по
слову оператора; скилл сам НЕ решает выключать). `last_fallback_ts` —
пишет ТОЛЬКО резерв (время своего последнего прохода); скилл его не
трогает.

## §3. Проход — вызов процедуры qa-loop с лимитом 5

**Лимит срабатываний ОДНОГО прохода окна = 5** (опрос оператора
2026-08-16 — НЕ стоячее «20» из `rules.yaml:16`, тот дефолт остаётся
для НЕ-оконных ручных/фабричных прогонов). Выполни процедуру
`.claude/skills/qa-loop/SKILL.md` ЦЕЛИКОМ, как если бы её вызвали
`/qa-loop 5` — той же сессией, ЯВНЫЙ лимит 5 переопределяет
`max_triggered_workflows`. Из этих 5 слотов 2 — коридор автоматизации
(слово оператора 2026-08-20; норма, причины недобора и строка сводки —
SKILL.md qa-loop, шаги 4 и 6).

**Лок прохода — интерактивная ветка** (SKILL.md qa-loop §1 шаг 0а,
env `AO3_LOOP_HOLDER` НЕ задан — окно не имеет обёртки): `python
scripts/loop_lock.py acquire`, как обычный ручной проход. Держи
`holder` из строки `ACQUIRED` для `release` на закрытии прохода (та
же дисциплина, что у qa-loop чек-листа).

Соблюдай пульс §1 на протяжении ВСЕГО прохода (не только в начале и
конце) — это единственное, что защищает от ложной STALLED-тревоги
сторожа на долгом проходе (§6 спеки: STALL_IN_PASS = 90 мин при живом
локе).

## §4. Классификация состоявшегося прохода

После завершения (лок снят или BUSY-выход — см. §5 про BUSY отдельно):

- **BUSY** — проход НЕ состоялся (см. §5, отдельная обработка, НЕ
  считается ни успешным, ни пустым, НЕ идёт в `passes_done`).
- **doctor-FAIL** — проход состоялся КАК ДЕГРАДИРОВАННЫЙ (`passes_done
  += 1`, сводка прохода несёт строку деградации из шага 1 qa-loop
  «Код 1 (FAIL) = эскалация уже записана doctor'ом»). Отдельной
  тревоги ЭТОТ скилл по нему НЕ объявляет — doctor уже сам эскалирует.
- **Пустой** — проход состоялся (`passes_done += 1`) И 0 срабатываний
  правил шага 4 И секция «отложено» шага 6 пуста («отложено: нет») И
  дельта ре-скана 4а пуста.
- **Обычный** — состоялся, есть срабатывания.

## §5. BUSY-протокол

Лок занят чужим holder'ом (шаг 0а вернул BUSY):
1. **Пульс** `"ждём лок holder=<h> ts=<t>"` (см. таблицу §1).
2. Пауза 600с (`ScheduleWakeup`, нейтральный текст + nonce-токен, см.
   §7) — эта попытка НЕ считается пустым/успешным проходом, НЕ жжёт
   бюджет `passes_done`.
3. **После 3 BUSY подряд** (≈20 мин накопленного ожидания) — **задай
   ВОПРОС оператору прямо в окне** (обычным сообщением диалога: кто
   держит лок — `holder`/`ts` из строки BUSY, — и что фабрика ждёт;
   назови опцию `python scripts/loop_lock.py release --force`, если
   оператор уверен, что холдер мёртв). Ожидание ПРОДОЛЖАЕТСЯ паузами
   по 600с независимо от того, ответил ли оператор сразу — вопрос не
   блокирует цикл ожидания.
4. **`busy_giveup`** — стоп при накопленных **120 минутах** BUSY-ожидания
   БЕЗ слова оператора (терминальный путь, см. §6). Остаточный риск
   ПРИНЯТ явно: `busy_giveup` (120 мин) < TTL лока
   (`loop_lock_ttl_hours`, 240 мин, `state/sla.yaml`) — окно может
   сдаться раньше, чем чужой лок протухнет сам; компенсатор — вопрос
   оператору уже с 20-й минуты (п.3).

## §6. Продолжение и терминальные пути

**Budgeted (`/factory N`):**
- Веди СОСТОЯВШИЕСЯ проходы (§4), пока `passes_done < N`.
- **Ранний стоп** при 2 ПУСТЫХ проходах ПОДРЯД — `stopped_reason:
  two_empty`, даже если `passes_done < N`.
- **Перебор до N+2**: если к моменту `passes_done == N` очередь всё
  ещё рождает срабатывания (последние проходы не были пустыми —
  работа продолжает поступать), веди ЕЩЁ до 2 проходов сверх N
  (`passes_done` может дойти максимум до `N+2`), затем стоп
  `budget_done` независимо от состояния очереди на этот момент — БЕЗ
  самовольного дальнейшего расширения.
- Иначе, при достижении `passes_done == N` (без непрерывной подачи
  работы) — `stopped_reason: budget_done`.

**Unlimited (`/factory`):** та же логика прохода/классификации/раннего
стопа при 2 пустых подряд — БЕЗ верхней границы `N`; терминалы —
`operator_stop` (слово «остановись», см. заголовок) или `busy_giveup`
(§5). `two_empty` СИММЕТРИЧНО применяется и здесь (2 пустых подряд —
стоп, даже без бюджета).

**Enum `stopped_reason`:** `operator_stop | budget_done | two_empty |
busy_giveup`. Ровно ОДНО из этих значений на КАЖДОМ терминальном пути.

**Каждый терминальный путь ОБЯЗАН:**
1. Записать (CAS, §1) `mode: "stopped"` + `stopped_reason: <enum>` в
   `state/factory-mode.json`.
2. **Погасить wakeup-таймер** (не планировать следующий `ScheduleWakeup`
   — урок «no-command-as-wakeup-prompt»: фантомный перезапуск после
   штатного финиша — тот же класс инцидента, что и с командой в
   prompt).
3. Дать оператору итоговую сводку: `passes_done`/`budget_total`,
   суммарно сработавших правил, новые эскалации, `stopped_reason`.

**Аварийный обрыв сессии** (краш/закрытие окна) — `stopped_reason`
**НЕ пишется** (некому писать) — это ПО ПОСТРОЕНИЮ вход сторожа
(`scripts/factory_watchdog.py`, ветка «mode активный, тишина >
порога»), НЕ пятое значение enum. Не пытайся угадать/имитировать этот
путь кодом скилла — сторож существует именно для этого случая.

## §7. Паузы и самопробуждение

- **Непустой проход** (успешный, не BUSY, не пустой) → пауза **60с**
  перед следующим.
- **Пустой ИЛИ BUSY** → пауза **600с**.
- Механизм паузы — `ScheduleWakeup` с **нейтральным текстом**, несущим
  ТОЛЬКО якорь nonce: например `"factory-continue nonce=<твой
  session_nonce>"` — БЕЗ слэш-команды и БЕЗ инструкций в тексте
  (урок «no-command-as-wakeup-prompt»: slash-команда/императив в
  prompt рождает фантомные повторные вызовы поверх штатного
  завершения). Разбудившее сообщение — источник восстановления
  СВОЕГО nonce в §0 п.1 после компакции контекста.
- **Инвариант порогов** (документирует, ПОЧЕМУ 60/90/600 выбраны так):
  `STALL_NO_LOCK` сторожа (60 мин, без лока) СТРОГО БОЛЬШЕ, чем
  максимальная легитимная пауза (600с = 10 мин) ПЛЮС каденция сторожа
  (30 мин) = 40 мин < 60 мин — даже самая долгая штатная пауза между
  проходами не может сама по себе вызвать ложную тревогу, ПОКА
  пульс §1 продолжает обновлять `updated_ts` на каждой BUSY-попытке
  внутри паузы (по построению — пауза САМА и есть шаг с пульсом, см.
  таблицу §1).

## §8. Лимиты подписки (v8, 2026-08-18)

Лимит подписки **рвёт цепочку вождения насовсем**: следующее звено
`ScheduleWakeup` ставит только УСПЕШНО завершившийся ход, а сорванный
лимитом ход не ставит ничего. Толкнуть окно снаружи нечем — сторож
каналом в чужую интерактивную сессию не располагает. Поэтому:

- **Окно после лимитного перерыва не оживает само.** Это признанное
  свойство, а не поломка: чинить нечего, отчёт «фабрика не поехала»
  писать не надо. Возобновление — слово оператора в этом окне.
- **Сторож в лимитном окне молчит и не спавнит резерв** (v8, детали —
  docs/tasks/factory-visible-window.md §v8). В `state/factory-
  watchdog.json` это видно полями `usage_limit_until`/
  `usage_limit_grace_until`, в `state/orchestrator-log.md` — строкой
  `usage-limit`.
- **Проснулся после долгой тишины и видишь эти поля** — не считай
  простой своей ошибкой вождения и НЕ заводи по нему эскалацию: назови
  причину оператору строкой сводки («перерыв N ч — лимит подписки,
  сброс был в <ts>») и продолжай с текущего прохода.

## Границы (жёстко, как у qa-loop)

- Эта сессия — тот же водитель, что `/qa-loop`: те же ограничения
  (не трогать `app-under-test/`, не выполнять работу воркеров самой,
  не снимать `Blocked`/`wip` руками) действуют на протяжении ВСЕЙ
  серии проходов, не только одного.
- Диспетчеризация независимых срабатываний, headless-заход, F2-блок,
  ре-скан 4а, коммит узким списком путей — ВСЁ ПО ПРОЦЕДУРЕ qa-loop
  БЕЗ ИЗМЕНЕНИЙ; этот скилл добавляет ТОЛЬКО внешний цикл
  (владение/пульс/классификация/паузы/терминальные пути) поверх неё.
- НЕ веди второй параллельный проход поверх уже ведомого этой же
  сессией (один водитель — одна последовательность вызовов qa-loop,
  сериализовано самим циклом §3-§7).
