# TC-190 — Фоновая вкладка на удалённый локальный файл: состояние после релонча (замок текущего поведения)

**Статус `Draft` — намеренно, эскалация (правило «Эскалация» роли
test-designer).** В отличие от TC-184 (docs/01 §9 явно разрешает Review с
фактическим Then для того случая), здесь у `bugs/BUG-060.md` заявлено ТРИ
альтернативных «ожидалось» без выбора владельца/разработчика — не бинарный
вопрос «так и задумано или нет», а неопределённость самого требуемого
поведения. Not решаю за владельца: Then ниже — рабочая формулировка ДЛЯ
ФИКСАЦИИ ФАКТА (материал для будущего Review после решения), кейс остаётся
`Draft`, пока `bugs/BUG-060.md` не получит ответ в «Обсуждении» (`awaiting:
dev`/решение владельца) — тогда test-designer переводит в `Review` с Then
под выбранную альтернативу.

## Предусловия
- Приложение запущено с чистыми данными.
- Засеяна работа с `downloadPath`, файл реально существует на диске.
- На вкладке Files долгим нажатием по карточке через overlay открыта фоновая
  вкладка на этот файл (`file://<downloadPath>`, тот же приём, что TC-174/189)
  — persisted `open_tabs_urls` несёт этот URL на позиции 1.

## Сценарий (Given-When-Then)

**Given** фоновая вкладка на `file://<downloadPath>` открыта, файл на диске
существует, WebView этой вкладки корректно отрендерил содержимое (заголовок
чипа TabStrip показывает title работы)

**When** пользователь через Library overlay той же карточки тапает «Delete
downloaded file» (сам файл удалён с диска, `adb shell ls` подтверждает
отсутствие)
**And** процесс приложения убит и перезапущен

**Then (наблюдаемый факт текущей сборки — регрессионный замок, НЕ вердикт
"так и должно быть")**
- вкладка ВОССТАНАВЛИВАЕТСЯ по persisted `open_tabs_urls` (не исчезает) —
  `wait_persisted_tab_count` держит прежний счёт
- при переключении на неё WebView показывает страницу ошибки — текст
  содержит «Couldn't load this page» и код `net::ERR_FILE_NOT_FOUND`
- чип этой вкладки на TabStrip деградирует до подписи «about:blank» (не
  сохраняет прежний заголовок работы)

**Это ФАКТИЧЕСКОЕ поведение текущей сборки, зафиксированное как регрессионный
замок — НЕ вердикт "так и задумано".** Идеальное поведение НЕ решено:
`bugs/BUG-060.md` называет три альтернативы («вкладка закрывается сама» /
«graceful-ошибка с восстановлением» / «пересоздание на web-версию работы»),
ни одна не выбрана владельцем/разработчиком. Then этого кейса фиксирует
ТЕКУЩЕЕ наблюдаемое состояние (замок регрессии — если поведение измени́тся
без явного решения, кейс должен упасть и привлечь внимание), а не
предвосхищает решение. Как только решение будет принято и зафиксировано в
`bugs/BUG-060.md`, Then этого ОДНОГО кейса переписывается под выбранную
альтернативу — `red_lock` намеренно НЕ проставлен (в отличие от TC-176/
BUG-059): там есть единственное чёткое ожидаемое значение, здесь — открытый
выбор из нескольких вариантов, значит нет единого «зелёного» состояния,
которое кейс мог бы ждать.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вкладка | фоновая, `file://<downloadPath>`, открыта с Files |
| Действие | Delete downloaded file → kill+relaunch |
| Наблюдаемо после | вкладка жива, ошибка `ERR_FILE_NOT_FOUND`, чип «about:blank» |

## Заметки для автоматизации
- Полностью переиспользует инфраструктуру TC-189 (сидинг, kill+relaunch,
  persisted-prefs оракулы) плюс `library_screen.tap_delete_downloaded_file`
  (готов, `library_screen.py:150-152`) и `adb shell ls` для подтверждения
  удаления файла (тот же приём, что TC-035).
- Текст ошибки WebView — читается через `contexts.in_webview` +
  `page_source`/`execute_script`, ЛИБО через нативный `WebResourceError`
  callback приложения, если он где-то surfaced в UI (не проверено — на
  усмотрение реализации, любой наблюдаемый канал подходит, если совпадает с
  текстом Then).
- Чип TabStrip «about:blank» — видимый Text-узел чипа, тот же приём, что
  `tab_chip_title_at` (`browser_screen.py:373`), но ТОЛЬКО при <=7 вкладках
  (виртуализация LazyRow, тот же класс ограничения, что CH-009
  инвариант-чек) — в этом кейсе вкладок всего 2, ограничение не задевает.
- Не дублирует TC-035 (удаление файла БЕЗ открытой фоновой вкладки на него) и
  TC-189 (persist БЕЗ удаления файла).
- Блокера автоматизации нет — сам факт (не решение) наблюдаем существующими
  примитивами.
