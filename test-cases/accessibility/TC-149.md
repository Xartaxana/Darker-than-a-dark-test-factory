# TC-149 — Свип контраста: инжектированные bridge-элементы и наши фикстуры держат WCAG-порог

## Предусловия
- Приложение запущено в replay-режиме на `listing_basic.mitm`; работа
  `LOVED` (`900000001`) засеяна рейтингом `SAVE` и непустым комментарием ДО
  первого рендера (`seed_db.seed_with_comment`, тот же приём, что TC-075) —
  на её блёрбе в листинге отрисованы закрашенный Rate-бейдж
  (`data-ao3-rate-btn`, `BADGE.SAVE`) и Note-кнопка (`data-ao3-note-btn`).
- `listing_basic.mitm` несёт СВОЙ ЖЕ work-page flow для `LOVED`
  (`scripts/build_replay_recordings.py::build_listing_basic`, флоу для ВСЕХ
  5 работ листинга записаны в ТОМ ЖЕ `.mitm`, не в отдельном файле) —
  навигация с листинга на страницу работы `LOVED` и обратно остаётся внутри
  ОДНОГО replay-сеанса; второй `.mitm`/повторный запуск приложения не
  требуется (граница П1 dedup «другой replay-файл/другой запуск — не
  сливать» не задета: маршрут использует ОДНУ фикстуру одной цены).
- Тема приложения переключаема (side panel toggle, тот же примитив, что
  TC-108/TC-148).
- `fontSizeStep` зафиксирован на дефолте (0) — комбинация с font-scale вне
  scope первой итерации (см. «Заметки для автоматизации» ниже).

## Сценарий (Given-When-Then)

**Given** приложение открыто в replay-режиме на листинговой странице
(`listing_basic.mitm`, Light-тема); на блёрбе засеянной работы `LOVED`
видны закрашенный Rate-бейдж (`data-ao3-rate-btn`) и Note-кнопка
(`data-ao3-note-btn`)

**When**
1. для Rate-бейджа и Note-кнопки на листинге через `execute_script`
   вычисляется `getComputedStyle(el).color` против ЭФФЕКТИВНОГО
   `background-color` (поднимаясь по родителям до первого непрозрачного
   фона) и переводится в WCAG-контраст-ratio (точка маршрута «листинг»,
   Light);
2. WebView навигируется на страницу работы `LOVED` (`BrowserScreen.
   open_work`, ТОТ ЖЕ replay-сеанс — flow для этой work-страницы уже
   записан в `listing_basic.mitm`); тем же способом вычисляется контраст
   для заголовка (`h2.title.heading`) и первого абзаца тела фикстуры
   (`.wrapper > p` — прямой потомок, НЕ вложенные филлерные `<p>` из
   `render_reading_ux_filler_html`) (точка маршрута «work-страница», Light);
3. тема переключается на Dark (side panel toggle); контраст title/body
   пересчитывается на ТЕКУЩЕЙ (work) странице (точка «work-страница», Dark);
4. WebView навигируется обратно на `LISTING_BASIC_URL` (тот же
   replay-сеанс, та же фикстура отдаёт тот же HTML); контраст Rate-бейджа/
   Note-кнопки пересчитывается (точка «листинг», Dark)

**Then** для каждой из четырёх комбинаций «точка маршрута × тема» (листинг×
Light, work-страница×Light, work-страница×Dark, листинг×Dark) вычисленный
ratio КАЖДОГО узла этой точки >= 4.5:1 (обычный текст) либо >= 3:1 (крупный
текст — по классификации `font-size`/`font-weight` узла)

**Инвариант:** свойство «вычисленный контраст держит свой WCAG-порог»
верно ОДНОВРЕМЕННО для ВСЕХ узлов ОБЕИХ точек маршрута (инжектированные
bridge-элементы листинга `LOVED` + фикстурные узлы её же work-страницы) И
для ОБОИХ системных вариантов темы (light и dark) — та же тема-семья
C4-банка («смена темы не меняет...»), что TC-108/TC-059; здесь
дополнительно проверяется НЕЗАВИСИМОСТЬ свойства от узла И от точки
маршрута (не только от темы). Маршрут «листинг → work-страница ТОЙ ЖЕ
работы → назад на листинг» — тот же класс поимённого воспроизводимого
маршрута, один проход, без разных фикстур/запусков, что TC-148/TC-150.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Порог | WCAG 4.5:1 (обычный текст) / 3:1 (крупный текст) |
| Маршрут | листинг (`listing_basic.mitm`) → work-страница `LOVED` → листинг (тот же replay-сеанс) |
| Инжектированные узлы (точка «листинг») | Rate-бейдж `data-ao3-rate-btn`, Note-кнопка `data-ao3-note-btn` (работа `LOVED`) |
| Фикстурные узлы (точка «work-страница», НАШИ) | `h2.title.heading` (заголовок), `.wrapper > p` (первый абзац тела — прямой потомок, НЕ вложенные филлерные `<p>` `render_reading_ux_filler_html`) |
| Темы | Light и Dark (обе стороны, на ОБЕИХ точках маршрута) |

## Заметки для автоматизации
- Примитив исполнения JS в WebView (`execute_script`) уже применялся в
  протоколе CH-005; переключение темы и скриншот-примитивы уже используются
  TC-047..049/TC-059/TC-108 — новой инфраструктуры не требуется.
- Инжектированные элементы задают цвет ИНЛАЙНОВЫМ `style.cssText`
  (`ao3_bridge.js:191-193,291-292`, сверено с HEAD fdd3f728, было
  148-151/248-252), не через внешний stylesheet/CSS custom
  properties — `getComputedStyle` резолвит их без дополнительных шагов;
  явных селекторов для контраст-проверки НЕ хватает — они уже есть
  (`data-ao3-rate-btn`/`data-ao3-note-btn` — атрибуты, назначенные при
  создании кнопки, стабильны).
- **Реализация формулы контраста — новый код (не блокер):** относительная
  яркость по формуле W3C (sRGB -> linear -> luminance) и подъём по DOM
  до первого непрозрачного `background-color` — рутинная реализация поверх
  уже читаемых `getComputedStyle`-значений, не отсутствующая
  фикстура/сидинг и не неавтоматизируемый штатно UI; test_debt-баг не
  заводится.
- **Граница scope (обязательна, docs/01 §9 — «чужая вёрстка вне скоупа»):**
  свип идёт ТОЛЬКО по нашим инжектированным элементам и по узлам НАШЕЙ
  replay-фикстуры (`build_replay_recordings.py`/`recording_builder.py`), не
  по вёрстке archiveofourown.org — контраст чужого текста живого AO3 НЕ наш
  дефект и не находка этого кейса. Live-режим прогона для ЭТОГО кейса не
  предусмотрен (только replay), чтобы граница выполнялась структурно, а не
  по вниманию исполнителя.
- **dp/px и viewport-масштаб:** контраст — цветовое свойство, не размерное,
  прямой зависимости от `devicePixelRatio`/`textZoom` нет; тем не менее если
  `textZoom` (см. TC-051/TC-145) на момент прогона отличается от 100%,
  классификация «крупный текст» (3:1 вместо 4.5:1) обязана учитывать ТЕКУЩИЙ
  отрендеренный `font-size`, а не номинальный CSS-размер фикстуры — иначе
  порог для одного и того же узла может быть выбран неверно при
  нестандартном `fontSizeStep`. Given этого кейса фиксирует `fontSizeStep`
  на дефолте (0) — комбинация с font-scale вне scope первой итерации.
- **Non-goal явно:** контраст НАТИВНОГО Compose-слоя (кнопки/панели вне
  WebView) остаётся testability gap TC-108 (a11y-дерево не отдаёт цвета) —
  этот кейс его не закрывает и не дублирует TC-108 (тот — luma-sanity
  нативных зон bottom bar/заголовка, не вычисленный WCAG-ratio DOM).
  Динамические состояния (открытый диалог/оверлей, живой снекбар) — вне
  scope, обе точки маршрута — в обычном (не fullscreen, без открытых
  оверлеев) состоянии.
- **Блокер стабилизации на стеке 2 (test-automator, 2026-08-21, `bugs/
  AT-BUG-095.md`, не test_debt самой оракульной части кейса — Given/When/
  Then корректны, код теста написан):** `framework/core/mitm.py::
  is_ca_installed()` проверяет ТОЛЬКО APEX-стор доверия
  (`/apex/com.android.conscrypt/cacerts/`), которого на стеке 2
  (`ao3_test_api29`) физически нет (`bugs/AT-BUG-028.md`) — CA реально
  установлен в системном сторе (`/system/etc/security/cacerts/`,
  подтверждено живым замером), но Python-чек об этом не знает и бросает
  ложный `RuntimeError` до первого шага теста, блокируя ЛЮБОЙ
  `@pytest.mark.replay` тест на этом стеке, не только TC-149. Фикс —
  `framework/core/mitm.py`, вне DoD test-automator (не тест/страница) —
  диспатч фикса за Lead. TC-149 остаётся `Approved`, `automated_by` пуст
  до фикса AT-BUG-095 и повторной стабилизации на стеке 2.
- **Разрешение эскалации `TC-149-GIVEN-BLURB-VS-WORK-PAGE-CONFLICT`
  (test-designer, 2026-08-20, `state/escalations.md`):** прежний Given
  требовал ОБА набора маркеров (`data-ao3-rate-btn`/`data-ao3-note-btn` —
  инжектируются ТОЛЬКО в `li[id^="work_"].work.blurb`, т.е. только на
  листинге; `h2.title.heading`/`.wrapper p` — существуют ТОЛЬКО в
  `render_work_page_html`, т.е. только на work-странице) НА ОДНОЙ открытой
  странице — структурно недостижимо. Given переписан на маршрут из ДВУХ
  точек (листинг работы `LOVED` → её же work-страница → назад на листинг),
  что соответствует развилке (а) критик-эскалации, реализованной КАК ОДИН
  кейс (аналог `TC-148`/`TC-150` — поимённый маршрут, один проход).
  Ключевая находка при редизайне: НОВОЙ фикстуры для этого маршрута НЕ
  потребовалось — `listing_basic.mitm` (`build_listing_basic`,
  `scripts/build_replay_recordings.py:27-70`) уже записывает work-page flow
  ДЛЯ ВСЕХ 5 работ листинга, включая `LOVED`, в ОДНОМ `.mitm`-файле; обе
  точки маршрута обслуживаются ОДНИМ replay-сеансом без второго запуска
  приложения (граница П1 dedup «другой replay-файл — не сливать» не
  задета — фикстура одна). Блокер снят редизайном Given, не test_debt-багом
  (missing_fixture неприменим — фикстура уже существует и уже подходит).
