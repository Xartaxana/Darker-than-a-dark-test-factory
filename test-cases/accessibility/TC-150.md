# TC-150 — Свип перекрытий: bounding-rect'ы нативных интерактивных элементов не пересекаются

## Предусловия
- Приложение запущено с чистыми данными, работа W засеяна (тот же seed, что
  TC-009/TC-106/TC-148), открыто >=2 вкладки (для `TabStrip`).
- Маршрут свипа — тот же поимённый маршрут, что TC-148: **Library -> Browse
  (work page, side panel свёрнут) -> Browse (side panel раскрыт) ->
  Settings**, `TabStrip` на Browse.
- Все состояния — статические/персистентные (см. non-goal ниже, тот же
  выбор границы, что TC-148 — консистентность решения по всей области).

## Сценарий (Given-When-Then)

**Given** маршрут Library -> Browse (свёрнут) -> Browse (раскрыт) ->
Settings пройден один раз, на каждой точке виден полный набор нативных
интерактивных элементов экрана

**When** на каждой точке маршрута accessibility-дерево читается напрямую
через UiAutomator2, из него извлекаются `bounds` ВСЕХ элементов с признаком
интерактивности (`clickable=true` либо явная роль button/switch/tab), и для
каждой ПАРЫ РАЗНЫХ (не родитель-потомок) таких элементов на одном экране
вычисляется пересечение прямоугольников `bounds`

**Then** ни для одной пары РАЗНЫХ интерактивных элементов одного экрана
пересечение `bounds` не найдено (кроме ожидаемого вложения потомок-в-родителя
— напр. текстовая подпись внутри своей кнопки, которая не считается
самостоятельной интерактивной целью)

**Инвариант:** свойство «bounding-rect'ы РАЗНЫХ интерактивных элементов не
пересекаются» верно ОДНОВРЕМЕННО для ВСЕХ пар элементов на КАЖДОЙ точке
поимённого маршрута — не для одной проверенной пары на одном экране;
находка по ЛЮБОЙ паре на ЛЮБОЙ точке маршрута — красный результат этого
прогона.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Маршрут | тот же, что TC-148: Library -> Browse (свёрнут/раскрыт) -> Settings + `TabStrip` |
| Единица проверки | попарное пересечение `bounds` РАЗНЫХ (не parent-child) интерактивных узлов на одном экране |
| Источник bounds | accessibility-дерево UiAutomator2 (нативный слой; WebView-контент — testability gap, см. ниже) |

## Заметки для автоматизации
- Примитив чтения `bounds` — тот же, что TC-106/TC-108/TC-148, новой
  инфраструктуры не требуется.
- **Новый код (не блокер):** попарная проверка пересечения прямоугольников
  (axis-aligned rectangle intersection) — рутинная геометрия поверх уже
  читаемых `bounds`; различение «родитель-потомок» (ожидаемое вложение,
  напр. `Text` внутри `TextButton`) от «два независимых интерактивных
  соседа» — по иерархии accessibility-дерева (родительский узел исходного
  запроса), не по одной лишь геометрии. Не отсутствующая фикстура/сидинг и
  не неавтоматизируемый штатно системный UI — test_debt-баг не заводится.
- **Как минимум нативный слой (явная граница scope, docs/01 §9):** этот
  кейс проверяет ТОЛЬКО элементы, чьи `bounds` достоверны из
  accessibility-дерева (нативный Compose-слой). Перекрытия ВНУТРИ
  WebView-контента (DOM-элементы AO3/наших фикстур) accessibility-деревом
  не отдаются — вне scope этого кейса; если впоследствии появится способ
  читать DOM-геометрию через WebView, это отдельное расширение оракула, не
  этот кейс.
- **Non-goal явно (тот же выбор, что TC-148, консистентность по области):**
  перекрытия ВО ВРЕМЕНИ (уведомление/снекбар поверх интерактива N секунд —
  фасет 1 `bugs/BUG-017.md`, «парад снекбаров») статическим свипом не
  ловятся В ПРИНЦИПЕ — их оракул отдельный (амплификация-тур шаблона
  чартера, `docs/templates/charter.md`), не этот кейс. Динамические/
  транзитные состояния (раскрытая НИЖНЯЯ панель со скримом, fullscreen,
  открытые диалоги/оверлеи вроде `RatingOverlay`, живые снекбары) НЕ входят
  в маршрут первой итерации — та же граница, что TC-148 (раскрытый SIDE
  panel — персистентный toggle, включён; транзитные состояния — отложены).
- **Ожидаемый результат — вероятно PASS на первой итерации** (в отличие от
  TC-148, у оракула (в) нет заранее измеренных красных кандидатов в docs/01
  §9) — но кейс написан от ОЖИДАЕМОГО поведения независимо от предположения
  о результате; реальный исход решает прогон, красный триажится штатно.

- [x] Given описывает полное состояние, воспроизводимое фикстурами
- [x] Then проверяет наблюдаемое поведение (геометрия, которую реально
  видит система доступности), а не реализацию
- [x] Заголовок сформулирован от ожидаемого поведения
- [x] Указаны приоритет, область и источник требования
- [x] Кейс независим от порядка выполнения других кейсов
- [x] Область комбинаторная (свойство должно быть верно для ВСЕХ пар
  элементов на ВСЕХ точках маршрута) — инвариант назван строкой
  `Инвариант:` выше
- [x] Слой **L4**, строка «почему не L2» дана явно (координатор,
  2026-08-20, критик-гейт поправил первоначальный выбор test-automator'а
  с L3 на L4 — тест несёт `@pytest.mark.live` и физически ходит на живой
  AO3, replay-записи нет; `docs/01-test-strategy.md` определяет L3 как
  e2e-**replay**, L4 — как e2e-**live**, тот же класс поправки, что
  TC-148 §»почему не L2«): оракул — реальные `bounds`
  ВСЕХ интерактивных узлов accessibility-дерева, читаемые UiAutomator2
  (`driver.page_source` на живом устройстве/эмуляторе) НАПРЯМУЮ (не
  curated-список локаторов, а полный обход дерева с иерархией узел->
  родитель для различения parent-child от независимых соседей,
  `framework/core/a11y_tree.py`) — Compose-layout, реальная
  композиция/наложение узлов друг на друга и итоговая структура
  accessibility-дерева вычисляются рендер-движком Android, которого в
  device-free L2-гарнизоне (jsdom) физически нет: jsdom не строит
  accessibility-дерево Compose и не может произвести `bounds`/иерархию
  для попарной геометрической проверки. L2 неприменим структурно, не
  по цене.
