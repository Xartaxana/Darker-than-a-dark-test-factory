# TC-267 — Прогресс чтения — персональный индикатор вкладки, не глобальный, и гаснет вне work-страниц

## Предусловия
- Приложение запущено с чистыми данными (`clean_state`).
- Replay-режим, `works_multi.mitm` (`recording_builder.WORKS_MULTI_FILENAME`) —
  уже несёт ДВЕ разные work-страницы (`ALL_WORKS[0]=LOVED`, `ALL_WORKS[1]=KUDOSED`)
  с reading-UX филлер-контентом (`AT-BUG-030`) и листинговую страницу
  (`WORKS_MULTI_LISTING_URL`) — используется как non-work цель.

## Сценарий (Given-When-Then)

**Given** Tab A открыта на work-странице `LOVED` через холодный `open_deep_link`
(реюз домашней вкладки на старте) и НЕ прокручена — прогресс `onPageLoaded`
только что сброшен, полоска/текст на нижней панели показывает `≈0.0`; Tab B
открыта ВТОРЫМ `open_deep_link` на work-странице `KUDOSED` (новая активная
вкладка — `tabs[0].url` уже не `HOME_URL`, реюз-условие не срабатывает)

**When** пользователь на Tab B (активна) прокручивает её ПРИМЕРНО ДО СЕРЕДИНЫ
документа (частичная серия `swipe_scroll_active_tab`, останов по достижении
`scrollY`, близкого к половине высоты филлер-контента `AT-BUG-030`) — читает
текст индикатора; затем продолжает прокрутку ДО САМОГО НИЗА документа
(повторный `swipe_scroll_active_tab` до стабилизации scrollY) — читает текст
индикатора снова; затем переключается на Tab A (`switch_to_tab(position=0)`,
Tab A с момента открытия не трогалась)

**Then** на Tab B, ПОСЛЕ частичной прокрутки (промежуточная точка), текст
индикатора прогресса показывает значение, близкое к `0.5` (середина
документа) — followup_tc[1] CH-011 явно требовал точку 50% в дополнение к
0%/100%, не только крайние значения

**And** на Tab B (активна, после продолжения прокрутки до низа) текст
индикатора прогресса показывает значение, близкое к `1.0` (документ
прокручен до конца) — в формате `<доля>` (одна-две значащих цифры после
точки), тот же формат, что измерила CH-011

**And** сразу после переключения на Tab A текст индикатора показывает
СОБСТВЕННОЕ значение Tab A (`≈0.0`), А НЕ унаследованное значение Tab B
(`≈1.0`) — контраст двух РАЗНЫХ одновременно существующих значений доказывает,
что индикатор персонален для вкладки (`TabInfo.readingScrollPercent`), в
отличие от сиблинг-бага соседнего глобального индикатора `_activeScrollY`
(`BUG-080`)

**And** пользователь на Tab A (активна, только что показывала `≈0.0`)
переходит на нерабочую (non-work) страницу — листинг
(`browser_steps.open_listing(driver, rb.WORKS_MULTI_LISTING_URL)`, навигация
В ТОЙ ЖЕ вкладке, не новая) — полоска и текстовый индикатор ИСЧЕЗАЮТ из
нижней панели целиком (`BottomBar.kt:48`, `isWorkPage` false на листинге)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Tab A | work `LOVED` (900000001), не прокручена, индикатор `≈0.0` |
| Tab B | work `KUDOSED` (900000002), прокручена до середины (`≈0.5`), затем до низа, индикатор `≈1.0` |
| Формат текста индикатора | десятичная дробь `<доля>`, измерено CH-011 (0.0/0.5/0.74/0.76/1.0) |
| После перехода Tab A на листинг | индикатор отсутствует на нижней панели |

## Заметки для автоматизации
- **Числовой оракул есть, вопреки прежнему допущению плана CH-011** — узел
  `android.widget.ProgressBar` с атрибутом `text`, содержащим десятичную
  дробь (не одна голая полоска без значения); bounds `[0,2195][1080,2252]`
  (измерено CH-011 на этой сборке — сверить заново при заметном расхождении
  разрешения эмулятора). Помощника в `framework/` нет — добавить тонкий
  `browser_steps.read_reading_progress_text`/`assert_reading_progress_absent`
  (`AppiumBy.CLASS_NAME, "android.widget.ProgressBar"`, `get_attribute("text")`).
  НЕ блокер — тривиальный локатор, тот же класс решения, что TC-266/FAB (прямой
  дешёвый native-оракул, не требующий записи фикстуры).
- Обе work-страницы и листинг уже покрыты `works_multi.mitm` — новой записи не
  требуется; `AT-BUG-030` подтверждает наличие reading-UX филлер-контента на
  обеих work-страницах (высота, достаточная для нетривиального scrollY).
- Вторая вкладка — через `app_steps.open_deep_link(work_b.url)` (та же дверь
  «в» из Mission CH-011, создаёт НЕ-нулевую активную вкладку, минуя sticky
  chromedriver-прилипание) — не через library card/long-press (избыточно для
  этого сценария).
- Прокрутка до низа — `browser_steps.swipe_scroll_active_tab` в цикле (жест
  нативный, не WEBVIEW-JS — адресуется тем, что физически видно на экране,
  sticky-прилипание chromedriver к вкладке-0 (`AT-BUG-070`) здесь НЕ
  задействуется вовсе), пока очередное чтение НАТИВНОГО текста
  `android.widget.ProgressBar` не перестанет расти — стабилизация читается
  ТЕМ ЖЕ оракулом, что и целевой Then, отдельного WEBVIEW-опроса scrollY не
  требуется.
- **Батарея правил-реакций — н/п:** `bridge-scroll-reporting` не входит в
  поимённый инвентарь правил-реакций реестра (`background-auto-kudos-trigger`
  — единственная тегированная запись); это пер-вкладочный derived-индикатор
  состояния чтения, не событие-с-побочным-эффектом.
- **C4-банк комбинаторных областей:** `bridge-scroll-reporting` НЕ входит в
  перечисленные категории (фильтры/сортировки/рейтинги-видимость/
  backup-restore/tabs/темы) — формальная строка `Инвариант:` не требуется по
  букве нормы; кейс тем не менее демонстрирует заявляемое свойство
  («персонально для вкладки») КОНТРАСТОМ двух одновременно различных
  значений, не единственным примером — по духу нормы этого достаточно.
- **Наблюдаемость и направление негативного Then (третий And):** переход
  «индикатор виден → индикатор отсутствует» на ОДНОЙ И ТОЙ ЖЕ вкладке —
  положительный якорь («≈0.0» замерен непосредственно перед переходом на той
  же Tab A) делает негатив достижимо ложным, не вакуумным; сам эффект —
  DOM/UI-состояние, читаемое напрямую (не сетевой вызов), калибровка Lead
  2026-07-30 (AT-BUG-029) неприменима.
- Не red-locked: found_bugs CH-011 (`BUG-080`/`BUG-081`/`BUG-082`) не
  документирует дефект именно в `readingScrollPercent`/`BottomBar` — предмет
  BUG-082 другой (глобальное поле `uiState.resumeOffer`, снекбар «Continue
  reading»). Ожидание — зелёный прогон.
- Ветка подписи «Ch N/M» (`chTot>1`) сознательно ВНЕ скоупа этого кейса —
  недостижима текущим корпусом фикстур (`select#selected_id` отсутствует),
  см. `bugs/AT-BUG-089.md` (заведён этим же ходом).
