# TC-203 — Живое исчезновение баннера при выключении «Hide Disliked works»

## Предусловия
- Приложение запущено, `seeded_library` (в т.ч. `DISLIKED`, `rating=DISLIKE`).
- Settings в дефолтном состоянии (`ratedHidden=true`) — на листинге баннер виден
  с текстом "Some works may be hidden by your visibility settings", блёрб
  DISLIKED скрыт (то же исходное состояние, что TC-013/015/197).
- Открыта листинговая страница (replay `listing_basic.mitm`).

## Сценарий (Given-When-Then)

**Given** приложение запущено с `seeded_library`, Settings в дефолтном состоянии
(`ratedHidden=true`), листинг открыт, баннер виден, блёрб DISLIKED скрыт

**When** пользователь, НЕ покидая уже открытую листинговую вкладку, переходит на
Settings и выключает тумблер «Hide Disliked works» (`viewModel.toggleHideRating
(Rating.DISLIKE)`), затем возвращается на ту же (НЕ перезагруженную) вкладку
Browse — приложение проталкивает смену на открытую вкладку живым JS-вызовом
(`MainActivity.kt` реагирует на пересчитанные `ratedWorksHidden`/`ao3FilterActive`
→ `BrowserScreen.kt:161-168` → `window.setHiddenBanner` → `updateHiddenBanner`)

**Then** узел `#ao3-companion-hidden-notice` исчезает из DOM БЕЗ навигации/reload
страницы (URL вкладки не изменился, `document.readyState` не переходил в
`loading` заново)
**And** одновременно блёрб DISLIKED становится видимым (тот же live-push эффект,
что TC-015, для рейтинг-фильтрации) — согласованность между рейтинг-фильтрацией
и баннером сохраняется и в живом пути, не только при загрузке страницы

**Инвариант:** живой путь (`window.setHiddenBanner`, вызванный из Kotlin без
навигации) и путь загрузки страницы (`updateHiddenBanner()` при инъекции
bridge-скрипта, TC-197/198/199/200/201) сходятся к ОДНОМУ и тому же итоговому
DOM-состоянию для данной пары флагов — переключение тумблера «на лету» даёт
РОВНО тот результат, который дала бы свежая загрузка страницы с новыми
значениями флагов (свойство конвергенции живого/загрузочного пути, тот же класс,
что TC-093 для dim/hide).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа | `DISLIKED` из `framework/data/works.py`, `rating=DISLIKE` |
| Состояние ДО | `ratedHidden=true`, баннер виден, блёрб скрыт |
| Действие | выключение «Hide Disliked works» в Settings, без re-навигации листинга |
| Состояние ПОСЛЕ | `ratedHidden=false`, баннер отсутствует, блёрб виден |

## Заметки для автоматизации
- Не блокер: метод чтения баннера — см. заметку TC-197.
- Тот же live-push паттерн, что TC-015/093: выполнить действие в Settings,
  вернуться на уже открытую вкладку Browse БЕЗ повторного
  `browser_steps.open_listing`, затем опросить DOM.
- `settings_steps.set_hide_rating(driver, "Disliked", False)` — существующий шаг.
- Проверка «без reload» — тот же приём, что TC-093/015: URL вкладки не менялся
  (`browser_steps.assert_active_tab_url` с исходным URL) и/или `document.
  readyState` не сбрасывался в `loading` в промежутке (если нужен более
  строгий сигнал, чем неизменность URL).
- **Батарея правил-реакций — полная оценка для двух мест вызова правила
  (page-load init `:995` и live-push `setHiddenBanner:505-509`):**
  - **edge vs level** — н-п: `LaunchedEffect(ratedWorksHidden, ao3FilterActive)`
    в Compose ключуется РАВЕНСТВОМ значений — пересчитанные `ratedWorksHidden`/
    `ao3FilterActive` не меняются при несвязанных действиях (напр. правка
    шрифта), поэтому эффект не перезапускается «случайно» на нейтральном
    save-пути (класс BUG-014 здесь неприменим: нет общего save-пути с
    предикатом состояния — только derived-state recompute). Это гарантия
    Compose-фреймворка, не наблюдаемая как отдельный пользовательский Then
    без инструментирования внутреннего кода — не добавляю синтетический шаг.
  - **идемпотентность** — н-п: `window.setHiddenBanner` перезаписывает
    `textContent`/вызывает `.remove()` безусловно; повторный вызов с теми же
    значениями не создаёт второй узел и не дублирует эффект (в отличие от
    сетевого auto-download/auto-kudos).
  - **ретроактивность** — н-п: нет персистентного per-работы состояния —
    баннер полностью производный, каждый вызов пересчитывает всё заново.
  - **off-инвариант** — покрыт сиблингами TC-198/TC-201 (явный негативный Then).
  - **propagation** — ПРИМЕНИМО, покрыто отдельным кейсом TC-204 (тот же код
    `BrowserScreen.kt:161-168` рассылает на ВСЕ webViews, не только активную
    вкладку — риск класса BUG-012, здесь проверяется только single-tab путь).
