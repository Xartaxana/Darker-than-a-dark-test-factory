# TC-275 — journey: обе ветки действия «Resume» плюс немедленная не-повторяемость оффера

## Предусловия
- Приложение запущено с чистыми данными (`clean_state`).
- Replay-режим, `works_multi.mitm` (work LOVED, ao3_id 900000001, reading-UX
  филлер-контент `AT-BUG-030`) — та же фикстура, что TC-273/TC-274/TC-267,
  без новой записи.
- **Journey, П1 spec-p1-dedup v7:** три чекпойнта одного L3-слоя (тот же
  fixture-класс на всём протяжении — только повторные `open_deep_link` и
  ОДНА навигация через side panel «Home», БЕЗ закрытия вкладок, без
  релончей/пересидинга) — потолок ≤5 соблюдён (3), никакой границы
  фикстуры/слоя не пересекает.
- **Ревизия 2 (критик-раунд, доработка Б3):** исходная редакция ЧП1 получала
  mismatch-ветку ЗАКРЫТИЕМ владельца (`swipe_close_tab`) в узком окне внутри
  `SnackbarDuration.Long` (~10с) — критик указал на два риска: (а) тайминг
  (открыть переключатель + swipe close + найти/тапнуть Resume могли не
  уложиться в окно) и (б) конкурирующий снекбар «Tab closed»/Undo
  (`MainActivity.kt:315-328`) на ТОМ ЖЕ Mutex-сериализованном хосте
  (`browser_screen.py:423-431`, класс TC-024). Редакция 2 получает
  mismatch-ветку через `navigateActiveTabTo` side panel «Home»
  (`MainActivity.kt:713`) — вкладка-владелец НИКОГДА не закрывается, поэтому
  конкурирующий снекбар «Tab closed» физически не порождается ни разу за
  весь прогон. Каждый тап «Resume» ДОПОЛНИТЕЛЬНО предваряется явной
  проверкой видимости+текста снекбара (не блокирует вслепую) — если гонка
  всё же случится, тест падает ЯВНО на этой проверке, а не даёт ложный
  негатив на Then действия.

## Сценарий (Given-When-Then)

**Given** (общий для всех чекпойнтов) первый `open_deep_link(work_loved.url)`
(Tab A, реюз домашней вкладки) загружает work LOVED; Tab A прокручивается
`swipe_scroll_active_tab` ПРИМЕРНО ДО СЕРЕДИНЫ (индикатор `≈0.40`); пауза
≥ 3000мс (`PROGRESS_SAVE_DEBOUNCE_MS`) — Room-запись `readProgressPercent=40,
readProgressUrl=<канонический URL work LOVED>` зафиксирована. Tab A
ОСТАЁТСЯ открытой (не трогается) до конца прогона — это ровно тот же
триггер-механизм подтверждения записи, что TC-273/TC-274.

## Чекпойнты

1. **Mismatch-ветка (владелец навигирован Home, НЕ закрыт).** Второй
   `open_deep_link(work_loved.url)` открывает НОВУЮ Tab X (реюз-условие уже
   не срабатывает) — её `onPageLoaded` вызывает `maybeOfferResume(X, LOVED,
   url)`; `suppressResumeForWork` в этот момент `null` (после Given ни разу
   не взводился) — оффер генерируется штатно, `offer.tabId = X`, `offer.url
   = <URL LOVED>`, и на этот момент СОВПАДАЕТ с текущим URL самой Tab X.
   **Предтап-проверка:** `resume_offer_snackbar_visible`+`_text` подтверждают
   «Continue reading at 40%?» — оффер реально виден на Browse, Tab X активна.
   Пользователь раскрывает side panel (`side_panel_steps.expand`) и тапает
   иконку Home (`side_panel_steps.tap_home`) — вызывает
   `browserViewModel.navigateActiveTabTo(HOME_URL)` НА ТОЙ ЖЕ Tab X (панель
   автосворачивается); Tab X теперь на `HOME_URL` — НЕ work-страница,
   `maybeOfferResume` для этой загрузки не вызывается, `uiState.resumeOffer`
   и `suppressResumeForWork` не тронуты этим шагом. Третий
   `open_deep_link(WORKS_MULTI_LISTING_URL)` открывает Tab Y (не
   work-страница — `maybeOfferResume` не вызывается) — Tab Y становится
   АКТИВНОЙ; Tab X по-прежнему СУЩЕСТВУЕТ (просто не активна, на `HOME_URL`).
   **Предтап-проверка (повтор):** `resume_offer_snackbar_visible`+`_text`
   ПОВТОРНО подтверждают, что оффер «Continue reading at 40%?» всё ещё виден
   (никто его не закрывал/не гасил — ни открытие Tab Y, ни навигация Home не
   являются `tabClosedMessage`, `MainActivity.kt:356-362` их не трогает) —
   если бы оффер к этому моменту истёк/погас, тест ОСТАНОВИЛСЯ БЫ ЗДЕСЬ с
   явной ошибкой, а не тапнул вслепую. Пользователь нажимает «Resume»
   (`tap_resume_snackbar_action`). **Then:** `acceptResumeOffer` ищет
   `tabs.find{id==X}` — НАХОДИТ (X никогда не закрывалась) — но
   `currentUrl = X.url = HOME_URL != offer.url` — MISMATCH (сравнение идёт
   именно с URL владельца `offer.tabId`, а не с URL активной вкладки) —
   `navigateActiveTabTo(offer.url)` переносит АКТИВНУЮ вкладку (Tab Y,
   которая ДО этого была на URL листинга и никогда не открывала work LOVED)
   на URL work LOVED. Наблюдаемо: URL активной вкладки (Tab Y) МЕНЯЕТСЯ с
   URL листинга на URL LOVED, а URL Tab X (владельца) остаётся `HOME_URL`
   неизменным — пользователя, смотревшего на посторонний листинг, молча
   уводит на чужую work-страницу (самостоятельная грань R-16, docs/01 §9
   п.3), при этом ни одна вкладка не была закрыта за весь чекпойнт.

2. **Немедленная не-повторяемость (suppression).** Пересидинг не требуется —
   прямое продолжение чекпойнта 1: переход Tab Y на URL LOVED из чекпойнта 1
   САМ порождает `onPageLoaded(Y, LOVED_url)`; `pendingResumeScroll.remove(Y)`
   не находит записи (запись из accept числится под `X` — `pendingResumeScroll
   [X]=40`, безобидно повисает на РЕАЛЬНО существующей Tab X до её
   следующей собственной загрузки work-страницы, вне скоупа этого TC) —
   падает в `maybeOfferResume(Y, LOVED, url)`; `suppressResumeForWork`
   взведён РОВНО тапом чекпойнта 1 (`acceptResumeOffer:613`, значение —
   `workId` LOVED) — совпадает — вызов ГАСИТСЯ, флаг сбрасывается в `null`.
   **Then:** после того как Tab Y заканчивает загрузку work LOVED, НИ ОДИН
   новый снекбар «Continue reading» не появляется на этой же загрузке (явная
   проверка `resume_offer_snackbar_visible` с разумным ожиданием возвращает
   `False`) — это несмотря на то, что Room-строка LOVED по-прежнему несёт
   `readProgressPercent >= порога` (сама запись НЕ трогалась чекпойнтами 1-2,
   `persistReadingProgress` не вызывалась) — единственная причина отсутствия
   оффера — одноразовый guard `suppressResumeForWork`, взведённый именно
   ЭТИМ тапом.

3. **Match-ветка (владелец активен и на месте, флаг уже чист).** Четвёртый
   `open_deep_link(work_loved.url)` открывает Tab Z (реюз не срабатывает,
   Tab Y уже не на `HOME_URL`) — `onPageLoaded(Z, LOVED_url)` вызывает
   `maybeOfferResume(Z, LOVED, url)`; `suppressResumeForWork` уже `null`
   (сброшен чекпойнтом 2) — оффер генерируется штатно СВЕЖИЙ: `offer.tabId
   = Z`, `offer.url = <URL LOVED>` — и тут же ТРИВИАЛЬНО совпадает с
   ТЕКУЩИМ URL самой Tab Z (только что загрузившей этот URL).
   **Предтап-проверка:** `resume_offer_snackbar_visible`+`_text` подтверждают
   «Continue reading at 40%?» непосредственно перед тапом. Пользователь
   нажимает «Resume». **Then:** `acceptResumeOffer` находит `tabs.find{id==Z}`
   с `url == offer.url` — MATCH — `evalJs(Z, "ao3ScrollToPercent(40)")` —
   URL активной вкладки (Tab Z) НЕ меняется (нет навигации), а текстовый
   индикатор прогресса (`android.widget.ProgressBar`) на Tab Z после
   короткого ожидания показывает значение, близкое к сохранённому `≈0.40` —
   контраст с чекпойнтом 1 (где то же самое действие «Resume» породило
   НАВИГАЦИЮ, а не скролл на месте) демонстрирует, что ветвление
   действительно зависит ОТ СОВПАДЕНИЯ URL владельца, а не от порядка/
   случайности/присутствия закрытых вкладок.

## Заметки для автоматизации
- **Слой L3, устройство обязательно — почему не L2.** Все три чекпойнта
  проверяют взаимодействие РЕАЛЬНОГО многовкладочного состояния
  (`_uiState.value.tabs`, реальные WebView per tab), РЕАЛЬНОГО
  Mutex-сериализованного Compose `SnackbarHostState` и РЕАЛЬНОГО таймсинга
  между навигацией/загрузкой страниц. jsdom-харнесс L2 не эмулирует ни
  множественные Android-вкладки, ни нативный снекбар-хост с очередью показа,
  ни реальную задержку `onPageLoaded`/`LaunchedEffect` — сам предмет
  проверки (гонка/очерёдность двух реальных UI-элементов, ветвление по
  реальному состоянию нескольких вкладок) структурно не существует в jsdom
  (тот же класс обоснования, что TC-268.md:138-140).
- **Порядок чекпойнтов НЕ перестановочен.** Mismatch-ветка (ЧП1) обязана
  идти ПЕРВОЙ: `suppressResumeForWork` — одноразовый флаг БЕЗ привязки к
  `workId`/`tabId` своего следующего вызова (`maybeOfferResume:584-585` —
  сбрасывается НА ЛЮБОМ следующем вызове, совпал `workId` или нет). Если
  начать с match-ветки, её accept НЕ порождает нового `onPageLoaded` (нет
  навигации) — флаг останется «взведённым» и МОЛЧА погасит offer-генерацию
  следующего чекпойнта, ломая тест ложным негативом. Текущий порядок
  (mismatch → suppression-чек как естественное продолжение → match)
  гарантированно потребляет флаг ДО чекпойнта 3.
- **Почему `navigateActiveTabTo` через side panel «Home», а НЕ закрытие
  вкладки (критик-доработка Б3).** Закрытие владельца (`swipe_close_tab`)
  порождает СВОЙ снекбар «Tab closed»/Undo на ТОМ ЖЕ Mutex-хосте
  (`MainActivity.kt:315-328`, класс очереди — `browser_screen.py:423-431`/
  TC-024) — прямая конкуренция за видимый слот с офером именно в момент,
  когда он должен быть виден для тапа. `side_panel_steps.tap_home`
  (`SidePanel.tap_home`, `MainActivity.kt:713`) вызывает
  `navigateActiveTabTo(HOME_URL)` НА МЕСТЕ (та же вкладка, тот же `tabId`,
  никакого закрытия/нового снекбара) — единственный побочный эффект
  панели — её собственное авто-сворачивание, которое НЕ является снекбаром
  и хост не трогает. Итог: mismatch достигается БЕЗ закрытия вкладки, race
  с конкурирующим снекбаром структурно исключена, а не просто менее вероятна.
- **Предтап-проверки — во всех ТРЁХ чекпойнтах** (по прямому требованию
  критик-раунда): каждый тап «Resume» предваряется явным
  `resume_offer_snackbar_visible`+`_text`; если по какой-то причине оффер
  всё же истёк/погас к моменту проверки, тест падает ИМЕННО на этой строке
  с диагностируемой причиной, а не даёт слепой тап с непредсказуемым
  исходом (`acceptResumeOffer:612` делает ранний `return`, если
  `uiState.resumeOffer == null` — слепой тап на уже погасшем оффере молча
  ничего не делает).
- **Снекбар-локаторы — тонкий класс, общий с TC-273/TC-274**
  (`resume_offer_snackbar_visible`/`_text`/`tap_resume_snackbar_action`) —
  переиспользуется, не дублируется отдельным диффом.
- **`side_panel_steps.expand`/`tap_home`** — уже существуют
  (`framework/steps/side_panel_steps.py:18,73`; `framework/screens/
  side_panel.py:31,104`) — не новый локатор, тривиальная интеграция.
- **Наблюдаемость и достижимость Then:** оба ассерта URL (ЧП1: URL Tab Y
  СМЕНИЛСЯ на чужой, URL Tab X остался `HOME_URL`; ЧП3: URL Tab Z НЕ
  сменился, контраст с ЧП1) читаются напрямую из `open_tabs_urls`/нативного
  заголовка вкладки — не сетевой эффект, калибровка `AT-BUG-029`
  неприменима. ЧП2 (негатив «нет второго снекбара») имеет положительный
  якорь В ТОМ ЖЕ прогоне: тот же УЗЕЛ снекбара только что был показан и
  потреблён в ЧП1 тем же кодовым путём (`maybeOfferResume` успешно порождал
  снекбар минимум дважды до этого момента — на ЧП1 и на предтап-проверках) —
  недостижимость исключена, а не предполагается.
- **Батарея правил-реакций:** идемпотентность — ПОКРЫТА ЧП2 (повтор события
  «загрузка work-страницы с уже-прочитанной позицией» сразу после accept не
  дублирует эффект). Edge-vs-level — н/п этой конкретной поверхности
  (пересохранения работы не задействованы ни в одном чекпойнте, персиcтенция
  прогресса — отдельная точка `persistReadingProgress`, не затронутая этим
  TC). Off-инвариант/ретроактивность — н/п (нет тумблера настройки для
  функции резюме). Propagation — н/п: единственный «консьюмер» эффекта —
  сам Scaffold-снекбар, других потребителей `resumeOffer` в коде нет.
- **Остаток DoD п.4, сознательно НЕ покрытый (P2, не needs-design):**
  «отказ (decline/истечение снекбара) НЕ подавляет будущие предложения»
  (`consumeResumeOffer` НЕ трогает `suppressResumeForWork` — в отличие от
  accept; частично уже продемонстрировано ПОЗИТИВНО в TC-274, Н1-якорь —
  свайп-отказ там НЕ гасит следующую offer-генерацию) — отдельный Given
  (новый work, полный dismiss-жест, явная повторная генерация оффера ТОГО
  ЖЕ work'а как самостоятельный Then) не входит в минимальный набор DoD этой
  design-задачи (пункт 4 помечен «по усмотрению» координатором) —
  decline-путь как ПОЛНОЦЕННЫЙ отдельный TC остаётся остатком, не
  блокирующим закрытие design-метки области.
