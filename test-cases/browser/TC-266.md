# TC-266 — регресс-замок BUG-080 (Open): FAB ДОЛЖЕН отражать реальную позицию вкладки сразу после переключения (сейчас — красный)

> **Статус замка.** `bugs/BUG-080.md` — `Open` (сценарий (а), найдено
> exploratory-charter CH-011, 2026-08-20). Этот тест ОЖИДАЕМО ПАДАЕТ до фикса
> Kotlin-стороны (`switchTab` должен либо пересчитывать `_activeScrollY` из
> реальной позиции вкладки-цели, либо гейт FAB должен читать позицию иначе,
> чем через общий индикатор, обнуляемый переключением). Заголовок и Then
> сформулированы от ОЖИДАЕМОГО (спецификационного) поведения — красный факт
> живёт здесь, в теле кейса, не в заголовке (правило CLAUDE.md, прецедент
> TC-264). `red_lock` пока пуст (кейс не автоматизирован, см. чек-лист) —
> будет выставлен test-automator'ом/test-reviewer'ом вместе с `automated_by`
> (прецедент TC-139).

## Предусловия
- Приложение запущено с чистыми данными (`clean_state`).
- Replay-режим, `tab_markers.mitm` (`recording_builder.tab_marker_url`,
  `TAB_MARKER_COUNT=8`, area=tabs фикстура — уже используется TC-023/024/025).

## Сценарий (Given-When-Then)

**Given** открыты две вкладки на маркерных страницах (`tab_marker_url(1)`,
`tab_marker_url(2)`, различаются нативным заголовком чипа); активная вкладка 1
прокручена вглубь свайпом до позиции >= 600px (`swipe_scroll_active_tab`) —
узел FAB (content-desc `Scroll to top`) появляется, снимок тройки «FAB есть +
`open_tabs_urls` scrollY + `active_tab_index`»; переключение на вкладку 2
(`switch_to_tab(position=1)`) — вкладка 2 свежая, сверху, FAB отсутствует;
вкладка 1 физически ОСТАЁТСЯ на своей глубокой позиции (никто её не трогал)

**When** пользователь переключается ОБРАТНО на вкладку 1 (`switch_to_tab(position=0)`)
— без единого касания экрана после переключения

**Then (ожидаемое, спецификационное)** FAB «Scroll to top» виден СРАЗУ (в
пределах ~1с — время рендера/пересчёта, не время ожидания пользовательского
жеста) — вкладка 1 физически стоит на позиции >= 600px, все четыре побочных
условия гейта выполнены (вкладка BROWSE, не work-page, панель погашена, нет
оверлея рейтинга) — гейт обязан отражать РЕАЛЬНУЮ позицию активной вкладки

**Then (фактическое на этой сборке — КРАСНОЕ, регресс-замок BUG-080)** непрерывный
опрос узла FAB (`~0.5с интервал, бюджет >= 7с`) показывает ЕГО ОТСУТСТВИЕ ВСЁ
окно — `switchTab:340-346` обнулил `_activeScrollY` при первом переключении и
ничего не пересчитал при возврате; FAB появляется ТОЛЬКО ПОСЛЕ того, как
пользователь сам минимально прокрутит вкладку (событие `scroll`, троттл
200мс) — измерено BUG-080: 5.5с/6.5с в двух независимых прогонах, 0/8 в
амплификационной серии переключений

**Инвариант (направление негативного Then):** различающий ассерт
(«FAB виден / не виден при возврате на физически глубоко прокрученную
вкладку») положителен по спецификации и достижимо ложен на текущей сборке —
Given явно доказывает, что вкладка 1 физически стоит на позиции >= 600px
(снята ДО переключения на вкладку 2), поэтому отсутствие FAB после возврата
не может объясняться «вкладка физически не прокручена» — единственная
переменная между ожиданием и фактом — пересчёт `_activeScrollY` на двери
`switchTab`.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вкладка 1 | `tab_marker_url(1)`, физическая позиция >= 600px (глубокая) |
| Вкладка 2 | `tab_marker_url(2)`, позиция 0 (свежая) |
| Ожидаемое время появления FAB после возврата | ~1с (спецификация) |
| Фактическое (red) | FAB отсутствует >= 7с непрерывного опроса, до первого касания |
| Дискриминатор guard'а | минимальный свайп 150-180px зажигает FAB немедленно (BUG-080) |

## Заметки для автоматизации
- **Оракул — нативный, дешёвый, без помощника в `framework/`:** узел с
  content-desc `Scroll to top` (`MainActivity.kt:566`). Поиск по строке
  `Scroll to top|scroll_to_top|scrollToTop` по всему репозиторию (CH-011,
  case-insensitive) на момент заведения этого кейса не даёт ни одного шага
  фабрики — добавить тонкий `browser_steps.assert_scroll_to_top_fab_visible`/
  `assert_scroll_to_top_fab_absent` (poll по `AppiumBy.ACCESSIBILITY_ID`,
  `"Scroll to top"`) по образцу существующих native-оракульных степов. НЕ
  блокер (`test_debt` не заводится) — локатор тривиален, класс отличается от
  `AT-BUG-035`-подобных находок (там отсутствовал сам DOM-узел ФИКСТУРЫ; здесь
  недостаёт только тонкой Python-обёртки над уже существующим нативным
  элементом приложения).
- Идентификация вкладок — по нативному заголовку чипа
  (`tab_marker_title`/`browser_steps.tab_chip_title_at`), тот же приём, что
  TC-023/024/025 — не заходит в WEBVIEW-контекст, не подвержен sticky-прилипанию
  chromedriver.
- Снимок тройки «FAB + `open_tabs_urls` (scrollY) + `active_tab_index`» — до и
  после КАЖДОГО шага, меняющего активную вкладку (норма CH-011); prefs —
  ТОЛЬКО через `adb.run_as_file_or_raise` + `app_steps._parse_persisted_tabs`
  (класс AT-BUG-044/045/055 — «сырой» `adb.run_as`/`shell cat` запрещены).
- **Батарея правил-реакций — н/п:** гейт FAB не входит в поимённый инвентарь
  правил-реакций реестра фич (`docs/feature-registry.yaml`, единственная
  явно тегированная запись — `background-auto-kudos-trigger`); это derived
  UI-гейт (конъюнкция условий), не событие-с-побочным-эффектом в смысле
  инвентаря CLAUDE.md.
- Этот кейс закрывает ТОЛЬКО дверь `switchTab` (сценарий (а) `BUG-080`,
  флагманская находка Г1). Двери `closeTab`/Undo (сценарий (б)) и
  `deep-link`/фоновое открытие (сценарий (в)) — из ТОГО ЖЕ бага, но другая
  природа Given (закрытие/восстановление вкладки, отдельная навигационная
  дверь) — по норме «слой сначала, дедуп внутри слоя» это ОТДЕЛЬНЫЕ
  кандидаты на кейсы, не чекпойнты этого journey (излишнее раздутие одного
  теста разноприродными Given). Оставляю строкой в отчёте координатору:
  области `browse-scroll-to-top-fab` для полного покрытия нужны ещё 1-2
  кейса на двери (б)/(в), не закрытые этим ходом.
