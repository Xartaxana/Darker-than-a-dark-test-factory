# TC-273 — Оффер возобновления чтения появляется только выше порога 5%, ниже — не появляется вовсе, тот же тест доказывает оба конца контрастом

## Предусловия
- Приложение запущено с чистыми данными (`clean_state`).
- Replay-режим, `works_multi.mitm` (`recording_builder.WORKS_MULTI_FILENAME`) —
  несёт ДВЕ разные work-страницы (`ALL_WORKS[0]=LOVED` ao3_id 900000001,
  `ALL_WORKS[1]=KUDOSED` ao3_id 900000002) с reading-UX филлер-контентом
  (`AT-BUG-030`, достаточная высота для нетривиального scrollY) — та же
  фикстура, что уже несёт TC-267 (соседняя область, полоска прогресса, НЕ
  дублируется этим кейсом: TC-267 не касается Room/оффера).

## Сценарий (Given-When-Then)

**Given** приложение запущено; первый `open_deep_link(work_loved.url)` —
холодный реюз домашней вкладки (Tab A, `tabs[0].url` был `HOME_URL`) —
загружает work LOVED

**When** пользователь на Tab A прокручивает СОВСЕМ немного —
`swipe_scroll_active_tab` короткой дистанцией, контроль по тексту
`android.widget.ProgressBar` — индикатор показывает `≈0.03` (3%, СТРОГО
НИЖЕ `MIN_PROGRESS_PERCENT=5`); выдерживается пауза ≥ 3000мс
(`PROGRESS_SAVE_DEBOUNCE_MS`) после ПОСЛЕДНЕГО события скролла — Room-запись
(если бы она случилась) успела бы дебаунситься; затем ВТОРОЙ
`open_deep_link(work_loved.url)` — реюз-условие уже не срабатывает (`Tab A`
не на `HOME_URL`), открывается НОВАЯ Tab B на ТОМ ЖЕ URL work LOVED —
единственный способ ретриггернуть `onPageLoaded`→`maybeOfferResume` для
этого `workId` без релонча приложения

**Then** на Tab B (только что загрузившей work LOVED, активна) снекбар
«Continue reading…» НЕ появляется ни в течение 5 секунд ожидания, ни позже —
`persistReadingProgress:549` не записал строку (`percent < 5`), поэтому
`maybeOfferResume:590` не находит удовлетворяющую порогу запись и не пишет
`uiState.resumeOffer`; беглый просмотр НЕ создаёт оффер, вне зависимости от
того, что `onReadingProgress` реально сработал и бридж доставил ненулевой
процент

**And** (контраст, тот же прогон) третий `open_deep_link(work_kudosed.url)`
открывает Tab C на work KUDOSED; пользователь прокручивает Tab C ПРИМЕРНО ДО
СЕРЕДИНЫ документа (`swipe_scroll_active_tab` до стабилизации, индикатор
`≈0.40`) — СТРОГО ВЫШЕ порога; пауза ≥ 3000мс; четвёртый
`open_deep_link(work_kudosed.url)` открывает Tab D на ТОМ ЖЕ URL work
KUDOSED

**And** на Tab D (только что загрузившей work KUDOSED, активна) снекбар
«Continue reading at 40%?» появляется в течение разумного окна (≤ 8с) с
кнопкой «Resume» — доказывает, что ПОРОГ — единственная переменная,
отличающая два прогона (тот же механизм ретриггера через второй deep-link,
разные ЛИШЬ проценты прочитанного: 3% против 40%)

**Инвариант:** оффер возобновления чтения существует для work'а тогда и
только тогда, когда последняя сохранённая позиция чтения этого work'а
`>= MIN_PROGRESS_PERCENT` — свойство верно для ЛЮБОГО процента, продемонстрировано
контрастом двух значений по разные стороны границы (3% / 40%) в рамках одного
прогона, не единственным примером.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Work LOVED (900000001) | прокручена до `≈0.03` (ниже порога 5%) |
| Work KUDOSED (900000002) | прокручена до `≈0.40` (выше порога 5%) |
| Оффер для LOVED (Tab B) | отсутствует |
| Оффер для KUDOSED (Tab D) | «Continue reading at 40%?» + кнопка «Resume» |

## Заметки для автоматизации
- **Слой L3, устройство обязательно — почему не L2.** Проверяемое поведение
  живёт на стыке трёх реальных подсистем одновременно: реальная Room БД с
  дебаунсом записи (`PROGRESS_SAVE_DEBOUNCE_MS=3000`, реальные таймеры
  `viewModelScope.launch{delay(...)}`), реальный жизненный цикл вкладок
  Android (повторный `open_deep_link` создаёт НОВУЮ реальную вкладку/WebView,
  наблюдаемое ветвление зависит от `_uiState.value.tabs`) и реальный
  нативный Compose `SnackbarHostState` (текст, кнопка, таймауты показа).
  jsdom-харнесс L2 не поднимает ни Room, ни Android-активность, ни
  Compose-дерево — там нет ни настоящего процесса, ни настоящего
  WebView-таймсинга, ни настоящего снекбар-хоста, которые тут и составляют
  предмет проверки (тот же класс обоснования, что TC-268.md:138-140).
- **Механизм ретриггера — повторный `open_deep_link` на ТОТ ЖЕ URL, НЕ
  релонч приложения.** `onPageLoaded` — единственная точка вызова
  `maybeOfferResume` (`:663-667`); повторный deep-link после того, как
  текущая единственная вкладка уже не на `HOME_URL`, открывает НОВУЮ вкладку
  (реюз-условие TC-267 верно: `tabs[0].url == HOME_URL`) — этот кейс
  сознательно ОПИРАЕТСЯ на это поведение вместо релонча (дешевле, не тянет
  `adb kill`/debounce-гонку персистентности вкладок).
- **Тонкое расширение, НЕ блокер (тот же класс, что TC-267/268):** для
  снекбара «Continue reading» готового локатора/шага нет (`browser_steps.py`
  знает только снекбары Undo/«Opened in background», по тому же паттерну —
  `undo_snackbar_visible`/`opened_in_background_snackbar_visible`). Добавить
  симметрично: `resume_offer_snackbar_visible(driver, timeout)`,
  `resume_offer_snackbar_text(driver)`, `tap_resume_snackbar_action(driver)` —
  Compose Snackbar host, тот же класс узла, что уже 2 раза адресован в
  `browser_screen.py`.
- **Наблюдаемость и направление негативного Then:** негатив («оффер НЕ
  появился для LOVED») достижимо ложен — позитивный якорь ЕСТЬ В ТОМ ЖЕ
  прогоне (тот же ретриггер-механизм, тот же тип узла, работа KUDOSED ДАЁТ
  оффер несколькими действиями позже) — калибровка Lead 2026-07-30
  (`AT-BUG-029`) неприменима: эффект не сетевой, читается напрямую нативным
  UI-узлом, и альтернатива «механизм в принципе не способен показать оффер»
  исключена контрастом.
- **Батарея правил-реакций (событие=`onPageLoaded` work-страницы;
  условие=`readProgressPercent >= MIN_PROGRESS_PERCENT`; эффект=`uiState.
  resumeOffer` записан):**
  - off-инвариант — ПОКРЫТ явным негативным Then (Tab B, работа LOVED).
  - идемпотентность/edge-vs-level/propagation — н/п этому конкретному TC
    (адресуются TC-274/TC-275: TC-275 покрывает идемпотентность повторного
    показа после accept; propagation/edge-vs-level не имеют дополнительной
    поверхности в ЭТОЙ функции сверх уже покрытого — сама запись пишется из
    ЕДИНСТВЕННОЙ точки `onReadingProgress`, других call site нет).
  - ретроактивность — н/п: у функции нет пользовательского тумблера
    настройки («включить/выключить» отслеживание прогресса отсутствует в
    Settings), поэтому «объект, размеченный до включения настройки» не
    применимо к этой поверхности.
- **C4-банк комбинаторных областей:** `reading-progress` не входит в
  перечисленные категории (фильтры/сортировки/рейтинги-видимость/backup-
  restore/tabs/темы) — формальная строка `Инвариант:` не обязательна по
  букве нормы; добавлена по духу нормы (порог — универсальное свойство, не
  единственный пример).
- **Сознательно НЕ проверяется этим кейсом:** нюанс «строковый `timestamp`
  НЕ трогается записью прогресса, у прогресса собственные часы
  `readProgressAt`» (docs/01 §9, обоснование в тексте области) — это
  внутреннее состояние Room, не наблюдаемое ни через UI, ни через уже
  существующие хелперы чтения БД: `seed_db.read_work_ratings()`/
  `read_work_ratings_full()`/`_read_full_rows()` НЕ включают колонки
  `readProgress*`/не читают отдельно `timestamp` vs `readProgressAt`
  (сверено чтением `framework/data/seed_db.py`). Добавление этих полей в
  существующие read-хелперы — тонкое расширение схожего класса, что уже
  описанные выше снекбар-локаторы (не новая фикстура/replay-запись, только
  SELECT-колонки) — НЕ заводится test_debt-багом: не блокирует ни один Then
  этого кейса, минимальный набор Then области (п.1 docs/01 §9) полностью
  закрыт наблюдаемым поведением через снекбар-оракул.
