# TC-162 — Эвикция окна PAGE_WINDOW=3: состав DOM после каскада и обновление точки восстановления в prefs

## Предусловия
- Приложение запущено с чистыми данными; `infinite_scroll = ON` установлен
  до навигации.
- Открыта replay листинговая страница `listing_paginated.mitm`, страница 1
  из 5 (1 work-блёрб на страницу).
- Режим replay.

## Сценарий (Given-When-Then)

**Given** `infinite_scroll = ON`; открыта страница 1 `listing_paginated.mitm`
(`ids=['900000001']`)

**When** пользователь делает ОДИН скролл к самому низу документа (жест,
максимизирующий каскад — приём TC-130 «заметка»/CH-006 протокол)

**Then** после каскада подгрузок DOM держит РОВНО `PAGE_WINDOW=3` страницы —
множество `li[id^="work_"]` равно `['900000002','900000003','900000004']`
(блёрб страницы 1, `900000001`, физически ОТСУТСТВУЕТ в DOM — эвикция
удалила его узел, не просто скрыла)
**And** в prefs (`ao3_settings.xml`, ключ, соответствующий точке
восстановления вкладки) появляется обновлённая пара `listingRestoreUrl` (со
значением `page=2`, т.е. НОВАЯ старейшая страница окна, а не исходная
страница 1) и обновлённый `scrollY`, отражающий позицию ПОСЛЕ каскада

**Инвариант:** окно подгруженных страниц — множество РОВНО из `PAGE_WINDOW`
элементов после любого каскада, превысившего этот размер: при добавлении
(N+1)-й страницы удаляется САМАЯ СТАРАЯ (по порядку подгрузки, не по
номеру), и точка восстановления в prefs синхронно сдвигается на новую
старейшую страницу окна — свойство про МНОЖЕСТВО (состав окна + связанная с
ним точка восстановления), не про то, что именно ПЕРВАЯ страница
изначально была `900000001`.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| `infinite_scroll` | ON |
| `ids` в DOM ДО скролла | `['900000001']` |
| `ids` в DOM ПОСЛЕ каскада | `['900000002','900000003','900000004']` (ровно 3, `900000001` отсутствует) |
| `listingRestoreUrl` в prefs после | указывает на `page=2` |
| `scrollY` в prefs после | обновлён (не исходное значение до скролла) |

## Заметки для автоматизации
- Не заблокировано инфраструктурой — `listing_paginated.mitm` уже собран
  (тот же вывод, что TC-129/TC-130).
- Скролл к самому низу документа (`scrollTo(0, document.body.scrollHeight)`)
  — здесь ЖЕЛАТЕЛЬНЫЙ инструмент (в отличие от TC-130, где он explicitly
  избегается non-goal'ом): этот кейс специально целится в эвикцию, а не
  избегает её.
- Чтение состава DOM — тот же снимок-паттерн, что TC-130
  (`browser_steps.snapshot_work_blurb_ids`), сравнение множества, не
  порядка/подстрок.
- Чтение `listingRestoreUrl`/`scrollY` из prefs — тот же примитив, что уже
  использует `app_steps.py` для чтения `ao3_settings.xml`
  (`adb.run_as(f"cat {path}")`, образец `_read_tabs_prefs_raw`/
  `wait_tabs_persisted` для вкладок) — нужен собственный regex-парсер под
  КОНКРЕТНЫЕ ключи `listingRestoreUrl`/связанный `scrollY` (по образцу
  `_parse_persisted_tabs`), рутинная автоматизация, не блокер (тот же класс
  работы, что уже сделан для `open_tabs_urls`).
- Это design-only лок ТЕКУЩЕГО механизма по коду (не бага): вопрос «хорошо
  ли для пользователя, что точка восстановления молча подменяется» —
  отдельный, уже поднят как предложение усиления R-16 в `docs/01 §10`
  (CH-006 находка 4, решение владельца отдельным треком, test-strategist);
  этот кейс НЕ предрешает тот вердикт и не привязан к его исходу — он
  фиксирует наблюдаемое поведение, заданное кодом сегодня, чтобы будущая
  регрессия (например, эвикция начинает ломать DOM непредсказуемо, либо
  наоборот перестаёт обновлять prefs) была поймана.
- **Батарея правил-реакций (оценка применимости):** это не auto-download/
  auto-kudos класс (реакция на СВОЁ прямое действие — скролл, который сам
  запросил подгрузку, а не побочный эффект несвязанного сохранения) —
  та же логика, что TC-130 применяет к скроллу в целом; тем не менее
  edge-vs-level — н-п (эвикция — не предикат состояния сущности, а порог
  размера окна, пересчитываемый на каждом append); off-инвариант — уже
  покрыт TC-129 (при OFF подгрузки нет вовсе, эвикции взяться неоткуда).
  Ретроактивность — н-п (нет понятия «страница размечена до/после
  включения настройки»). Идемпотентность — н-п (эвикция — не действие
  пользователя, а последствие роста множества, повторный ИДЕНТИЧНЫЙ скролл
  без нового контента не меняет состав, что уже отмечено протоколом CH-006
  как инструментальная деталь, не свойство для отдельного ассерта).
  Propagation — н-п (эффект скоупится к DOM конкретной вкладки, prefs —
  побочный канал ТОЙ ЖЕ вкладки, не разделяется другими потребителями).
