# TC-263 — navigateEffective вызывает location.replace, а не location.href, при автопрыжке с опустошённой страницы

## Предусловия
- L2 bridge-harness, страница листинга с ЕДИНСТВЕННОЙ работой и `li.next`.

## Сценарий (Given-When-Then)

**Given** страница листинга с одной работой W (без рейтинга), есть `li.next`
(URL следующей страницы)

**When** страница опустошается фильтром через загрузку (`window.applyRatings
(JSON.stringify({W:'DISLIKE'}))` БЕЗ `__ao3LiveRatingPush` — та же ветка,
что делает TC-260 зелёной, "загрузка автопрыгивает")

**Then** вызван ИМЕННО `Location.prototype.replace` (счётчик подмены == 1,
аргумент == URL следующей страницы) **and** `Location.prototype.assign`
(альтернативный API, добавляющий запись в историю) НЕ вызван ни разу —
различающий контраст между «заменить» и «добавить запись» наблюдаем
напрямую по ДВУМ независимым счётчикам подмены, не по единственному факту
«какая-то навигация произошла»

**Инвариант:** при АВТОМАТИЧЕСКОМ (не инициированном пользователем)
переходе с опустошённой фильтром страницы бридж всегда выбирает API,
который НЕ растит историю WebView новой записью — свойство верно для
любого URL следующей страницы, здесь проверено representative-случаем
(единственная опустошающая работа), тот же representative-приём, что уже
принят в TC-159 для самого факта автопрыжка.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| `Location.prototype.replace` вызовов | 1, аргумент == next URL |
| `Location.prototype.assign` вызовов | 0 |

## Заметки для автоматизации
- Инфраструктура/блокер — как в TC-260 (`checkPageDensity` не layout-
  гейтирован, обычный L2, монки-патч `Location.prototype` — тот же приём).
- Подмена ОБОИХ методов (`replace` И `assign`) нужна одновременно — иначе
  негатив «assign не вызван» был бы неотличим от «assign недоступен в
  jsdom вовсе» (наблюдаемость негативного Then, F-34): подмена делает
  оба метода одинаково НАБЛЮДАЕМЫМИ (пишут в свои счётчики), поэтому «0
  вызовов assign» — честный, а не вакуумный негатив.
- Это ЗЕЛЁНАЯ грань записи `bridge-empty-page-auto-advance-replaces-
  history` (JS-часть, подтверждена и живым прогоном fix-verifier BUG-019
  — «рост history.length ограничен +1/press вместо +2/press», таблица
  «Верификация»). КРАСНАЯ грань той же записи (пользовательский Back
  по-прежнему заперт — Kotlin-стек `TabNavHistory` не чувствителен к
  `replace`/`href`) — ОТДЕЛЬНЫЙ кейс **TC-264** (L3, `red_lock: BUG-019`).
  По норме П2 (слой сначала, дедуп внутри слоя) эти две грани НЕ сливаются
  в один кейс: разная природа Given (jsdom-документ vs реальное устройство
  + системный Back) — граница слоя, не «та же фикстура с вариацией».
- Блокера автоматизации нет.
