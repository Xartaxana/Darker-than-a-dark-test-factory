# TC-184 — Auto-apply OFF: навигация не дописывает фильтр, а активный профиль снимается (регрессионный замок)

## Предусловия
- Приложение запущено, replay-режим (`listing_basic.mitm`).
- Фикстура `filter_profile_applied_seeded` — профиль «My saved search»
  активен (`activeFilterId` установлен, см. TC-182 «как достичь»).
- Тумблер «Auto-apply on navigation» переключён в **OFF**
  (`settings_screen.set_..._toggle(False)`, TC-181 даёт рутинный примитив).

## Сценарий (Given-When-Then)

**Given** профиль «My saved search» активен, тумблер Auto-apply — OFF,
активная вкладка на `LISTING_BASIC_URL` БЕЗ параметров фильтра

**When** пользователь переходит (обычная навигация, НЕ через кнопку применения
фильтра) на филируемую страницу листинга — например, повторный
`driver.get(LISTING_BASIC_URL)`

**Then** URL активной вкладки ОСТАЁТСЯ `LISTING_BASIC_URL` — параметр
`queryString` профиля НЕ дописан (`assert_active_tab_url(driver,
rb.LISTING_BASIC_URL)`) — явный НЕГАТИВНЫЙ Then, не отсутствие проверки
**And** активный профиль СНИМАЕТСЯ — `active_filter_profile_id` пропадает из
SharedPreferences `ao3_settings`, панель фильтра листинга после этой навигации
показывает «None» (`assert_active_filter_shown(driver, "None")` либо прямое
чтение prefs)

**ЭТО ФАКТИЧЕСКОЕ поведение текущей сборки, зафиксированное как регрессионный
замок — НЕ вердикт "так и задумано".** Задуманность ветки «OFF снимает
активный профиль при первой же обычной навигации» НЕ подтверждена (вопрос
вынесен владельцу/разработчику, §10 (ч) docs/01-test-strategy.md); Then
формулируется по наблюдаемому факту кода
(`BrowserViewModel.kt:501-504`), не как утверждение "профиль остаётся
выбранным" — если решение владельца изменит ожидание, меняется Then этого
ОДНОГО кейса, дизайн остальной области не затрагивается.

**Инвариант:** при OFF ЛЮБАЯ навигация (не только на филируемую страницу,
`onPageLoaded` не проверяет `isFilterable`), кроме той, что взведена самой
кнопкой применения (TC-185), снимает активный профиль, если он был
установлен, — свойство держится независимо от того, какая именно страница
загружается.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Тумблер | OFF |
| URL до/после навигации | `LISTING_BASIC_URL` / `LISTING_BASIC_URL` (не изменился) |
| Активный профиль до/после | «My saved search» / нет (снят) |

## Заметки для автоматизации
- Инфраструктура — та же, что TC-182 (готова, не блокер).
- Снятие активного профиля наблюдается ДВУМЯ путями — оба легальны, выбор за
  реализацией: (а) UI FilterPanel показывает «None»
  (`assert_active_filter_shown`, тот же примитив, что TC-041, с именем
  `"None"` — литеральный текст `BottomBar.kt Text(activeFilter?.name ?:
  "None")`); (б) прямое чтение SharedPreferences (`active_filter_profile_id`
  отсутствует) — тот же приём, что `assert_theme_mode_pref`, новый
  однострочный wrapper по образцу.
- **Наблюдаемость негативного Then (URL не изменился):** это НЕ сетевой
  эффект — URL читается напрямую из persisted-состояния приложения
  (`assert_active_tab_url`), не зависит от короткого замыкания WebView —
  класс AT-BUG-029 не применим, негатив достижимо ложен (если бы перехват
  сработал вопреки OFF, URL реально содержал бы `work_search`, что тест
  увидел бы).
- Не путать с TC-041 (там навигация ВЫЗВАНА кнопкой применения фильтра —
  `applyFilter`, отдельный код-путь с `pendingFilterApplication`, см. TC-185)
  — здесь навигация ОБЫЧНАЯ (переход по ссылке/повторная загрузка), не через
  UI фильтра.
- Блокера автоматизации нет.

## Заметки: батарея правил-реакций
- **off-инвариант** — предмет ИМЕННО этого кейса: явный негативный Then
  («URL не изменился») + дополнительный наблюдаемый факт (профиль снят),
  оба зафиксированы как регрессионный замок.
- Остальные пункты батареи — см. TC-182 (level/ON), TC-183
  (edge/идемпотентность), TC-185 (исключение внутри OFF-ветки).
