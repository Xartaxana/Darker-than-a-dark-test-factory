# TC-206 — FilterPanel на НЕфильтрованной deep-link-вкладке отражает ЕЁ состояние, не глобальный профиль (red lock BUG-070)

## Предусловия
- Приложение запущено, replay-режим (`listing_basic.mitm`, несёт пару
  `LISTING_BASIC_URL`/`LISTING_FILTERED_URL`).
- Фикстура `filter_profile_applied_seeded` — профиль «My saved search»
  засеян.
- Тумблер «Auto-apply on navigation» — **ON** (дефолт). Сверка ON —
  ТОЛЬКО UI-оракулом `settings_steps.assert_auto_apply_filter_enabled`
  (`:95`); prefs-оракул (`assert_auto_apply_filter_pref`, `:495`,
  `adb.run_as`) здесь НЕДОСТИЖИМ по построению — `auto_apply_filter`
  физически отсутствует в `ao3_settings.xml` до первого визита в Settings
  (методическая находка CH-010 #5), а сценарий Settings не посещает.
- На Browse открыт `LISTING_BASIC_URL`, профиль применён из FilterPanel
  (`browser_steps.select_filter_option`, путь TC-041/TC-182) — единственная
  активная вкладка получила URL `LISTING_FILTERED_URL`,
  `assert_active_filter_shown(driver, "My saved search")` подтверждает
  панель.

## Сценарий (Given-When-Then)

**Given** профиль «My saved search» активен и ПРИМЕНЁН к единственной
открытой вкладке (её URL = `LISTING_FILTERED_URL`), тумблер Auto-apply — ON

**When** пользователь получает и открывает **deep-link** на
`LISTING_BASIC_URL` (`app_steps.open_deep_link`, реальный Android
`ACTION_VIEW` intent, предваряется `wait_home_ready_for_deep_link`) — новая
вкладка (позиция 1) становится активной

**Then** новая активная вкладка несёт URL, побайтово равный
`LISTING_BASIC_URL` — БЕЗ параметров профиля
(`wait_persisted_tab_count(2)` + `assert_persisted_tab_url_at(1,
rb.LISTING_BASIC_URL)`) — программная загрузка `openOrNavigateDeepLink`
минует `shouldOverrideUrlLoading` по построению, это ОЖИДАЕМЫЙ и уже
подтверждённый (не спорный) факт (`bugs/BUG-070.md`, Actual #1)
**And** FilterPanel НЕ утверждает, что профиль применён к ТЕКУЩЕЙ активной
вкладке, чей URL не несёт параметров профиля (нативный триггер
`BottomBar.kt`, читается через UiAutomator2 — НЕ WebView-контекст, sticky
context AT-BUG-018 здесь не применим) — наблюдаемая форма на текущем стеке:
триггер показывает **«None»**
(`browser_steps.assert_active_filter_shown(driver, "None")`); иная форма
индикации «профиль не применён к этой вкладке» кейс тоже удовлетворяет и
требует правки этой строки Then на ревью — развилка фикса владельцем НЕ
закрыта (см. заметки)

**ОЖИДАЕМОЕ ПАДЕНИЕ на текущей сборке** (прецедент TC-139/TC-176/TC-205:
кейс пишется по ожидаемому поведению спецификации, а не по факту сборки) —
по коду (`BottomBar.kt:251/284-288`) триггер панели рендерит ГЛОБАЛЬНЫЙ
`activeFilterId` без проверки принадлежности вкладке: панель фактически
продолжает показывать «My saved search» на НЕфильтрованной вкладке
(`bugs/BUG-070.md`, Actual #2, воспроизведено дважды независимо). Один и тот
же экран одновременно утверждает «фильтр применён» (панель) и «фильтр не
применён» (реальный URL/содержимое). Красный результат триажится как
**APP_BUG/BUG-070**, не как расхождение теста со спекой.

**Инвариант:** FilterPanel обязана отражать состояние ТЕКУЩЕЙ активной
вкладки (применён ли профиль к её URL), а не глобальный `activeFilterId` —
свойство держится для ЛЮБОЙ вкладки, к которой профиль не был применён,
независимо от того, какой ПРОГРАММНОЙ дверью она создана: deep-link здесь —
один из минимум четырёх таких путей по коду (`applyFilter`-загрузка новой
вкладки `:216`, Back `:244`, первичная загрузка/восстановление вкладки
`:486`/`:501`, `wv.reload()` при смене темы `:157` — полный список
`bugs/BUG-070.md` «Анализ»); этот кейс — представитель класса через
deep-link, остальные три двери по коду идентичны и не требуют отдельного
кейса (см. заметки).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Тумблер | ON |
| Активный профиль (глобально) | «My saved search» — жив, deep-link его не трогает |
| URL новой вкладки (факт) | `LISTING_BASIC_URL` (без параметров) |
| Панель (спека, ожидание) | «None» |
| Панель (сборка, факт, BUG-070) | «My saved search» |

## Заметки для автоматизации
- Инфраструктура ГОТОВА, блокера нет: `open_deep_link`/
  `wait_home_ready_for_deep_link` (`app_steps.py:190/131`),
  `wait_persisted_tab_count`/`assert_persisted_tab_url_at` (`app_steps.py`),
  `select_filter_option`/`assert_active_filter_shown` (`browser_steps.py`,
  использованы TC-041/TC-182) — тот же набор, что уже применяют соседние
  кейсы области.
- **Оба оракула Then — НЕ WebView-контекст** (`open_tabs_urls` из prefs;
  нативный UiAutomator2-триггер панели) — это НАМЕРЕННЫЙ выбор, повторяющий
  тот, что уже сделала сессия CH-010 при находке самого бага: попытка читать
  баннер страницы (`window.__ao3FilterActive`,
  `#ao3-companion-hidden-notice`) на deep-link-вкладке ТРЕБУЕТ адресации
  `execute_script`/`driver.get` к КОНКРЕТНОЙ НЕ-нулевой вкладке, которая
  недостижима на текущем стеке (sticky WebView context, класс
  AT-BUG-018/019/022) — CH-010 явно НЕ включила эти значения баннера в
  `bugs/BUG-070.md` как доказательство по той же причине (см. «Обсуждение»
  бага). Этот кейс НЕ проверяет баннер вовсе — Then целиком построен на двух
  безопасных оракулах, инфраструктурного блокера у ЭТОГО кейса нет.
- **Достижимость различающей развилки** (кодификация Lead 2026-08-14, класс
  TC-204): `assert_active_filter_shown` — presence текста ПО ВСЕМУ ДЕРЕВУ
  (`filter_dropdown_has_option` → `is_present(by_text(name))`,
  `browser_screen.py:301-302`), НЕ чтение узла триггера. Граница оракула:
  раскрытая выпадашка `AppDropdownMenu` несёт СОБСТВЕННЫЙ пункт «None»
  (`optionLabel = { it?.name ?: "None" }`, `BottomBar.kt:302-309`) —
  ассерт валиден, только если выпадашка на момент Then СВЁРНУТА (в потоке
  кейса она закрывается сама после `select_filter_option`, вакуумности нет,
  но границу называем явно). Given предварительно доказывает, что тот же
  примитив на ДРУГОЙ (исходной) вкладке реально показывает «My saved
  search» (проверено ДО When) — примитив умеет различать оба значения на
  этой же сборке, различие не вакуумно.
- Контраст той же цели ДРУГОЙ дверью (клик по ссылке внутри страницы,
  проходящей `shouldOverrideUrlLoading`) — НЕ этот кейс: `bugs/BUG-070.md`
  прямо называет его «remains open», заблокирован тем же sticky-context —
  заведён отдельным test_debt (`bugs/AT-BUG-070.md`, CH-010 followup_tc #2),
  не дублируется здесь.
- **Гейт red_lock/automated_by (rework 2026-08-14, attempt 2):** `red_lock`
  оставлен пустым на этапе дизайна — его ставит ТОЛЬКО тот, кто пишет
  реальный красный автотест и подтверждает его красноту прогоном
  (test-automator, с Bash), не test-designer (нет Bash, не может
  подтвердить красноту). red_lock ставится ВМЕСТЕ с `automated_by`, когда
  тест написан и подтверждён красным — см. прецедент TC-139/BUG-015 и
  TC-176/BUG-059. Описание ожидаемо-красного поведения (заголовок от
  спеки, Then читает текущий дефект BUG-070) остаётся в теле кейса — это
  законный Review-кейс без замка.
- **Развилка фикса BUG-070 владельцем НЕ ЗАКРЫТА** (баг `awaiting: dev`,
  `requirements` этого кейса не ссылается на docs/01 §10 — вопрос там же
  вынесен, не решён): панель может либо (a) показать «None» (наблюдаемая
  форма, взятая в Then), либо (b) показать имя профиля с пометкой «не
  применён к этой вкладке», либо (c) начать применять фильтр и на
  программных дверях — при (c) падает и Then #1 («URL побайтово равен
  LISTING_BASIC_URL»), объявленный здесь ОЖИДАЕМЫМ и неспорным фактом. При
  выборе варианта (c) владельцем этот кейс подлежит переписыванию целиком,
  Then #1 перестаёт быть инвариантом.
- Не путать с **TC-182** (там навигация ЗАНОВО на филируемую страницу В ТОЙ
  ЖЕ вкладке — перехват СРАБАТЫВАЕТ, URL получает фильтр) и с **TC-131..135**
  (deep-link считает вкладки, профилей в Given нет).

## Заметки: батарея правил-реакций (E = навигация на филируемую страницу
через ПРОГРАММНУЮ дверь [deep-link], C = ON && активный профиль, S =
дописывание `queryString` — единственная дверь `shouldOverrideUrlLoading`)
- **edge vs level** — этот кейс сам ЯВЛЯЕТСЯ edge-местом вызова относительно
  TC-182 (level, `shouldOverrideUrlLoading`-путь): программная дверь S не
  проходит ПО ПОСТРОЕНИЮ (не дефект — подтверждённый факт, см. Then #1);
  дефект лежит В ДРУГОМ узле — см. propagation ниже.
- **ретроактивность** — н-п.
- **off-инвариант** — н-п: тумблер здесь ON (OFF-ветка — TC-184/TC-205).
- **идемпотентность** — н-п отдельным сценарием: одиночный deep-link.
- **propagation** — ИМЕННО предмет дефекта: единственный визуальный
  «потребитель» состояния применения (FilterPanel) не узнаёт, что НОВАЯ
  активная вкладка не несёт применённого фильтра — показывает устаревшее
  для ЭТОЙ вкладки состояние. Класс шире одного места вызова (см.
  «Инвариант» выше, четыре программные двери) — этот кейс представитель
  через deep-link, не дублируется тремя оставшимися.
