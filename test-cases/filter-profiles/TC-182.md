# TC-182 — Auto-apply ON: навигация на филируемый листинг дописывает фильтр активного профиля

## Предусловия
- Приложение запущено, replay-режим (`listing_basic.mitm` — несёт ВТОРОЙ flow
  под `recording_builder.LISTING_FILTERED_URL`, байт-в-байт равный
  `LISTING_BASIC_URL + '&' + FILTER_APPLIED_QUERY_STRING`).
- В Room засеян один `FilterProfile` — фикстура `filter_profile_applied_seeded`
  (conftest.py): имя «My saved search», `queryString =
  recording_builder.FILTER_APPLIED_QUERY_STRING` — подобран так, чтобы
  `applyFilter`/автоприменение построило URL, СОВПАДАЮЩИЙ с записанным flow.
- Тумблер «Auto-apply on navigation» в состоянии **ON** (дефолт).
- Профиль «My saved search» установлен активным (`activeFilterId` == id
  профиля) — например, через одноразовое ручное применение из FilterPanel
  ДО основного When (тот же приём, что TC-041), либо прямой сидинг
  `active_filter_profile_id` в prefs, если сидинг-примитив уже существует.

## Сценарий (Given-When-Then)

**Given** профиль «My saved search» активен, тумблер Auto-apply — ON, вкладка
Browse открыта на `LISTING_BASIC_URL` БЕЗ параметров фильтра

**When** пользователь переходит (навигирует WebView) на филируемую страницу
листинга ЗАНОВО (например, повторный `driver.get`/переход по ссылке на тот же
базовый URL без `work_search`)

**Then** `shouldOverrideUrlLoading` перехватывает загрузку и перезагружает
вкладку по URL с ДОПИСАННЫМ `queryString` активного профиля — итоговый URL
активной вкладки побайтово равен `recording_builder.LISTING_FILTERED_URL`
(`assert_active_tab_url(driver, rb.LISTING_FILTERED_URL)`)
**And** FilterPanel листинга показывает «My saved search» как активно
применённый (`assert_active_filter_shown`)

**Guard, часть того же Then (иначе кейс не отличит «применилось» от
«применилось ВЕЗДЕ»):** перехват сработал именно потому, что исходный URL
НЕ содержал `work_search` и страница входит в `FILTERABLE_PAGE` — это
предпосылка, не отдельная проверка этого кейса (негативная сторона guard'а —
TC-183).

**Инвариант:** при ON и активном профиле КАЖДАЯ навигация на филируемую
страницу БЕЗ уже присутствующего `work_search` детерминированно перезаписывает
URL, дописывая ТЕКУЩИЙ `queryString` активного профиля — независимо от того,
какая именно филируемая страница загружается (свойство держится для всего
класса `FILTERABLE_PAGE`, не только для одного конкретного URL из Given).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Активный профиль | «My saved search», `queryString = FILTER_APPLIED_QUERY_STRING` |
| Тумблер | ON |
| URL до навигации | `LISTING_BASIC_URL` (без параметров) |
| URL после (ожидание) | `LISTING_FILTERED_URL` (побайтово) |

## Заметки для автоматизации
- Инфраструктура УЖЕ ГОТОВА — не блокер: `filter_profile_applied_seeded`
  (`conftest.py:580-596`), `rb.LISTING_FILTERED_URL`/`FILTER_APPLIED_QUERY_STRING`
  (`recording_builder.py:45-58`), `browser_steps.assert_active_tab_url`,
  `browser_steps.assert_active_filter_shown` — тот же набор, что уже
  использует `test_apply_filter_profile` (TC-041, `test_filter_profiles.py:187-202`).
  Разница с TC-041: там пользователь САМ выбирает профиль из FilterPanel
  (ручное применение, `applyFilter`); здесь профиль УЖЕ активен, а перехват
  срабатывает от ОБЫЧНОЙ навигации (`shouldOverrideUrlLoading`, другой
  код-путь) — не дублирует TC-041.
- «Профиль установлен активным ДО When» — простейший путь: переиспользовать
  `test_apply_filter_profile`-подобный шаг (открыть листинг, выбрать профиль
  из FilterPanel — это САМО ПО СЕБЕ уже вызовет `applyFilter`/навигацию с
  фильтром) — тогда «повторная навигация ЗАНОВО» этого кейса означает ВТОРОЙ
  переход на базовый URL уже ПОСЛЕ того, как профиль стал активным
  (например, `driver.get(LISTING_BASIC_URL)` ещё раз) — так Then этого
  кейса проверяет именно АВТО-применение при обычной навигации, а не
  повторяет TC-041 (ручное применение).
- Не дублирует TC-183 (guard — страница УЖЕ несёт `work_search`, повторного
  дописывания НЕ происходит) и TC-041 (ручное применение из FilterPanel).
- Блокера автоматизации нет.

## Заметки: батарея правил-реакций (событие E = навигация на филируемую
страницу без `work_search`; условие C = ON + активный профиль; эффект
S = перезапись URL)
- **edge vs level** — уровневый триггер: перехват срабатывает на КАЖДОЙ
  такой навигации (не только на «первом переходе»/семантическом переходе) —
  сам этот кейс уже покрывает level-путь; EDGE (страница уже несёт
  `work_search` — навигация НЕ считается «первой») закрывает TC-183.
- **ретроактивность** — **н-п**: настройка/активный профиль — не per-объектная
  метка на данные, созданные до включения фичи; concept referent отсутствует.
- **off-инвариант** — закрывает TC-184 (тумблер OFF).
- **идемпотентность** — закрывает TC-183 (повторная загрузка уже
  отфильтрованной страницы не дублирует/не удваивает параметры — тот же
  guard `!url.contains("work_search")` не даёт перехвату сработать дважды).
- **propagation** — **н-п**: эффект — синхронный перехват КОНКРЕТНОЙ
  загрузки конкретной вкладки, не broadcast; открытые ПРОЧИЕ вкладки не
  затронуты этой навигацией (класс BUG-012 сюда не относится — там речь о
  внешней мутации Room, не о навигации).
