# TC-183 — Guard: уже отфильтрованная страница не получает повторного дописывания параметров

## Предусловия
- Приложение запущено, replay-режим (`listing_basic.mitm`).
- Фикстура `filter_profile_applied_seeded` — профиль «My saved search»
  (`queryString = FILTER_APPLIED_QUERY_STRING`), тумблер Auto-apply — **ON**.
- Активная вкладка уже находится на `recording_builder.LISTING_FILTERED_URL`
  (т.е. URL УЖЕ содержит `work_search`-параметр — либо потому что фильтр уже
  был применён этим же профилем, либо потому что пользователь сам перешёл по
  ссылке с ручным `work_search`).

## Сценарий (Given-When-Then)

**Given** профиль «My saved search» активен, тумблер Auto-apply — ON,
активная вкладка уже открыта на `LISTING_FILTERED_URL` (URL содержит
`work_search`)

**When** страница на этой же вкладке перезагружается (`driver.get` того же
URL ещё раз, симулируя pull-to-refresh/повторную загрузку)

**Then** URL активной вкладки ПОСЛЕ перезагрузки остаётся ПОБАЙТОВО тем же
`LISTING_FILTERED_URL` — параметр `queryString` профиля НЕ дописан ВТОРОЙ раз
(не удвоен, URL не превращается в `...&work_search[...]=...&work_search[...]=...`)
**And** `shouldOverrideUrlLoading` НЕ вызывает `view.loadUrl` с изменённым URL —
косвенно наблюдаемо через отсутствие ДВОЙНОЙ навигации (проверяется тем же
`assert_active_tab_url`, не отдельным сетевым счётчиком)

**Инвариант:** guard `!url.contains("work_search")` — единственное условие,
отсекающее повторное авто-применение; он одинаково защищает ДВА разных по
происхождению случая одинаково: страницу, УЖЕ отфильтрованную ЭТИМ ЖЕ
механизмом (идемпотентность повторной загрузки), и страницу, отфильтрованную
ВРУЧНУЮ пользователем через форму AO3 Sort&Filter (не перетирается
авто-применением) — оба случая неотличимы для guard'а по одному и тому же
признаку подстроки в URL.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| URL до перезагрузки | `LISTING_FILTERED_URL` (уже содержит `work_search`) |
| Действие | повторная загрузка того же URL |
| URL после (ожидание) | тот же `LISTING_FILTERED_URL`, без дублирования параметров |

## Заметки для автоматизации
- Тот же инфраструктурный набор, что TC-182 (`filter_profile_applied_seeded`,
  `rb.LISTING_FILTERED_URL`, `browser_steps.assert_active_tab_url`) — просто
  Given стартует УЖЕ на filtered-URL, а не на базовом.
- Достижение стартового состояния «уже на filtered-URL» — тем же путём, что
  TC-041/TC-182 (выбор профиля из FilterPanel один раз до этого кейса), либо
  прямой навигацией `driver.get(rb.LISTING_FILTERED_URL)`, если replay-flow
  матчится и при прямом заходе (сверить при реализации — оба flow
  `listing_basic.mitm` записаны независимо от того, КАК на них попали).
- Механизм повторной загрузки — `driver.navigate().refresh()` или повторный
  `browser_steps.open_listing(driver, rb.LISTING_FILTERED_URL)` — оба должны
  дать идентичный результат этому Then, конкретный способ — на усмотрение
  реализации, если он реально триггерит `shouldOverrideUrlLoading` (обычный
  `driver.get` того же URL — WebView вызывает колбэк независимо от того,
  идентичен ли URL предыдущему).
- Не дублирует TC-182 (level-путь, URL БЕЗ `work_search` изначально).
- Блокера автоматизации нет.
