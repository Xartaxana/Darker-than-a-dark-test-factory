# TC-286 — Сбой закачки на приёмнике не теряет standing-запрос: следующий проход синхронизации повторяет попытку и докачивает работу

## Обоснование объёма (одна работа, два прохода — не journey)

Один семантический механизм (`fulfillSendRequests`, ветка `:342-346`) и одна
природа Given (remote-снимок через GitLab-Snippet-мок), тот же приём, что
TC-280 Вариант A. Это НЕ journey: между двумя `When` нет переключения экрана
за пределы Settings, состояние W локально созревает ЕСТЕСТВЕННО (его меняет
только код приложения на каждом проходе), удалённый снимок (GitLab snippet)
НЕ меняется между проходами вовсе.

**Редизайн attempt 2 (2026-08-21, критик-вход REJECT на attempt 1, координатор
предписал технику формат-инъекции).** Attempt 1 держался на СИНТЕТИЧЕСКОМ
`404` на работе-странице + переключении между ДВУМЯ `.mitm`-композициями
внутри одного теста (реконфигурация `sync_replay`) — категоричное
утверждение «ни один существующий примитив это не даёт безопасно» оказалось
НЕВЕРНЫМ: критик эмпирически доказал рабочую альтернативу, которая покрывает
ветку `:342-346` СЕГОДНЯ, БЕЗ единой правки фреймворка и с НУЛЕВЫМ риском
live-forward. Техника: **ОДНА `.mitm`-композиция на ВЕСЬ тест, ОДИН
`sync_replay.start(...)`.** Work-страница записана РОВНО ОДИН раз —
`rb.render_work_page_html(work, include_epub=False)` (несёт PDF/HTML/MOBI,
БЕЗ EPUB-пункта; тот же приём, что `build_work_no_epub_link`/TC-237,
precedent AT-BUG-071). Различающий фактор — НЕ содержимое ответа сервера
(оно идентично на обоих проходах, `server_replay_reuse=true` отдаёт ТУ ЖЕ
запись повторно), а КЛИЕНТСКАЯ настройка `downloadFormat`
(`DownloadRepository.kt:28-30`), переключаемая между проходами через UI
Settings (`settings_steps.select_download_format`, precedent AT-BUG-071/
TC-236):

- **Проход 1 (формат EPUB):** регекс `DownloadRepository.kt:220` ищет
  `href=".../\.epub..."` — страница БЕЗ EPUB-пункта не даёт совпадения ->
  `fetchDownloadUrl` возвращает `null` немедленно (non-local `return` внутри
  `repeat(3)`, единственная попытка) -> `downloadWork` бросает `IOException`
  -> `Result.failure`. **Второй HTTP-запрос (сама закачка) физически НЕ
  отправляется** — регекс проваливается ДО построения `downloadUrl`,
  незаписанных запросов нет, live-forward-риск равен нулю.
- **Проход 2 (формат переключён на HTML, тот же снимок W, тот же
  `sendRequestedAt`, никто не отправлял новый Send):** регекс ищет
  `href=".../\.html..."` — ТА ЖЕ work-страница (include_epub=False сохраняет
  HTML-пункт) даёт совпадение -> `fetchDownloadUrl` находит `download_url(work)`
  -> второй GET уходит на записанный `.html`-флоу (`rb.render_downloaded_
  work_html(work)`) -> `Result.success`.

Этот дизайн **закрывает потребность в `bugs/AT-BUG-092.md`** — ни
реконфигурация `sync_replay`, ни расширение `mitm.start_replay` для этой
ветки больше не требуются; статус и содержание бага пересмотрены этим же
ходом (см. «Заметки для автоматизации» и сам файл бага).

## Предусловия

- `clean_state()` ДО инстанцирования `driver` (конвенция области `sync`).
- Работа **W := `W.LOVED`** (`framework/data/works.py`).
- Локальная библиотека ПУСТА (W нет вовсе) — удалённый снимок несёт W с
  `rating=LIKE`, `sendRequestedAt=T0` (свежий `now`), тот же приём, что
  TC-280 Вариант A. `T0` НЕ меняется между двумя проходами синхронизации —
  это ОДИН standing-запрос, ни одного нового `Send` за весь кейс.
- **Remote-строка несёт ЯВНЫЙ ФИКСИРОВАННЫЙ `timestamp=T_fixed`**
  (`gsm.work_json(ao3_id, T_fixed, rating=..., sendRequestedAt=T0, ...)` —
  параметр `timestamp` ОБЯЗАТЕЛЬНЫЙ позиционный, `framework/data/
  gitlab_snippet_mock.py:112-131`), НЕ «опущен на волю дефолта». Это не
  косметика: `T_fixed` неизменен между обоими проходами, поэтому на ВТОРОМ
  проходе LWW-слияние `SyncRepository.kt:168-179` видит `remoteTs<=localTs`
  (тай, поля уже совпадают после проходa 1) — полевой merge даёт
  `merged == lRow`, записи в Room нет. Если бы `timestamp` был пропущен, `LibraryJson.
  workFromJson:57` подставлял бы `fallbackNow` (свежий `now` НА КАЖДЫЙ
  вызов) — удалённая строка побеждала бы КАЖДЫЙ проход, Room переписывался
  бы на каждом merge, и debounce-авто-триггер (см. ниже) перевзводился бы
  на КАЖДОМ проходе, а не только на первом.
- **Формат загрузки переключён на EPUB** (`settings_steps.select_download_
  format(driver, "EPUB")`) ДО первого «Sync now» — часть Given, не отдельный
  `When`.
- **ОДНА `.mitm`-композиция на ВЕСЬ тест** (никакой реконфигурации, никакого
  второго `sync_replay.start()`):
  - `gsm.make_snippet_get_flow(SNIPPET_ID, remote)` + `gsm.make_snippet_
    update_flow(SNIPPET_ID)` — тот же снимок на ОБА прохода (T0 не
    продвинут).
  - `rb.make_html_get_flow(work.url, rb.render_work_page_html(work,
    include_epub=False))` — ОДНА запись, обслуживает ОБА прохода через
    `server_replay_reuse=true` (`framework/core/mitm.py:441`).
  - `rb.make_html_get_flow(rb.download_url(work), rb.render_downloaded_
    work_html(work))` — нужна ТОЛЬКО проходу 2 (успех), присутствует в
    композиции с самого начала (флоу, не запрошенный проходом 1, простаивает
    безопасно).

## Сценарий (Given-When-Then)

**Given** состояние из «Предусловия» (`.mitm` поднят один раз на весь тест,
формат загрузки — EPUB)

**When** пользователь настраивает синк (`configure_sync`) и жмёт «Sync now»
В ПЕРВЫЙ раз

**Then** диалог «Sync complete» показывает «1 works updated» (merge вставил
строку W — это происходит ПЕРЕД `fulfillSendRequests` и не зависит от исхода
закачки)
**And** `downloadWork` реально пытается скачать: GET work-страницы
исполняется целиком (мокнутый ответ реально приходит, регекс `.epub`
реально прогоняется против реального тела и реально не находит совпадения)
и завершается `Result.isFailure`; второй GET (сама закачка) НЕ отправляется
**And** в Room у W: `sendHandledAt` остаётся `null` (запрос НЕ помечен
отработанным — ветка `:342-346` не вызывает `upsertWorkRating`)
**And** в Room у W: `downloadPath` остаётся `null` (файл НЕ записан)
**And** файл W НЕ появляется на диске (ни в `getExternalFilesDir("ao3_
downloads")`, ни в кастомной SAF-папке)
**And** снекбар «Downloaded N works sent from another device» НЕ появляется
(`received` инкрементируется только на ветке успеха `:337-341`, до неё
управление не доходит)
**And** работа W НЕ появляется на вкладке Files/Downloads экрана Library

**When** (дождавшись, пока UI первого прохода — диалог «Sync complete» —
ПОЛНОСТЬЮ закроется, тот же приём, что TC-280 Вариант A; проверка вкладки
Files/Downloads из Then прохода 1 не только ДОПУСТИМА здесь, но и ПОЛЕЗНА —
именно её длительность гарантированно поглощает 5-секундное окно debounce-
таймера, см. «Заметки для автоматизации») пользователь переключает
формат загрузки на HTML (`settings_steps.select_download_format(driver,
"HTML")`) — та же Settings-страница, тот же экран — и жмёт «Sync now»
ВТОРОЙ раз — удалённый снимок НЕ менялся (тот же `T0`, тот же `T_fixed`,
никто не отправлял новый Send), `.mitm` НЕ переключался (та же композиция,
что и в проходе 1)

**Then** guard `:331` (`sendHandledAt(null) < sendRequestedAt(T0)`)
по-прежнему истинен — W оценивается СНОВА тем же проходом
`fulfillSendRequests`, НЕЗАВИСИМО от того, произвёл ли merge на этот раз
хоть одно изменение (ретрай управляется ИМЕННО локальным водяным знаком, не
фактом мержа) — это различающий факт, ради которого построен кейс
**And** `downloadRepo.downloadWork` завершается `Result.isSuccess` (тот же
GET work-страницы, ТОТ ЖЕ мокнутый ответ, но теперь регекс `.html` находит
совпадение; второй GET уходит на записанный `.html`-флоу и отдаёт тело)
**And** снекбар «Downloaded 1 work sent from another device» появляется
(`received == 1` — эта работа реально прошла закачку впервые на этом
проходе)
**And** в Room у W: `downloadPath` заполнен и указывает на `.html`-файл
(`downloadFormat` был HTML в момент вызова `downloadWork` — `ext` читается
динамически, `DownloadRepository.kt:52`)
**And** в Room у W: `sendHandledAt >= sendRequestedAt(T0)` (запрос теперь
отработан)
**And** работа W появляется на вкладке Files/Downloads экрана Library

## Заметки для автоматизации

- **Блокера НЕТ (закрыт редизайном attempt 2).** `bugs/AT-BUG-092.md`
  описывал невозможность переключить ответ ОДНОГО URL между двумя
  `sync_replay`-проходами — этот дизайн не нуждается в таком переключении
  вовсе: ОДИН записанный флоу обслуживает ОБА прохода (`server_replay_
  reuse=true`), различие приходит с КЛИЕНТСКОЙ стороны (`downloadFormat`).
  `AT-BUG-092.md` пересмотрен этим же ходом: `test_cases` обнулён,
  предложено закрытие (test-designer не может сам перевести `Open ->
  Rejected` — актор `by: [human]`, `schemas/transitions.yaml` — оставлено
  координатору/человеку, запись в «Обсуждение» бага).
- Генерация страницы без EPUB-ссылки — БЕЗОПАСНЫЙ, УЖЕ доказанный приём:
  `include_epub=False` в `_download_list_html`/`render_work_page_html`,
  precedent AT-BUG-071 (`build_work_no_epub_link`, TC-236/TC-237, живая
  регенерация с побайтовым сравнением). Этот кейс не изобретает новую
  инфраструктуру — переиспользует существующую в НОВОМ контексте (sync
  вместо ручного download-тапа с карточки).
- **Гонка с ВТОРЫМ авто-триггером синхронизации — исправленная модель
  (критик-фикс B2, раунд 2: прежняя версия абзаца опиралась на неверное
  время взвода таймера и на неизмеренную латентность — обе ошибки
  исправлены здесь).** `MainActivity.kt:171-174`
  (`repeatOnLifecycle(RESUMED){syncIfNeeded()}`) НЕ пересекается с этим
  кейсом: единственный RESUMED-переход происходит на старте `driver`, ДО
  `configure_sync`, `isConfigured=false` -> выход немедленный, без побочных
  эффектов. Есть ВТОРОЙ, независимый авто-триггер —
  `MainActivity.kt:176-184`: `merge(allWorkRatings.drop(1),
  allFilterProfiles.drop(1)).onEach{markDirty()}.debounce(5_000).
  collect{syncIfNeeded()}`.
  **Когда таймер взводится (не когда переключается формат — раньше):**
  запись мержа W ПРОХОДА 1 (`SyncRepository.kt:185-197`, происходит ВНУТРИ
  первого `fulfillSendRequests`-цикла, ДО того как Then прохода 1 вообще
  начинает проверяться) — единственная эмиссия `allWorkRatings`, которая
  взводит debounce на 5000мс. Таймер срабатывает ОДИН раз, ~5с спустя,
  ПОКА формат ещё EPUB (Then прохода 1 — десятки секунд adb-pull/UI-
  проверок, окно 5с истекает задолго до второго When) — авто-`syncNow()`
  на этом срабатывании ХАРМЛЕСС (гейт `:112-118` его НЕ отсекает,
  `lastAutoCheckAt==0` изначально, но формат всё ещё EPUB -> та же
  гарантированная неудача, никакого live-forward, второй GET по-прежнему
  не отправляется).
  **Почему таймер НЕ перевзводится на проходе 2 (настоящая причина
  безопасности, не скорость действий):** merge второго прохода — NO-OP
  благодаря ФИКСИРОВАННОМУ remote `T_fixed` (см. «Предусловия» —
  `remoteTs<=localTs` -> ветка `:168-179` возвращает `lRow`, Room НЕ
  переписывается, `allWorkRatings` НЕ эмитит). Без новой Room-записи
  debounce-коллектор не взводится заново — единственное окно, когда НОВАЯ
  запись могла бы взвести таймер повторно и создать реальную гонку со
  вторым тапом, — это 5-секундный интервал ПОСЛЕ переключения формата на
  HTML, НО такого события в этом кейсе нет вовсе (переключение формата не
  пишет в Room, только `downloadRepo.downloadFormat`). Порядок действий
  (диалог закрыт -> переключить формат -> второй тап) остаётся обязательным
  требованием (не даёт словить остаток первого диалога/снекбара, класс
  TC-280 Вариант A), но НЕ является защитой от debounce-гонки — той гонки,
  как показано выше, структурно не существует при зафиксированном
  `T_fixed`. Не устраняется как отдельный механизм — здесь просто
  отсутствует по конструкции Given, в отличие от residual-вектора TC-282.
- Наблюдение полей `sendHandledAt`/`sendRequestedAt` из теста: в
  `framework/` НЕТ готового хелпера для их чтения — по образцу
  `_pull_send_fields` в `runs/reference/test_bug078_verify_temp_
  REFERENCE.py` (сырой SQL/`seed_db`-чтение по аналогии с
  `read_work_ratings_full`), тот же приём, что уже задокументирован в
  TC-280 (см. его «Заметки для автоматизации»).
- Наблюдаемость негативного Then (класс AT-BUG-029): «снекбара нет»/
  «downloadPath остаётся null»/«файла нет» после провального прохода — это
  НЕ короткое замыкание постороннего сервиса: GET work-страницы РЕАЛЬНО
  исполняется через мокнутый ответ (весь код `downloadWork` до самого
  регекса реально проходит, отличается только то, какое расширение ищет
  регекс); достижимость доказана ПОЗИТИВНО в ЭТОМ ЖЕ прогоне вторым проходом
  (тот же снекбар/`downloadPath`/вкладка Files РЕАЛЬНО заполняются при
  успехе, ТА ЖЕ запись сервера) — не вакуумная проверка.
- Направление негативного Then (класс TC-204/CLAUDE.md): инвертировать в
  чисто-позитивный ассерт здесь нельзя — предмет кейса ровно в том, что
  провал НЕ продвигает водяной знак; достижимость обеспечена ближайшим
  позитивным `When`/`Then` внутри ТОГО ЖЕ теста (второй проход, ТА ЖЕ
  запись сервера, другой клиентский формат), не кросс-кейсовым якорем.
- Порядок: диалог «Sync complete» первого прохода обязан ПОЛНОСТЬЮ
  закрыться перед переключением формата и вторым тапом «Sync now» — иначе
  assert рискует поймать остаток первого диалога/снекбара, тот же класс
  гонки, что TC-280 Вариант A; это требование НЕ связано с debounce-гонкой
  (см. выше — она структурно отсутствует при фиксированном `T_fixed`) и НЕ
  означает «действовать быстро». Наоборот: полный Then прохода 1
  (Room-пулл, файл, вкладка Files) заведомо длиннее 5с, и именно это
  переводит ЕДИНСТВЕННОЕ срабатывание взведённого проходом 1 debounce-
  таймера в окно, где формат ещё EPUB (хармлесс). Сокращать паузу между
  проходами НЕ нужно и ВРЕДНО: переключение формата на HTML раньше, чем
  истечёт 5-секундное окно, даёт авто-`syncNow()` с УСПЕШНОЙ закачкой ДО
  второго тапа — снекбар и `sendHandledAt` закрываются вне второго `When`,
  и Then прохода 2 становится ложно-красным.
- Батарея правил-реакций (`fulfillSendRequests`, единственная точка
  вызова `SyncRepository.kt:244-245`):
  - **edge-vs-level — ПОКРЫТА, комплементарная грань к TC-280.** TC-280
    доказывает «успешный проход, повторённый БЕЗ изменений, не задваивает
    закачку» (уровень уже закрыт водяным знаком). Этот кейс доказывает
    ОБРАТНОЕ направление того же уровневого предиката: «проваленный
    проход НЕ закрывает водяной знак — уровень остаётся открытым, и
    ЛЮБОЙ следующий проход, даже без нового Send, обязан повторить
    попытку». Не дубль.
  - **идемпотентность — покрыта как следствие.** Успешный ретрай
    происходит РОВНО один раз (после первого успеха водяной знак
    закрывается — доказательство в Then второго прохода
    `sendHandledAt>=T0`); третий гипотетический проход не тестируется
    отдельно — тот сценарий уже покрыт TC-280 (повторная синхронизация с
    закрытым водяным знаком не задваивает).
  - ретроактивность — н-п: нет выключаемой настройки, влияющей на этот
    механизм (тот же вывод, что TC-279/280/283).
  - off-инвариант — н-п: та же причина.
  - propagation — н-п в рамках этого кейса: единственные наблюдаемые
    консьюмеры — вкладка Files и снекбар, оба проверены на ОБОИХ проходах;
    открытых вкладок/других экранов, которым нужно узнать о приходе
    отдельно (класс BUG-012), в этой области нет (см. TC-280 для того же
    вывода).

Инвариант: **отработка standing-запроса (`sendHandledAt` продвигается до
`sendRequestedAt`) происходит РОВНО в двух случаях — (а) БЕЗ попытки
закачки, если файл уже есть локально (`downloadPath != null`,
`SyncRepository.kt:332-335`, доказано TC-280 Вариант B), либо (б) ПОСЛЕ
попытки закачки, ТОЛЬКО если она завершилась успехом (`result.isSuccess`,
`:337-341`); НИКОГДА — на неуспешной попытке (`:342-346`, эта ветвь). Пока
ни (а), ни (б) не выполнены, следующий проход синхронизации переоценивает
ту же работу заново — независимо от того, сколько попыток уже провалилось и
произвёл ли merge этого прохода хоть одно изменение.**
