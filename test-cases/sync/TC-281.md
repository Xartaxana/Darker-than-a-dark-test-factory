# TC-281 — Миграция схемы 8→9→10 не теряет данные и не падает

## Предусловия
- На устройстве установлена БД в схеме v8 (ПОСЛЕ `sync_tombstones`
  из миграции 7→8, ДО `readProgress*`/`sendRequestedAt`/`sendHandledAt`),
  заполненная: несколько работ с рейтингом/заметкой/тегами/`downloadPath`,
  хотя бы один фильтр-профиль, хотя бы одно надгробие (`sync_tombstones`).
- Новая сборка (со схемой v10) устанавливается/запускается впервые поверх
  этой БД — ОБЕ миграции (`MIGRATION_8_9`, `MIGRATION_9_10`) выполняются
  ПОДРЯД за один старт (Room прогоняет цепочку миграций от текущей версии
  файла до целевой версии класса за один проход, не одну на релонч).

## Сценарий (Given-When-Then)

**Given** БД схемы v8 с засеянными рейтингами/заметками/тегами/путями
загрузок, фильтр-профилем и надгробием лежит в песочнице приложения

**When** приложение новой сборки (схема v10) запускается впервые поверх этой
БД

**Then** приложение НЕ падает при старте (`fallbackToDestructiveMigration`
по-прежнему НЕ включён — отказ любой из двух миграций наблюдался бы как
краш, а не тихая потеря)
**And** все ранее засеянные рейтинги/заметки/теги/пути загрузок видны в
Library без изменений
**And** фильтр-профиль виден в Settings без изменений
**And** надгробие (`sync_tombstones`) по-прежнему присутствует (миграции
8→9/9→10 не трогают эту таблицу — регресс-контроль соседней таблицы)
**And** новые колонки (`readProgressUrl/Percent/Chapter/ChapterTotal/At`,
`sendRequestedAt`, `sendHandledAt`) у ВСЕХ перенесённых строк пусты (`NULL`)
— `ALTER TABLE ... ADD COLUMN` без `DEFAULT` даёт `NULL` на существующих
строках, ни одна из старых работ не считается «уже отправленной» или
«читающейся» просто по факту миграции
**And** пункт Library-карточки любой из перенесённых работ подписан
дословно «Send to my other devices» (НЕ «…again») — прямое пользовательское
подтверждение, что `sendRequestedAt` действительно `NULL`, не только
значение в БД

Инвариант: множество пользовательских записей (работы/профили/надгробия) и
значения ВСЕХ полей, существовавших в схеме v8, после миграции идентичны
исходным; НИ ОДНО новое поле схемы v10 не получает значения «из ниоткуда» —
то же свойство персистентности при миграции, что TC-217 доказывает для
7→8, распространённое на цепочку 8→9→10 (двух миграций подряд, а не одной).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Исходная схема | v8 (`sync_tombstones` есть, `readProgress*`/`sendRequestedAt`/`sendHandledAt` нет) |
| Целевая схема | v10 |
| Данные | ≥2 работы (разные рейтинги, одна с `downloadPath`), 1 фильтр-профиль, 1 надгробие |
| Новые колонки после миграции | все `NULL` у перенесённых строк |

## Заметки для автоматизации
- Блокера нет — тот же класс приёма, что TC-217 (её заметки: «построение
  baseline технически не требует новой фикстуры-заглушки»), продлённый на
  два ALTER TABLE вместо одного. Два равноценных пути построения v8-baseline
  (выбор — на кодировании, не блокер дизайну):
  (а) взять актуальный `_pull_baseline` (уже v10 после установки текущей
  сборки), выполнить `ALTER TABLE work_ratings DROP COLUMN <col>` по каждой
  из 7 новых колонок (SQLite ≥3.35 поддерживает `DROP COLUMN`; версия
  `sqlite3`, доступная в проекте, уже используется тем же модулем
  `seed_db.py` для прямых SQL-операций) и откатить `PRAGMA user_version = 8`
  перед `push_app_file`;
  (б) держать под рукой закоммиченный файл-снимок v8-схемы (детерминированнее,
  не зависит от версии `sqlite3` на CI-машине) — тот же путь, что TC-217
  называет «надёжнее».
- Проверка «пункт подписан ‘Send to my other devices’, не ‘…again’» —
  тот же локатор, что TC-279 (`lib.by_text("Send to my other devices")`,
  ОТСУТСТВИЕ текста «again» рядом) — переиспользовать степ, не изобретать
  новый.
- Не путать с `settings-restore-merge` (JSON-бэкап через Settings) — здесь
  проверяется БИНАРНАЯ миграция Room-схемы при апгрейде APK, другой
  механизм и другой риск (падение приложения на старте), тот же контраст,
  что называет TC-217.
- Отличие от TC-217 (не дубль, не слияние): TC-217 держит РОВНО ОДНУ
  миграцию (7→8, создание `sync_tombstones`); путь 8→10 «этот кейс не
  проходит» заявляет НЕ сам TC-217, а `docs/01-test-strategy.md` §9 п.5
  (`:2467`) — разный исходный/целевой номер схемы, разное число миграций
  за один старт, разный набор новых колонок под проверкой
  (`readProgress*`+`sendRequestedAt`+`sendHandledAt` против
  `sync_tombstones`). Разная природа Given (другой файл-снимок схемы) —
  граница слияния П1 не пройдена, кейсы намеренно раздельные.
