# TC-228 — Батарея: идемпотентность окна авто-триггера

## Предусловия
- Синхронизация настроена. Приложение только что выполнило успешный
  авто-триггер (первый выход на передний план после запуска — `dirty` уже
  сброшен, `sync_last_at` только что записан).

## Сценарий (Given-When-Then)

**Given** авто-триггер только что успешно отработал, локальных изменений с
тех пор не было

**When** пользователь СРАЗУ повторно сворачивает и разворачивает приложение
(второй выход на передний план в пределах 60 секунд от первого)

**Then** второй авто-триггер НЕ делает сетевого запроса вовсе — гейт
`!dirty && (now - lastAutoCheck) < 60000` подавляет его целиком (перехват
mitm показывает 0 запросов на этот второй When, в отличие от TC-216/222,
где запрос уходит, но ничего не публикует)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Интервал между триггерами | < 60 000 мс |
| Локальные изменения между ними | нет |
| Ожидаемое число сетевых запросов на второй триггер | 0 |

## Заметки для автоматизации
- **Н-п (edge-vs-level, обязательная строка батареи):** пункт батареи
  «edge vs level» здесь неприменим по конструкции — гейт `dirty` +
  60-секундное окно УМЫШЛЕННО уровневый по спецификации (не предикат
  сохранения, который должен реагировать на переход состояния, как в
  классе BUG-014), это и есть заявленная семантика авто-триггера; test-
  strategist явно закрыл этот красный флаг в docs/01 §9 («класс BUG-014 не
  горит»).
- Требует mitm-наблюдения (тот же приём, что TC-227) — 0 запросов, не 0
  публикаций.
