# TC-280 — Приёмник обрабатывает standing-запрос «Send to my other devices»: качает один раз, не задваивает, не качает лишний раз при уже-скачанном файле

## Обоснование объёма (три варианта, один кейс — не journey)

Три `When`/`Then`-варианта ниже делят ОДИН семантический механизм
(`fulfillSendRequests`) и одну природу Given (remote-снимок через
GitLab-Snippet-мок + `sync_replay`, тот же класс, что TC-207..231) — не
journey с чекпойнтами (нет сквозного мутирующего состояния между вариантами,
каждый — свежий `clean_state()`), тот же приём, что TC-272. Вариант A
внутри себя несёт ДВА последовательных «Sync now» — это НЕ отдельный
вариант, а обязательная edge-vs-level-проба (CLAUDE.md, класс BUG-014):
разделять её на свой Given означало бы копировать тот же Given ради того же
Then другим словами, что запрещено правилом дедупа.

**Осознанный остаток (третья кодовая ветка — сбой закачки, `:342-346`,
«оставляет неотработанным, следующий проход повторит») — НЕ включена в этот
кейс.** Причина не «лень», а конкретный риск: единственный БЕЗОПАСНЫЙ способ
форсировать сбой именно на `fetchDownloadUrl` (не затронув `/downloads/...`
эндпойнт вовсе, см. код) — синтетический `status=404` на GET САМОЙ страницы
работы (`DownloadRepository.kt:205-222`: код `>=400` не в диапазоне 500-599
⇒ немедленный `return null`, без ретраев); это ДОКАЗАННО безопасный приём
(тот же класс, что `make_html_get_flow(status=404)` уже используют
`fetchAo3WorkPage`-тесты, AT-BUG-061), но полное доказательство «следующий
проход РЕАЛЬНО докачивает» требует ВТОРОЙ, уже успешной, `.mitm`-подмены
ВНУТРИ одного теста (пере-конфигурация `sync_replay` вторым вызовом) —
техника, которую этот дизайн НЕ видел живьём ни в одном существующем тесте
области `sync`. Риск ошибиться здесь — случайно не заматчить реальный
`/downloads/...` GET и уйти в LIVE-forward на archiveofourown.org
(`server_replay_extra=forward`, `framework/core/mitm.py:388-390`) —
недопустимо (правило проекта «никогда не грузить живой AO3»). P2-остаток:
дизайн вернётся к этой ветке отдельным ходом, когда пере-конфигурация
`sync_replay` внутри одного теста будет подтверждена на другом кейсе (или
координатор решит иначе) — область НЕ needs-design из-за этого остатка
(см. закрытие §9: edge-vs-level-проба, наиболее рисковая часть правила-
реакции по классу BUG-014, покрыта; эта ветка — младший по риску остаток
ВНУТРИ ядра, явно поименован, не молчаливый пропуск).

## Предусловия
- `clean_state()` ДО инстанцирования `driver` (тот же порядок, что
  `loved_liked_seeded_for_merge` в reference-файле — иначе автосинк на
  первом `onResume` уходит live на `gitlab.com` с протухшим тестовым
  токеном).
- `sync_replay` (poднимает mitm-прокси device-wide, `ignore_content=True`
  для PUT/POST) — та же фикстура, что TC-207..231/BUG-078-верификация.
- GitLab Snippet ID = `SNIP1`, токен фиктивный (`glpat-test-token-*`) —
  синк настраивается в теле теста через `settings_steps.configure_sync`.
- Работа `W = W.LOVED` (`framework/data/works.py`) — та же, что использует
  BUG-078-верификация; `download_flows = rb.read_flows(settings.RECORDINGS_DIR
  / rb.WORK_WITH_DOWNLOAD_FILENAME)` — существующая, уже воспроизводимая
  запись (TC-032/033), нужна ТОЛЬКО вариантам, где закачка реально
  происходит (A).

## Сценарий (Given-When-Then)

### Вариант A — качает один раз; ВТОРАЯ синхронизация с тем же standing-запросом закачку НЕ повторяет (edge-vs-level-проба, ОБЯЗАТЕЛЬНА)

**Given** локальная библиотека ПУСТА (работы W нет вовсе); удалённый снимок
несёт W с `rating=LIKE`, `sendRequestedAt=T0` (свежий `now`) —
`gsm.work_json(...)`, затем `remote_work["sendRequestedAt"] = T0` (тот же
приём, что `test_receiving_device_downloads_and_shows_snackbar`); `.mitm`
включает `download_flows` + GET/PUT снипета

**When** пользователь настраивает синк (`configure_sync`) и жмёт «Sync now»
В ПЕРВЫЙ раз

**Then** диалог «Sync complete», текст содержит «1 works updated» (merge
вставил строку W)
**And** снекбар «Downloaded 1 work sent from another device» появляется
(ЕДИНСТВЕННОЕ число «work», не «works» — `count==1`, `MainActivity.kt:336`)
**And** в Room у W: `downloadPath` заполнен (файл РЕАЛЬНО скачан через
настоящий `DownloadRepository.downloadWork` на мокнутый AO3-эндпойнт), rating
остаётся LIKE
**And** `sendHandledAt >= sendRequestedAt` (запрос помечен отработанным)
**And** (контраст точки 3 области) текст диалога «Sync complete» НИГДЕ не
упоминает «sent»/«received»/число присланных работ — единственное
сообщение об этом событии несёт снекбар, не диалог (`SettingsScreen.kt:1448-1453`,
`changes` не включает `receivedWorks`)

**When** (дождавшись, пока снекбар первой синхронизации ПОЛНОСТЬЮ исчезнет с
экрана — иначе проба второй синхронизации рискует поймать текст ПЕРВОГО
снекбара, а не отсутствие второго) пользователь жмёт «Sync now» ВТОРОЙ раз
подряд — remote-снимок НЕ менялся (тот же `T0`, никто не отправлял «Send
again»)

**Then (edge-vs-level-проба, класс BUG-014)** диалог «Sync complete» на этот
раз показывает дословно «No incoming changes. Snippet updated.» (НЕ «1 works
updated» — remote timestamp строки теперь равен локальному после первого
слияния, ties keep local, `updatedWorks == 0`, `SyncRepository.kt:168`; но
`published == true`: `outText = outRoot.toString(2)` — pretty-print с
отступом 2 (`SyncRepository.kt:259`) — НИКОГДА не равен компактному телу
мока `json.dumps(...)` (`gitlab_snippet_mock.py:151-156`), поэтому публикация
снипета происходит заново и диалог идёт по ветке `SettingsScreen.kt:1461`,
а не по «Everything already in sync.» `:1462`, которая требует ещё и
`!published`)
**And** отдельно — содержательное утверждение слияния: текст диалога НЕ
содержит «works updated» (слияния строк не было)
**And** снекбар прихода НЕ появляется во второй раз (`receivedWorks == 0` —
`sendHandledAt` уже `>= sendRequestedAt`, `fulfillSendRequests` пропускает W
по `continue` на `:331`)
**And** `downloadPath` W идентичен значению после первой синхронизации
(строка/файл не тронуты повторно) — уровневый предикат
`sendHandledAt < sendRequestedAt` удержан монотонным водяным знаком, ДВЕ
синхронизации подряд с одним и тем же standing-запросом дают РОВНО ОДНУ
закачку, не две

### Вариант B — работа с уже скачанным файлом: запрос помечается отработанным БЕЗ повторной закачки, снекбар прихода НЕ показывается

**Given** локальная работа W уже засеяна С downloadPath (`seed_with_download`
— реальный файл-фикстура на устройстве), `rating=LIKE`, `timestamp=T_local`,
`sendRequestedAt=null`; удалённый снимок несёт W со СТАРШИМ `timestamp`
(`T_local - 60_000`, гарантированно проигрывает построчное сравнение,
`remoteTs <= localTs` — ветка «local wins», та же, что
`test_local_row_wins_but_send_request_still_merges`) и ДРУГИМ рейтингом
(`DISLIKE`, чтобы победа local была видна), но НОВЫМ `sendRequestedAt =
T_local + 30_000` (новее текущего `sendHandledAt=null`); `.mitm` включает
GET/PUT снипета И `download_flows` — эта ветка кода `downloadWork` не
вызывает их вовсе (см. Then), но флоу присутствуют СТРАХОВКОЙ: если
предположение о ветке `:332-335` окажется неверным, тест обязан упасть на
несовпадении утверждения, а не уйти `server_replay_extra=forward` на живой
archiveofourown.org (`framework/core/mitm.py:441-442`)

**When** пользователь настраивает синк и жмёт «Sync now»

**Then** rating W остаётся LIKE (локальная строка победила построчное
сравнение, удалённый DISLIKE проигнорирован для этого поля)
**And** `sendRequestedAt` W всё равно замержился полевым способом
(`= T_local + 30_000`, `withNewerSendRequest` работает НЕЗАВИСИМО от того,
кто выиграл строку — `SyncRepository.kt:172-178`)
**And** `downloadPath` W НЕ изменился — остался ТЕМ ЖЕ путём, что был до
синка (файл уже был, `fulfillSendRequests` пошёл по ветке `:332-335`,
`downloadRepo.downloadWork` НЕ вызывался — никакого сетевого скачивания не
произошло)
**And** `sendHandledAt >= sendRequestedAt` (запрос помечен отработанным)
**And** снекбар «…sent from another device» НЕ появляется (эта ветка НЕ
инкрементирует `receivedWorks` — `:333` не наращивает счётчик прихода,
только вставка/закачка `:337-341` его наращивает) — отличается от Варианта A
именно этим наблюдаемым фактом, несмотря на то, что запрос формально
«отработан» в обоих случаях

  (`seed_db.read_work_ratings_full()`/сырой SQL по образцу `_pull_send_fields`

  здесь — мок, реальный код исполняется целиком).
- Направление негативного Then: «снекбара НЕ появляется» (Вариант A вторая
  синхронизация, Вариант B) — достижимость доказана ПОЗИТИВНЫМ якорем в
  ТОМ ЖЕ прогоне (Вариант A: снекбар РЕАЛЬНО появился на первой
  синхронизации той же работы; Вариант B: тот же снекбар реально появляется
  в Варианте A с тем же кодом пути UI) — не вакуумная проверка (правило
  CLAUDE.md «направление негативного Then»/класс AT-BUG-029).
- Батарея правил-реакций (`fulfillSendRequests` — правило-реакция,
  единственная точка вызова `SyncRepository.kt:244-245`):
  - edge-vs-level — ПОКРЫТА явно (Вариант A, вторая синхронизация,
    ОБЯЗАТЕЛЬНАЯ проба класса BUG-014).
  - ретроактивность — н-п: нет настройки-переключателя, включающей этот
    механизм; работает всегда для любого standing-запроса независимо от
    того, когда он был помечен.
  - off-инвариант — н-п: выключаемой настройки нет (сам синк можно не
    настраивать, но это не «off» этого правила, а отсутствие Given).
  - идемпотентность — ПОКРЫТА явно (Вариант A, edge-vs-level-проба —
    идемпотентность И есть содержание пробы здесь).
  - propagation — н-п в рамках ЭТОГО кейса: единственный наблюдаемый
    потребитель эффекта на приёмнике — вкладка Files (через `downloadPath`)
    + снекбар, оба проверены; открытых вкладок/других экранов, которым
    нужно узнать о приходе (класс BUG-012), в этой области нет.
- **Дефект-сосед (доклад, не расширение scope):** `receivedWorks`
  (снекбар) и `updatedWorks` (текст диалога «N works updated») — ДВА
  РАЗНЫХ счётчика с разной семантикой, и Вариант B демонстрирует прямое
  расхождение: `updatedWorks` считает эту работу (sendRequestedAt
  смержился → `merged != lRow`), а `receivedWorks` — нет (файл не качался).
  Это НЕ баг (оба счётчика корректны по своему определению), но соседний
  наблюдательный факт, который стоит явно занести в §9 при следующей
  ревизии точки 3 области (асимметрия сообщений) — уже отмечена
  стратегом, здесь только эмпирическое подтверждение второй гранью.
