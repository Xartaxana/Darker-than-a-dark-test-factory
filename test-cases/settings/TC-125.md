# TC-125 — Tap to scroll ON переживает kill+relaunch приложения

## Предусловия
- Приложение запущено с чистыми данными; тумблер «Tap to scroll (work pages)»
  включён через Settings.
- Открыта replay work-страница, документ высокий (общий блокер с
  `bugs/AT-BUG-030.md`, узел 3), нижняя панель свёрнута, >=2 вкладки, не
  fullscreen.

## Сценарий (Given-When-Then)

**Given** `tap_to_scroll = ON` (установлен через Settings); открыта replay
work-страница; тап по нижней трети подтверждённо скроллит страницу (baseline)

**When** приложение убито (`adb shell am force-stop`) и перезапущено (без
очистки данных)

**Then** тумблер «Tap to scroll (work pages)» в Settings по-прежнему
отображает ON (значение читается из `SharedPreferences` при старте,
`SettingsScreen.kt:177`)

**And** на открытой после перезапуска replay work-странице тап по нижней трети
снова скроллит страницу — JS-состояние `window.__ao3TapToScroll` корректно
переинициализировано при свежей загрузке страницы после релонча (значение
тумблера пережило смерть процесса, а не сбросилось к дефолту `false`)

**Инвариант:** значение `tap_to_scroll` — персистентный `SharedPreferences`
флаг, независимый от жизненного цикла процесса приложения; наблюдаемый эффект
(тап скроллит) после kill+relaunch идентичен эффекту ДО kill — persist переживает
и UI-отображение тумблера, и JS-инъекцию.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| `tap_to_scroll` до kill | ON |
| `tap_to_scroll` после relaunch (Settings) | ON |
| Эффект тапа после relaunch | скроллит, как и до kill |

## Заметки для автоматизации
- **Запас до низа документа для тапа ПОСЛЕ релонча — рассуждение
  ПЕРЕПИСАНО по факту реализации (Lead 2026-07-30, разбор эскалации;
  прежняя редакция attempt 2/N6 ОТМЕНЕНА живым прогоном — см. докстринг
  `test_tap_to_scroll_survives_kill_and_relaunch`).** Прежняя арифметика
  («второй тап стартует с позиции baseline-тапа ≈0.95×innerHeight»)
  неприменима к принятой реализации дважды: (а)
  `prescroll_to_tap_zone_invariant_position` выполняется ДО baseline-тапа,
  так что позиция work-вкладки до kill ≈`1.95×innerHeight`, а не `0.95×`;
  (б) главное — второй тап после релонча вообще приходится на ДРУГУЮ
  вкладку: тест закрывает восстановленную неактивную вкладку-0
  (`swipe_close_tab`, обход sticky-WEBVIEW-контекста, приём TC-025) и
  работает с выжившей второй (Library) вкладкой, которую этот тест никогда
  не скроллил — она восстановлена с `scrollY=0`. Диагностический запас от
  0 при `maxScroll >= 2×innerHeight` (узел 3 AT-BUG-030) очевиден:
  `0.95×innerHeight` вниз однозначно наблюдаем, кламп исключён. Прежний
  инвариант-страховка сохраняет смысл в одной части: будущая правка,
  меняющая, КАКАЯ вкладка получает тап после релонча (или добавляющая ей
  предскролл), обязана пересчитать запас заново, не полагаясь на этот
  пункт молча.
- **Блокер общий с `bugs/AT-BUG-030.md`** (узел 3) — кейс добавлен в
  `test_cases` этого бага этим же ходом.
- Тот же паттерн kill+relaunch, что уже используют существующие тесты
  персистентности (TC-025 «персистентность URL+scroll после рестарта»,
  TC-110 `test_compatibility.py:129`) — оба через
  `app_steps.restart_app_via_adb` (`am force-stop` + relaunch, настоящая
  смерть процесса); реализация TC-125 переиспользует его же. Ссылка на
  TC-051 УБРАНА (Lead 2026-07-30, критик-вход attempt 1/Б3): TC-051
  использует `app_steps.restart_app` (`terminate_app`/`activate_app`
  Appium API) — НЕ смерть процесса, для проверки SharedPreferences-персиста
  это другой, более слабый класс рестарта.
- Реплей-прокси (mitmproxy) должен пережить сам relaunch приложения — это
  инфраструктурный факт уже проверенных сценариев (TC-025 автоматизирован),
  не новый риск.
