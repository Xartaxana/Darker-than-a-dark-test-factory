# TC-169 — Reset brightness on start ON: старт всегда берёт системную яркость

## Предусловия
- Чистая установка/`pm clear` (дефолт `reset_brightness_on_start=true`, тумблер
  не тронут).
- Автояркость ОС выключена (`Settings.System.SCREEN_BRIGHTNESS_MODE` =
  MANUAL) на весь кейс — иначе система может сама переписать выставленное
  вручную значение независимо от теста; восстановить исходный режим в
  teardown.
- Системная яркость управляется через adb
  (`settings put system screen_brightness <0-255>`).
- Открыт экран Settings, виден слайдер «Brightness» и процентная подпись
  рядом с ним.

## Сценарий (Given-When-Then)

**Given** системная яркость выставлена в S1 (например 30%, `adb` — ДО
первого запуска), тумблер «Reset brightness on start» в состоянии ON
(дефолт), приложение только что запущено — подпись слайдера на Settings
показывает ~30%

**When** пользователь тянет слайдер «Brightness» до заметно другого значения
(~90%), НЕ трогает тумблер «Reset brightness on start»
**And** убивает процесс приложения (`force-stop`)
**And** меняет системную яркость через `adb` на ДРУГОЕ значение S3
(например 60%) — отличное и от S1, и от ручной правки
**And** заново запускает приложение

**Then** на экране Settings после релонча процентная подпись слайдера
показывает ~60% (текущую системную S3 НА МОМЕНТ старта) — НЕ ~90% (ручная
правка слайдера не пережила рестарт) и НЕ ~30% (значение не закешировано с
предыдущего запуска)
**And** ни один холодный старт при ON не показывает значение, которое
пользователь когда-либо выставлял слайдером вручную, — только текущее
системное (негативная грань тумблера в состоянии ON)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Системная яркость до 1-го старта (S1) | ~30% |
| Ручная правка слайдера (не персистит) | ~90% |
| Системная яркость на момент relaunch (S3) | ~60% |
| Ожидаемая подпись слайдера после relaunch | ~60% (== S3) |

## Заметки для автоматизации
- Наблюдаемый прокси — процентная подпись рядом со слайдером
  (`brightnessLabel(uiState.brightnessValue)`, `SettingsScreen.kt:670-674,
  1322`) — обычная `Text`-нода, читается напрямую (НЕ luma-скриншот, как
  TC-055/TC-146: там прокси нужен для реального затемнения окна/overlay,
  здесь достаточно прочитать сериализованный state).
- Управление системной яркостью — `adb shell settings put system
  screen_brightness <0-255>` (raw 0-255, `detectBrightnessValue()` делает
  `raw/255f`). Нужен новый adb-хелпер по ТОЧНОМУ образцу
  `framework/core/adb.py::set_font_scale`/`set_night_mode` (settings put
  system <key> <value> ДО старта, восстановление дефолта в teardown —
  тот же класс дисциплины). Это рутинная реализация по существующему
  шаблону, НЕ отсутствующая фикстура/блокер (в отличие от прецедентов
  AT-BUG-004/005/006).
- Драйв слайдера — тот же примитив, что уже открывает TC-146
  (`BRIGHTNESS_SLIDER`, drag или accessibility-action set); переиспользовать
  реализацию TC-146, не дублировать.
- Тумблер «Reset brightness on start» — ТОТ ЖЕ приём XPath `following::`, что
  `set_tap_to_scroll`/`set_infinite_scroll`
  (`framework/screens/settings_screen.py:105-149`, секция Reader содержит
  «Reset brightness on start» СРАЗУ рядом с этими двумя уже
  автоматизированными тумблерами) — здесь тумблер не трогается вовсе (ON
  остаётся дефолтом), локатор пригодится TC-170.
- Kill+relaunch — `restart_app_via_adb`/
  `restart_app_via_adb_asserting_new_process`
  (`framework/steps/app_steps.py:500-570`) — реальная смерть процесса, не
  `onPause`/`onStop`.
- Границы: НЕ дублирует TC-146 (слайдер/WebView-эффект в рамках одного
  запуска, без kill) и TC-055 (жест) — этот кейс не проверяет реальное
  затемнение окна/overlay, только persist-семантику через kill+relaunch.
- Кейс НЕ C4-комбинаторной семьи (единичный бинарный persistence-тумблер,
  не множество/отношение элементов — банк инвариантов §C4 не покрывает
  точечные persistence-переключатели без второго измерения), строка
  `Инвариант:` не требуется — то же основание, что TC-146 явно называет для
  соседнего слайдера.
- Батарея правил-реакций: edge vs level — н-п (единственная точка входа —
  прямой тап по тумблеру, здесь вообще не тронут; нет скрытого save-пути,
  вызываемого посторонним событием); ретроактивность — н-п (настройка
  глобальная, не per-объект); off-invariant — этот Then И ЕСТЬ
  off-invariant грани ON (сохранённое ручное значение никогда не
  проявляется); идемпотентность — н-п (Switch не перевызывается с тем же
  значением без настоящего тапа, здесь тумблер не трогается); propagation —
  н-п (единственный потребитель — холодный старт `MainActivity.onCreate`,
  нет broadcast/других вкладок).
