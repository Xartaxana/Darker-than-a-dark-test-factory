# TC-186 — Fetch missing metadata: очередь только из пустых title, прогресс, запись только непустых результатов

## Предусловия
- Приложение запущено, replay-режим (заблокировано — см. «Заметки для
  автоматизации», `bugs/AT-BUG-061.md`).
- В Room засеяны ТРИ строки: (а) работа A с ПУСТЫМ `title` — попадёт в
  очередь, скрейп вернёт непустой title (запись обновится); (б) работа B с
  ПУСТЫМ `title` — попадёт в очередь, но скрейп для неё НЕ ДАСТ непустого
  результата (например, HTTP-ошибка/пустая разметка на записанной странице —
  запись НЕ обновится, остаётся с пустым title); (в) работа C с УЖЕ
  ЗАПОЛНЕННЫМ title, автором, фандомом — НЕ должна попасть в очередь вовсе.
- Экран Settings открыт, секция «Fetch missing metadata» видна.

## Сценарий (Given-When-Then)

**Given** в Room три работы: A (пустой title, скрейп даст успех), B (пустой
title, скрейп не даст успеха), C (title уже заполнен)

**Then** подпись под «Fetch missing metadata» показывает «2 works have no
title yet» (только A и B — C НЕ считается, `getWorksNeedingMetadata`
фильтрует по пустому title, не по «все работы»)

**When** пользователь нажимает «Fetch»

**Then** пока идёт процесс, подпись показывает «Fetching 1 / 2…», затем
«Fetching 2 / 2…» (наблюдаемый прогресс `N/total`), кнопка на месте «Fetch»
временно становится «Stop»

**Then** по завершении (без нажатия Stop) состояние — `Done`: подпись «Updated
1 works» (обновилась только A — единственная, для которой скрейп дал непустой
title)
**And** в Room: title работы A ЗАПОЛНЕН скрейпнутым значением (плюс
author/fandom/wordCount, если скрейп их дал); title работы B ОСТАЁТСЯ пустым
(запись НЕ перезаписана пустым/мусорным значением); работа C НЕ ТРОНУТА
(её исходные title/author/fandom неизменны — байт-в-байт)

**Явная анти-ловушка (docs/01 §9):** это НЕ класс `bugs/BUG-048.md`
(перезапись ХОРОШИХ метаданных) — работа C не входит в очередь по построению
(фильтр по пустому title), и Then этого кейса явно проверяет её
неприкосновенность, а не полагается на предположение.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа A | title пусто → очередь → скрейп успешен → title заполнен |
| Работа B | title пусто → очередь → скрейп неуспешен → title остаётся пустым |
| Работа C | title уже заполнен → НЕ в очереди → неизменна |
| Итоговый счётчик | «Updated 1 works» |

## Заметки для автоматизации
- **АВТОМАТИЗИРОВАНО (2026-08-14).** Прежний блокер `bugs/AT-BUG-061.md`
  устранён и `Verified` (replay-запись `work_metadata_fetch.mitm` существует
  и эмпирически подтверждена — см. сам баг) ещё ДО этого хода; этот проход
  дописал недостающий слой (локаторы `settings_screen.py`, шаги
  `settings_steps.py`, Then обоих кейсов) и заполнил `automated_by`. Given
  сеет строки с ТЕМИ ЖЕ ao3_id, что несёт запись (`rb.METADATA_FETCH_WORK_A`/
  `rb.METADATA_FETCH_WORK_B_AO3_ID`), но с `title=""` — текущее (до fetch)
  состояние; запись несёт целевой (скрейпнутый) результат.
- **Ограничение прогонов (docs/01 §9, явное требование, не блокер):** только
  replay/mitm — живые позитивные пробы ЭТОГО пути запрещены (запросы к
  archiveofourown.org от имени пользователя, тот же довод, что для
  авто-kudos).
- Cookie для `fetchAo3WorkPage` берётся из `CookieManager.getInstance()
  .getCookie(...)` (`SettingsScreen.kt:1023-1024`) — сверено живым прогоном
  (2026-08-14): server-replay матчит flow ТОЛЬКО по
  scheme+method+path+query+host+port (`recording_builder.py` модульный
  докстринг «Матчинг server-replay») — заголовки запроса (включая Cookie) на
  матчинг не влияют; работа A получает ПОЛНЫЙ скрейпнутый результат без
  предварительного логина/cookie, отсутствие cookie результат скрейпа не
  меняет.
- Оракул очереди/счётчика — текстовые подписи (`SettingsScreen.kt:1006-1044`,
  обычный `Text`, без скриншотов; `SettingsScreen.metadata_queue_count_
  visible`/`metadata_progress_visible`/`metadata_done_visible` — точный текст
  сверен с исходником, включая ellipsis U+2026).
- Чтение Room после завершения — `seed_db.read_work_ratings_full()`
  (готов, `seed_db.py:319`) — состав возвращаемых полей
  (title/author/fandom/word_count) сверен перед написанием SELECT (урок
  CH-007/CH-008 про урезанный `read_work_ratings`).
