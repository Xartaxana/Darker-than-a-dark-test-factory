# TC-135 — Холодный старт по VIEW-интенту: reuse единственной home-вкладки

## Предусловия
- Приложение НЕ запущено (`am force-stop` или чистый старт), данные чистые
  (`clean_app`): prefs пусты, `open_tabs_urls` отсутствует — при следующем
  старте `BrowserViewModel.init` (`:181-186`) создаст ровно одну вкладку со
  значением-константой `HOME_URL` (`https://archiveofourown.org`, БЕЗ слэша).
- Replay-режим, фикстура `tab_markers.mitm` (маркерная страница записана;
  mitm-прокси поднят ДО старта приложения — штатный порядок replay-фикстуры).

## Сценарий (Given-When-Then)

**Given** приложение остановлено, prefs пусты (холодный старт создаст
единственную вкладку `HOME_URL` без слэша, ещё НЕ перезаписанную
`onPageLoaded`)

**When** приложение запускается САМИМ deep-link-интентом: `am start -a
android.intent.action.VIEW -d <url маркерной страницы> <package>` — сценарий
пользователя «тап по ao3-ссылке извне при незапущенном приложении»

**Then** число вкладок равно 1 — сработала ветка ПЕРЕИСПОЛЬЗОВАНИЯ
(`navigateActiveTabTo`, `BrowserViewModel.kt:639-641`), новая вкладка НЕ
создана
**And** содержимое единственной вкладки — маркерная страница deep-link'а
(`open_tabs_urls` содержит ровно 1 запись, и это URL маркера, не
`HOME_URL`/home со слэшем)

**Инвариант:** ветка reuse (`tabs.size==1 && tabs[0].url == HOME_URL`
побайтово) достижима ШТАТНЫМ пользовательским путём — холодным запуском
приложения по внешней ao3-ссылке: `onResume` (`MainActivity.kt:96-101`)
обрабатывает intent синхронно ДО того, как сетевая загрузка home успевает
завершиться и `onPageLoaded` перезаписывает URL со слэшем; буферизованный канал
(`Channel.BUFFERED`, `BrowserViewModel.kt:154-157`) гарантирует, что эмиссия до
старта коллектора (`MainActivity.kt:262-268`) не теряется. Пара TC-132 (тёплый
старт, home догружена → создание второй вкладки) + TC-135 (холодный старт, home
не загружена → reuse) закрывает ОБЕ ветки условия `BrowserViewModel.kt:639`.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Состояние до When | приложение остановлено, prefs пусты |
| Запуск | `am start -a VIEW -d <marker-url>` (холодный старт интентом) |
| Вкладок после | 1 (reuse, НЕ 2) |
| URL единственной вкладки | маркерная страница (не home) |

## Заметки для автоматизации
- **ПРЕДПОСЫЛКА КОД-ТРАССИРОВАНА, НЕ ИЗМЕРЕНА (критик-вход ESC-011, attempt 2;
  дизайн — Lead, разбор эскалации 2026-07-31).** Разрешение гонки «intent vs
  загрузка home» на холодном старте в пользу intent'а выведено построчной
  трассировкой (`onResume` до сетевой загрузки; `Channel.BUFFERED`), но живым
  прогоном НЕ подтверждено. **Первый шаг автоматизации — дизамбигуация:** если
  на реальном устройстве home успевает догрузиться раньше обработки intent'а
  (наблюдение: вкладок стало 2), это НЕ провал кейса, а опровержение
  предпосылки — вернуть кейс в дизайн строкой измерения (доклад координатору,
  не молчаливый скип). Замер CH-005 R2.5 мерил ТЁПЛЫЙ старт (home уже была
  догружена) — к холодному не применим, противоречия с ним нет.
- Запуск интентом при остановленном приложении — вариация существующего
  `app_steps.open_deep_link` (`am start -a VIEW -d`); отличие от TC-133/134:
  там intent приходил в ЖИВОЕ приложение, здесь он и есть запуск. Appium-сессия
  при этом должна пережить force-stop приложения (`no_reset=True`,
  `restart_app_via_adb` — существующий класс приёма, TC-110/TC-125).
- НЕ использовать `wait_home_ready_for_deep_link` перед When — этот шаг
  существует ровно для того, чтобы УЙТИ из reuse-окна (докстринг
  `app_steps.py:109-118`); здесь нужно противоположное: слать intent сразу,
  окно и есть предмет кейса.
- Счёт вкладок и URL — из prefs `open_tabs_urls` (ловушка виртуализации
  TabStrip — см. TC-131); дождаться персиста `wait_tabs_persisted`.
- Если mitm-replay не содержит какого-то запроса холодного старта — сверить по
  `tab_markers.mitm` (запись велась с холодного старта сессии CH-005, home и
  маркеры записаны); уход в live детектируется штатным признаком
  (`div#tos_prompt`).

## Наблюдение test-automator (2026-07-31, дизамбигуация по протоколу заметок)

Реализован тест по буквальному сценарию: Appium-сессия (`driver`) автозапускает
приложение (`autoLaunch` по умолчанию, `capabilities.build_options` не выставляет
`autoLaunch=false`) — это ОБЫЧНЫЙ запуск, не часть кейса; шагом-обвязкой
(`adb.force_stop()` + повторный `pm clear`) устройство возвращалось в буквальный
Given («приложение НЕ запущено, prefs пусты») ПЕРЕД отправкой самого
deep-link-интента (`am start -a VIEW -d <marker-url> <package>`, реальный холодный
старт). Then проверялся по `open_tabs_urls`: количество вкладок + URL позиции 0.

**Результат — 3/3 прогона, ДЕТЕРМИНИРОВАННО (не флейково):** количество вкладок
осталось 1 (как и ожидает Then), НО URL единственной вкладки — `https://
archiveofourown.org/` (home, ПОЛНОСТЬЮ догруженная, со слэшем), а НЕ маркерная
страница deep-link'а. Это ОТЛИЧАЕТСЯ от сигнатуры опровержения, ANTICIPATED в
заметках кейса («вкладок стало 2») — здесь количество совпало с ожиданием, но
содержимое нет: reuse-навигация (`navigateActiveTabTo`/`pendingNavigationUrl`)
на маркер, по всей видимости, не долетела до WebView вовсе (URL вкладки остался
равен результату ОБЫЧНОЙ загрузки home, инициированной при создании вкладки).

Гипотеза (НЕ подтверждена глубже трассировки, приведена для передачи контекста,
не как вердикт): `openOrNavigateDeepLink` (BrowserViewModel.kt:637-644) только
выставляет `pendingNavigationUrl` в uiState — сам `WebView.loadUrl()` вызывается
ОТДЕЛЬНЫМ `LaunchedEffect(uiState.pendingNavigationUrl, activeTab?.id)`
(`BrowserScreen.kt:212-219`) через `webViews[activeId]?.loadUrl(url)` (safe-call
на возможно ещё НЕ созданный WebView — сам WebView создаётся ДРУГИМ,
независимым `LaunchedEffect(tabs.map { it.id })`, `BrowserScreen.kt:116-145`).
Если эффект с `pendingNavigationUrl` срабатывает РАНЬШЕ, чем WebView для
единственной вкладки успевает быть создан — `loadUrl` на `null` молча
проходит как no-op, `clearPendingNavigation()` вызывается безусловно (навигация
теряется), а WebView, созданный следующим эффектом, УЖЕ грузит `tab.url`
(по-прежнему `HOME_URL`, т.к. `navigateActiveTabTo` НЕ переписывает
`tabs[0].url` напрямую — это делает только последующий `onPageLoaded`),
т.е. загружает и в итоге сохраняет именно home. Эта гипотеза — race МЕЖДУ ДВУМЯ
Compose-эффектами при холодном старте, НЕ буквально «сетевая загрузка home
успевает раньше onResume», как сформулировано в исходной предпосылке кейса, но
итог для Then тот же: reuse не производит наблюдаемый эффект (URL) на маркерной
странице. Код `app-under-test` не менялся и не будет меняться этим агентом —
гипотеза не проверена дальнейшей трассировкой/логами, приведена только чтобы
следующий разбор не начинал с нуля.

**Вывод: предпосылка кейса (reuse детерминированно наблюдаем как «URL вкладки
= маркер») НЕ подтверждена 3/3 живыми прогонами** — устойчиво воспроизводится
обратное (URL остаётся home). Тестовый код и правки `app_steps.py` из этой
попытки НЕ закоммичены (`git checkout --` этой же сессии) — дерево чистое,
`automated_by` не выставлен. Решение о переформулировке/дизайне кейса —
за координатором/test-designer (см. `result: blocked` в отчёте
test-automator).
