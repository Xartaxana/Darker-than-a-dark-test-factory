# TC-133 — Возврат из recents не переоткрывает уже обработанный deep-link

## Предусловия
- Приложение запущено с чистыми данными (`clean_app`).
- Replay-режим, фикстура `tab_markers.mitm`.
- Открыто 3 вкладки: 0 — Home (полностью догружена), 1 и 2 — созданы ДВУМЯ
  предшествующими deep-link'ами (`ao3_tab_marker=1`, `ao3_tab_marker=2`) — тот же
  Given-паттерн, что TC-084 («3 вкладки после deep-link'ов» — измеренная база
  CH-005 R2 п.6 / Г6в, «3 вкладки до и после», строка 8 таблицы находок).

## Сценарий (Given-When-Then)

**Given** открыто 3 вкладки (Home, маркер 1, маркер 2), последний обработанный
deep-link — тот, что создал вкладку 2 (`deepLinkHandled == true` для него)

**When** приложение отправлено в фон (не убито) и затем возвращено на передний
план БЕЗ отправки нового deep-link intent'а — командой `am start` на компонент
Activity БЕЗ флага `-d` (тот же операционный приём, каким CH-005 измерил R2 п.6 /
Г6в: «возврат в приложение из recents (am start без -d)»), что порождает новый intent
БЕЗ `dataString`, а не буквальный тап по миниатюре в системном UI recents

**Then** число вкладок остаётся 3, набор URL и их порядок — теми же, что до
возврата (проверяется через prefs `open_tabs_urls`)
**And** ни маркер 1, ни маркер 2 НЕ переоткрываются повторно (нет дубликата вкладки
с тем же URL) — `intent.dataString` нового intent'а пуст, поэтому
`handleDeepLink`/`openOrNavigateDeepLink` не вызываются вовсе на этом событии

**Инвариант:** для ЛЮБОГО события жизненного цикла, которое приводит приложение на
передний план БЕЗ доставки НОВОГО intent'а с непустым `dataString` (простой
возврат из фона/recents), множество вкладок (число, URL, порядок) не меняется —
`deepLinkHandled`/`intent.dataString` защищают от повторной обработки одного и
того же URL независимо от того, сколько раз подряд происходит такой возврат.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вкладок до возврата | 3 (Home, маркер 1, маркер 2) |
| Способ возврата | `adb shell am start -n <package>/<activity>` БЕЗ `-d` (после отправки в фон, без force-stop) |
| Вкладок после возврата | 3, тот же набор/порядок |

## Заметки для автоматизации
- Отправка в фон — `driver.background_app(-1)` (Appium, удержание в фоне до явного
  возврата) ИЛИ `adb shell input keyevent KEYCODE_HOME`; возврат — `adb shell am
  start -n <APP_PACKAGE>/<APP_ACTIVITY>` без `-d` (в отличие от
  `app_steps.open_deep_link`, который явно шлёт `-a android.intent.action.VIEW -d
  <url>`). Небольшая новая обёртка по образцу уже существующих
  `app_steps.open_deep_link`/`restart_app_via_adb` (`framework/steps/app_steps.py:154,189`)
  — не блокер, тривиальная композиция уже используемых примитивов (`adb.shell`,
  `settings.APP_PACKAGE`, `settings.APP_ACTIVITY`).
- Счёт/набор вкладок — из prefs `open_tabs_urls`, не из иконок TabStrip (см.
  ловушку в TC-131).
- Различать от TC-134: там дополнительно происходит СМЕРТЬ процесса
  (`force_stop`), здесь процесс остаётся живым — разные пути к `onNewIntent`, но
  один и тот же защитный механизм (`deepLinkHandled`), поэтому кейсы раздельные
  (один сценарий — один кейс), не одна ветвящаяся проверка.
- Перед первым deep-link'ом дождаться загрузки home
  (`app_steps.wait_home_ready_for_deep_link`) — тот же класс гонки, что в
  TC-022..025/131/132.
