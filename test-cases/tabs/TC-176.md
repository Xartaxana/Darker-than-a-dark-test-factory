# TC-176 — Счётчик снекбара называет число фоново открытых вкладок, а не общее число (красный замок BUG-059)

## Предусловия
- Приложение запущено с чистыми данными, replay-режим (`listing_basic.mitm`).
- В Room засеяны минимум 2 РАЗЛИЧИМЫЕ работы на любой рейтинговой вкладке
  Library (не Files — цель должна быть AO3-URL, не локальный файл, см.
  TC-173/174).
- Открыт экран Library, открыта ровно 1 вкладка Browse (Home) —
  `wait_persisted_tab_count(1)`.

## Сценарий (Given-When-Then)

**Given** приложение на экране Library, открыта ровно 1 вкладка (Home)

**When** пользователь долгим нажатием по карточке №1 открывает overlay и
тапает «Open in background tab» (первое фоновое открытие сессии)
**And** дожидается, пока снекбар полностью исчезнет с экрана (поллинг
отсутствия текста «Opened in background», не таймер — см. заметки)
**And** долгим нажатием по карточке №2 (ДРУГАЯ работа) открывает overlay и
тапает «Open in background tab» (второе фоновое открытие сессии)

**Then** снекбар после ВТОРОГО открытия показывает дословно «Opened in
background (2 tabs)» — «2» здесь означает число вкладок, открытых В ФОНЕ за
эту сессию (по одной на каждое действие «Open in background tab»), а не
общее число вкладок приложения

**ОЖИДАЕМОЕ ПАДЕНИЕ на текущей сборке** (прецедент TC-139: кейс пишется по
ожидаемому поведению спецификации, а не по факту сборки): по коду
(`BrowserViewModel.kt:283`, `tabCount = newTabs.size`) счётчик реально
показывает ОБЩЕЕ число вкладок — на момент второго открытия это 3 (Home +
2 фоновых), и снекбар фактически покажет «Opened in background (3 tabs)».
Красный результат триажится как **APP_BUG/BUG-059**, не как расхождение
теста со спекой; ссылка: `bugs/BUG-059.md`.

**Почему сценарий строится на ДВУХ открытиях, а не на одном.** Одно фоновое
открытие из чистого состояния всегда даёт ровно 1 фоново-открытую вкладку —
ожидаемый текст был бы «Opened in background (1 tab)», единственное число.
Эта ветка НЕДОСТИЖИМА как предмет автоматизированного кейса (директива
координации CH-009 2026-08-10: «кейс на "1 tab" не писать» — при формуле
ОБЩЕГО числа `tabCount` никогда не бывает 1, т.к. Home всегда занимает
слот-0, поэтому единственно-числовая ветка теста была бы либо вакуумной на
текущей сборке, либо провоцировала бы обсуждение отдельной грамматической
ветки, не относящейся к сути дефекта). Два последовательных открытия дают
ожидаемое «2» (число фоновых действий) против фактического «3» (общий
счёт) — оба множественного числа, дефект демонстрируется без обращения к
недостижимой ветке.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вкладок до сценария | 1 (Home) |
| Фоновых открытий | 2 (разные работы) |
| Ожидаемый текст (спека) | «Opened in background (2 tabs)» |
| Фактический текст (сборка, BUG-059) | «Opened in background (3 tabs)» |

## Заметки для автоматизации
- **Блокер? Нет — но два реальных примитива нужно ДОБАВИТЬ, оба рутинные:**
  1. Поллинг отсутствия снекбара по ПРОИЗВОЛЬНОМУ тексту (не только «Tab
     closed») — `swipe_dismiss_snackbar` (`browser_screen.py:414-428`)
     параметризован ТОЛЬКО на `TAB_CLOSED_SNACKBAR_TEXT`, погасить «Opened in
     background» им нельзя (CH-009 test-automator note #3). Решение — НЕ
     свайп, а `wait_until`/`assert_holds_for`-поллинг ОТСУТСТВИЯ
     `by_text_contains("Opened in background")` (тот же класс примитива, что
     уже использует `undo_snackbar_visible`/`tab_limit_dialog_visible` через
     `by_text_contains`) — не требует нового локатора, только новую функцию
     ожидания по существующему приёму.
  2. Явный `driver.update_settings({"waitForIdleTimeout": 100})` ПЕРЕД обоими
     действиями (CH-009 test-automator note #4: дефолтный
     `waitForIdleTimeout` подвесил `find_elements` на 12.9-13.7с во время
     анимации снекбара в разведке — без этой настройки бюджет ожидания
     снекбара/его исчезновения ненадёжен). Рутинная настройка драйвера, не
     блокер.
- **Наблюдаемость негативного/красного Then:** здесь Then читает ВИДИМЫЙ
  UI-текст (не сетевой эффект) — класс AT-BUG-029/калибровки Lead 2026-07-30
  не применим (это не вопрос «увидит ли тест сетевой эффект», а прямое
  чтение текста снекбара, гарантированно рендерящегося при любом значении
  счётчика).
- **Явно НЕ ассертируется (директива координации, измерение CH-009):**
  семантика «второе открытие ЗАМЕНЯЕТ сообщение первого новым счётчиком»
  (заявлена кодом — `LaunchedEffect` ключуется на всём сигнале). Измеренный
  пол цикла двери (координатные тапы) — 3.12-3.50с против жизни снекбара
  3.3-4.8с (CH-009 findings) — таймингово флейково по построению:
  сценарий этого кейса явно ЖДЁТ полного исчезновения первого снекбара
  ПЕРЕД вторым действием именно чтобы НЕ зависеть от гонки замены/показа.
  Проверка самой замены (что произойдёт, если второе действие случится,
  пока первый снекбар ещё жив) — предмет CH-009 (found), не этого кейса;
  повторный скриптованный тест на этот тайминг НЕ заводится.
- **Батарея правил-реакций** (E = «Open in background tab», S = снекбар с
  счётчиком):
  - edge vs level — **н-п**: нет save-пути с предикатом состояния; каждое
    действие — самостоятельный триггер сигнала, семантики «повтор без
    перехода» здесь нет.
  - ретроактивность — **н-п**: нет объектов, размеченных до появления
    функции/настройки; сигнал существует с момента появления самой фичи.
  - off-инвариант — **н-п**: у снекбара нет отдельного тумблера
    включения/выключения; эффект срабатывает при КАЖДОМ фоновом открытии
    безусловно.
  - идемпотентность — **н-п**: повторное открытие ОДНОЙ И ТОЙ ЖЕ карточки
    намеренно создаёт вторую вкладку с тем же URL (дедупликации нет,
    CH-009 Г8) — это осознанное поведение кода, отдельно не ревизуется этим
    кейсом (докладывается как дефект-собрат, не находка).
  - propagation — **н-п**: единственный потребитель сигнала —
    `SnackbarHostState` самого `MainActivity` (Scaffold), нет
    broadcast/других экранов/вкладок, которым нужно об этом узнать.
- Оракул счёта вкладок для Given/промежуточных проверок — persisted-prefs
  (`wait_persisted_tab_count`), не WEBVIEW/TabStrip-иконки (виртуализация,
  тот же класс, что CH-009 инвариант-чек).
