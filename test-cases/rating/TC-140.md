# TC-140 — Граница: без открытой вкладки работы kudos не отправляется вовсе

## Предусловия
- Приложение запущено, режим replay (`listing_basic.mitm`, после фикса
  `bugs/AT-BUG-035.md`).
- Работа W = `LOVED` (900000001) без рейтинга.
- Открыта ОДНА вкладка — листинговая страница с блёрбом W. Никакой work-вкладки
  самой W не открыто (ни активной, ни в фоне) — единственная другая потенциальная
  вкладка в этом сценарии не заводится вовсе, чтобы граница была однозначной
  (не «есть другая работа», а «нет вкладок W»).

## Сценарий (Given-When-Then)

**Given** приложение в replay-режиме; открыта только листинговая вкладка с блёрбом
W (без рейтинга); никакой work-вкладки W не открыто

**When** пользователь Rate-кнопкой W открывает bottom-sheet и выбирает рейтинг
«Kudosed» (LIKE)

**Then** рейтинг сохраняется — бейдж «Kudosed» появляется у блёрба W, работа
отображается на вкладке Kudosed Library (запись в Room и обновление бейджа не
зависят от наличия открытой work-вкладки — это отдельный, безусловный путь)
**And** (наблюдаемое доказательство отсутствия клика, единственно возможное в
момент, когда для клика физически не было вкладки) пользователь ПОСЛЕ этого
открывает work-страницу W через `rating_steps.open_work_page` (навигация IN-PLACE
той же, единственной вкладки — см. заметки, почему НЕ long-press) — на
СВЕЖЕЗАГРУЖЕННОЙ странице узел `#kudo_submit` НЕ несёт
`data-kudo-clicked`: открытие вкладки уже ПОСЛЕ факта не могло получить клик,
который случился бы в момент простановки рейтинга (если бы случился), а сама
загрузка страницы не триггерит клик повторно/отложенно (в коде нет отложенной
доставки kudos-эффекта на будущие вкладки — сверено чтением: `evalJs` вызывается
синхронно внутри `applyRating`, никакого «pending kudos» состояния не заводится)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `framework/data/works.py::LOVED` (900000001), рейтинг не задан |
| Устанавливаемый рейтинг | Kudosed (LIKE) |
| Открытые вкладки в момент When | только листинг (без work-вкладки W) |

## Заметки для автоматизации
- **БЛОКЕР (test_debt) — общий для области:** `bugs/AT-BUG-035.md`; `automated_by`
  пуст. Обоснование общее для всех семи кейсов — см. TC-138
  (`test_cases: [TC-138..TC-144]`).
- **Наблюдаемость негативного Then — специфика этого кейса.** В отличие от
  TC-139/141/142/143, здесь НЕТ вкладки, на которой можно наблюдать «клика не
  было» В МОМЕНТ действия (условие `:857-858` само буквально означает «нет
  вкладки — некуда стрелять evalJs»). Наблюдение вынесено на шаг ПОСЛЕ: открыть
  work-страницу W уже после простановки рейтинга и убедиться, что узел
  `#kudo_submit` свежезагруженной страницы «чист». Это осмысленно отличает
  реальное отсутствие эффекта от гипотетического альтернативного дефекта
  («приложение доставляет kudos-клик отложенно на следующую открытую вкладку
  той же работы») — если бы такой баг существовал, этот шаг его бы поймал.
- **Открытие work-страницы ПОСЛЕ рейтинга — ТОЛЬКО `rating_steps.open_work_page`**
  (навигация IN-PLACE в текущей, единственной вкладке — `BrowserScreen.open_work`
  делает `driver.get()` внутри уже открытого WebView-контекста, новой вкладки не
  создаёт). Вариант `browser_steps.long_press_work_link` (использован TC-138/139)
  здесь НЕДОПУСТИМ (исправлено critic attempt2, S2): long-press открывает ВТОРУЮ
  вкладку в фоне, оставляя листинговую (Tab A, вкладка-0) живой — это втягивает
  кейс в тот же sticky-context блокер B1, что и TC-138/139/142/143, без всякой
  необходимости, поскольку здесь и так нужна только ОДНА вкладка. `open_work_page`
  сохраняет сценарий одновкладочным.
- Чтение `#kudo_submit` — `contexts.in_webview` на единственной открытой вкладке
  (после навигации IN-PLACE она и есть вкладка-0/единственная, риска залипания
  на «не той» вкладке из `AT-BUG-022` здесь нет — в отличие от TC-138/139/142/143,
  где вкладок две; проверка контекста перед чтением всё равно обязательна).
- **Батарея правил-реакций** (место вызова `:856-861`, граница по УСЛОВИЮ
  наличия вкладки — вторая часть предиката, не значение рейтинга):
  - edge vs level — **н-п для ЭТОГО кейса**: граница ортогональна оси
    edge/level (она про наличие вкладки, не про переход/уровень рейтинга),
    закрыта отдельно TC-138 (edge) и TC-139 (level).
  - ретроактивность/off-инвариант — **н-п**, см. TC-138 (нет тумблера).
  - идемпотентность — **н-п**: единичное действие, вкладки для повторного
    клика нет.
  - propagation — **н-п**: нет вкладки-потребителя вовсе — граница СУТЬ
    отсутствие propagation-цели.
