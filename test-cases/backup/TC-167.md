# TC-167 — Restore не-JSON файла: «Restore failed», данные не изменились

## Предусловия
- Приложение запущено, в Room засеяны работы с рейтингами/заметками/тегами
  и 1 filter-профиль (ненулевое исходное состояние — иначе негатив «данные
  не изменились» был бы вакуумным на пустой базе).
- Подготовлен файл `restore_probe_bad.html` — валидный HTML (НЕ JSON),
  например копия скачанной work-страницы; лежит в корне `/sdcard/Download`.
- SAF file picker доступен.

## Сценарий (Given-When-Then)

**Given** в Room есть непустой набор работ с рейтингами/заметками/тегами и
1 filter-профиль; подготовлен не-JSON файл `restore_probe_bad.html`

**When** пользователь выполняет «Restore from backup» и выбирает
`restore_probe_bad.html`

**Then** появляется диалог с заголовком «Restore failed» и текстом,
называющим ошибку парсинга (дословно, по измерению CH-007: «Value
&lt;!DOCTYPE of type java.lang.String cannot be converted to JSONObject»)
**And** состав Room (`read_work_ratings()`/`read_filter_profiles()`) ПОСЛЕ
попытки Restore идентичен состоянию ДО — ни одна работа/профиль не
добавлены, не удалены, не изменены (полусостояния нет: отказ парсинга
происходит ДО применения какой-либо мутации к базе)

**Инвариант:** отказ Restore (любая причина парсинга) — атомарная операция
относительно состояния Room: либо весь импорт применяется по правилам
merge, либо (при ошибке) НЕ применяется НИЧЕГО — не бывает частично
применённого набора работ/профилей. Сиблинг — TC-168 (пустой файл, другой
текст ошибки, тот же инвариант атомарности).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Файл для Restore | `restore_probe_bad.html` (валидный HTML, не JSON) |
| Диалог | «Restore failed» / «Value &lt;!DOCTYPE of type java.lang.String cannot be converted to JSONObject» |
| Состав Room до/после | идентичен |

## Заметки для автоматизации
- Не заблокировано инфраструктурой — SAF file picker + `read_work_ratings`/
  `read_filter_profiles` уже существуют и используются TC-021.
- Файл кладётся в КОРЕНЬ `/sdcard/Download` (не во вложенную SAF-подпапку)
  — тот же приём размещения, что CH-007 бонус-проба («их покрывает и
  pre-session `rm ch007_*`, и штатный `saf_pick_file`»); `rm` файла ДО и
  ПОСЛЕ теста (не оставлять leftover в общем root-хранилище — тот же класс
  осей, что CH-007 Data setup «leftover в общем хранилище»).
- Точный текст диалога — измерен CH-007 (детерминированное сообщение
  `org.json`-исключения для `.html`-контента); если фактический текст на
  момент автоматизации отличается по деталям экранирования, ассерт вправе
  проверять характерную подстроку («cannot be converted to JSONObject»),
  но заголовок «Restore failed» — точное совпадение.
- Сверка Room до/после — снимок ОБОИХ (`read_work_ratings`,
  `read_filter_profiles`) СРАЗУ после закрытия диалога ошибки, сравнение
  списком (не количеством) — чтобы уловить гипотетическую частичную
  мутацию (например, один профиль всё же добавился бы), а не только
  изменение размера.
- Дублирует TC-167/TC-168 friend: НЕ дублирует друг друга — разные входные
  файлы дают разные (детерминированные) тексты ошибки, это и есть предмет
  различия (см. TC-168).
- **Наблюдаемость негатива (правило CLAUDE.md про негативный Then):** этот
  негатив — про ЛОКАЛЬНОЕ состояние Room (не про сетевой/фоновый эффект),
  сверяется ПРЯМЫМ чтением базы, не коротким замыканием стороннего сервиса
  — класс AT-BUG-029/калибровки Lead 2026-07-30 сюда не относится
  (эффект — запись в Room, читается напрямую).
- Батарея правил-реакций — н-п: Restore — прямое явное действие
  пользователя.
