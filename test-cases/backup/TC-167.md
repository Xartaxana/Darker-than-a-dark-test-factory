# TC-167 — Restore битого файла: «Restore failed» с текстом причины, данные не изменились (два варианта входа)

**Поглощает:** TC-168 (П1 spec-p1-dedup v7, docs/tasks/p1-dedup-lead-pass.md Р2:
«restore не-JSON против restore пустого файла. Один механизм (отказ парсинга +
атомарность), различие — вариант битого входа и дословный текст ошибки»).

## Предусловия
- Приложение запущено, в Room засеяны работы с рейтингами/заметками/тегами
  и 1 filter-профиль (ненулевое исходное состояние — иначе негатив «данные
  не изменились» был бы вакуумным на пустой базе). Тот же baseline для обоих
  вариантов ниже.
- Подготовлены ДВА файла в корне `/sdcard/Download`: `restore_probe_bad.html`
  (валидный HTML, НЕ JSON — вариант A) и `restore_probe_empty.json` (0 байт —
  вариант B).
- SAF file picker доступен.

## Сценарий (Given-When-Then)

### Вариант A — не-JSON контент (родной сценарий TC-167)

**Given** в Room есть непустой набор работ с рейтингами/заметками/тегами и
1 filter-профиль; подготовлен не-JSON файл `restore_probe_bad.html`

**When** пользователь выполняет «Restore from backup» и выбирает
`restore_probe_bad.html`

**Then** появляется диалог с заголовком «Restore failed» и текстом,
называющим ошибку парсинга (дословно, по измерению CH-007: «Value
&lt;!DOCTYPE of type java.lang.String cannot be converted to JSONObject»)
**And** состав Room (`read_work_ratings()`/`read_filter_profiles()`) ПОСЛЕ
попытки Restore идентичен состоянию ДО — ни одна работа/профиль не
добавлены, не удалены, не изменены (полусостояния нет: отказ парсинга
происходит ДО применения какой-либо мутации к базе)

### Вариант B — пустой файл (0 байт) — поглощает TC-168

**Given** в Room есть непустой набор работ с рейтингами/заметками/тегами и
1 filter-профиль (тот же baseline, что вариант A); подготовлен ПУСТОЙ файл
`restore_probe_empty.json` (0 байт)

**When** пользователь выполняет «Restore from backup» и выбирает
`restore_probe_empty.json`

**Then** появляется диалог с заголовком «Restore failed» и текстом «End of
input at character 0 of » (дословно, по измерению CH-007) — ОТЛИЧНЫМ от
текста варианта A: пользователь получает РАЗНЫЕ сообщения для «файл не того
формата» и «файл пуст», хотя оба ведут к одному и тому же заголовку ошибки
**And** состав Room (`read_work_ratings()`/`read_filter_profiles()`) ПОСЛЕ
попытки Restore идентичен состоянию ДО (та же атомарность, что вариант A)

**Инвариант:** отказ Restore (любая причина парсинга) — атомарная операция
относительно состояния Room: либо весь импорт применяется по правилам
merge, либо (при ошибке) НЕ применяется НИЧЕГО — не бывает частично
применённого набора работ/профилей. Свойство доказано ДВУМЯ представителями
(варианты A и B) с разными причинами отказа и разными дословными текстами —
если бы регрессия свела оба текста к одному неинформативному сообщению,
именно различие текстов между вариантами это бы поймало.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вариант A: файл | `restore_probe_bad.html` (валидный HTML, не JSON) |
| Вариант A: диалог | «Restore failed» / «Value &lt;!DOCTYPE of type java.lang.String cannot be converted to JSONObject» |
| Вариант B: файл | `restore_probe_empty.json` (0 байт) |
| Вариант B: диалог | «Restore failed» / «End of input at character 0 of » |
| Состав Room до/после (оба варианта) | идентичен |
| Текст ошибки A vs B | отличается (разные причины парсинга) |

## Заметки для автоматизации
- Не заблокировано инфраструктурой — SAF file picker + `read_work_ratings`/
  `read_filter_profiles` уже существуют и используются TC-021.
- Оба файла кладутся в КОРЕНЬ `/sdcard/Download` (не во вложенную
  SAF-подпапку) — тот же приём размещения, что CH-007 бонус-проба; `rm`
  ОБОИХ файлов ДО и ПОСЛЕ теста (не оставлять leftover в общем
  root-хранилище — тот же класс осей, что CH-007 Data setup «leftover в
  общем хранилище»). Файл варианта B — 0 байт, создаётся `adb shell touch`
  (или `echo -n "" >`).
- Точный текст диалога варианта A — измерен CH-007 (детерминированное
  сообщение `org.json`-исключения для `.html`-контента); если фактический
  текст на момент автоматизации отличается по деталям экранирования, ассерт
  вправе проверять характерную подстроку («cannot be converted to
  JSONObject»), но заголовок «Restore failed» — точное совпадение. Текст
  варианта B — тот же принцип строгости (заголовок точный, тело — по
  подстроке при необходимости).
- Сверка Room до/после — снимок ОБОИХ (`read_work_ratings`,
  `read_filter_profiles`) СРАЗУ после закрытия диалога ошибки, сравнение
  списком (не количеством) — чтобы уловить гипотетическую частичную
  мутацию (например, один профиль всё же добавился бы), а не только
  изменение размера. Приём одинаков для обоих вариантов.
- Оба варианта — независимые прогоны ОДНОГО параметризованного теста (тот же
  baseline Room, разные входные файлы) — не journey/чекпойнты (нет мутации
  общего состояния между вариантами, каждый самодостаточен и НЕ зависит от
  результата другого) — секция «Чекпойнты» не нужна.
- **Наблюдаемость негатива (правило CLAUDE.md про негативный Then):** этот
  негатив — про ЛОКАЛЬНОЕ состояние Room (не про сетевой/фоновый эффект),
  сверяется ПРЯМЫМ чтением базы, не коротким замыканием стороннего сервиса
  — класс AT-BUG-029/калибровки Lead 2026-07-30 сюда не относится
  (эффект — запись в Room, читается напрямую). Довод одинаков для обоих
  вариантов.
- Батарея правил-реакций — н-п: Restore — прямое явное действие
  пользователя (оба варианта).
