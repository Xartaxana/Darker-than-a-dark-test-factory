# Живой пуш рейтинга не уводит пользователя со страницы — автопрыжок плотности срабатывает ТОЛЬКО от загрузки, не от живой оценки

# TC-260 — checkPageDensity игнорирует опустошение страницы, вызванное живым пушем рейтинга, но не игнорирует опустошение при загрузке

## Предусловия
- L2 bridge-harness, страница листинга с ЕДИНСТВЕННОЙ видимой работой и
  `li.next` (следующая страница есть).
- `window.__ao3HiddenRatings` — дефолт бриджа `['DISLIKE']`
  (`ao3_bridge.js:46`), менять не нужно.

## Сценарий (Given-When-Then)

**Given** страница листинга с одной работой W (пока без рейтинга), рейтинги
не применены, есть `li.next`

**When** страница симулирует ПЕРВИЧНУЮ загрузку с уже проставленным рейтингом
DISLIKE у W: `window.applyRatings(JSON.stringify({W:'DISLIKE'}))` вызывается
БЕЗ поднятого `window.__ao3LiveRatingPush` (флаг `undefined`/`falsy`,
контрольная ветка — так уже ведёт себя `browse-infinite-scroll`/TC-159 на
устройстве)

**Then** `navigateEffective` вызывается (страница опустошена фильтром,
`_effectiveNextUrl` есть) — наблюдаемо через подмену
`Location.prototype.replace` (см. заметки): счётчик вызовов == 1, аргумент
== `_effectiveNextUrl`

**When** харнесс сбрасывает счётчик подмены и симулирует ЖИВОЙ пуш: сначала
`window.__ao3LiveRatingPush = true` (ровно то, что делает
`broadcastRatingChange` ПЕРЕД вызовом `applyRatings`), затем ТОТ ЖЕ вызов
`window.applyRatings(JSON.stringify({W:'DISLIKE'}))`, опустошающий страницу
ровно так же, как в предыдущем шаге

**Then** `navigateEffective`/`Location.prototype.replace` НЕ вызывается ни
разу — страница не покидается: пользователь остаётся на том же документе с
открытым (в реальном приложении) rating-sheet, скрытость последней работы
объясняется баннером `bridge-hidden-works-banner`, а не автопрыжком

**Инвариант:** `checkPageDensity` реагирует на «страница визуально пуста +
есть next» ОДИНАКОВО по данным, но результат зависит от ИСТОЧНИКА вызова —
загрузка страницы автопрыгивает, живой пуш рейтинга (посреди чтения) — нет;
различающий ассерт для КАЖДОЙ из двух ветвей ПОЛОЖИТЕЛЕН (вызов был / вызова
не было по прямому счётчику подмены, а не по отсутствию побочного эффекта
без контроля) — оба состояния демонстрируются в ОДНОМ прогоне на одной и
той же фикстуре, что исключает вакуумный зелёный «потому что фикстура
изначально пуста».

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Ветка «загрузка» (`__ao3LiveRatingPush` falsy) | `location.replace` вызван 1 раз, url == next |
| Ветка «живой пуш» (`__ao3LiveRatingPush=true`) | `location.replace` НЕ вызван (0 раз) |
| Работа W | одна, становится единственной видимой → DISLIKE → скрыта |

## Заметки для автоматизации
- Инфраструктура принята (N5/N6), блокера нет. `checkPageDensity` НЕ
  layout-гейтирован (не читает `getBoundingClientRect`/`scrollY` вовсе,
  только `li.style.display`+флаги) — B4/B10 не применимы, чистый L2-кандидат
  без пограничных оговорок (в отличие от TC-259/TC-263, где вовлечён
  scroll-триггер).
- **Наблюдение навигации** — монки-патч `Location.prototype.replace`
  ДО вызова `applyRatings`, тот же класс приёма, что подмена
  `Element.prototype.getBoundingClientRect` в
  `test_layout_fail_open_canary.py` (прецедент: подмена прототипного
  метода — не test_debt, ординарная техника харнесса): action
  `{"id":"patch","type":"eval","code":"window.__ao3ReplaceCalls=[];
  Location.prototype.replace=function(u){window.__ao3ReplaceCalls.push(u);};
  'patched'"}` ПЕРВЫМ действием запроса (действия одного `bridge_call`
  выполняются по порядку, `run_bridge.js:207-218`); дальше — обычные
  `applyRatings`/флаг-actions, финально `{"id":"calls","type":"eval",
  "code":"JSON.stringify(window.__ao3ReplaceCalls)"}`.
- Оба состояния (загрузка / живой пуш) — ОДИН `bridge_call`, счётчик
  `__ao3ReplaceCalls` явно обнуляется между веткой 1 и веткой 2 отдельным
  action'ом (`window.__ao3ReplaceCalls=[]`) — иначе Then второй ветки
  («0 раз») был бы неотличим от «уже был 1 вызов из первой ветки, второй
  не добавился по факту, а не по гейту» — важно для честности негатива
  (F-34/наблюдаемость негативного Then, CLAUDE.md).
- `_didAutoAdvance` — внутренний флаг, взводится `true` ПОСЛЕ первого
  успешного автопрыжка и блокирует повторный (`checkPageDensity:674`
  `if (_didAutoAdvance) return;`) — если тест собирается вызывать
  `applyRatings` дважды с реальным опустошением в ОБЕИХ ветках на одной и
  той же jsdom-сессии, вторая (живая) ветка должна опустошать ДРУГУЮ,
  ранее не опустошённую работу/страницу, либо вызывающий должен явно
  сбросить `_didAutoAdvance` — иначе «не вызвано» во второй ветке будет
  ложным зелёным (сработал не гейт `__ao3LiveRatingPush`, а
  `_didAutoAdvance`). Надёжный вариант: два РАЗНЫХ `bridge_call` (два
  свежих jsdom-документа) — по одному на ветку, а не два действия в одном
  документе; тогда `_didAutoAdvance` каждый раз начинает с `false`, и
  сравнение веток идёт по счётчику `Location.prototype.replace`
  МЕЖДУ вызовами, а не внутри одного.
- Дистинкция от `browse-infinite-scroll`/TC-159 (device, R-11): TC-159
  проверяет тот же факт «загрузка опустошённой фильтром страницы
  автопрыгивает» НА УСТРОЙСТВЕ сквозным путём; этот кейс — тот же факт
  device-free (контрольная ветка, дешёвая) ПЛЮС контрастную ветку
  (живой пуш), которую TC-159 явно выводит за свои границы («этот кейс их
  не переоткрывает и не ассертит», `TC-159.md:54-59`). Дублирования
  Given/Then нет — разные слои, разный набор ассертов (P1 spec-p1-dedup:
  слой сначала, дедуп внутри слоя — TC-159 остаётся L3/L4, этот кейс L2,
  граница слоя не склеивается).
- Полный сквозной путь «тап по рейтингу в UI → страница реально не
  уехала» (упомянутый в §9 как «L3 — для сквозного пути») этим кейсом НЕ
  закрывается — он проверяет именно предикат-контракт бриджа, что и
  является TITLE записи реестра `bridge-live-rating-push-no-auto-advance`
  целиком (никакого «/»-дробления в title нет). Устройственный сквозной
  путь — естественный follow-up, не обязателен для закрытия ЭТОЙ записи
  реестра; названо в отчёте test-designer, отдельной needs-design-метки
  не заводится (не в мандате test-designer заводить новые записи реестра).
