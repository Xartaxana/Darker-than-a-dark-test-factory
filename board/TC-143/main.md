# TC-143 — Снятие рейтинга Kudosed повторным тапом через листинг не кликает kudos

## Предусловия
- Приложение запущено, режим replay (`listing_basic.mitm`, после фикса
  `bugs/AT-BUG-035.md`).
- Работа W = `LOVED` (900000001) засеяна напрямую в Room с рейтингом LIKE
  (Kudosed), без личных тегов.
- Открыты ДВЕ вкладки: Tab A — листинг с блёрбом W (бейдж Kudosed); Tab B —
  work-страница W, открытая в фон (тот же приём, что TC-138/139/142).
- На Tab B узел `#kudo_submit` без `data-kudo-clicked` (baseline).

## Сценарий (Given-When-Then)

**Given** работа W имеет рейтинг Kudosed (LIKE); открыты Tab A (листинг, бейдж
Kudosed) и Tab B (work-страница W, `#kudo_submit` без `data-kudo-clicked`)

**When** на Tab A пользователь Rate-кнопкой W открывает bottom-sheet и повторно
нажимает уже выбранную кнопку «Kudosed» (deselect — `rating-deselect-on-tap`,
общий toggle-механизм `RatingOverlay.kt`, тот же приём, что TC-117 для панели, но
здесь через листинговый путь `applyRating`)

**Then** рейтинг снят — работа W исчезает из вкладки Kudosed экрана Library (при
отсутствии комментария/тегов/файла строка удаляется целиком)
**And** ПОСЛЕ этого Tab A закрывается (`browser_steps.swipe_close_tab(driver,
position=0)`) — идиома reduce-to-one (тот же приём, что TC-138/139/142,
обоснование `browser_screen.py:319-329`, см. заметки): Tab B остаётся
единственной живой WebView, chromedriver переподключается к ней. На Tab B узел
`#kudo_submit` НЕ получает `data-kudo-clicked` — ветка `rating == null`
(`:803-838`) завершается `return@launch` (:837) ДО того, как код доходит до
строки `:856` — вызов evalJs с kudos структурно недостижим для этого сохранения

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `W.LOVED`, засеяна напрямую с rating=LIKE → null (deselect) |
| Открытые вкладки | Tab A (листинг), Tab B (work-страница W) |
