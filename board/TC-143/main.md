# TC-143 — Снятие рейтинга Kudosed повторным тапом через листинг не кликает kudos

## Предусловия
- Приложение запущено, режим replay (`listing_basic.mitm`, после фикса
  `bugs/AT-BUG-035.md`).
- Работа W = `LOVED` (900000001) засеяна напрямую в Room с рейтингом LIKE
  (Kudosed), без личных тегов.
- Открыты ДВЕ вкладки: Tab A — листинг с блёрбом W (бейдж Kudosed); Tab B —
  work-страница W, открытая в фон (тот же приём, что TC-138/139/142).
- На Tab B узел `#kudo_submit` без `data-kudo-clicked` (baseline).

## Сценарий (Given-When-Then)

**Given** работа W имеет рейтинг Kudosed (LIKE); открыты Tab A (листинг, бейдж
Kudosed) и Tab B (work-страница W, `#kudo_submit` без `data-kudo-clicked`)

**When** на Tab A пользователь Rate-кнопкой W открывает bottom-sheet и повторно
нажимает уже выбранную кнопку «Kudosed» (deselect — `rating-deselect-on-tap`,
общий toggle-механизм `RatingOverlay.kt`, тот же приём, что TC-117 для панели, но
здесь через листинговый путь `applyRating`)

**Then** рейтинг снят — работа W исчезает из вкладки Kudosed экрана Library (при
отсутствии комментария/тегов/файла строка удаляется целиком)
**And** ПОСЛЕ этого Tab A закрывается (`browser_steps.swipe_close_tab(driver,
position=0)`) — идиома reduce-to-one (тот же приём, что TC-138/139/142,
обоснование `browser_screen.py:319-329`, см. заметки): Tab B остаётся
единственной живой WebView, chromedriver переподключается к ней. На Tab B узел
`#kudo_submit` НЕ получает `data-kudo-clicked` — ветка `rating == null`
(`:803-838`) завершается `return@launch` (:837) ДО того, как код доходит до
строки `:856` — вызов evalJs с kudos структурно недостижим для этого сохранения

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `W.LOVED`, засеяна напрямую с rating=LIKE → null (deselect) |
| Открытые вкладки | Tab A (листинг), Tab B (work-страница W) |

## Заметки для автоматизации
- **БЛОКЕР (test_debt) — общий для области:** `bugs/AT-BUG-035.md`; `automated_by`
  пуст. Обоснование общее — см. TC-138 (семь кейсов области, один тикет
  `test_cases: [TC-138..TC-144]`).
- Деселект через листинговый bottom-sheet — ОДИН вызов
  `rating_steps.rate_via_listing_overlay(driver, "LIKE")` по уже выбранной кнопке
  (тот же класс приёма, что `rate_current_work` для панели в TC-117 — тап по уже
  выбранному рейтингу снимает его). ВТОРОЙ тап здесь недопустим (переустановил
  бы LIKE на уже пустой строке через другую ветку — искажает предмет кейса).
- Механика чтения Tab B — идиома reduce-to-one, тот же метод, что TC-138/139/142
  (`browser_screen.py:319-329`, close Tab A → `contexts.in_webview` на Tab B) —
  НЕ «активировать вкладку в UI перед switch_to.context» (исправлено critic
  attempt2, см. подробности TC-138).
- **Наблюдаемость негативного Then, вопреки первому впечатлению «ветка
  структурно не содержит вызова — проверять нечего»** (тот же класс обоснования,
  что закрыт для авто-скачивания TC-117, 2026-07-29/30): Then защищает от
  гипотетического бага (например, деселект по ошибке не доходит до `return@launch`
  и продолжает исполнение в код ниже, который бы совпал с уже-Kudosed веткой).
  Узел `#kudo_submit` инструментирован и присутствует на открытой Tab B — если бы
  такой баг существовал, тест бы его поймал; негатив не вакуумный.
- Отличать от TC-142 (смена на ДРУГОЙ рейтинг, не null) — разные код-ветки
  `applyRating` (`rating != null` vs `rating == null`), оба входа design-пункта
  §9 покрыты по отдельности (один сценарий — один кейс), тот же принцип, что
  развёл TC-116/TC-117 для авто-скачивания.
- **Батарея правил-реакций** (место вызова — ветка `rating == null`, :803-838,
  листинговый путь):
  - edge vs level — **н-п для ЭТОГО кейса**: здесь нет предиката LIKE/SAVE вовсе
    (ветка `return@launch` раньше) — ортогональная ось, закрытая парой
    TC-138/TC-139.
  - ретроактивность/off-инвариант — **н-п**, см. TC-138 (нет тумблера).
  - идемпотентность — **н-п**: единичное действие.
  - propagation — **н-п**, см. TC-138.
