# TC-205 — Снятие активного фильтр-профиля фоновой загрузкой (Library) сопровождается уведомлением (red lock BUG-068)

## Предусловия
- Приложение запущено, replay-режим (`listing_basic.mitm`).
- Фикстура `filter_profile_applied_seeded` — профиль «My saved search» засеян
  (`app_steps.seed_filter_profiles`, `conftest.py:580-596`).
- В Room засеяна работа `W.LOVED` (`ao3_id=900000001`) на РЕЙТИНГОВОЙ вкладке
  Library, НЕ Files (`app_steps.seed_library([(W.LOVED, "SAVE")])`, тот же
  приём, что TC-173) — нужна видимая карточка для двери фонового открытия.
- На Browse открыт `LISTING_BASIC_URL`, профиль применён из FilterPanel
  (`browser_steps.select_filter_option`, путь TC-041/TC-182) —
  `active_filter_profile_id` в prefs `ao3_settings` установлен, панель
  показывает «My saved search» (`assert_active_filter_shown` подтверждает).
- В Settings тумблер «Auto-apply on navigation» переключён в **OFF** (заход в
  Settings — с Browse, ловушка `saf_steps`).
- Пользователь переходит на экран **Library** (Browse больше не виден,
  вкладка с активным профилем остаётся живой в фоне).

## Сценарий (Given-When-Then)

**Given** профиль «My saved search» активен, тумблер Auto-apply — OFF,
пользователь на экране Library, вкладка Browse с профилем — в фоне

**When** пользователь долгим нажатием по видимой карточке работы открывает
overlay и тапает «Open in background tab»
(`library_steps.open_in_background_via_overlay`) — фоновая вкладка получает
WebView и грузится, пока экран остаётся Library

**Then** активный фильтр-профиль СНИМАЕТСЯ — опрос prefs `ao3_settings`
(интервал ~0.5с, бюджет 3-4с, `adb.run_as_file_or_raise`, с контролем
валидности снимка — ключи `auto_apply_filter`/`open_tabs_urls` присутствуют в
каждом прочтении) фиксирует исчезновение `active_filter_profile_id` —
подтверждённый факт (`bugs/BUG-068.md`, 0/8 отклонений на 2х независимых
прогонах), НЕ предмет спора этого кейса
**And** экран остаётся Library — переход не произошёл, пользователь НЕ видит
браузер/панель фильтра в момент события
**And** в течение ВСЕГО жизненного цикла снекбара фонового открытия
пользователю показывается сообщение, называющее фильтр/профиль
(регистронезависимое совпадение «filter|profile|saved search» в тексте
снекбара либо любого нового узла snackbar-host'а) — ЭТО и есть ассерт,
ради которого существует кейс; на сборке 6f884d97 он ПАДАЕТ (BUG-068)

**Ожидаемое (спецификация, R-16 «есть сообщение — норма», `docs/01-test-strategy.md`
§10 (р)):** снятие состояния, невидимого пользователю в момент изменения,
сопровождается заметным сигналом — снекбар/уведомление, упоминающее фильтр
или профиль, появляется в течение того же окна, что и штатный снекбар
фонового открытия.

**ОЖИДАЕМОЕ ПАДЕНИЕ на текущей сборке** (прецедент TC-139/TC-176: кейс
пишется по ожидаемому поведению спецификации, а не по факту сборки) — по
коду (`BrowserViewModel.kt:501-504`) сброс НЕ сопровождается никаким
сигналом: единственный видимый артефакт — снекбар фонового открытия «Opened
in background (N tabs)» (проверка ОБЯЗАНА покрывать полный бюджет его жизни,
не один кадр — источники BUG-068/CH-010 документируют опрос prefs, не
полнобюджетный опрос снекбара; это требование к будущему тесту, не
установленный факт), который НЕ упоминает фильтр/профиль вовсе, и никакое
ДРУГОЕ сообщение не
появляется. Красный результат триажится как **APP_BUG/BUG-068**, не как
расхождение теста со спекой; ссылка: `bugs/BUG-068.md`.

**Инвариант:** при OFF и активном профиле СБРОС `activeFilterId` происходит
на ЛЮБОЙ завершённой загрузке ЛЮБОЙ вкладки — включая фоновые/чужие,
независимо от того, какой экран видит пользователь в момент события; на
текущей сборке НИ ОДИН из этих путей (кроме событий, для которых существует
собственный несвязанный снекбар) не даёт пользователю никакого сигнала о
смене состояния фильтра — свойство держится для всего класса «загрузка
любой вкладки», не только для двери фонового открытия из этого сценария.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Тумблер | OFF |
| Активный профиль до | «My saved search» |
| Активный профиль после (факт) | нет (снят, опрос prefs) |
| Экран пользователя в момент события | Library (не Browse) |
| Ожидаемое сообщение (спека) | появляется |
| Фактическое сообщение (сборка, BUG-068) | отсутствует |

## Заметки для автоматизации
- Инфраструктура ГОТОВА, часть примитивов уже существует (не добавлять заново):
  1. Тумблер Auto-apply — `settings_steps.set_auto_apply_filter_toggle`
     (`:85`) и `assert_auto_apply_filter_enabled` (`:95`), XPath уже
     реализован в `SettingsScreen.set_auto_apply_filter`/
     `is_auto_apply_filter_checked` (`settings_screen.py:216-232`) — новый
     примитив НЕ нужен.
  2. Опрос ОТСУТСТВИЯ `active_filter_profile_id` в prefs — новый
     однострочный wrapper по ФОРМЕ образца `assert_theme_mode_pref`
     (`settings_steps.py:467-470`), но НЕ по способу чтения: тот образец
     читает через `adb.run_as("cat …")` — запрещённая форма (класс
     AT-BUG-044/045/055); использовать `run_as_file_or_raise` (как и
     сформулировано ниже), CH-010 инвариант-чек (2-4 чтения с интервалом
     ~0.5с, контроль валидности снимка по ключам
     `auto_apply_filter`/`open_tabs_urls`) — тот же приём, что TC-184
     планировал для позитивной стороны того же ключа.
  3. Ассерт — В НАПРАВЛЕНИИ СПЕКИ (появление, не отсутствие). Готовые
     примитивы уже есть: `BrowserScreen.opened_in_background_snackbar_text`
     (`browser_screen.py:441`) читает ДОСЛОВНЫЙ текст снекбара,
     `browser_steps.wait_opened_in_background_snackbar_shown_then_gone`
     (`:2204`) сначала доказывает, что снекбар вообще появился (иначе
     ожидание тривиально истинно — см. его докстринг), и держит окно до
     полного исчезновения. Совпадение обязано быть РЕГИСТРОНЕЗАВИСИМЫМ:
     `new UiSelector().textMatches("(?i).*(filter|profile|saved search).*")`,
     НЕ `by_text_contains` — он `UiSelector().textContains`
     (`base_screen.py:47-49`), регистрозависим и пропустит «Filter cleared».
     Поллинг ОТСУТСТВИЯ — это описание ТЕКУЩЕГО факта для триажа, НЕ ассерт
     кейса.
- **Наблюдаемость негативного Then:** сообщение — UI-артефакт (снекбар/
  нотиф), не сетевой эффект — класс AT-BUG-029 не применим. Достижимость
  различающей развилки (кодификация Lead 2026-08-14, класс TC-204): примитив
  поллинга читает ЛЮБОЙ НОВЫЙ текст snackbar-host'а, не привязан заранее к
  конкретной строке — если бы фикс добавил реальный снекбар/бейдж, поллинг
  бы его поймал; достижимость доказана тем, что snackbar-host в ЭТОМ ЖЕ
  сценарии УЖЕ производит наблюдаемый снекбар («Opened in background») —
  реальный, не гипотетический механизм рендера, просто без нужного текста.
- Не путать с **TC-184** (та же ветка кода `onPageLoaded:501-504`, но через
  ОБЫЧНУЮ навигацию, которую пользователь делает сам и видит сразу — там
  предмет кейса не про сообщение, а про URL/факт снятия). Здесь — ЧУЖАЯ
  фоновая загрузка, пользователь смотрит на Library, предмет — ИМЕННО
  отсутствие сигнала.
- Не путать с **TC-176** (тот же снекбар фонового открытия, но предмет там —
  корректность СЧЁТЧИКА вкладок, не фильтр-профиль; здесь предмет —
  отсутствие упоминания фильтра в этом снекбаре/где-либо ещё).
- **Гейт red_lock/automated_by (rework 2026-08-14, attempt 2):** `red_lock`
  оставлен пустым на этапе дизайна — его ставит ТОЛЬКО тот, кто пишет
  реальный красный автотест и подтверждает его красноту прогоном
  (test-automator, с Bash), не test-designer (нет Bash, не может
  подтвердить красноту). red_lock ставится ВМЕСТЕ с `automated_by`, когда
  тест написан и подтверждён красным — см. прецедент TC-139/BUG-015 и
  TC-176/BUG-059. Описание ожидаемо-красного поведения (заголовок от
  спеки, Then читает текущий дефект BUG-068) остаётся в теле кейса — это
  законный Review-кейс без замка.
- Вариант (б)/(в)/(г) `bugs/BUG-068.md` (передняя дверь `onOpenFile`,
  обратный порядок, смена темы) — тот же корень, НЕ дублируются отдельными
  кейсами (баг сам их объединяет одним тикетом, «классовая полнота» в его
  «Обсуждение»); этот кейс — регрессионный замок на вариант (а), достаточный
  представитель класса для конвейера.

## Заметки: батарея правил-реакций (E = завершённая загрузка ЛЮБОЙ вкладки,
C = OFF && activeFilterId != null, S = `setActiveFilter(null)`)
- **edge vs level** — это НОВОЕ МЕСТО ВЫЗОВА того же level-триггера, что уже
  закрыт TC-184 (там — видимая пользовательская навигация); здесь — фоновая/
  чужая загрузка. Level-семантика (эффект срабатывает на КАЖДОЙ загрузке, не
  только «первой») не переисследуется отдельно — это TC-184.
- **ретроактивность** — н-п: активный профиль — не per-объектная метка на
  данные, созданные до включения тумблера.
- **off-инвариант** — ИМЕННО предмет этого кейса: явный Then про ОТСУТСТВИЕ
  сообщения при OFF на этом конкретном месте вызова.
- **идемпотентность** — н-п отдельным сценарием: одно фоновое открытие,
  повторные открытия — предмет TC-176 (там же и амплификация CH-010 Г7).
- **propagation** — н-п в узком смысле broadcast (класс BUG-012 не
  применим): единственный потребитель сигнала — сам пользователь на текущем
  экране, других вкладок/окон, которым нужно узнать о сбросе, нет.
