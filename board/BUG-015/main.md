# BUG-015 — Авто-клик kudos на AO3 срабатывает ретроактивно при изменении тега

## Окружение
- Версия: 1.10 (versionCode 11), живое приложение
- Устройство: не указано (репродукция на живом приложении)
- Сборка: сборка приложения
- **Примечание:** баг обнаружен анализом кода (`BrowserViewModel.kt`), живой репро — в очереди фабрики (needs-design область §9, docs/01). Этот отчёт фиксирует дефект на уровне кода с гипотезой воспроизведения для live-верификации конвейером.

## Шаги воспроизведения (Given-When-Then, гипотеза)

**Given**
1. Приложение установлено и запущено
2. На странице работы установлена отметка Like (LIKE рейтинг) или Favorite (SAVE рейтинг)
3. На стороне AO3 автоматически был выполнен клик по кнопке kudos (уменьшение счётчика хотя бы раз)

**When**
1. Пользователь возвращается на ту же работу (или открывает её в overlay из листинга)
2. Пользователь добавляет новый тег или правит существующий тег (сохраняет через рейтинг-overlay или панель work-страницы)

**Then (ожидалось)**
- При правке тега на уже Like/Favorite-отмеченной работе: сервер AO3 получит текстовый запрос на изменение тега, но **НЕ будет нового запроса на клик kudos** (рейтинг не менялся — это правка метаданных, не простановка нового рейтинга)
- Счётчик kudos на AO3 остаётся неизменным (или меняется на основе действительной логики, если серверная дедупликация это дозволяет)

**Actual (фактически, по коду)**
- При правке тега на работе с УЖЕ установленным рейтингом LIKE или SAVE приложение **повторно отправляет клик на kudo_submit** на живом archiveofourown.org, хотя пользователь не просил это действие
- Побочный эффект: незапрошенная сетевая операция на стороннем сайте от имени пользователя при текстовой операции (правка тега)

## Частота
Гипотетически всегда при условиях репро (требуется live-верификация). По коду дефект присутствует во всех трёх путях сохранения рейтинга.

## Артефакты
- Код-анализ: `BrowserViewModel.kt` (файл `app/src/main/java/com/example/ao3_wrapper/ui/browser/BrowserViewModel.kt`)
- Связанный баг (сиблинг, аналогичный класс дефекта): `BUG-014.md`

## Анализ (баг приложения)

Корень лежит в коде авто-клика kudos при рейтингах типа LIKE/SAVE. Проблема: класс бага — **edge-vs-level** (переход vs предикат).

### Точки в коде (три пути)

Поиск по `rating == Rating.LIKE || rating == Rating.SAVE` показывает три вызова:

1. **`applyRating` (~:856–860)** — клик kudos при LIKE/SAVE:
```kotlin
if (rating == Rating.LIKE || rating == Rating.SAVE) {
    evalJs(..., "var b=document.getElementById('kudo_submit');if(b)b.click();")
}
```

2. **`onRateWorkRequested` (~:1053–1055)** — тот же предикат при рейтинге из листинга:
```kotlin
if (rating == Rating.LIKE || rating == Rating.SAVE) {
    evalJs(..., "var b=document.getElementById('kudo_submit');if(b)b.click();")
}
```

3. **`savePanelRating` (~:756–758)** — правка тега через панель work-страницы:
```kotlin
// НЕ кликает kudos вообще — АСИММЕТРИЯ!
// Только скачивание (autoDownloadSaved), но не kudos
```

### Семантика дефекта

Ожидаемое поведение: авто-клик kudos должен срабатывать только при **переходе** "рейтинг становится LIKE/SAVE при включённом приложении", а не при **проверке** "рейтинг==LIKE|SAVE && приложение==On" на каждом сохранении метаданных.

Текущий код срабатывает при любом обновлении записи БД, где rating уже LIKE/SAVE — это захватывает и правку тега, и правку комментария, хотя эти операции не меняют рейтинг и не должны инициировать клик на стороннем сайте.

### Асимметрия путей

- **`applyRating` (листинг, рейтинг-overlay)**: кликает kudos на LIKE|SAVE
- **`onRateWorkRequested` (листинг, другой путь)**: кликает kudos на LIKE|SAVE
- **`savePanelRating` (панель work-страницы)**: **НЕ кликает kudos вообще** (только скачивание при SAVE)

Это создаёт класс вторичного дефекта: **inconsistency** (противоречивое поведение при едином действии пользователя — правке тега).

### Почему severity: major

1. **Незапрошенное действие на стороннем сайте** — пользователь добавляет тег (локальная текстовая операция), а приложение отправляет клик на живой archiveofourown.org по `kudo_submit` без явного запроса. Это нарушает принцип наименьшего удивления (principle of least surprise).

2. **Побочные эффекты** — клик может изменить счётчик kudos, если серверная дедупликация AO3 не срабатывает в этом конкретном сценарии (timing, сессия пользователя, состояние БД сайта). **Оговорка честности:** AO3 может иметь механизм серверной дедупликации для повторных kudos от одного IP/пользователя, но незапрошенный запрос остаётся фактом независимо от того, отклонен ли он на сервере.

3. **Эффект масштаба** — любая правка тега/комментария/заметки на Liked/Saved-работе вызывает клик, что может неожиданно потратить трафик при использовании мобильной сети.

4. **Асимметрия путей усложняет отладку** — пользователь может заметить, что клик kudos происходит при правке через листинг, но не через панель work-страницы, что выглядит как баг UX.
