# TC-172 — Restore: скип по id и релинк файла сканом — независимые эффекты одного вызова

## Предусловия
- Приложение запущено, Library пуста (`clean_state`).
- «Auto-download favorite works» включён в Settings.
- Открыта страница работы W.LOVED (`ao3_id=900000001`) через replay-запись
  `rb.WORK_WITH_DOWNLOAD_FILENAME` (та же запись, что TC-032/033/112/114/115).
- SAF file picker доступен.

## Сценарий (Given-When-Then)

**Given** Library пуста, Auto-download включён, страница работы W.LOVED
открыта через replay

**When** пользователь через панель рейтинга ставит W.LOVED рейтинг «Loved»
(SAVE) — авто-скачивание запускается, карточка в Library (FAVORITE)
получает open-иконку (файл скачан, имя построено приложением из title)
**And** в Settings выполняет «Back up data», выбирает файл F через SAF —
F содержит W.LOVED с рейтингом SAVE (без `downloadPath`, экспорт несёт
только `downloadFile`-имя, не путь)
**And** выполняет «Clear all ratings» и подтверждает — строка W.LOVED
удаляется из `work_ratings`, САМ скачанный файл на диске НЕ удаляется
(`clearAllRatings` трогает только таблицу рейтингов)
**And** возвращается на страницу работы W.LOVED (replay) и ставит рейтинг
«Read» (НЕ Loved — READ не запускает авто-скачивание) — создаётся НОВАЯ
строка с тем же ao3Id, `downloadPath=null` (ссылки на файл ещё нет)
**And** в Settings выполняет «Restore from backup», выбирает ТОТ ЖЕ файл F

**Then** появляется диалог «Backup restored» с ТОЧНЫМ текстом «Restored 0
works, 0 filters (1 works already existed). Also relinked 1 and added 0
downloaded file(s).» — работа СКИПНУТА как уже существующая (0 imported,
1 already existed), И в том же диалоге релинкнут 1 файл — оба эффекта
одного вызова Restore, не два отдельных прохода
**And** после закрытия диалога прямое чтение Room показывает: рейтинг
W.LOVED остаётся **«Read»** (ЛОКАЛЬНАЯ версия, НЕ откатилась на бэкапное
«Loved» — скип отбрасывает бэкапную версию целиком, как в TC-171), но
`downloadPath` теперь ЗАПОЛНЕН (файл релинкован сканом НЕСМОТРЯ на скип)
**And** карточка W.LOVED видна на вкладке READ (не FAVORITE) с
open-иконкой — скип и релинк применились к ОДНОЙ и той же строке
одновременно, без конфликта

**Инвариант:** решение «импортировать/скипнуть строку по `ao3Id`»
(`existingIds`, снимок Room) и решение «релинковать файл по имени»
(`scanForOrphanedDownloads`, скан каталога) вычисляются НЕЗАВИСИМО друг от
друга над РАЗНЫМИ источниками данных (таблица `work_ratings` vs. файловая
система) в рамках ОДНОГО вызова `importFromUri` — скип строки НЕ
блокирует релинк её файла и не зависит от того, была ли строка
импортирована (ветка А, TC-039) или скипнута (ветка Б, этот кейс); оба
случая дают one и тот же объединённый диалог с формулой
`Restored X, Y filters (Z already existed). Also relinked R and added A
downloaded file(s).`, где X/Z и R/A считаются по независимым правилам.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| W.LOVED рейтинг в бэкапе | SAVE (Loved) |
| W.LOVED рейтинг ПОСЛЕ локального пересоздания | READ |
| W.LOVED рейтинг ПОСЛЕ Restore | READ (== локальный, не бэкапный SAVE) |
| `downloadPath` ПОСЛЕ Restore | заполнен (релинкован сканом) |
| Диалог | «Restored 0 works, 0 filters (1 works already existed). Also relinked 1 and added 0 downloaded file(s).» |
| Вкладка карточки после | READ, с open-иконкой |

## Заметки для автоматизации
- Инфраструктура НЕ новая: авто-скачивание через `enable_auto_download` +
  `rating_steps.rate_current_work` — TC-032 (Automated); SAF backup/clear/
  restore — TC-021 (Automated); relink-диалог и его точный текст —
  TC-039 (Automated, тот же формат строки, здесь дополненный веткой
  скипа); повторная простановка рейтинга той же работы после Clear all —
  тот же примитив `rating_steps.open_work_page`/`rate_current_work`,
  вызванный дважды в одном тесте (реплей-запись `WORK_WITH_DOWNLOAD_
  FILENAME`, судя по докстрингу test_downloads.py, несёт транзакции для
  ОДНОГО открытия work-страницы + скачивания; повторное открытие той же
  страницы ВТОРОЙ раз в одном тесте нужно сверить с записью — если replay
  не покрывает повторный запрос той же work-страницы, требуется либо
  повторное использование того же кассетного ответа (mitm replay обычно
  отдаёт запись per URL многократно, не одноразово — сверить поведением
  `conftest.py`/`mitm.py`), либо новая мини-запись; это ТЕХНИЧЕСКАЯ
  проверка реализации, не блокер дизайна — сценарий воспроизводим
  логически, конкретный replay-механизм решает test-automator).
- Сверка после Restore — прямым чтением Room
  (`seed_db.read_work_ratings_full()` — нужен полный набор полей, включая
  `downloadPath`, которого нет в `read_work_ratings()`, см.
  `seed_db.py:319` и докстринг про AT-BUG-046) + карточка Library (вкладка
  READ, open-иконка) как второй, UI-уровневый оракул того же факта — тот
  же двухуровневый приём наблюдения релинка, что TC-039
  («оракул релинка — КОСВЕННЫЙ», CH-007 таблица).
- Точный текст диалога — формула по коду (`SettingsScreen.kt:1186-1191`),
  не литерал «на глаз»: `Restored ${imported} works, ${importedProfiles}
  filters` + (если skipped>0) ` (${skipped} works already existed).` иначе
  `.` + (если relinked>0 || added>0) ` Also relinked ${relinked} and added
  ${added} downloaded file(s).` — при 0 работ/0 фильтров/1 скип/1 релинк/0
  добавлено ЭТА формула детерминированно даёт указанную строку.
- Дельта к TC-039 (там строка Restore ИМПОРТИРУЕТСЯ — ветка А, Library
  пуста весь сценарий) и TC-171 (там скип без каких-либо скачанных файлов)
  — этот кейс — ветка Б чартера CH-007 Г3, ранее не покрытая НИ ОДНИМ
  кейсом (находка 4, вердикт `ok`, оставлена кандидатом в followup_tc).
- **Батарея правил-реакций** — рассмотрена: off-invariant для «нет
  совпадающего файла ⇒ нет релинка» уже покрыт КОСВЕННО каждым backup/
  restore кейсом без скачанных файлов (TC-021/165-168/171 — везде «Also
  relinked» отсутствует в диалоге, так как `relinkedDownloads=0 &&
  addedDownloads=0`), отдельного кейса не требует; edge vs level и
  идемпотентность — н-п, Restore/рейтинг — явные прямые действия
  пользователя без скрытого альтернативного save-пути; propagation — н-п,
  единственный потребитель релинка — Room-запись, читаемая тем же экраном
  Library, broadcast/другие вкладки не участвуют.
