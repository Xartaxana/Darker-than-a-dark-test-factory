# TC-154 — Удаление скачанного файла подметает оба места загрузок; последующий скан не воскрешает работу (регресс-замок BUG-047)

## Предусловия
- Работа W (`ao3_id 900000001`) в Room с рейтингом SAVE, `downloadPath`
  указывает на файл `ao3_A_900000001.html` в папке загрузок.
- В той же папке лежит ВТОРОЙ файл того же `ao3Id` — `ao3_ЛОКАЛЬНЫЙ_
  900000001.html` (сирота, не в `downloadPath`).
- Открыт экран Library, вкладка FAVORITE показывает карточку W с иконкой
  «Open downloaded».

## Сценарий (Given-When-Then)

**Given** работа W скачана (`downloadPath` = `ao3_A_900000001.html`), на
диске лежит ещё один файл того же `ao3Id` (`ao3_ЛОКАЛЬНЫЙ_900000001.html`,
не связан с Room)

**When** пользователь long-press по карточке W → «Delete downloaded file» →
затем Settings → «Scan for downloads»

**Then** файл `ao3_A_900000001.html` удалён с диска, `downloadPath` работы W
обнулён, карточка W показывает Download-иконку (не Open) — это ожидаемая,
незатронутая фиксом часть (путь TC-035)
**And** ВТОРОЙ файл (`ao3_ЛОКАЛЬНЫЙ_900000001.html`, сирота того же `ao3Id`)
ТОЖЕ удалён с диска — `deleteDownload` подметает ВСЕ файлы с хвостом
`_<ao3Id>.html` в ОБОИХ местах загрузок (SAF custom-папка и дефолтная
`ao3_downloads`), не только явно указанный в `downloadPath`
(`DownloadRepository.kt:146-169`); на диске не остаётся ни одного файла
этого `ao3Id`
**And** ПОСЛЕ ручного скана диалог гласит `«No .html files found in the
download folder.»` (файлов этого `ao3Id` для релинка не осталось —
`totalFound == 0`), `downloadPath` работы W остаётся пустым
**And** карточка W ОСТАЁТСЯ на Download-иконке после скана, не переключается
обратно на «Open downloaded» — явно удалённая пользователем связь
«строка↔файл» не восстанавливается сканом

## Фактическое поведение после фикса (сильнее исходного design-ожидания)
Дизайн-этап кейса ожидал более слабый инвариант — «сирота остаётся на диске,
но скан не должен её привязать». Фактический фикс (`a968f6b`) сильнее: он
удаляет ОБА файла того же `ao3Id` в момент «Delete downloaded file», поэтому
сироте физически неоткуда взяться к моменту скана. Оба наблюдения совместимы
(«явное удаление не отменяется сканом» выполняется даже полнее буквального
текста дизайн-этапа) — Then выше отражает фактическую, более сильную,
проверку (см. `bugs/BUG-047.md` «Верификация»/«Обсуждение», запись
`fix-verifier @ 2026-08-11T16:33:00Z`, где эта дельта к дизайн-тексту названа
явно).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `ao3_id 900000001`, rating=SAVE |
| Файл в downloadPath | `ao3_A_900000001.html` |
| Файл-сирота (до удаления; после удаления — тоже должен исчезнуть) | `ao3_ЛОКАЛЬНЫЙ_900000001.html` |

## Заметки для автоматизации
- Сетап (precondition — два файла одного `ao3Id`, один из них привязан) —
  SAF-подпапочная техника, тот же приём, что TC-153/TC-038/TC-039:
  `saf_steps.saf_pick_folder(driver, f"Download/{subfolder}")`
  (`framework/steps/saf_steps.py:187`) + `adb.push_external(local_html,
  remote_path)` (`framework/core/adb.py:289`). Оба файла заранее в уникальной
  SAF-подпапке → подпапка выбрана как папка загрузок → silent-скан
  релинкует работу на ОДИН детерминированный файл-победитель по
  `lastModified` → карточка «Open downloaded», второй файл остаётся сиротой
  на диске — это и есть Given кейса. Та же техника использована
  fix-verifier'ом на живом устройстве (`bugs/BUG-047.md` «Верификация»,
  запись 2026-08-11T16:33:00Z).
- **BUG-021-механизм (правка заметки через overlay листинга → обнуление
  `downloadPath` → повторное скачивание → второй файл) БОЛЬШЕ НЕ РАБОТАЕТ
  как способ получить precondition:** BUG-021 сам `Verified` тем же
  коммитом `a968f6b` — фикс (`existing.copy(...)`) теперь СОХРАНЯЕТ
  `downloadPath` при правке заметки, повторное скачивание для уже
  привязанной работы больше не запускается. Не использовать эту дверь для
  сетапа (см. также `bugs/BUG-046.md` «Обсуждение», запись `fix-verifier @
  2026-08-11T16:11:00Z`, тот же вывод).
- Удаление через overlay карточки — существующий путь TC-035
  (`library_steps.delete_via_overlay(driver, work.title, "Delete downloaded
  file")`, точный текст «Delete downloaded file», не «Delete work»).
- Проверка отсутствия файлов на диске после удаления — прямая `adb shell
  ls` содержимого SAF-подпапки на файлы с хвостом `_<ao3Id>.html`
  (device-side проверка, эквивалент витнесса fix-verifier, `bugs/BUG-047.md`)
  — сильнее и надёжнее проверки только текста диалога, рекомендуется как
  основной assert для And-пункта «второй файл тоже удалён».
- Дельта к TC-035: TC-035 знает только сценарий с ОДНИМ файлом (после
  удаления папка пуста и скан не воскрешает ничего — этот путь фиксом не
  затронут, остаётся зелёным контролем); TC-154 — специфично про ИСХОДНЫЙ
  остаток второго файла ДО удаления и подтверждение, что `deleteDownload`
  подметает его тоже, а не оставляет сиротой.
- Область — та же реконсиляция «файлы на диске ↔ одна строка Room», что
  TC-153 (сиблинг-кейс, тот же класс BUG-046/047, одна и та же папка/сид).
  Здесь фокус — на пользовательском НАМЕРЕНИИ (явное удаление подметает всё
  связанное), а не на идемпотентности счётчика — отдельный сценарий, не
  дублирует TC-153.
- `download_oracle` — та же настройка, что в TC-153 (маркер ожидаемого
  числа файлов на сетапе; при SAF-технике папка вне дефолтного каталога —
  см. заметку TC-153).
