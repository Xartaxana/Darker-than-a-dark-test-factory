# TC-132 — Deep-link на «уведённую» с HOME_URL единственную вкладку создаёт вторую

## Предусловия
- Приложение запущено с чистыми данными (`clean_app`) — на холодном старте ровно
  1 вкладка со значением `HOME_URL` (`https://archiveofourown.org`, БЕЗ слэша).
- Replay-режим, фикстура `tab_markers.mitm`.
- **Ловушка анти-флейк (CH-005, находка 5), учтённая в самом Given:** условие
  reuse — `tabs.size==1 && tabs[0].url == HOME_URL` — сравнение СТРОКОВОЕ и точное;
  `onPageLoaded` домашней страницы перезаписывает URL вкладки на
  `https://archiveofourown.org/` (СО слэшем), т.е. окно, где reuse формально
  возможен, существует только ДО завершения загрузки home и закрывается сам по
  себе обычным ходом событий. Этот кейс СОЗНАТЕЛЬНО не целится в узкое окно ДО
  загрузки (нестабильно, измерено CH-005 R2.5 — создание второй вкладки на
  ДОГРУЖЕННОЙ home), а фиксирует детерминированно достижимую, реально
  наблюдаемую ветку: дождаться полной загрузки home (`onPageLoaded` уже
  отработал — тот же признак, что использует `wait_home_ready_for_deep_link` в
  TC-022..025 для устранения гонки) и ТОЛЬКО ПОТОМ слать deep-link.

## Сценарий (Given-When-Then)

**Given** открыта ровно 1 вкладка, домашняя страница ПОЛНОСТЬЮ догрузилась
(`onPageLoaded` отработал — URL вкладки фактически `https://archiveofourown.org/`
СО слэшем, что уже НЕ равно константе `HOME_URL` без слэша)

**When** в приложение отправлен deep-link на URL маркерной страницы

**Then** число вкладок становится 2 (НЕ переиспользование — создана НОВАЯ вкладка)
**And** новая вкладка становится активной и её содержимое соответствует URL
deep-link'а
**And** вкладка 0 (бывшая единственная, ex-home) сохраняет своё прежнее содержимое
без изменений — deep-link её НЕ тронул

**Инвариант:** ветка переиспользования (`navigateActiveTabTo`, без роста числа
вкладок) срабатывает СТРОГО когда `tabs.size==1 И tabs[0].url` побайтово равен
`HOME_URL` без слэша; ЛЮБОЕ отклонение — включая штатную перезапись URL со слэшем
после реальной загрузки домашней страницы — уводит `openOrNavigateDeepLink` в
ветку `openTab` (новая вкладка, счёт растёт на 1). Свойство верно вне зависимости
от ТОГО, чем именно вкладка была уведена с точного значения `HOME_URL`
(перезагрузка, навигация, deep-link) — сравнение всегда точное строковое, не
URL-нормализующее.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Вкладок до deep-link | 1 (home, уже полностью догружена) |
| Deep-link URL | маркерная страница `tab_markers.mitm` |
| Вкладок после deep-link | 2 |

## Заметки для автоматизации
- Ожидание полной загрузки home — существующий шаг
  `app_steps.wait_home_ready_for_deep_link` (`browser_screen.py::wait_home_page_loaded`,
  ждёт JS-маркер `window.__ao3AppDark`, доказывающий `onPageLoaded`), уже
  используемый в TC-022..025 КАК РАЗ для того, чтобы УЙТИ от узкого reuse-окна —
  здесь он используется по прямому назначению: гарантирует именно ЭТУ, стабильную
  ветку.
- Deep-link — `app_steps.open_deep_link`.
- Счёт вкладок и URL — из prefs `open_tabs_urls` (см. ловушку в TC-131), а не из
  иконок TabStrip.
- **Парный кейс TC-135 (positive-reuse ветка):** истинная положительная ветка
  reuse (deep-link при `tabs[0].url`, ещё побайтово равном `HOME_URL`) покрыта
  отдельным кейсом `test-cases/tabs/TC-135.md` через ХОЛОДНЫЙ СТАРТ приложения
  самим VIEW-интентом. Прежняя формулировка этого пункта («ветка не имеет
  надёжного детерминированного воспроизведения… mitm.py не содержит
  delay/latency») снята вердиктом critic (ESC-011, attempt 2) как недоказанный
  негатив: reuse-состояние не требует механизма задержки — оно является
  состоянием ПО УМОЛЧАНИЮ до `onPageLoaded` (докстринг
  `app_steps.wait_home_ready_for_deep_link`, `app_steps.py:109-118`: ожидание
  введено ровно затем, чтобы из этого состояния ВЫЙТИ). Этот кейс (TC-132)
  остаётся фиксацией ОТРИЦАТЕЛЬНОЙ ветки условия — пара TC-132 + TC-135
  закрывает обе ветки `BrowserViewModel.kt:639`.

**Фактическое поведение (test-automator, 2026-07-31).** Реализовано

**По этому кейсу.**
- Traceability: `@allure.id("TC-132")` == id кейса; `@pytest.mark.p1` ==
  `priority: P1`; `automated_by` указывает на существующую
  `test_deep_link_after_home_loaded_creates_second_tab_not_reuse`
  (`test_tabs.py:449`).
- Соответствие по смыслу (п.3): инвариант «reuse строго при `tabs.size==1 И
  tabs[0].url` побайтово == `HOME_URL` без слэша» проверяется как СВОЙСТВО:
  тест сначала ДОКАЗЫВАЕТ отклонение предпосылки (`assert_persisted_tab_url_at(0,
  HOME_URL + "/")` — та самая штатная перезапись со слэшем), и только потом
  фиксирует следствие (2 вкладки, активна позиция 1, вкладка 1 несёт URL
  deep-link'а, вкладка 0 НЕ тронута). Это сильнее, чем «вкладок стало две»:
  проверяется и причина, и сохранность соседа.
- Красная проба (п.7): моя собственная порча (TC-135, см. там) уронила ИМЕННО
  `wait_persisted_tab_count` — тот же шаг, который несёт ключевой ассерт этого
  кейса (`test_tabs.py:478`), и текст падения оказался буквально тем, что автор
  заявил для красной пробы TC-132 («число вкладок в open_tabs_urls не стало
  N»). Свидетельство «умеет падать» для этого ассерта получено мной напрямую.
- Флейк-риск (п.5): активность вкладки читается из `active_tab_index` того же
  `apply()`, что и `open_tabs_urls` (не из WEBVIEW — обход прилипания
  chromedriver к вкладке-0 без разрушающего reduce-to-one); все ожидания явные;
  живой AO3 не используется.
- Ссылка на парный TC-135 в заметках актуальна: обе ветки условия
  `BrowserViewModel.kt:639` закрыты, зависимости этого теста от TC-135 в коде
  нет (тесты независимы, что подтверждено одиночным `-k` прогоном TC-135).
