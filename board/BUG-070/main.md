# ON + deep-link в новую вкладку: FilterPanel продолжает показывать профиль активным, хотя URL/содержимое вкладки НЕфильтрованы

_Спроецировано из `bugs/BUG-070.md` (источник правды).
Статус в нашей машине: **Open**._

# BUG-070 — Панель фильтра врёт о применении: deep-link открывает нефильтрованную вкладку, но триггер продолжает показывать активный профиль

## Окружение
- Версия приложения: source_commit 6f884d97 (versionCode 12)
- Режим: replay (`listing_basic.mitm`)
- Найдено: exploratory charter CH-010 (2026-08-14), сид 2

## Шаги воспроизведения (Given-When-Then)

**Given**
1. Приложение запущено, replay-режим, тумблер «Auto-apply on navigation» —
   ON (дефолт)
2. Профиль «My saved search» применён из FilterPanel на `LISTING_BASIC_URL`
   (`select_filter_option`, путь TC-041) — активная вкладка получает URL
   `LISTING_FILTERED_URL`, `assert_active_filter_shown` подтверждает панель
   показывает «My saved search»

**When** пользователь получает и открывает **deep-link** на
`LISTING_BASIC_URL` (`app_steps.open_deep_link`, реальный Android
`ACTION_VIEW` intent — тот же путь, каким работает открытие ссылки из
другого приложения/мессенджера)

**Then (ожидалось по коду)** — `openOrNavigateDeepLink`
(`BrowserViewModel.kt:637-655`) грузит URL программно (`loadUrl`), минуя
единственную дверь авто-применения `shouldOverrideUrlLoading`
(`BrowserScreen.kt:616-631`) — новая вкладка обязана остаться
НЕфильтрованной.

**Actual (подтверждено, оба независимых прогона)**
1. Новая вкладка (позиция 1, `active_tab_index=1`, подтверждено
   `wait_persisted_tab_count(2)`) несёт URL **побайтово равный**
   `LISTING_BASIC_URL` — БЕЗ параметров `work_search` профиля
   (`assert_persisted_tab_url_at(1, rb.LISTING_BASIC_URL)` прошёл), т.е.
   контент вкладки — НЕфильтрованный листинг
2. **FilterPanel (нативный триггер, `BottomBar.kt Text(activeFilter?.name
   ?: "None")`, читается через UiAutomator2 — НЕ WebView-контекст, sticky
   context класса AT-BUG-018 здесь не применим) продолжает показывать
   «My saved search» как активно применённый** —
   `filter_dropdown_has_option(name)` вернул `True`
3. `active_filter_profile_id` в prefs остаётся заполненным (профиль жив —
   ожидаемо, deep-link не трогает `activeFilterId`)

Итог: пользователь смотрит на страницу без каких-либо признаков ограничения
контента, но панель приложения продолжает утверждать, что персональный
фильтр-профиль активен. Один и тот же экран одновременно говорит и
«фильтр применён» (панель), и «фильтр не применён» (реальный
URL/содержимое) — панель ГЛОБАЛЬНА (`activeFilterId` — одно состояние на
всё приложение), тогда как факт применения — свойство КОНКРЕТНОЙ вкладки.

## Частота

## Анализ

`activeFilterId` (BrowserViewModel.kt) — ОДНО состояние на всё приложение
(persist `active_filter_profile_id`, `:578-584`). URL и факт применения
фильтра — свойства КОНКРЕТНОЙ вкладки (`currentUrlFilterParams`, `:492`).
Панель триггера (`BottomBar.kt:251/284-288`) рендерит ИМЯ активного
профиля БЕЗ проверки, применён ли этот профиль К ТЕКУЩЕЙ АКТИВНОЙ вкладке —
она просто показывает глобальное состояние, выдавая его за
для-этой-страницы факт.

То же расхождение по построению верно и для остальных ТРЁХ программных
дверей, перехвата не проходящих (не проверено этой сессией индивидуально,
но код идентичен): `applyFilter`-загрузка новой вкладки (`:216`), Back
(`:244`), первичная загрузка любой вкладки при восстановлении
(`loadTabContent`, `:486`/`:501`) и `wv.reload()` при смене темы (`:157`) —
ЛЮБАЯ из них создаёт/обновляет вкладку без применения фильтра, но панель
не различает вкладки.

**Контраст (дверь, ПРОХОДЯЩАЯ перехват):** попытка проверить ту же цель
кликом по ссылке внутри страницы (content-initiated навигация через
`window.location.href`, тот же код-путь, что реальный тап по `<a href>`)
не дала интерпретируемого результата в этой сессии — см. ловушку
«sticky WebView context» ниже. Заявленный код (`shouldOverrideUrlLoading`)
ДОЛЖЕН подхватывать `getActiveFilterQueryString` и переписывать URL — это
осталось неподтверждённым эмпирически, хотя логика кода для этого случая
уже покрыта существующим `assert_persisted_tab_url_at(...,
LISTING_FILTERED_URL)`-паттерном для КЛИКА (не JS location.href).

## Обсуждение

**[exploratory-tester @ 2026-08-14] Граница метода — sticky WebView
context.** Chromedriver в этом приложении «прилипает» к вкладке,
созданной ПЕРВОЙ (класс AT-BUG-018/019/022) — `driver.execute_script`
внутри `contexts.in_webview` не гарантированно бьёт по ВИЗУАЛЬНО активной
вкладке при >1 живом WebView. Баннер страницы
(`#ao3-companion-hidden-notice`, `window.__ao3FilterActive`) читался ЭТИМ
способом в данной сессии и вернул `True` — но эта проба, вероятнее всего,
читала tab-0 (изначальную ФИЛЬТРОВАННУЮ вкладку), а не tab-1 (deep-link),
поэтому **эти конкретные значения баннера в тикет НЕ включены как
доказательство** — заявленный в тикете дефект опирается ТОЛЬКО на два
надёжных оракула: persisted `open_tabs_urls` (не WebView-контекст) и
нативный UiAutomator2-триггер панели (не WebView-контекст). Проверка
самого баннера на вкладке deep-link, а также контраст через реальный клик
по ссылке — remains open, см. `followup_tc` в CH-010.md.
