# Back после автопрыжка плотности возвращает пользователя на страницу, с которой автопрыжок начался

_Спроецировано из `test-cases/browser/TC-264.md` (источник правды).
Статус в нашей машине: **Review**._

# TC-264 — регресс-замок BUG-019 (Reopened): Back после автопрыжка ДОЛЖЕН вернуть на страницу-источник (сейчас — красный)

> **Статус замка.** `bugs/BUG-019.md` — `Reopened` на сборке `aa377e0e`
> (fix-verifier 2026-08-17, независимо подтверждено критик-входом +
> контрольным экспериментом «Back без автопрыжка работает штатно» —
> исключена гипотеза «Back сломан вообще»). Этот тест ОЖИДАЕМО ПАДАЕТ до
> фикса Kotlin-стороны (`TabNavHistory`/`recordPageLoad` должны отличать
> «страница, до которой докрутил автопрыжок» и не пушить её повторно при
> возврате туда же, либо Back должен перестать быть чистым `loadUrl`).
> Заголовок и Then сформулированы от ОЖИДАЕМОГО (спецификационного)
> поведения — красный факт живёт здесь и в `red_lock`, не в заголовке
> (правило CLAUDE.md, прецедент TC-139).

## Предусловия
- Приложение запущено с чистыми данными; тумблер «Infinite scroll (listing
  pages)» — ON; `hide_disliked` — дефолт ON.
- Replay-режим, `listing_paginated.mitm` (5 страниц, по 1 работе на
  странице), `seed_library`.
- Почему не L2: реальный системный Back + Kotlin-стек `TabNavHistory` +
  реальный WebView reload — устройство обязательно (сам факт, из-за
  которого баг живёт, — расхождение JS-истории WebView и Kotlin-истории
  приложения, недоступное jsdom-харнессу).
- **Достижимость Given (норма «направление негативного Then», CLAUDE.md,
  прецедент TC-204/TC-139).** Позитивный якорь, доказывающий, что различие
  «вернулся / не вернулся» физически наблюдаемо, а не вакуумно: **TC-261**
  (тот же прогон-класс) уже устанавливает, что системный Back в Browse
  штатно переводит вкладку на её предыдущую запись `TabNavHistory` — без
  автопрыжка Back работает. Здесь Given специально строит ситуацию, где
  ЕДИНСТВЕННОЕ отличие от штатного случая — присутствие автопрыжка между
  переходом и Back; если бы Back был просто сломан вообще, различающий
  Then был бы красным ПО ДРУГОЙ причине — контрольный эксперимент критика
  BUG-019 («Back без автопрыжка работает штатно») уже закрыл эту
  альтернативную гипотезу, поэтому различающий ассерт здесь честно
  атрибутируется именно автопрыжку, не общей поломке Back.

## Сценарий (Given-When-Then)

**Given** работа страницы 1 листинга (единственная) помечена DISLIKE,
`hide_disliked=ON`, `infinite_scroll=ON`; пользователь открывает страницу 1
→ приложение САМО выполняет автопрыжок на страницу 2 (тот же факт, что
TC-159); на странице 2 зафиксирован маркер документа
(`window.__ch006Marker`) и снят `{href, history.length}` — снапшот landed-
состояния

**When** пользователь нажимает системный Back (реальная кнопка/жест,
`contexts.to_native` + `driver.back()`, НЕ `window.history.back()` из
webview-контекста)

**Then (ожидаемое, спецификационное)** пользователь возвращается на
страницу 1 — `href`/landed work id меняются, маркер документа страницы 2
теряется (документ реально сменился, не косметика)

**Then (фактическое на этой сборке — КРАСНОЕ, red_lock BUG-019)** снятый
ПОСЛЕ Back снапшот `{href, historyLength}` показывает: `href`/landed work
id **НЕ меняются** (пользователь остаётся на странице 2), `history.length`
растёт на +1 (не +2, как до фикса aa377e0 — измеримое частичное улучшение,
но симптом «заперт» воспроизводится) — Kotlin `BackHandler`→`goBack(tabId)`
находит в `TabNavHistory` запись страницы 2 (записана повторно тем же
`recordPageLoad` при reload'е страницы 1 → повторном автопрыжке) и
загружает СНОВА страницу 2

**Инвариант:** различающий Then («вернулся / не вернулся») ПОЛОЖИТЕЛЕН —
Given явно доказывает, что штатный Back работает (см. «Достижимость Given»
выше), поэтому текущее красное падение атрибутируется ИМЕННО взаимодействию
автопрыжка с `TabNavHistory`, не общей поломке навигации.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа страницы 1 | единственная, `rating=DISLIKE` |
| Landed-страница после загрузки | 2 (автопрыжок, как TC-159) |
| Ожидаемо после Back | страница 1 (спецификация) |
| Фактически после Back (red) | страница 2, `history.length` +1/press |

## Заметки для автоматизации
- **Готовый, уже прогнанный на устройстве рецепт** — `bugs/BUG-019.md`,
  таблица «Верификация», буквальный сценарий fix-verifier (seed 2a):
  `app_steps.clean_state()` + `app_steps.seed_library([(works.LOVED,
  "DISLIKE")])` ДО старта Appium-сессии → `enable_infinite_scroll` →
  `assert_rating_hidden(driver,"Disliked",True)` → `open_listing(LISTING_
  PAGINATED_URL)` → `wait_until` на `"page=2"` в query → снять
  `{href, history.length}` + выставить `window.__ch006Marker` (webview-
  контекст) → `contexts.to_native(driver)` + `driver.back()` →
  `time.sleep(3)` settle → повторный снимок `{href, history.length,
  marker}` + id блёрбов. Этот же recipe (без seed 2b цепочки — она для
  TC-160-класса накопления, не нужна здесь) — прямая основа реализации,
  НЕ требует нового примитива; scratch-версия уже зелёно доказала
  воспроизводимость (`test_bug019_verify.py`, временный, был удалён после
  прогона согласно permission-hygiene, но рецепт дословно сохранён в теле
  бага для аудируемости).
- Ассерт (красная сторона): `ids_after != landed_id or href_after !=
  href_before` — если BUG-019 когда-нибудь фиксится по-настоящему (Kotlin-
  сторона учится не пушить повторно ту же landed-страницу), это условие
  станет FALSE и тест позеленеет — `red_lock` снимается штатно правилом
  rules.yaml после перевода `bugs/BUG-019.md` в `Fixed`+ (тот же механизм,
  что TC-139/BUG-015).
- Маркер `window.__ch006Marker` — свидетельство ТОЛЬКО для факта «документ
  реально пересоздан» (не косметика); не путать с постоянным API бриджа,
  это тестовый флаг, выставляемый самим тестом через `execute_script`.
- Блокер автоматизации отсутствует: `listing_paginated.mitm` уже собран
  (TC-129/130/159), сидинг — `seed_library`, приём системного Back — уже
  проверен вживую (BUG-019 fix-verifier witness).
