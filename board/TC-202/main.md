# Баннер не показывается на странице отдельной работы, даже если visibility-скрытие активно (баннер существует только над листингом)

# TC-202 — Баннер не показывается вне листинговой страницы

## Предусловия
- Приложение запущено, `seeded_library` (в т.ч. `DISLIKED`, `rating=DISLIKE`).
- Settings в дефолтном состоянии (`ratedHidden=true`: Display mode=Hide, Disliked
  в hidden-set) — баннер должен быть виден на листинге ("…your visibility
  settings", как в TC-197).
- Открыта листинговая страница (replay `listing_basic.mitm`) в ОДНОЙ вкладке;
  баннер присутствует.

## Сценарий (Given-When-Then)

**Given** приложение запущено с `seeded_library`, Settings в дефолтном состоянии
(`ratedHidden=true`), в текущей вкладке открыт листинг, баннер виден с текстом
"Some works may be hidden by your visibility settings"

**When** пользователь, В ТОЙ ЖЕ вкладке, переходит на страницу отдельной работы
(work id из `ALL_WORKS`, для которой в `listing_basic.mitm` уже записан
отдельный work-page flow — `recording_builder.py::build_listing_basic`, ТРЕТИЙ..
СЕДЬМОЙ flow — по одному на каждую из 5 эталонных работ)

**Then** на work-странице узла `#ao3-companion-hidden-notice` НЕТ вовсе —
`document.querySelector('ol.work.index.group')` не находит листинговый контейнер
на work-странице, гейт `ao3_bridge.js:471-476` не даёт баннеру появиться,
независимо от значений флагов
**And** значения `window.__ao3RatedHidden`/`window.__ao3FilterActive` на
work-странице по-прежнему `true`/соответствующие (флаги инжектируются на КАЖДОЙ
загрузке страницы, `BrowserScreen.kt:605-606`, включая work-страницы) — это
подтверждает, что причина отсутствия баннера ИМЕННО отсутствие `ol`, а не сброс
флагов приложением

**Инвариант:** присутствие баннера требует ОБОИХ условий одновременно — хотя бы
один из флагов true И страница содержит `ol.work.index.group`; недостаточно
только флагов (доказано здесь: флаги остаются true/активны, баннера всё равно
нет). Дополняет TC-201 (там недостаточно только `ol`-контекста без флагов —
оба false на листинге тоже не дают баннера) — вместе два кейса показывают, что
ни одно условие по отдельности не достаточно, а не только необходимо.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Исходная страница | листинг (`listing_basic.mitm`), баннер виден |
| Целевая страница | work-страница любой из 5 эталонных работ (тот же `.mitm`) |
| `ratedHidden`/`ao3FilterActive` на целевой странице | не изменились (флаги приложения) |
| Баннер на целевой странице | отсутствует |

## Заметки для автоматизации
- Не блокер: метод чтения баннера — см. заметку TC-197.
- Навигация на work-страницу — существующий шаг `rating_steps.open_work_page(driver,
  work_id)` (`BrowserScreen.open_work` — навигация ТЕКУЩЕЙ вкладки, не новая
  вкладка, что важно: банер должен исчезнуть В ТОЙ ЖЕ вкладке, а не просто
  отсутствовать на свежей); подходящий work id — любой из `framework/data/works.py::ALL`
  (не обязательно DISLIKED — важен сам факт work-страницы, не рейтинг).
- **Наблюдательная оговорка (не влияет на Then, честности ради):** внутри
  `updateHiddenBanner()` есть ДВЕ разные причины отсутствия узла на разных
  типах страниц — (а) свежий JS-контекст полной навигации (WebView создаёт
  новый `window` на каждую загрузку, `hiddenNoticeEl` стартует `null`, гейт
  `:471-476` просто возвращается рано без вызова `.remove()`) и (б) КОД ветки
  `.remove()` для случая, когда `hiddenNoticeEl` уже был установлен В ТОМ ЖЕ
  JS-контексте и `ol` внезапно пропал БЕЗ полной навигации. Тест
  чёрного ящика (этот кейс) наблюдает только (а) — единственный путь,
  достижимый обычной пользовательской навигацией в этом приложении (все
  переходы между листингом и work-страницей — полные навигации, SPA-роутинга
  нет); путь (б) выглядит защитным кодом на случай будущей
  SPA-навигации и с точки зрения пользователя неотличим от (а) (баннера нет в
  обоих случаях) — не расширяю кейс синтетической пробой ради покрытия
  конкретной строки, это была бы проверка деталей реализации, а не
  наблюдаемого поведения.
- **Батарея правил-реакций:** см. общую оценку в TC-201 (off-инвариант),
  TC-203 (edge-vs-level/idempotency/ретроактивность), TC-204 (propagation) —
  не дублирую; этот кейс — про второе МЕСТО ВЫЗОВА гейта (`:471-476`, «вне
  листинга»), а не про новый пункт батареи.
