# BUG-068 — Фильтр-профиль (OFF) снимается ЛЮБОЙ загрузкой ЧУЖОЙ/фоновой вкладки, невидимо для пользователя

## Окружение
- Версия приложения: source_commit 6f884d97 (versionCode 12)
- Режим: replay (`listing_basic.mitm`)
- Найдено: exploratory charter CH-010 (2026-08-14), сиды 1(а)/1(б)/1(в)/1(г)

## Контекст (чтобы не путать с уже известным)

Факт «при выключенном тумблере "Auto-apply on navigation" любая загрузка
страницы снимает активный фильтр-профиль» УЖЕ известен: код
`BrowserViewModel.kt:501-504` (`onPageLoaded`, ветка `if (!autoApplyFilter &&
activeFilterId != null) setActiveFilter(null)`), уже зафиксирован
регрессионным кейсом TC-184 (снятие профиля при ОБЫЧНОЙ пользовательской
навигации в ОДНОЙ вкладке, ассерт снимается сразу после действия) и уже
поднят как открытый вопрос владельцу/разработчику (docs/01-test-strategy.md
§10 (ч), R-09: «сброс профиля при OFF — задумано или дефект»). **Этот баг —
НЕ про сам факт сброса.** Он про ГДЕ и КАК ИМЕННО он происходит в случаях,
которые TC-184 не покрывает и о которых пользователь физически не может
узнать в момент события — это отдельное наблюдение, шире вопроса §10 (ч)
(сам open-вопрос §10(ч) явно допускает такую трактовку).

`onPageLoaded(tabId, url)` (`:474`) не проверяет НИ `tabId` (какая именно
вкладка загрузилась), НИ `isFilterable` (та ли это вообще страница) — сброс
срабатывает на ЛЮБОЙ завершённой загрузке ЛЮБОЙ вкладки, включая вкладки,
создаваемые/загружаемые, пока пользователь стоит на СОВЕРШЕННО ДРУГОМ
экране (Library, Settings) и в принципе не смотрит на браузер.

## Шаги воспроизведения (Given-When-Then)

**Given**
1. Приложение запущено, replay-режим (`listing_basic.mitm`)
2. Фикстура: один фильтр-профиль «My saved search» засеян
   (`seed_filter_profiles`), плюс работа в библиотеке (для двери фонового
   открытия) или файл со скачанным HTML (для двери `onOpenFile`)
3. На Browse открыт `LISTING_BASIC_URL`, профиль применён из FilterPanel
   (`select_filter_option`) — `active_filter_profile_id` в prefs
   `ao3_settings` установлен, панель показывает «My saved search»
4. В Settings тумблер «Auto-apply on navigation» переключён в **OFF**
5. Пользователь переходит на экран **Library** (Browse больше не виден)

**When** (4 независимых варианта, все воспроизведены дважды)

- **(а)** На Library long-press карточки работы → «Open in background tab»
  (`library_steps.open_in_background_via_overlay`) — фоновая вкладка
  получает WebView и грузится, пока экран остаётся Library.
- **(б)** На вкладке FILES тап иконки «Open downloaded» по скачанному
  локальному файлу (`onOpenFile`, `MainActivity.kt:522-526` →
  `browserViewModel.openTab(url, background=false)`) — «передняя» дверь,
  переключающая экран на Browse, но целевой URL `file://…` не имеет
  никакого отношения к AO3/фильтрам. Доказано, что страница РЕАЛЬНО
  отрендерилась (не error-путь BUG-060-класса): `document.title` вернул
  осмысленный заголовок, `document.body.innerHTML.length` = 10893.
- **(в)** Обратный порядок: сначала фоновое открытие ПРИ ON (профиль не
  тронут — ветка сброса стоит внутри `!autoApplyFilter`, подтверждено),
  затем OFF, затем ПАУЗА 3.3с без единой навигации (профиль пережил паузу
  все 6 опросов) — «отложенная мина»: профиль умирает на ПЕРВОЙ ЖЕ
  последующей загрузке, какой бы вкладкой она ни была вызвана.
- **(г)** Смена ТЕМЫ (Light→Dark) со стороны Settings —
  `LaunchedEffect(darkTheme)` (`BrowserScreen.kt:151-158`) делает
  `wv.reload()` для ВСЕХ живых WebView — настройка, не имеющая отношения к
  фильтрам, тоже гасит профиль.

**Then (ожидалось)** — если сброс задуман как «предохранитель от
рассинхронизации URL и профиля», ожидание разумного поведения: сброс
происходит либо (1) только при загрузке, которую пользователь реально видит,
либо (2) сопровождается заметным сигналом («фильтр снят», снекбар/бейдж),
как того требует R-16 (правило владельца: «есть сообщение — норма»).

**Actual (фактически)** — во ВСЕХ четырёх вариантах профиль снимается БЕЗ
единого сообщения, пока пользователь смотрит на экран, не имеющий отношения
к браузеру/фильтрам:

| Вариант | Момент смерти (опрос prefs ~0.5с/шаг) | Экран пользователя в момент смерти |
|---|---|---|
| (а) фоновое открытие с Library | 1-й опрос (≤0.5с после действия) | Library — снекбар «Opened in background» НЕ упоминает фильтр |
| (б) `onOpenFile`, передняя дверь | 1-й опрос (≤0.5с) | Browse (файл отрендерился), но пользователь открывал ФАЙЛ, не листинг |
| (в) отложенная мина | 0 опросов при паузе (профиль жив), 1-й опрос ПОСЛЕ единственной загрузки | Browse — но пользователь мог не связать загрузку с потерей фильтра |
| (г) смена темы | 2-й опрос (~1с) | Settings — пользователь листает темы, не браузер |

Единственный видимый пользователю артефакт — FilterPanel начинает
показывать «None» вместо имени профиля, но панель СВЁРНУТА по умолчанию
(раскрывается отдельным жестом, `MainActivity.kt onFilterSelected`) и не
видна ни на Library, ни на Settings вовсе (`browser_screen.py:288-302`) —
то есть единственный оракул истины скрыт на экране, где событие
произошло, и не показывается проактивно.

## Анализ

Корень — `onPageLoaded(tabId, url)` (`BrowserViewModel.kt:474`, ветка сброса
`:501-504`) читает ГЛОБАЛЬНОЕ состояние `activeFilterId` без привязки к
конкретной вкладке/экрану. `BrowserScreen.kt:120-137` создаёт и грузит
WebView для ВСЕХ вкладок сразу (комментарий `MainActivity.kt:473`
«Browser is always rendered to keep WebViews alive») — то есть ЛЮБОЕ
открытие вкладки (фоновое, переднее, deep-link, восстановление при
релонче) вызывает `onPageLoaded` независимо от того, смотрит ли
пользователь на браузер. Смена темы добавляет ЕЩЁ один источник
непричастных к фильтрам `reload()`-вызовов, бьющих по той же ветке.

Независимо от вердикта по §10(ч) (задумана ли САМА идея «OFF снимает
профиль при загрузке»), КОНКРЕТНОЕ поведение «снимает молча, пока
пользователь не на браузере» — самостоятельная проблема доверия:
пользователь, полагающий, что настроенный фильтр всё ещё активен (панель в
последний раз, когда он её видел, показывала имя профиля), вернётся на
Browse и увидит нефильтрованный контент, не понимая, когда и почему это
произошло.

## Обсуждение

**[exploratory-tester @ 2026-08-14] Классовая полнота.** Все 4 варианта
объединены в один тикет (не 4 отдельных) — общий корень
`onPageLoaded:501-504` без tabId/isFilterable проверки; фикс на уровне
класса закрывает все четыре одним изменением (например: сбрасывать
профиль ТОЛЬКО когда `tabId == activeTabId` И пользователь реально видит
экран Browse, либо всегда сопровождать сброс снекбаром независимо от
экрана).

**Связь с §10(ч):** этот тикет не заменяет открытый вопрос владельцу про
задуманность самой ветки OFF — он сужает его: даже если ветка задумана,
конкретная реализация без экранной/tabId-проверки и без сигнала
пользователю остаётся находкой этой сессии, требующей отдельного решения.

**Ограничение метода:** момент смерти профиля пойман опросом с шагом
~0.5с — точный момент внутри этого окна не измерялся (не требовалось для
демонстрации самого явления). Панель FilterPanel не проверялась на предмет
краткого мелькания имени перед «None» (best-effort по духу CH-010, не
ассерт).
