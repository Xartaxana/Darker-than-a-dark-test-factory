# TC-272 — Сбой публикации sync: дословный диалог, но уже слитые данные не откатываются (три ветки: update/create/generic)

## Обоснование отдельного кейса (не слияние с TC-224)

TC-224 доказывает сбой на этапе ЧТЕНИЯ (`fetchRemote`) — там сбой происходит
ДО какого-либо слияния, поэтому «локальные данные не изменились» тривиально
верно и является правильным Then. Здесь Given принципиально ДРУГОЙ: чтение
УСПЕШНО (либо не требуется вовсе — первое устройство), слияние УЖЕ
применилось к Room, и сбой происходит СТРОГО ПОЗЖЕ — на публикации
(`createSnippet`/`updateSnippet`). Это другая стоимость/природа Given (П1
Р1: разный этап пайплайна, разный набор предварительных сетевых
транзакций — GET+PUT против одного GET, а на варианте B GET не происходит
вовсе), не «тот же Given, другой Then» — слияние с TC-224 запрещено по
критерию границы. Дословный текст диалога 401/403 СОВПАДАЕТ с TC-224
вариантом B — это ожидаемо (общий catch в `syncNow` не различает источник
исключения), не повод сливать: несущая проверка здесь — НЕ текст диалога
(он уже доказан TC-224), а РАЗНОЕ поведение локальных данных при сбое на
этом этапе, которое TC-224 в принципе не может продемонстрировать (его
Given никогда не доходит до слияния).

**Расхождение с docs/feature-registry.yaml, найдено при проектировании:**
title записи `sync-failure-messages` заявляет одним предложением «локальные
данные при этом не меняются» для ВСЕХ перечисленных кодов/причин без
исключения. Это верно для ветки чтения (TC-224), но НЕ верно для ветки
публикации (доказано вариантом A ниже — слияние коммитится в Room ДО
попытки публикации и не откатывается, если публикация проваливается).
Это не блокирует дизайн (код однозначен, PROJECT.md здесь ни при чём) —
докладываю строкой в отчёте координатору для владельца реестра
(test-strategist), сам title реестра не правлю (вне owns этого хода).

## Предусловия
- Синхронизация настроена (instance + токен валидны в фикстуре мока).
- Три независимых варианта (A/B/C) — каждый со своим Given, не
  journey/чекпойнты (нет мутации общего состояния между вариантами, каждый
  самодостаточен, отдельный прогон параметризованного теста — тот же приём,
  что TC-224/TC-167/TC-242).
- Мок GitLab (`gitlab_snippet_mock.py`) уже поддерживает произвольный
  `status=` для всех трёх эндпойнтов (`make_snippet_get_flow`,
  `make_snippet_create_flow`, `make_snippet_update_flow`) — фикстура НЕ
  требует расширения, только новую комбинацию статусов в `.mitm`
  конкретного теста (см. «Заметки для автоматизации»).

## Сценарий (Given-When-Then)

### Вариант A — updateSnippet 401/403 после успешного слияния (родной сценарий)

**Given** Snippet ID = `SNIP1` (уже сконфигурирован); локально работа X имеет
рейтинг LIKE (timestamp T0); мок GET `.../raw` отдаёт remote-снимок, где
работа X несёт рейтинг SAVE с timestamp T1 > T0 (remote выигрывает по
LWW); локально ТАКЖЕ есть непубликованная работа Z с рейтингом DISLIKE,
отсутствующая в remote-снимке (гарантирует `outText != remoteRaw` после
слияния → публикация будет предпринята); мок PUT `.../snippets/SNIP1`
отвечает `403`

**When** пользователь нажимает «Sync now»

**Then** диалог «Sync failed» с дословным текстом «GitLab rejected the
token (HTTP 403). It needs the 'api' scope.» (текст СОВПАДАЕТ с TC-224
вариантом B — общий catch не различает источник; различающий признак ниже)
**And** рейтинг работы X В ROOM УЖЕ РАВЕН SAVE (не LIKE) — слияние с remote
ПРИМЕНИЛОСЬ несмотря на то, что публикация провалилась и общий диалог
показывает ошибку; это ПОЗИТИВНЫЙ, а не вакуумный оракул — если бы сбой
происходил на чтении (как в TC-224), рейтинг X остался бы LIKE, поэтому сам
факт SAVE доказывает, что тест реально дошёл до ветки `updateSnippet`, а не
до ветки `fetchRemote`
**And** работа Z (локальный непубликованный рейтинг DISLIKE) остаётся в Room
без изменений — провал публикации не откатывает и не портит непубликованные
локальные мутации, они просто ждут следующей попытки синка
**And** подпись «Last synced …» на экране Settings НЕ обновляется (остаётся
тем значением, что было ДО этого прогона, включая «Not synced yet», если
синк ранее не проходил успешно) — `dirty`/`PREF_LAST_SYNC_AT` не
проставляются при сбое (`SyncRepository.kt:275-276` не достигается),
поэтому следующий авто/ручной прогон повторит попытку публикации, а не
молча решит, что всё синхронизировано

### Вариант B — createSnippet 401/403 на первом устройстве (Snippet ID пуст)

**Given** Snippet ID В SETTINGS ПУСТ (типичное первое устройство, тот же
Given-класс, что TC-223, но с ошибкой вместо успеха); локально есть 1
оценённая работа; мок POST `/api/v4/snippets` отвечает `403` (GET `.../raw`
не вызывается вовсе — `snippetId?.let { fetchRemote(it) }` пропускает
чтение при пустом ID)

**When** пользователь нажимает «Sync now»

**Then** диалог «Sync failed» с дословным текстом «GitLab rejected the
token (HTTP 403). It needs the 'api' scope.» (тот же дословный текст, что
вариант A и TC-224 вариант B — различающий признак здесь другой, см. ниже)
**And** поле Snippet ID в Settings ОСТАЁТСЯ ПУСТЫМ (`prefs.edit().
putString(PREF_SNIPPET_ID, newId)` на `SyncRepository.kt:267` не
выполняется — `createSnippet` бросает исключение строкой раньше, до
записи в prefs) — контраст с TC-223, где то же поле САМО заполняется
номером при УСПЕХЕ; здесь явно показано, что провал не оставляет поле в
испорченном промежуточном состоянии (не null-строка, не частичный ID)
**And** состав Room (`read_work_ratings_full()`) идентичен состоянию ДО
прогона — в отличие от варианта A, здесь слияния не было вовсе (GET не
вызывался), поэтому «данные не изменились» здесь — корректный (не
вакуумный) Then: чтение и слияние в принципе не были достигнуты этим
Given, что отличает вариант B от варианта A по механизму, а не только по
коду ответа

### Вариант C — прочий HTTP-код на публикации (генерик-фолбэк, поглощает остаток «прочие HTTP-коды» `sync-failure-messages`)

**Given** тот же Given, что вариант A (Snippet ID = `SNIP1`, слияние
происходит успешно, есть непубликованная локальная работа Z), но мок PUT
отвечает `500` вместо `403`

**When** пользователь нажимает «Sync now»

**Then** диалог «Sync failed» с дословным текстом «GitLab returned HTTP 500
updating the snippet» — ОТЛИЧАЕТСЯ от текста вариантов A/B (это первое
измерение генерик-фолбэка `updateSnippet` (`SyncRepository.kt:414`) в тест-сьюте вообще; ни
TC-224, ни варианты A/B этого текста не производят)
**And** рейтинг работы X в Room уже отражает слитое remote-значение (тот же
позитивный оракул достижимости, что вариант A) — доказывает, что и
generic-ветка публикации достигается ПОСЛЕ успешного слияния, тем же
механизмом, что вариант A

**Инвариант (по всем трём вариантам):** сбой публикации (`createSnippet`
ИЛИ `updateSnippet`, любой HTTP-код) НЕ откатывает уже закоммиченные в Room
мутации слияния и НЕ теряет непубликованные локальные изменения — свойство
«at-least-once, без потери и без ложного успеха»: `dirty` остаётся `true`,
поэтому следующий прогон повторит попытку публикации того же (или более
свежего) состояния. Это СВОЙСТВО отличается от инварианта TC-224
(«сбой = данные не меняются») — вариант A/C доказывают, что для ветки
публикации верно ПРОТИВОПОЛОЖНОЕ (данные меняются, потому что слияние уже
случилось), вариант B доказывает, что при ПУСТОМ Snippet ID (чтения не
было) исходный инвариант TC-224 всё же сохраняется — оба поведения
корректны для СВОЕГО Given, ни один не переиспользуется как проверка для
другого.

## Заметки для автоматизации
- **Не заблокировано инфраструктурой.** `gitlab_snippet_mock.py` уже несёт
  `make_snippet_get_flow(..., status=)`, `make_snippet_create_flow(...,
  status=)`, `make_snippet_update_flow(..., status=)` — тест собирает
  `.mitm` вручную (без `build_snippet_mock`, который жёстко ставит `200` на
  GET/PUT) комбинацией `[make_snippet_get_flow(200, ...), 
  make_snippet_update_flow(SNIP1, status=403)]` для варианта A/C и
  `[make_snippet_create_flow(status=403)]` (без GET-флоу вовсе) для
  варианта B. `sync_replay`/`ignore_content=True` — обязательны для
  PUT/POST (докстринг модуля, класс AT-BUG-073 attempt 1).
- Вариант A/C: сборка remote-снимка — `remote_snapshot_content(works=
  [work_json(X.ao3_id, T1, rating="SAVE")])`; локальный сид — X с LIKE и
  T0 < T1, плюс Z с DISLIKE и БЕЗ записи в remote-снимке (обеспечивает
  `outText != remoteRaw`). Сверка «X теперь SAVE» и «Z остался нетронутым»
  — прямое чтение Room (`read_work_ratings_full()`), тот же приём, что
  TC-224/TC-167.
- Вариант B: `settings_steps` — очистить поле Snippet ID ДО прогона (или
  седить пустым через prefs), тот же приём первого устройства, что TC-223.
- Подпись «Last synced …» (вариант A, четвёртый Then) — существующий
  локатор/степ TC-224-соседей (`sync-manual-run-result-dialog` кейсы TC-207
  и т.п. уже читают эту подпись) — переиспользовать, не изобретать новый.
- Батарея правил-реакций — н-п: «Sync now» — прямое явное действие
  пользователя (тот же вывод, что TC-224).
- Область не комбинаторная для этого кейса (три фиксированных ветки одного
  пайплайна, не фильтр/сортировка/backup) — строка «Инвариант:» дана как
  свойство пайплайна, не пример, но формальный банк C4 сюда буквально не
  подходит; добавлена по аналогии для дисциплины дизайна.
- **Дефект-собрат (доклад, не расширение scope):** генерик-фолбэк ВЕТКИ
  ЧТЕНИЯ (`SyncRepository.kt:367`, «GitLab returned HTTP <code> reading the
  snippet») тоже НИГДЕ не покрыт ни одним существующим кейсом — тот же
  класс пробела, что вариант C здесь закрывает для публикации. Не включаю
  в этот кейс (иначе четвёртый вариант дублирует Given TC-224 почти
  дословно, только меняет код ответа GET с 404/401/403 на 500 — по духу
  дедупа это расширение TC-224, не мой owns в этом ходе); строка в отчёте
  координатору.
