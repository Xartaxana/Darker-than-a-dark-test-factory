# TC-217 — Миграция схемы 7→8 не теряет данные и не падает

## Предусловия
- На устройстве установлена БД в схеме v7 (ДО добавления `sync_tombstones`),
  заполненная: несколько работ с рейтингом/заметкой/тегами/`downloadPath` и
  хотя бы один фильтр-профиль.
- Новая сборка (со схемой v8) устанавливается/запускается поверх этой БД.

## Сценарий (Given-When-Then)

**Given** БД схемы v7 с засеянными рейтингами/заметками/тегами/путями
загрузок и фильтр-профилем лежит в песочнице приложения

**When** приложение новой сборки (схема v8) запускается впервые поверх этой
БД

**Then** приложение НЕ падает при старте (`fallbackToDestructiveMigration`
не включён — отказ миграции наблюдался бы как краш, а не тихая потеря)
**And** все ранее засеянные рейтинги/заметки/теги/пути загрузок видны в
Library без изменений
**And** фильтр-профиль виден в Settings без изменений
**And** таблица `sync_tombstones` создана (доступна для последующего синка)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Исходная схема | v7 (до `sync_tombstones`) |
| Целевая схема | v8 |
| Данные | ≥2 работы (разные рейтинги, одна с downloadPath), 1 фильтр-профиль |

## Заметки для автоматизации
- Построение v7-baseline БД технически не требует новой фикстуры-заглушки:
  можно взять текущий `_pull_baseline`, применить `DROP TABLE
  sync_tombstones` и откатить `PRAGMA user_version` на 7 перед пушем на
  устройство, либо (надёжнее) держать под рукой закоммиченный файл-снимок
  v7-схемы. Информация для test-automator (выбор конкретного способа — при
  кодировании), не блокер этому дизайну.
- Не путать с `settings-restore-merge` (JSON-бэкап) — здесь проверяется
  БИНАРНАЯ миграция Room-схемы, другой механизм и другой риск (падение
  приложения на старте, не потеря конкретных полей).
