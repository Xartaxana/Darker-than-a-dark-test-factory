# TC-210 — Локальное удаление не воскресает обратным слиянием

## Предусловия
- Синхронизация настроена. Работа Z засеяна и оценена (уже была
  синхронизирована — т.е. `ao3Id` уже известен удалённой стороне).
- Пользователь удаляет Z через overlay «Delete work» — локально создаётся
  надгробие с `deletedAt=T_delete`.
- Удалённый снимок (мок) СТАРЫЙ — всё ещё содержит строку Z с
  `timestamp=T_row < T_delete` (симулирует устройство, не узнавшее об
  удалении).

## Сценарий (Given-When-Then)

**Given** работа Z удалена локально (overlay «Delete work», надгробие
`deletedAt=T_delete`) и удалённый снимок несёт более старую строку Z
(`T_row < T_delete`)

**When** пользователь запускает «Sync now»

**Then** работа Z ОСТАЁТСЯ отсутствующей в Library — надгробие побеждает
более старую входящую строку, удаление НЕ воскресает

Инвариант: локальное надгробие побеждает ЛЮБУЮ входящую строку с
`timestamp < deletedAt`, независимо от содержимого этой строки — иначе
устройство, не узнавшее об удалении вовремя, могло бы воскресить работу,
которую пользователь явно удалил.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа Z | удалена локально, deletedAt=T_delete |
| Удалённая строка | timestamp=T_row < T_delete |

## Заметки для автоматизации
- Sync-фикстура отсутствует — информация для test-automator, не блокер.
- Достижимые входы для создания надгробия — ВСЕ эквивалентны по коду
  (`RatingRepository.kt:20-46`): overlay «Delete work»/«Delete downloaded
  file» у stub-строки, Settings «Clear all ratings», удаление
  фильтр-профиля. Этот кейс использует «Delete work» как представителя;
  отдельных кейсов на каждый вход не заводится (не BUG-014-класс — все
  входы физически зовут одну и ту же функцию, асимметрии не найдено).
