# TC-170 — Reset brightness on start OFF: тап тумблера фиксирует значение, ручная правка переживает рестарт

## Предусловия
- Чистая установка/`pm clear` (дефолт `reset_brightness_on_start=true`).
- Автояркость ОС выключена (`Settings.System.SCREEN_BRIGHTNESS_MODE` =
  MANUAL) на весь кейс — тот же довод, что TC-169: иначе система может сама
  переписать значение; восстановить исходный режим в teardown.
- Системная яркость управляется через adb
  (`settings put system screen_brightness <0-255>`).
- Открыт экран Settings, виден слайдер «Brightness», его процентная
  подпись и тумблер «Reset brightness on start».

## Сценарий (Given-When-Then)

**Given** системная яркость выставлена в S1 (~30%, `adb`, ДО первого
запуска), тумблер «Reset brightness on start» в состоянии ON (дефолт),
приложение только что запущено — подпись слайдера показывает ~30%,
слайдер НЕ трогался

**When** пользователь переключает тумблер «Reset brightness on start» в
OFF (слайдер после этого НЕ трогает вовсе)
**And** меняет системную яркость через `adb` на другое значение S2
(~80%) — ПОСЛЕ переключения тумблера
**And** убивает процесс приложения (`force-stop`) и заново его запускает

**Then** на экране Settings после релонча подпись слайдера показывает
~30% (== S1, значение, зафиксированное САМИМ ФАКТОМ переключения тумблера
в момент тапа) — НЕ ~80% (S2, текущую системную на момент старта): тумблер
не просто меняет режим на будущее, а немедленно сохраняет значение,
которое было на экране в момент тапа

**When** пользователь (тумблер по-прежнему OFF) тянет слайдер «Brightness»
до заметно другого значения S3 (~85%)
**And** снова убивает процесс приложения и заново его запускает

**Then** на экране Settings после релонча подпись слайдера показывает
~85% (== S3, ручная правка) — сохранённое значение при OFF переживает
kill+relaunch, симметрично негативной грани ON из TC-169 (там ручная
правка НЕ переживала рестарт, здесь переживает)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Системная яркость до 1-го старта (S1) | ~30% |
| Системная яркость после переключения тумблера в OFF (S2) | ~80% (не должна повлиять) |
| Ожидаемая подпись после 1-го relaunch | ~30% (== S1, зафиксировано тапом тумблера) |
| Ручная правка слайдера при OFF (S3) | ~85% |
| Ожидаемая подпись после 2-го relaunch | ~85% (== S3) |

## Заметки для автоматизации
- Наблюдаемый прокси — тот же, что TC-169: процентная подпись слайдера
  (`brightnessLabel`, `SettingsScreen.kt:670-674, 1322`), обычный `Text`,
  без luma-скриншота.
- adb-хелпер системной яркости — тот же, что нужен TC-169
  (`settings put system screen_brightness <0-255>`, по образцу
  `framework/core/adb.py::set_font_scale`/`set_night_mode`); если TC-169
  реализуется первым, TC-170 переиспользует готовый хелпер без доработки.
- Драйв слайдера — тот же примитив, что TC-146/TC-169.
- **Тумблер «Reset brightness on start» здесь ВПЕРВЫЕ реально тапается**
  (TC-169 его не трогает, только называет локатор как задел). Приём —
  ТОТ ЖЕ XPath `following::`, что `set_tap_to_scroll`/`set_infinite_scroll`
  (`framework/screens/settings_screen.py:105-149`); добавить
  `set_reset_brightness_on_start(enabled: bool)`/
  `is_reset_brightness_on_start_checked()` по ТОЧНОМУ образцу
  `set_tap_to_scroll`/`is_tap_to_scroll_checked` (идемпотентный тап только
  при несовпадении текущего состояния с желаемым) — рутинная реализация по
  существующему шаблону, не отсутствующая фикстура/блокер.
- Kill+relaunch — `restart_app_via_adb`/
  `restart_app_via_adb_asserting_new_process`
  (`framework/steps/app_steps.py:500-570`), тот же приём, что TC-169.
- Порядок действий в первом When существен: смена S2 идёт СТРОГО ПОСЛЕ
  тапа тумблера — иначе тест не отличит «тумблер сохраняет значение в
  момент тапа» от «тумблер просто помнит последнее известное системное
  значение на момент старта» (оба гипотетических поведения дали бы разный
  результат только при этом порядке).
- Кейс НЕ C4-комбинаторной семьи — то же обоснование, что TC-169 (единичный
  бинарный persistence-тумблер, не множество/отношение элементов), строка
  `Инвариант:` не требуется.
- **Батарея правил-реакций — рассмотрена явно (в отличие от TC-169, здесь
  тумблер реально тапается, эффект `setResetBrightnessOnStart` — прямая
  рассматриваемая реакция «на тап тумблера в OFF — немедленно сохранить
  текущее значение»):**
  - edge vs level: н-п — единственная точка вызова
    `setResetBrightnessOnStart` во всём `SettingsScreen.kt` — сам Switch
    `onCheckedChange` (`:692`, подтверждено grep по имени функции); нет
    второго save-пути, которым можно было бы вызвать эффект без реального
    тапа. Compose `Switch` бистабилен — «повторить то же действие без
    перехода» through UI недостижимо (тап всегда меняет `checked`).
  - ретроактивность: н-п — настройка глобальная одиночная величина
    (яркость), не per-объектная метка; концепция «объект, размеченный до
    включения настройки» здесь не имеет referent.
  - off-invariant: это И ЕСТЬ явный позитивный Then первого When-блока —
    негативная половина (что происходит без переключения тумблера, т.е.
    ON) уже зафиксирована TC-169; здесь оба состояния тумблера полностью
    покрыты вместе.
  - идемпотентность: н-п по той же причине, что edge vs level — бистабильный
    Switch не допускает повторный тап «в то же состояние» без
    промежуточного противоположного тапа, кейс которого выходит за рамки
    этой пары граней (не требуется §9-пунктом).
  - propagation: н-п — единственный потребитель эффекта — `onCreate`
    следующего холодного старта (`readInitialBrightnessValue`), нет
    broadcast/других вкладок/окон.
- Границы: НЕ дублирует TC-146/TC-055 (сам слайдер/жест без kill) и TC-169
  (сторона ON) — этот кейс закрывает именно сторону OFF, включая
  неочевидный побочный эффект самого тапа.
