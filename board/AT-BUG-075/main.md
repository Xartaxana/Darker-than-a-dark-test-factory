# AT-BUG-075 — TC-176 остаточный дефицит запаса тайминга burst-окна (~0.7-0.85с, ориентир критика ≥1с)

## Окружение

Не зависит от сборки приложения: долг тестовой системы (`type: test_debt`,
`debt_kind: flaky_test` — долг про риск гонки, не про длительность). Текущая тестируемая сборка на момент заведения —
`7a43fab8` (фикс `bugs/BUG-059.md`, статус Fixed).

## Суть долга

`test-cases/tabs/TC-176.md` (снекбар «Opened in background (N tabs)» считает
burst, не общее число вкладок) верифицирует свойство `backgroundOpenBurst`
(`BrowserViewModel.kt:281/293-300`), которое сбрасывается ЖЁСТКИМ таймером
Compose Material3 `SnackbarDuration.Short` = 4000мс
(`MainActivity.kt:342-347`, однострочная форма `showSnackbar(text)`). Тест
обязан выполнить ВТОРОЕ полное UI-действие («long-press карточки → overlay →
тап пункта меню») ДО истечения этого таймера, отсчитываемого от завершения
ПЕРВОГО такого же действия.

Критик (устройство, 6 прогонов + граничный зонд) забраковал rework attempt1
(`framework/steps/library_steps.py::open_in_background_via_overlay` без
изменений от исходной автоматизации): натуральный зазор tap1→tap2 —
3.68-3.94с, запас до обрыва (граничный зонд критика: 3.91с PASS / 4.41с
FAIL) — 0.06-0.32с, что МЕНЬШЕ разброса между прогонами самого примитива
(3.56-3.79с, разброс 0.23с) — тест был обречён иногда падать
`AssertionError`'ом «(1 tab)» вместо «(2 tabs)» (не перехватывается
`--reruns`, который целится только в `ReadTimeoutError`/`MaxRetryError`).

**Rework attempt2 (этот проход)** сделал КЛАССОВУЮ правку самого примитива
(затрагивает ТАКЖЕ TC-173/174/175/189, таргетно перепрогнаны, регрессии
нет) — убран буквально ДВОЙНОЙ round-trip Appium-команды на уже известное
состояние (`has_work` дублировал `find` внутри `long_press_work`;
`delete_overlay_visible()` дублировал ожидание внутри `tap_open_in_background`
`tap()`), `longClickGesture` короче (1000мс → 600мс, эмпирически проверено
10+ живыми срабатываниями без единого промаха, запас 100мс над системным
long-press-порогом Android 500мс) — плюс (`test_tabs.py`) убран
промежуточный `wait_persisted_tab_count(2)` между двумя открытиями.

**Измеренный эффект (живое устройство, 2026-08-15):**
- Натуральный зазор tap1→tap2 (несколько прогонов): **~3.1-3.5с** (было
  3.68-3.94с) — заметное улучшение.
- Свой граничный зонд (та же техника, что у критика — искусственная
  задержка МЕЖДУ tap1 и tap2): 4.079с/4.216с — «(2 tabs)» PASS; 4.308с/
  4.535с — «(1 tab)» FAIL. Обрыв — **~4.2-4.3с** (не ровно 4000мс —
  фиксированный оффсет между Python-меткой и фактическим стартом таймера
  на устройстве).
- Запас натурального зазора до обрыва — **~0.7-0.85с**. Ниже
  критик-ориентира «≥1с» (DoD rework attempt2, п.2), хотя втрое-впятеро
  лучше, чем было (0.06-0.32с).

## Почему это долг, а не «ещё один rejected»

Приёмка этого раунда (DoD rework attempt2) допускала АЛЬТЕРНАТИВНЫЙ путь:
«если не можешь безопасно ужать примитив за разумное время — пересмотри
сценарий, обоснуй выбор». Пересмотр сценария (проверено, задокументировано
в TC-176.md): единственный ДРУГОЙ продуктовый триггер `openTab(background =
true)` — `BrowserScreen.kt:718` (long-press ссылки внутри WebView,
TC-026-класс, задокументированно НЕНАДЁЖНАЯ координатная инъекция для этого
UI, тот же порядок стоимости UI-round-trip'ов) — не даёт выигрыша и меняет
предмет кейса. Deep-link путь (`openOrNavigateDeepLink`,
`BrowserViewModel.kt:660-665`) всегда `background = false` — вообще не
эмитит `BackgroundTabOpen`, непригоден. Дальнейшее ужатие ТРЕБУЕТ правок за
пределами манифеста этого диспатча (владение — только `TC-176.md` +
функция теста `test_tabs.py` + ОДНА функция `library_steps.py`):

1. **`framework/screens/library_screen.py`** — поддержка передачи УЖЕ
   найденного элемента карточки №2 в `long_press_work`/новый метод, чтобы
   вынести дорогой `find()` ЗА ПРЕДЕЛЫ временнóго окна (карточка №2 может
   быть найдена ДО тапа по карточке №1, пока бюджет ещё не тикает) — по
   оценке этого прохода экономит ~0.3-0.9с (наблюдаемая стоимость `find`
   в диагностике этого раунда). **Заодно чинит слоевой дрейф, внесённый
   rework attempt2** (критик-вход, находка 2, task_id `TC-176-burst-fix`):
   `library_steps.open_in_background_via_overlay` сейчас САМ делает
   `driver.execute_script("mobile: longClickGesture", ...)` и собирает
   локатор карточки, дублируя `LibraryScreen.long_press_work`, вопреки
   `docs/02-framework-architecture.md:44` (long-press — зона `screens/`, не
   `steps/`). Риск реален: в `library_screen.py:43-50` уже есть TODO про
   card-scoped локатор карточки — его починка в скопированный код `steps/`
   не попадёт. Правка этого пункта обязана параметризовать
   `long_press_work(title, duration_ms=...)` и убрать дубль из
   `library_steps.py`, а не только оптимизировать тайминг.
2. **`framework/core/adb.py`** (новый helper) — отключение системных
   `window_animation_scale`/`transition_animation_scale`/
   `animator_duration_scale` на время прогона (стандартный приём ускорения
   UI-автоматизации, НЕ правка `app-under-test/`) — уберёт
   Compose-анимационную составляющую задержки `tap_open_in_background`
   (наблюдаемая стоимость `tap`-шага в этом раунде — 0.8-1.8с, подозревается
   частичный вклад bottom-sheet slide-in анимации).

Ни один из путей не тронут в этом раунде — оба вне манифеста, требуют
отдельного дispatch'а с расширенными правами на указанные файлы.

## Критерий готовности (Fixed)

1. Один (или оба) из путей выше реализован(ы) — `library_screen.py`
   получает поддержку пред-найденного элемента ЛИБО `adb.py` получает
   helper отключения animation scale (используемый ТОЛЬКО в TC-176 или
   шире, по решению исполнителя).
2. Граничный зонд (та же техника, что в этом файле/TC-176.md) повторён —
   натуральный зазор tap1→tap2 отстоит от обрыва НЕ МЕНЕЕ чем на 1с
   (критик-ориентир).
3. TC-176 зелёный 3 раза подряд; TC-173/174/175/189 (если менялся
   `library_screen.py`) таргетно перепрогнаны без регрессии.
4. `TC-176.md` обновлён новыми числами зонда, эта запись переведена в
   `Fixed`.

**2026-08-15T14:52:22Z — test-maintainer, заведение (rework attempt2,
self-retry по rejected критика на `TC-176-burst-fix`).** Блокер обнаружен
при попытке довести запас тайминга до критик-ориентира ≥1с в рамках
манифеста, ограниченного `TC-176.md` + `test_tabs.py`-функцией + ОДНОЙ
функцией `library_steps.py`: эмпирически (12+ живых прогонов + 6-точечный
граничный зонд) показано, что классовая правка ЭТОГО примитива в ЭТИХ
границах даёт запас ~0.7-0.85с, не ≥1с — дальше упирается в стоимость
Appium-команд (`find`/`longClickGesture`/`tap`, ~0.3-1.8с каждая на этом
окружении) и Compose-анимацию overlay, ни то ни другое не сократить без
правок `library_screen.py`/`adb.py`, которые вне манифеста. Существующие
test_debt проверены (`grep -il "TC-176\|animation.scale\|window_animation\|
longClickGesture\|burst window"` bugs/*.md до создания этого файла) —
совпадений вне этого файла нет, дубликата нет.

**Дефекты-собратья (D-0043):** не расширял поиск за пределы
`open_in_background_via_overlay`/`TC-176` — вне мандата этого диспатча
(починка одного конкретного flaky-риска, не полный аудит Appium-таймингов
фреймворка). Один собрат ПОИМЕНОВАН явно (критик-вход, находка 4,
`TC-176-burst-fix`): `library_steps.py:112-122 delete_via_overlay` несёт
тот же двойной round-trip (`has_work`-подобная проверка + собственный
`find` внутри соответствующего screen-метода, ожидание `*_overlay_visible`
перед `tap_*`). Тайминговой нагрузки там нет (не завязан на 4-секундное
burst-окно) — чинить не срочно, но остаток явно поставлен в очередь этой
строкой, не молчанием.
