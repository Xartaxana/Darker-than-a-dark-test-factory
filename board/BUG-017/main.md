# BUG-017 — Быстрое закрытие вкладок → долгий парад снекбаров; подозрение на потерю Undo

## Окружение
- Версия приложения: 1.10 (versionCode 11), built_at 2026-07-02T02:39:46
- Эмулятор/устройство: тестировано ручно на реальном ПО (воспроизведено оператором)
- Режим: live (вручную через UI)

## Фасет 1: Парад снекбаров при быстром закрытии нескольких вкладок

### Шаги воспроизведения (Given-When-Then)

**Given:** открыто ≥4 вкладки в браузере

**When:** пользователь быстро закрывает 3+ вкладки подряд через TabStrip (свайп-вверх по чипу или крестик без задержки между закрытиями)

**Then (ожидалось):**
- Либо один агрегированный снекбар со счётчиком закрытых вкладок (например «3 tabs closed»), обновляемый при последующих закрытиях
- Либо каждый снекбар немедленно вытесняет предыдущий, максимум один видим одновременно

**Actual (фактически):**
- После каждого закрытия запускается отдельная корутина со `showSnackbar(..., duration=Short)` (~2.0–2.7 с)
- Compose's `SnackbarHostState` показывает снекбары **строго последовательно** (внутренний mutex)
- N закрытий = очередь из N снекбаров, суммарная длительность ≈ N × 2–2.7 сек
- При N=6 пользователь видит парад уведомлений ~12–16 секунд, перекрывающий контент и затрудняющий работу с приложением

### Частота
**Возникает при ЛЮБОМ быстром закрытии 3+ вкладок подряд** (повторяется 100% при таком входе; воспроизведено оператором)

### Корневая причина (из кода приложения)

**MainActivity.kt, строки 246–260** — метод `onCloseTab`:
```kotlin
val onCloseTab: (Int) -> Unit = { index ->
    val token = browserViewModel.closeTab(index)
    if (token != null) {
        coroutineScope.launch {                    // ← КАЖДОЕ закрытие = новая корутина
            val result = snackbarHostState.showSnackbar(
                message = "Tab closed",
                actionLabel = "Undo",
                duration = SnackbarDuration.Short,  // ← ~2.0–2.7 сек на этой сборке
            )
            if (result == SnackbarResult.ActionPerformed) {
                browserViewModel.restoreClosedTab(token)
            }
        }
    }
}
```

Compose's `SnackbarHostState` (внутренняя реализация) **показывает снекбары в очереди** (mutex-синхронизация). N одновременных корутин = N снекбаров в очереди. Каждый ждёт свой ~2–2.7 сек → парад.

## Фасет 2: Подозрение на потерю Undo-токенов при длительной задержке показа

### Описание подозрения

**(Арифметика исправлена 2026-07-31, разбор Lead по критик-входу CH-006
attempt 2 — defect_found BUG-017-facet2-arithmetic в routing-журнале; прежняя
редакция шагов 2–4 утверждала вытеснение токена САМОГО 6-го закрытия, что
противоречит коду.)** При быстром закрытии N вкладок подряд:

1. Закрытия 1–5: снапшоты сохраняются в `closedTabSnapshots` (буфер ёмкостью
   5, BrowserViewModel.kt:330)
2. Закрытие 6 (и каждое следующее): вытесняется снапшот СТАРЕЙШЕГО из
   закрытий (`closedTabSnapshots.remove(keys.min())`,
   BrowserViewModel.kt:331) — после N закрытий вытеснены токены 1..N−5,
   живы последние 5; токен самого свежего закрытия всегда ЖИВ
3. N корутин `showSnackbar` ждут очереди mutex'а `SnackbarHostState` (~2–2.7с
   каждая); снекбар закрытия 1 — ГОЛОВА очереди (показан сразу), задержаны
   снекбары закрытий 2..N
4. Опасная конъюнкция — «показ снекбара задержан очередью ∧ его токен уже
   вытеснен»: при N=6 она ПУСТА (вытеснен только токен 1, а его снекбар не
   задержан); впервые непуста при **N≥7** — к моменту показа снекбара
   раннего закрытия k (2 ≤ k ≤ N−5) его токен уже вытеснен последующими
   закрытиями
5. Пользователь видит живой снекбар с кнопкой "Undo" протухшего закрытия →
   нажимает → `restoreClosedTab(token)`: `closedTabSnapshots.remove(token)
   ?: return` (BrowserViewModel.kt:337) → молча ничего не делает

**Контроль (исправлено 2026-07-31 — прежний абзац нёс неподтверждённый
негатив):** МЕХАНИКА быстрой серии уже драйвится Automated-кейсом:
`framework/tests/test_tabs.py::test_undo_history_evicts_oldest_after_six_closes`
(TC-024) закрывает 6 вкладок подряд БЕЗ пауз (комментарий теста фиксирует
накопление очереди мьютекса), а шаг
`framework/steps/browser_steps.py::exhaust_undo_snackbars` жмёт Undo на
КАЖДОМ пойманном снекбаре и трактует молчаливый no-op вытесненного снапшота
как штатный ожидаемый исход. НЕ покрыт — **оракул отказа**: ни один TC не
ассертит, что при отказе Undo пользователь получает ВИДИМОЕ сообщение
(TC-024 проверяет только счётчики восстановления); отсутствие сообщения и
есть подозреваемый дефект (критерий владельца: «есть сообщение — всё норм»).
Живое воспроизведение конъюнкции N≥7 с человеческим вердиктом — CH-006
seed 5.

### Код-анализ (BrowserViewModel.kt, строки 336–346)

```kotlin
/** Reinserts the tab closed under [token], roughly at its original position. No-op if expired/unknown. */
fun restoreClosedTab(token: Long) {
    val snapshot = closedTabSnapshots.remove(token) ?: return  // ← return если токен забыт
    val state = _uiState.value
    if (state.tabs.size >= MAX_TABS) return                    // ← молчит, не уведомляет
    tabHistories[snapshot.tab.id] = snapshot.history
    val insertAt = snapshot.index.coerceIn(0, state.tabs.size)
    val newTabs = state.tabs.toMutableList().apply { add(insertAt, snapshot.tab) }
    _uiState.update { it.copy(tabs = newTabs, activeTabIndex = insertAt) }
    saveTabsToPrefs()
}
```

`closedTabSnapshots` — это `mutableMapOf<Long, ClosedTabSnapshot>()` (BrowserViewModel.kt:304). Ёмкость ограничена 5 (строка 330–332):
```kotlin
while (closedTabSnapshots.size > 5) {
    closedTabSnapshots.remove(closedTabSnapshots.keys.min())
}
```

При исчезновении токена нет сообщения об этом пользователю — функция просто возвращается (`?: return`). Ожидание: если Undo невозможен, приложение должно либо (а) заблокировать кнопку на снекбаре, либо (б) показать уведомление («Undo has expired»), как это делается в других приложениях.

## Связь с BUG-016

**BUG-016** («Undo закрытия вкладки на потолке 10 молча теряет вкладку») — другой сценарий молчаливого отказа Undo:
- **BUG-016**: Потолок MAX_TABS достигнут (10 вкладок) → попытка Undo → снапшот еще в буфере, но `if (state.tabs.size >= MAX_TABS) return` молчит
- **BUG-017, фасет 2**: Буфер переполнен (6+ закрытий) → попытка Undo → токена уже нет в буфере → `closedTabSnapshots.remove(token) ?: return` молчит

Оба — класс R-16 по критерию владельца: «молчаливая потеря функции / состояния пользователя, ожидание — видимое сообщение об отказе». Это соседи по симптому, требуют рассмотрения как системного дефекта Undo.

### Вердикт живого воспроизведения Фасета 2 (exploratory-tester, CH-006 seed 5, 2026-07-31)

**Фасет 2 ВОСПРОИЗВЕДЁН.** Среда: emulator-5554, replay `tab_markers.mitm`,
Appium 3.5.2, сборка та же (1.10 / versionCode 11). Протокол и скриншоты —
`exploratory-charters/CH-006.md` (пп. 15–16 протокола),
`exploratory-charters/attachments/CH-006/s5-*.png`.

**Измерения (сделаны ПЕРВЫМИ, до сценария — они же снимают вилку оценок):**

| Величина | Измерено | Прежние оценки |
|---|---|---|
| D — время жизни снекбара «Tab closed»+Undo | **≈ 3.3–3.8 с** (первый показ +0.48 с после свайпа, последний +3.81 с; гранулярность опроса 0.55 с) | 2.0–2.7 с (CH-005, оценка) vs ~4 с (докстринг `browser_steps.py:1911-1912`) — измерение поддерживает ВТОРУЮ |
| Δ — интервал между соседними свайп-закрытиями | **0.99–1.33 с** (среднее ≈1.17) | не измерялось |
| Длительность парада из 8 закрытий | **10.3–10.4 с** (два прогона) | Фасет 1: N×2–2.7 с |

**Сценарий и результат (2 независимых прогона, исход идентичен):** 9 вкладок
(Home + 8 маркеров, счёт из prefs `open_tabs_urls`) → 8 свайп-закрытий подряд
без пауз → обход очереди снекбаров с нажатием Undo на каждом; дискриминатор
исхода — число вкладок в prefs ДО/ПОСЛЕ каждого нажатия:

```
[(1, 1, 1, 'NO-OP'), (2, 1, 2, 'RESTORED'), (3, 2, 3, 'RESTORED'),
 (4, 3, 4, 'RESTORED'), (5, 4, 5, 'RESTORED'), (6, 5, 6, 'RESTORED')]
```

- Один **молчаливый no-op** — снекбар живой, кнопка Undo нажимается, счёт
  вкладок не меняется, **никакого сообщения об отказе в нативном дереве нет**
  (проверены подстроки cannot/expired/limit/error — ни одной).
- Ровно **5 восстановлений** — эмпирическое подтверждение ёмкости буфера 5
  (`BrowserViewModel.kt:330-332`): из 8 закрытых вкладок 3 невосстановимы.
- **Позитивный контроль выполнен в той же серии**: поздние снекбары
  восстанавливают вкладку ⇒ no-op не объясняется промахом тапа или
  авто-скрытием.

**Уточнение к описанию Фасета 2 (важно для оценки вероятности):** строгая
предпосылка, заложенная при планировании («вся серия обязана уложиться в
~2×D»), НЕ выполнена (10.3 с > ~7 с) — и тем не менее конъюнкция «показ
задержан ∧ токен вытеснен» наступила. Причина: ранние снекбары успевают
протухнуть НЕПОЙМАННЫМИ, и первым снекбаром, до которого пользователь
физически успевает дотянуться, оказывается снекбар уже вытесненного токена
(расчёт очереди: показы 1..3 укладываются в 0–12.1 с, первое нажатие
пришлось на t+12.6 с). Практический вывод: **дефект достижим на обычном
ручном темпе закрытия (Δ/D ≈ 0.35), а не только в синтетически быстрой
серии** — «маловероятный край» (вопрос 2 ниже) отвечается отрицательно.

**Что это меняет в самом баге:** пункт «Второй фасет: Undo после эвикции —
молча ничего не происходит (требует проверки)» в таблице проверяемых данных
больше не гипотеза; отметка о возможном повышении severity (молчаливая
потеря пользовательского состояния = major по критерию владельца) переходит
в решаемую развилку — решение за bug-reporter/владельцем, exploratory-tester
severity не двигает.

**Вопросы разработчику:**

2. Второй фасет (потеря токена при длительной очереди) — воспроизводима ли на CH-006 seed 5, или это маловероятный край?
3. Если оба фасета подтверждены, одно ли это исправление (агрегирование уведомлений) или два?

### Решение по severity-развилке (bug-reporter, 2026-07-31T19:35:00Z)

**Фасет 2 ВОСПРОИЗВЕДЁН на CH-006 seed 5 с полным набором измерений**, вердикт от exploratory-tester записан выше. Анализ данных:

- **Молчаливая потеря функции:** Undo срабатывает на живых токенах (проверено позитивным контролем), но молча откликается на вытесненные (no-op без сообщения об ошибке).
- **Оракул отказа отсутствует:** ни один TC не ассертит видимое сообщение при отказе Undo (критерий владельца: «есть сообщение — всё норм»). Наличие no-op БЕЗ сообщения = дефект по критерию владельца.
- **Конъюнкция достижима на обычном ручном темпе:** Δ/D ≈ 0.35 (интервал между закрытиями ≈ 35% времени жизни снекбара). Не синтетический edge-case.
- **Результат:** молчаливая потеря пользовательского состояния (невозможность отменить закрытие вкладки) = **major** по критерию владельца.

**Severity повышена с minor на major** (frontmatter обновлён; status: Open как и раньше). Фасет 1 (парад снекбаров) остаётся minor-уровнем (UX-обструкция, не молчаливая потеря). Оба фасета могут требовать общего исправления (агрегирование уведомлений снизит Δ/D и предотвратит конъюнкцию), вопрос разработчику остаётся актуален.
