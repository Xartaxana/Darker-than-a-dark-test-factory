# TC-166 — Restore: удалённый локально профиль возвращается, переименованный — остаётся под новым именем

## Предусловия
- Приложение запущено, в Room засеяны ДВА filter-профиля: P1 ("Profile
  One") и P2 ("Profile Two"), у каждого свой `queryString`.
- Backup-файл экспортирован, содержит ОБА профиля с исходными именами.
- После экспорта: P1 переименован через Settings UI в "Profile One
  RENAMED" (тот же id, `queryString` не изменился — образец TC-085); P2
  удалён через Settings UI (образец TC-086).
- SAF file picker доступен для Restore того же файла.

## Сценарий (Given-When-Then)

**Given** backup содержит профили P1 ("Profile One") и P2 ("Profile Two");
ПОСЛЕ экспорта P1 переименован локально в "Profile One RENAMED" (тот же
`id`), P2 удалён локально

**When** пользователь выполняет «Restore from backup» и выбирает ТОТ ЖЕ
файл

**Then** после Restore в Settings отображаются РОВНО ДВА профиля: один под
именем **"Profile One RENAMED"** (НЕ откатился на бэкапное "Profile One" —
совпадение по `id` даёт скип, имя из бэкапа не применяется), второй —
**"Profile Two"** (вернулся из бэкапа, `queryString` совпадает с исходным)
**And** `queryString` профиля P1 не изменился на всём протяжении сценария
(rename трогает только `name`, Restore его не касается из-за скипа по `id`)
**And** дубликатов по `id` нет — итоговое множество профилей в Room имеет
мощность 2, не 3

**Инвариант:** разрешение конфликта профилей при Restore определяется
ИСКЛЮЧИТЕЛЬНО по `id`, `name` в сравнении не участвует: локальное
переименование профиля, чей `id` уже есть в бэкапе, ПЕРЕЖИВАЕТ Restore (не
откатывается), а профиль, ЛОКАЛЬНО удалённый (его `id` отсутствует в
Room), Restore ВОЗВРАЩАЕТ из бэкапа с исходными полями — оба исхода
проверяются ОДНИМ вызовом Restore, множество id/name после равно ожидаемой
комбинации {P1 renamed, P2 original}, не задублировано и не потеряно.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| P1 имя до бэкапа | "Profile One" |
| P1 имя ПОСЛЕ локального rename | "Profile One RENAMED" |
| P1 имя ПОСЛЕ Restore | "Profile One RENAMED" (без изменений) |
| P2 после локального delete | отсутствует в Room |
| P2 после Restore | восстановлен, "Profile Two", исходный `queryString` |
| Итоговое число профилей | 2 |

## Заметки для автоматизации
- Не заблокировано инфраструктурой — `seed_filter_profiles`/
  `read_filter_profiles` уже существуют (TC-021), rename/delete-степы уже
  существуют (`framework/tests/test_filter_profiles.py`, использованы
  TC-085/TC-086), SAF backup/restore готовы (TC-021/TC-039).
- Сверка после Restore — прямым чтением Room
  (`seed_db.read_filter_profiles()` + сравнение по `(name, queryString)`,
  тот же паттерн, что `backup_steps.assert_filter_profiles_match` в TC-021),
  НЕ через текст диалога (диалог несёт только числа, не имена — сама эта
  черта диалога уже отмечена CH-007 находкой 3/Г1, не переоткрывается
  здесь).
- Дельта к TC-021: там оба профиля переживают Restore БЕЗ локальных
  изменений между экспортом и Restore (round-trip «как есть»); здесь ПОСЛЕ
  экспорта происходит ЛОКАЛЬНАЯ мутация (rename ОДНОГО, delete ДРУГОГО) —
  именно эта дельта и есть предмет кейса, ранее ничем не покрытая.
- Дельта к TC-085 (rename сохраняет `queryString`, без двери импорта) и
  TC-086 (delete через UI, без Restore) — здесь ОБЕ операции проверяются
  ЧЕРЕЗ дверь Restore, которую ни TC-085, ни TC-086 не затрагивают.
- **Батарея правил-реакций** — н-п: Restore — явное прямое действие
  пользователя, не авто-триггер побочного эффекта на несвязанном событии.
