# TC-287 — E-ink: удержание касания не даёт визуальной индикации ни на одном из двух потребителей `LocalRippleConfiguration`

## Предусловия
- Приложение запущено с чистыми данными (`clean_app`); в Library засеяна
  ОДНА работа рейтингом LIKE, видна во вкладке Liked (тот же сидинг, что
  используют существующие `long_press_work`-сценарии, напр. TC-173..176/
  TC-034/035).
- Settings достижим обычной навигацией из Library/Browser.
- Дефолт эталонного AVD: тема Light, E-ink mode OFF
  (`Build.MANUFACTURER != "ONYX"` — граница чёрного ящика, тот же довод,
  что TC-276).

## Сценарий (Given-When-Then)

**Given** Library открыта на вкладке Liked, засеянная работа видна карточкой; E-ink mode OFF

**When**
1. **Открытие оверлея действий (обычная навигация, НЕ часть зонда):**
   на засеянной карточке выполняется ОБЫЧНЫЙ завершённый долгий тап —
   `long_press_work` (`mobile: longClickGesture`, один блокирующий вызов,
   палец физически не удерживается между командами) — открывается
   `ModalBottomSheet` со ВСЕМИ пунктами (см. «Заметки», N3): «Open in
   background tab», «Rate / edit note», «Open in e-reader app», «Send to
   my other devices», «Delete work», «Delete downloaded file». Строка
   «Rate / edit note» находится (`by_text`) и кэшируется — она ПЛОСКИЙ
   `.clickable()`, без конкурирующего `onLongClick`.
2. **Проба foundation OFF («Rate / edit note»):** ДО касания снимается
   скриншот bounding-box строки — `shot_row_off_rest`. Сырой raw-touch:
   `pointerMove` в центр строки → `pointerDown` → УДЕРЖАНИЕ (пауза
   ~400мс, БЕЗ `pointerUp` в этом же `perform()`) → скриншот той же
   bounding-box — `shot_row_off_pressed` → ВТОРОЙ `perform()`:
   `pointerMove` в НЕЙТРАЛЬНУЮ зону оверлея (заголовок/подзаголовок
   `work.title` в шапке `WorkActionsSheetContent`, `:392-420` — текст без
   `.clickable()`, НЕ соседний `WorkActionMenuItem` — см. «Заметки»,
   безопасность жеста) → `pointerUp` (клик НЕ засчитывается — release вне
   bounds строки; оверлей остаётся открытым, ни один пункт не сработал).
3. **Проба Material3 OFF (Settings Switch):** оверлей закрывается (тап по
   скриму/back), переход в Settings; строка «E-ink mode» находится,
   элемент её `Switch` кэшируется. ДО касания — `shot_switch_off_rest`.
   Тем же приёмом (press → hold ~400мс → `shot_switch_off_pressed` →
   move-away-cancel в соседний неклик-абельный текст строки → release) —
   тумблер ЭТИМ жестом НЕ переключается.
4. E-ink mode ВКЛЮЧАЕТСЯ обычным тапом (`set_eink_mode(True)`, локатор
   по образцу TC-276); Settings-экран перерисовывается немедленно через
   `CompositionLocalProvider` (без reload/сети — тот же довод, что
   TC-276).
5. **Проба foundation ON:** возврат в Library/Liked, ТА ЖЕ карточка;
   повтор шага 1 (открытие оверлея обычным долгим тапом) и шага 2
   (hold-проба на «Rate / edit note») — `shot_row_on_rest`/
   `shot_row_on_pressed`.
6. **Проба Material3 ON:** возврат в Settings, ТОТ ЖЕ `Switch`; повтор
   пробы шага 3 — `shot_switch_on_rest`/`shot_switch_on_pressed`.

**Then**
- (позитивный контроль, доказывает достижимость зонда — ЖЁСТКИЙ ассерт)
  `shot_row_off_pressed` СУЩЕСТВЕННО ОТЛИЧАЕТСЯ от `shot_row_off_rest`,
  И `shot_switch_off_pressed` СУЩЕСТВЕННО ОТЛИЧАЕТСЯ от
  `shot_switch_off_rest` (в обычной теме удержание видимо рисует
  ripple/state-layer overlay на ОБОИХ виджетах). Если хотя бы одна из
  этих двух OFF-пар совпала — тест ОБЯЗАН упасть ИМЕННО на этом ассерте
  с диагностикой «зонд не поймал индикацию — проверить длительность
  удержания/idle-гейт перед interaction-командами (см. TC-278
  прецедент)», НЕ продолжать молча к ON-шагам с этим фактом как
  предупреждением.
- `shot_row_on_pressed` РАВЕН `shot_row_on_rest` (в пределах шумового
  допуска скриншота) — на E-ink строка «Rate / edit note» визуально НЕ
  меняется при удержании.
- `shot_switch_on_pressed` РАВЕН `shot_switch_on_rest` — на E-ink
  `Switch` визуально НЕ меняется при удержании.

**Инвариант:** свойство «удержание касания НЕ производит видимой
индикации» верно НЕЗАВИСИМО на ДВУХ render-call-sites — foundation
`.clickable()` без явной индикации (резолвится в `LocalIndication.current`,
который ВНУТРИ `MaterialTheme` — сам `ripple()`) и Material3 `Switch`
(использует `ripple()` напрямую) — при E-ink ON, и ЛОЖНО (индикация ЕСТЬ)
для ОБОИХ на ТЕХ ЖЕ виджетах тем же жестом при E-ink OFF. Это НЕ два
независимых механизма (attempt 1 ошибочно утверждал независимость через
`LocalIndication`/`LocalRippleConfiguration`) — оба render-call-site'а
в конечном счёте управляются ОДНИМ И ТЕМ ЖЕ гейтом,
`LocalRippleConfiguration provides null` (`Theme.kt:205`); кейс проверяет
это единое свойство на двух разных потребительских путях (семья
{состояние: off/on} × {render-call-site: foundation `.clickable()`/
Material3 `Switch`}), не два разных гейта — тот же класс OFF/ON-
достижимости, что позиционный инвариант TC-278.

## Заметки для автоматизации
- **«hold-across-two-perform()» — примитив НЕ верифицирован, живой
  спайк ОБЯЗАТЕЛЕН до автоматизации (критик-вход attempt 1, координатор
  attempt 2, `bugs/AT-BUG-093.md`):** существующий `ActionBuilder`/
  `POINTER_TOUCH` (`browser_screen.py:174-210`) до сих пор использовался
  ТОЛЬКО как ОДИН `perform()` с down+move+up внутри (см. также
  `swipe_scroll_active_tab_down`, `drag_brightness_down/up` — тот же
  класс, всегда один блокирующий вызов). Этот кейс планирует: первый
  `perform()` — `pointerMove`+`pointerDown` БЕЗ `pointerUp`; скриншот;
  второй `perform()` С ТЕМ ЖЕ pointer-id — `pointerMove`(в нейтральную
  зону)+`pointerUp`. Критик нашёл ПРЯМОЕ контр-свидетельство на РЕАЛЬНОМ
  стеке: `appium-uiautomator2-driver@8.0.1`
  (`lib/commands/actions.ts:94-96`) реализует `releaseActions` как
  **no-op**, что указывает на отсутствие межзапросного моделирования
  состояния указателя ЭТИМ драйвером — заявление «состояние пальца
  сохраняется между вызовами, стандартная W3C-семантика» НЕ подтверждено
  эмпирически на этом стеке. Устройство недоступно этому дизайн-заходу
  (координатор, attempt 2) — редизайн с попыткой ИЗБЕЖАТЬ примитива
  (перенос наблюдения на «после release», однократный `perform()`)
  разобран и ОТКЛОНЁН: и ripple (Compose `PressInteraction.Cancel` при
  drag-out гасит индикацию почти мгновенно, без плавного fade, в отличие
  от `Release`), и полноценный `.click()` без drag-out-cancel (триггерит
  реальный `onClick` — навигация/открытие оверлея меняет содержимое
  bbox ОДИНАКОВО что в OFF, что в ON, стирая различающий сигнал, тот же
  класс контаминации, что был у `onLongClick` в attempt 1) — оба
  альтернативных пути хуже исходного. Видеозапись
  (`startRecordingScreen`/frame-extraction) как альтернатива
  рассматривалась и ОТКЛОНЕНА: это ЕЩЁ ОДИН неверифицированный
  примитив (framework его вообще не использует нигде — `grep` пуст),
  не более надёжный, а НОВЫЙ риск сверху старого. **Вывод:** технику
  оставляем как ЛУЧШИЙ из известных вариантов дизайна, но она ОБЯЗАНА
  быть подтверждена живым спайком (`bugs/AT-BUG-093.md`, критерий Fixed)
  ДО того, как test-automator положится на неё в проде — не «рутина»,
  как ошибочно было заявлено в attempt 1.
- **Почему НЕ гонка со временем (в отличие от старого разностного
  тайминга TC-278):** удержание — это СОСТОЯНИЕ (палец физически внизу
  между двумя `perform()`-вызовами, ЕСЛИ примитив подтвердится), а не
  однократный переход; Material-ripple ПРИ УДЕРЖАНИИ остаётся видимым
  (state-layer держится, пока палец прижат, гаснет только на release)
  — 400мс произвольны и НЕ являются узким окном для ЛЮБОЙ задержки
  между `pointerDown` и скриншотом; для ON-стороны нечему появляться
  вообще (истинный гейт `LocalRippleConfiguration provides null`
  отключает рендер `ripple()` целиком), задержка тоже не критична. Этот
  довод — про надёжность ВРЕМЕНИ УДЕРЖАНИЯ, не про сам примитив
  межзапросного состояния (см. пункт выше).
- **Idle-гейт (предупреждение по прецеденту TC-278):** UiAutomator2
  ожидание «покоя» дерева перед interaction-командами
  (`framework/steps/app_steps.py::set_fast_idle_timeout`) МОЖЕТ повлиять
  на round-trip `perform()`-вызовов так же, как на `find_elements` в
  TC-176/TC-278 — автоматизатору стоит замерить живой round-trip перед
  калибровкой длительности удержания, не предполагать «достаточно
  400мс» без проверки.
- **E-ink-тумблер — новый локатор (не блокер, рутина, как в TC-276):**
  `set_eink_mode`/`is_eink_mode_checked` в `settings_screen.py`, приём
  `find_row_sibling`, ещё не реализован на момент дизайна.
- **Безопасность жеста:** move-away-цель ОБЯЗАНА быть неклик-абельной
  зоной — для строки оверлея это заголовок/подзаголовок работы вверху
  `WorkActionsSheetContent` (`:392-420`, чистый `Text`, без
  `.clickable()`), а НЕ соседний `WorkActionMenuItem` (иначе релиз
  сработал бы КАК КЛИК на соседнем пункте — «Delete work»/«Send to my
  other devices» и т.п. — это была бы РЕГРЕССИЯ приёма, не просто
  безобидный промах). Для `Switch` — соседний `Text` (заголовок/подзаголовок
  строки, `SettingsSwitchRow`, `:1651-1655`), не другая `SettingsSwitchRow`
  выше/ниже. Если жест всё же случайно завершится как клик (регрессия
  приёма) — тест ОБЯЗАН считать это отказом пробы, не игнорировать.
- **N3 (критик-вход attempt 1) — оверлей несёт ШЕСТЬ пунктов, не один:**
  «Open in background tab», «Rate / edit note», «Open in e-reader app»,
  «Send to my other devices», «Delete work», «Delete downloaded file»
  (`WorkActionsSheetContent`, `LibraryScreen.kt:421-471`) — существующие
  фреймворк-хелперы (`delete_overlay_visible`/`tap_delete_work`,
  `library_screen.py:318-322`) называют только «Delete work», это НЕ
  полный перечень пунктов оверлея; этот кейс использует «Rate / edit
  note» (не деструктивный пункт, безопасный носитель зонда).
- **`NoIndication` — мёртвый код (находка, НЕ решение за владельца
  кода приложения):** `Theme.kt:166-172` (`NoIndication`/`NoopNode`) и
  внешняя провизия `LocalIndication provides NoIndication`
  (`Theme.kt:204`) НИКОГДА не долетают до потребителей — `MaterialTheme`
  (`:207`/`:210`) переопределяет `LocalIndication` своей ВНУТРЕННЕЙ
  провизией (`ripple(...)`) для всего, что рендерится внутри него, а
  рендерится там весь `content` приложения. Удаление `NoIndication` из
  кода не изменит наблюдаемое поведение — этот кейс его НЕ упражняет и
  не заявляет обратного (в отличие от attempt 1). Не заводится багом
  (нет наблюдаемого пользователем дефекта — единственный реальный гейт
  `LocalRippleConfiguration provides null` работает корректно) — доклад
  координатору как находка кода приложения, не сам дизайн решает.
- **Батарея правил-реакций — н-п:** область не несёт событийного
  правила-реакции с СОХРАНЯЕМЫМ побочным эффектом (нет персистентной
  мутации/broadcast/авто-действия) — это чистая функция композиции от
  текущего значения `LocalEinkMode`/`einkMode`, пересчитываемая на
  каждый рендер; edge-vs-level/ретроактивность/propagation-пункты
  батареи неприменимы структурно, не по недосмотру.
- **Non-goal явно:** физика реального e-ink дисплея (смаз/остаточное
  изображение при РЕАЛЬНОМ ripple, если бы он не подавлялся) — вне
  чёрного ящика AVD, решение владельца 2026-08-20 (см. §9 области).

## Чек-лист качества (test-designer проходит перед `Review`)
- [x] Один сценарий — один кейс (одна проба «удержание → индикация»,
  повторённая для двух render-call-site'ов одного гейта и двух состояний
  тумблера — не два сценария)
- [x] Given описывает полное состояние, воспроизводимое `clean_app` +
  стандартным сидингом рейтинга
- [x] Then проверяет наблюдаемое поведение (реальный отрендеренный
  пиксель во время реального удержания), а не реализацию (не читает
  `LocalIndication`/`LocalRippleConfiguration` напрямую)
- [x] Заголовок сформулирован от ожидаемого поведения
- [x] Указаны приоритет, область, риск (R-13 A11Y ∩ R-11) и источник
  требования
- [x] Кейс независим от порядка выполнения других кейсов (move-away-
  cancel не оставляет состояния кроме E-ink ON и открытого/закрытого
  оверлея — оба сбрасываются `clean_app` следующего прогона)
- [x] Область комбинаторная (семья {off/on} × {render-call-site}) —
  инвариант назван строкой `Инвариант:` выше, честно про ОДИН гейт на
  двух путях, не про два независимых механизма
- [x] Область с правилом-реакцией — н-п с обоснованием (см. заметки)
- [x] Неверифицированный примитив автоматизации — назван явно, заведён
  `bugs/AT-BUG-093.md` (test_debt), не оставлен молчаливой заметкой
- [x] Слой **L3**, «почему не L2»: оракул — реально отрендеренный
  Compose-пиксель ВО ВРЕМЯ реального удержания (настоящий `ripple()`/
  `RippleConfiguration` движок Android runtime), зафиксированный настоящим
  Appium/UiAutomator2 round-trip; device-free L2-гарнизон (jsdom) не
  рендерит Compose и не имеет состояния указателя/ripple-движка вовсе —
  L2 структурно неприменим, тот же класс аргумента, что TC-276/278.
