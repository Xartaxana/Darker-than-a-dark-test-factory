# BUG-048 — молчаливая перезапись метаданных пересборщиком уносит рабочие оси библиотеки

## Статус решения

вариант «баг»): сама перезапись метаданных соответствует коду («освежили
метаданные со страницы»), предмет бага — что она **молчаливая** и уносит
рабочие оси библиотеки пользователя (фильтр по фандому, сортировка по
wordCount, видимость на вкладках). Источник наблюдений — exploratory-чартер
`CH-008` (находка 4, вердикт risk → переквалифицирован владельцем в баг).

## Механизм (сверено по коду)

У приложения два типа «дверей записи» в строку `work_ratings`:

- **двери-редакторы** — панель на странице работы: `existing.copy(...)`
  (`BrowserViewModel.kt:698-705`, `:746-753`) — метаданные и
  `downloadPath` переживают;
- **двери-пересборщики** — overlay листинга (bottom-sheet):
  `WorkRating(...)` конструктором (`BrowserViewModel.kt:807-813` «Save
  note» при `rating=null`, `:840-853` ветка с рейтингом) —
  `title/author/fandom/wordCount` берутся из СКРЕЙПА текущей страницы,
  `downloadPath` отсутствует в аргументах ⇒ дефолт `null` (аспект
  `BUG-021`).

Оси библиотеки строятся ИЗ САМИХ СТРОК, а не из справочника:
`LibraryViewModel.kt:76-78` (`allFandoms = flatMap+distinct` по полю
`fandom`), вкладки — `:70-74` по `rating`, FILES — `WorkRatingDao.kt:27-28`
(`WHERE downloadPath IS NOT NULL`), пустое состояние —
`LibraryScreen.kt:1072`. Поэтому перезапись поля стирает фандом не у одной
карточки, а из СПИСКА фильтр-панели целиком.

## Шаги воспроизведения (пользовательские, без инструментов)

Предусловие — сохранённые метаданные разошлись со страницей. Живые пути
расхождения: работа оценена давно, автор дописал главы (wordCount вырос)
или перетегировал фандом на AO3; восстановление из старого бэкапа (бэкап
несёт `fandom`/`word_count`); строка создана дверью с неполным скрейпом.

**Вариант А (мягкий — оси едут):**

**Given** работа оценена (например, Loved) и лежит в Library; сортировка по
wordCount даёт ей позицию; её фандом виден в списке фильтр-панели
**When** пользователь на ЛИСТИНГЕ открывает overlay работы и правит только
личную заметку («Save note») — действие, которое «не должно» трогать
метаданные
**Then (ожидалось)** заметка сохранена; заголовок/фандом/wordCount и место
работы в фильтрах/сортировках не меняются, ЛИБО пользователь получает
видимый сигнал «метаданные обновлены со страницы»
**Actual** молча: `title/fandom/wordCount` заменены значениями текущей
страницы → работа прыгает в сортировке по wordCount; если старый фандом был
только у неё — он исчезает из списка фильтр-панели (активный фильтр больше
не находит работу). Сообщения нет. (Чартер: фандом «Мой фандом» исчез из
пикера 2×; wordCount 777777→4200 сдвинул сортировку.)

**Вариант Б (жёсткий — работа исчезает отовсюду; пересечение с BUG-021):**

**Given** скачанная работа БЕЗ рейтинга (только заметка) — видна на вкладке
FILES
**When** правка заметки через overlay листинга
**Then (ожидалось)** работа остаётся видимой хотя бы на FILES
**Actual** пересборщик за один вызов оставляет `rating=null` И роняет
`downloadPath` (аспект `BUG-021`) → строка жива, файл на диске, но работа
не видна НИ НА ОДНОЙ вкладке («Nothing here yet») — из UI её больше не
найти. Контроль (находка 6 CH-008): при `rating=null` но живом
`downloadPath` работа на FILES видна — findability убивает именно ПАРА
эффектов одной двери.

**Контроль двери:** те же действия через ПАНЕЛЬ на странице работы ничего
не портят (наблюдение R3 чартера, скриншоты
`exploratory-charters/attachments/CH-008/`).

## Почему не дубликат BUG-021

`BUG-021` — потеря ПОЛЬЗОВАТЕЛЬСКОГО состояния (personal tags,
`downloadPath`) пересборщиком; его фикс — сохранить эти поля
(`existing.copy`-образец в соседней двери). `BUG-048` — про
UX-контракт ОСВЕЖЕНИЯ производных метаданных: даже корректное «обновили со
страницы» не должно молча уносить фильтруемость/сортируемость/видимость
работы. Фиксы могут пересечься (перевод overlay-дверей на `existing.copy`
закроет оба), но требование этого бага — отсутствие МОЛЧАЛИВОЙ потери осей
(сигнал пользователю или консервативное сохранение) — самостоятельное:
критерий владельца «есть сообщение — норма» (§10 (п)) здесь не выполнен.
