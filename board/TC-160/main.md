# TC-160 — Цепочка checkPageDensity доходит до первой непустой страницы (3 подряд пустых → страница 4)

## Предусловия
- Приложение запущено с чистыми данными; `infinite_scroll = ON`,
  `hide_disliked = ON`, `filter_display_mode = hide` (дефолты).
- В Room засеяны работы страниц 1, 2 и 3 листинга (`listing_paginated.mitm`,
  по 1 work-блёрбу на страницу) с рейтингом DISLIKE — каждая ЕДИНСТВЕННАЯ
  работа своей страницы; работа страницы 4 — БЕЗ рейтинга (видима).
- Режим replay.

## Сценарий (Given-When-Then)

**Given** работы страниц 1, 2, 3 листинга помечены DISLIKE (по одной,
единственной на страницу), работа страницы 4 без рейтинга (видима),
`infinite_scroll = ON`, `hide_disliked = ON`

**When** пользователь открывает страницу 1 листинга

**Then** приложение выполняет ЦЕПОЧКУ из ТРЁХ последовательных ПОЛНЫХ
навигаций (стр.1→2→3→4), каждая — самостоятельное срабатывание
`checkPageDensity` на своей загрузке (не одна навигация «через» три
страницы)
**And** итоговая страница — 4, на ней видна её собственная (не скрытая)
работа
**And** цепочка останавливается САМА на первой непустой странице — далее
автонавигаций нет

**Инвариант:** `checkPageDensity` — не одноразовая проверка входа, а
проверка, повторяющаяся на КАЖДОЙ НОВОЙ загрузке страницы независимо от
того, как пользователь на неё попал (ручная навигация или предыдущий
автопрыжок); цепочка из N подряд пустых страниц даёт РОВНО N полных
навигаций и останавливается на первой странице, где условие «все работы
скрыты» ложно — свойство обобщает representative-случай TC-159 (N=1) на
N=3.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работы страниц 1-3 | по одной, `rating=DISLIKE` каждая |
| Работа страницы 4 | без рейтинга (видима) |
| Итоговая страница | 4 |
| Число автонавигаций | 3 |

## Заметки для автоматизации
- Дельта к TC-159: тот же механизм, представитель N=3 вместо N=1; НЕ
  дублирует TC-159 — проверяет ДРУГОЕ свойство (остановку цепочки на первой
  непустой странице, а не единичный факт автонавигации).
- Наблюдение промежуточных навигаций — по коду каждая навигация полная
  (смена `pathname`), поэтому счётчик переходов можно снять через
  `browser_steps` хук на смену `location.href` (poll-differencing), либо
  через историю вкладки в prefs (`historyIndex`/`historyEntries`, тот же
  примитив, что использовала CH-006 дизамбигуация back-ловушки, но здесь —
  только СЧЁТ переходов, не Back). Итоговое состояние — то же, что TC-159
  (`assert_webview_location_changed` до `page=4`).
- Таймаут ожидания — шире, чем TC-159 (три последовательные загрузки вместо
  одной); `wait_until` с увеличенным бюджетом.
- Не заблокировано инфраструктурой: `listing_paginated.mitm` уже собран,
  сидинг трёх работ разных страниц — `seed_library` с тремя записями.
- **Батарея правил-реакций (оценка применимости):** амплификационный аспект
  этого кейса (серия автоматических повторений ОДНОГО правила) — сам кейс и
  есть амплификация checkPageDensity; отдельно оценивать её не требуется.
  Остальные пункты — н-п по тем же причинам, что TC-159 (ретроактивность,
  propagation); off-инвариант — сиблинг TC-161; идемпотентность в смысле
  «повтор действия не дублирует эффект» — н-п, здесь эффект по построению
  срабатывает N раз на N разных загрузках, это не повтор ОДНОГО и того же
  события.
