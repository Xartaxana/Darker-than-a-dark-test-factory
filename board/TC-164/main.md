# TC-164 — Restore в непустую Library: скип по ao3Id и релинк файла в одном диалоге

## Предусловия
- Приложение запущено, в Room ЗАСЕЯНА работа W (`ao3_id 900000001`) с
  рейтингом SAVE, `downloadPath = null` (файл считается ещё не привязанным —
  тот же легальный сетап, что TC-038: работа существует, скачанный файл на
  диске есть, но связь ещё не установлена).
- В ДЕФОЛТНОЙ папке загрузок (`getExternalFilesDir("ao3_downloads")`) лежит
  файл `orphan_900000001.html`, матчащий `WORK_ID_PATTERN` — положен заранее
  adb-шеллом (та же техника, что TC-038/TC-039).
- Подготовлен backup-файл (`{"version":2,"works":[…],"filterProfiles":[…]}`),
  содержащий работу с `ao3Id = 900000001` (та же работа, что уже в Room —
  условие СКИПА по `ao3Id`) и НЕ содержащий `downloadPath` (на момент этого
  бэкапа файла на устройстве не было — та же логика фикстуры, что TC-039).
- SAF file picker доступен.

## Сценарий (Given-When-Then)

**Given** Library НЕпуста — содержит работу W (`ao3_id 900000001`, рейтинг
SAVE, без привязанного файла); в папке загрузок лежит orphan-файл того же
`ao3Id`; backup-файл содержит работу с тем же `ao3Id`

**When** пользователь выполняет «Restore from backup» и выбирает
подготовленный файл

**Then** появляется РОВНО ОДИН диалог результата, объединяющий ОБА факта:
работа W пропущена как дубликат (`skippedCount`, "already existed") И её
файл перелинкован тем же импортом (`relinked 1`) — дословно: «Restored 0
works, 0 filters (1 works already existed). Also relinked 1 and added 0
downloaded file(s).»
**And** после закрытия диалога карточка работы W в Library показывает
иконку «Open downloaded» (не Download) — файл реально привязан
**And** рейтинг/прочие поля работы W НЕ изменились относительно состояния ДО
Restore (скип означает, что бэкапная версия строки не применилась —
локальное состояние выжило)

**Инвариант:** `importFromUri` выполняет РАЗРЕШЕНИЕ КОНФЛИКТА работ (скип по
`ao3Id`) и `scanForOrphanedDownloads()` КАК ДВЕ НЕЗАВИСИМЫЕ подсистемы
ОДНОГО вызова — скип строки по `ao3Id` НЕ мешает релинку её файла тем же
проходом, и оба счётчика сходятся в ОДНОМ диалоге результата (round-trip
множества файлов↔строк корректен даже когда round-trip множества
записей-работ даёт скип, не импорт) — сиблинг общего банка «backup → clear →
restore сохраняет множество записей и ключевые поля», здесь — частный
случай «restore НЕ трогает уже существующую запись, но всё ещё обслуживает
файловую подсистему».

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W до Restore | `ao3_id 900000001`, `rating=SAVE`, `downloadPath=null`, уже в Room |
| Orphan-файл | `orphan_900000001.html`, дефолтная папка загрузок |
| Backup | содержит `ao3Id=900000001`, без `downloadFile`/`downloadPath` |
| Диалог результата | «Restored 0 works, 0 filters (1 works already existed). Also relinked 1 and added 0 downloaded file(s).» |
| Карточка Library после | иконка «Open downloaded» |

## Заметки для автоматизации
- **Декой-барьер BUG-011 (обязателен по прецеденту TC-039)** — если
  orphan-файл кладётся в НОВУЮ (только что выбранную) SAF-папку ДО её
  выбора, асинхронный `scanForDownloads(silent=true)` может успеть создать
  stub-строку с тем же `ao3Id` РАНЬШЕ Restore и исказить счётчики (класс
  BUG-011). Этот кейс использует ДЕФОЛТНУЮ (не переключаемую) папку
  загрузок — папка не выбирается заново в рамках теста, поэтому гонки
  BUG-011 в этом потоке нет по построению (тот же вывод, что CH-007
  Ловушки: «на пустой подпапке скан при выборе не пишет в Room ничего»,
  здесь папка вообще не переключается). Если тест решит переключать папку —
  ОБЯЗАТЕЛЕН decoy-барьер `restore_scan_workspace`
  (`framework/tests/test_downloads.py`), как в TC-039.
- Не заблокировано инфраструктурой — SAF-инфраструктура полностью готова
  (`framework/steps/saf_steps.py`, `backup_steps.py`), тот же вывод, что
  TC-021/TC-039.
- Проверка «поля НЕ изменились» — через `seed_db.read_work_ratings()` (не
  требует `downloadPath`/`title`/`author` — этот кейс не ассертит их
  напрямую, downloadPath наблюдается КОСВЕННО через иконку карточки, тот же
  приём, что TC-039 «граница наблюдаемости»; блокер AT-BUG-046 сюда не
  относится — этот кейс не нуждается в расширенном `read_work_ratings()`).
- Дословный текст диалога — `backup_steps`/`settings_steps` существующий
  паттерн чтения алерта (образец TC-021/TC-039).
- Дельта к TC-039: там Library ПУСТА (import++, чистый релинк без скипа);
  здесь Library НЕпуста и целевая работа СКИПАЕТСЯ (тот путь кода `:348`,
  которого TC-039 не достигает вовсе — см. её докстринг «Restore + auto-scan
  показывают ровно один диалог», где работа именно ИМПОРТИРУЕТСЯ, не
  скипается).
- **Батарея правил-реакций (оценка применимости):** это CRUD-like операция
  восстановления, не auto-download/kudos класс общего фонового состояния —
  тем не менее банк C4 явно называет «backup → clear → restore сохраняет
  множество записей и ключевые поля» комбинаторным инвариантом, строка
  `Инвариант:` дана выше. Отдельные пункты батареи правил-реакций (edge-vs-
  level/ретроактивность/идемпотентность/propagation) — н-п: Restore не
  является правилом-реакцией в смысле авто-триггера на пользовательское
  действие с несвязанным побочным эффектом (это прямое, явно запрошенное
  пользователем действие), эта батарея к нему не применяется по определению
  CLAUDE.md (реакции на E при C, а не сам процесс, который пользователь
  затребовал напрямую).
