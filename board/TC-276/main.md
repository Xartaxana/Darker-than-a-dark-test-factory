# TC-276 — Нативный фон Settings: чисто белый/чёрный в E-ink, тёплый/неполный в обычных схемах (4 комбинации)

## Предусловия
- Приложение запущено с чистыми данными (`clean_app`), Settings открыт.
- Дефолт эталонного AVD: тема Light, E-ink OFF (`Build.MANUFACTURER != "ONYX"` —
  граница чёрного ящика называется явно, ONYX-дефолт этим кейсом не проверяется).
- Сценарий чисто нативный: WebView/replay/live не задействованы, сидинг работ
  не требуется — только Settings-экран и его тема/тумблер.

## Сценарий (Given-When-Then)

**Given** Settings открыт, тема Light, E-ink mode OFF (комбинация 1: light×off)

**When**
1. на комбинации 1 (light×off) через `region_luma_stats`-подобный приём
   (см. заметки) выбирается однородный (низкий std — самопроверка «в боксе
   нет текста/иконки») прямоугольник ФОНА экрана и вычисляется средний RGB
   этого прямоугольника;
2. тема переключается на Dark (`select_theme("DARK")`, E-ink остаётся OFF)
   → комбинация 2 (dark×off): тот же бокс, тот же замер;
3. E-ink mode включается (Settings-тумблер «E-ink mode», тема остаётся Dark)
   → комбинация 3 (dark×on): тот же бокс, тот же замер;
4. тема переключается обратно на Light (E-ink остаётся ON) → комбинация 4
   (light×on): тот же бокс, тот же замер

**Then** ДО сравнения с константами — самопроверка различимости (критик-фикс
Б5(б), детектор «бокс попал на тема-независимый элемент»): все ЧЕТЫРЕ
измеренных RGB ПОПАРНО РАЗЛИЧНЫ (ни одна из C(4,2)=6 пар не совпадает в
пределах допуска ±4/канал) — если хотя бы одна пара совпала, тест ОБЯЗАН
упасть с диагностикой «бокс сэмплинга не зависит от схемы — вероятно попал
на тема-независимый элемент (напр. TopAppBar)», не продолжать молча.

Затем средний RGB бокса в КАЖДОЙ из четырёх комбинаций совпадает (допуск
±4 на канал — цифровой скриншот без аналогового шума, допуск оставлен как
запас на возможные полупрозрачные штрихи у края бокса) со СВОИМ каноническим
фоновым значением схемы:
- light×off → `Ao3BackgroundLight` #FAF7F2 (250,247,242) — тёплый, НЕ чистый белый
- dark×off → `Ao3BackgroundDark` #1B1718 (27,23,24) — тёмно-коричневый, НЕ чистый чёрный
- dark×on → `EinkBackgroundDark` #000000 (0,0,0) — чистый чёрный
- light×on → `EinkBackgroundLight` #FFFFFF (255,255,255) — чистый белый

**Инвариант:** свойство «измеренный фон РОВНО равен канoническому фоновому
значению ТЕКУЩЕЙ схемы» верно НЕЗАВИСИМО для всех ЧЕТЫРЁХ комбинаций
{тема: light/dark} × {eink: off/on} — не для одного примера. Из четырёх
измерений следует заявленный контраст свойства: eink-комбинации дают
ахроматичный (R=G=B) фон на границе диапазона (0 или 255), обычные —
неахроматичный/неполный (тёплый оттенок в light, коричневый оттенок в
dark) — это и есть измеримая форма заголовка фичи «чисто белые/чёрные
поверхности... вместо обычных light/dark схем».

## Проверяемые данные
| Комбинация | Ожидаемый RGB (допуск ±4/канал) | Константа |
|---|---|---|
| light × eink OFF | (250,247,242) | `Ao3BackgroundLight` |
| dark × eink OFF | (27,23,24) | `Ao3BackgroundDark` |
| dark × eink ON | (0,0,0) | `EinkBackgroundDark` |
| light × eink ON | (255,255,255) | `EinkBackgroundLight` |

## Заметки для автоматизации
- **E-ink-тумблер — новый локатор (не блокер, рутина):** в
  `settings_screen.py` уже есть 6+ тумблеров через приём `find_row_sibling`
  (AT-BUG-080) — `is_tap_to_scroll_checked`/`set_tap_to_scroll`,
  `is_infinite_scroll_checked`/`set_infinite_scroll` и т.д. «E-ink mode»
  (`SettingsScreen.kt:712-716`) добавляется тем же приёмом
  (`_EINK_MODE_LABEL = "E-ink mode"`, `is_eink_mode_checked`/
  `set_eink_mode`) — не отсутствующая фикстура и не неавтоматизируемый
  штатно UI, test_debt-баг не заводится.
- **Новый примитив — средний RGB бокса (не блокер, рутина):** существующие
  luma-методы (`region_luma_stats`/`screenshot_avg_luma`/
  `top_chrome_avg_luma`, `framework/screens/browser_screen.py`) все делают
  `.convert("L")` (grayscale) — для ЭТОГО кейса нужен средний RGB БЕЗ
  конвертации в grayscale (те же PIL/скриншот-примитивы, просто без
  `.convert("L")` и с раздельным накоплением по каналам). Ровно тот же
  класс «рутинная реализация поверх уже читаемых значений», что формула
  WCAG-контраста в TC-149 («новый код, не блокер») — не отсутствующая
  фикстура/сидинг и не неавтоматизируемый штатно UI.
- **Выбор бокса — задача автоматизации, но КРИТИЧНО НЕ TopAppBar (критик-фикс
  Б5, координатор 2026-08-21):** прежний кандидат («верхняя полоса НАД
  заголовком секции Theme») ОШИБОЧЕН — это `Ao3TopBar`
  (`MainActivity.kt:509,838-841`), `containerColor =
  MaterialTheme.colorScheme.primary` — ИНВАРИАНТЕН ПО ОСИ eink (не
  зависит от background-констант вовсе), но РАЗЛИЧАЕТСЯ ПО ОСИ ТЕМЫ:
  `Ao3Red` #900000 (144,0,0) в `LightColorScheme` И `EinkLightColorScheme`,
  `Ao3RedDark` #4A232D (74,35,45) в `DarkColorScheme` И
  `EinkDarkColorScheme` (`Theme.kt`). На light-схемах тест упал бы
  «ожидалось (250,247,242), получено (144,0,0)», выглядя как баг
  приложения, хотя дефект — в выборе бокса; `std≈0` этот класс ошибки НЕ
  ловит (сплошной AppBar тоже даёт низкий std) — отсюда и обязательная
  попарная самопроверка различимости в Then выше (она сработала бы и
  здесь: совпали бы пары light×off/light×on и dark×off/dark×on).
  **Верный кандидат:** вертикальная маргинальная полоса ВДОЛЬ ЛЕВОГО (или
  правого) края экрана, НИЖЕ `Ao3TopBar` (топбар занимает лишь верхние
  ~5-8% высоты по замеру CH-005-style плотности), ВНУТРИ прокручиваемой
  content-`Column` (`SettingsScreen.kt:691-695`,
  `.fillMaxSize().verticalScroll(...).padding(horizontal=16.dp,
  vertical=8.dp)`) — сама `Column` фона не рисует (нет `.background()`),
  поэтому её собственный ГУТТЕР (16dp margin слева/справа, на ВСЮ высоту
  под топбаром) остаётся чистым `colorScheme.background` от родительского
  `Surface`, а всё содержимое строк настроек инсетнуто НА 16dp вправо от
  левого края и потому НИКОГДА не заходит в этот гуттер: например x∈[2px,
  10px] эталонного AVD (density 2.625, 16dp≈42px — запас от обеих границ
  гуттера), y∈[25%,45%] высоты экрана (комфортно ниже TopAppBar, внутри
  скроллящейся области, независимо от текущей позиции скролла — гуттер
  идёт по всей высоте Column). Перед тем как доверять цвету бокса,
  автоматизатор ОБЯЗАН самопроверкой убедиться, что бокс однороден — тот
  же `region_luma_stats`, который уже возвращает `std`: `std ≈ 0` в боксе
  means «в нём нет текста/иконки» (НЕОБХОДИМОЕ, но, как показал разбор
  критика, НЕ ДОСТАТОЧНОЕ условие — обязательна ЕЩЁ и попарная
  самопроверка различимости из Then).
- Порядок переключений (Light×off → Dark×off → Dark×on → Light×on) — 3
  дешёвых UI-тоггла подряд, БЕЗ пересидинга и БЕЗ повторного запуска
  приложения (граница П1 dedup «другой запуск — не сливать» не задета:
  вся последовательность — один и тот же прогон, один Given).
- WebView/replay/live не участвуют вовсе — тумблер E-ink триггерит
  `LaunchedEffect(einkMode)` в `BrowserScreen` (перезагрузка открытых
  вкладок), но этот эффект нерелевантен ЭТОМУ кейсу: здесь наблюдается
  ТОЛЬКО нативный Settings-экран, который перерисовывается немедленно
  через `CompositionLocalProvider`/`MaterialTheme`, без reload и без сети.
- **Non-goal явно (остаток вне скоупа ЭТОГО кейса, не блокирует
  закрытие):** заголовок реестровой записи `eink-palette-native` бандлит
  ТРИ разных наблюдаемых свойства — (а) чистота поверхностей [ЭТОТ
  кейс], (б) «сплошные непрозрачные границы» (alpha 13% `Ao3BorderLight`
  vs. opaque `EinkBorderLight` — тонкая линия, пиксельная геометрия
  штриха через скриншот заметно более хрупкая, чем целый фоновый
  регион — не покрыто), (в) «насыщенные цвета рейтингов» на НАТИВНЫХ
  экранах (Library-карточки/`RatingOverlay` — требует своего Given с
  засеянными рейтингами, другая поверхность экрана — не покрыто). (б) и
  (в) — доклад в отчёте (см. финальный ответ), кандидат на либо
  отдельный follow-up кейс, либо дробление записи реестра (правило 6).
