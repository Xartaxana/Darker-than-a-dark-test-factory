# Первый переход рейтинга в Kudosed через листинг при открытой вкладке работы отправляет kudos ровно один раз (позитивная граница)

# TC-138 — Позитивная граница: первый переход в Kudosed при открытой вкладке работы шлёт kudos один раз

## Предусловия
- Приложение запущено с чистыми данными, режим replay (`listing_basic.mitm`, **после
  фикса `bugs/AT-BUG-035.md`** — до фикса кейс не может быть закодирован, см.
  «Заметки для автоматизации»).
- Работа W = `LOVED` (900000001) без рейтинга (чистые данные, сидинг не требуется).
- Открыты ДВЕ вкладки: Tab A — листинговая страница с блёрбом W (Rate-кнопкой
  доступен нативный bottom-sheet); Tab B — work-страница самой W, открытая в фон
  long-press-ом по ссылке блёрба (`browser_steps.long_press_work_link`, тот же приём,
  что TC-026).
- На Tab B узел `#kudo_submit` ещё НЕ несёт атрибут `data-kudo-clicked` (baseline
  инструментированного узла фикстуры).

## Сценарий (Given-When-Then)

**Given** приложение в replay-режиме, работа W без рейтинга; открыты Tab A (листинг
с блёрбом W) и Tab B (work-страница W, в фоне); на Tab B узел `#kudo_submit` без
`data-kudo-clicked`

**When** на Tab A пользователь Rate-кнопкой W открывает нативный bottom-sheet и
выбирает рейтинг «Kudosed» (LIKE)

**Then** рейтинг сохранён: бейдж «Kudosed» появляется у блёрба W на Tab A без
перезагрузки (читается в штатном sticky-контексте chromedriver — Tab A это
вкладка-0, первая когда-либо созданная WebView, см. заметки), работа
отображается на вкладке Kudosed экрана Library
**And** ПОСЛЕ проверки бейджа Tab A закрывается (`browser_steps.swipe_close_tab(driver,
position=0)`) — идиома reduce-to-one (см. заметки, `browser_screen.py:319-329`):
единственной живой WebView остаётся Tab B, уничтожение прилипшей цели (Tab A)
форсирует chromedriver переподключиться к ней. На Tab B узел `#kudo_submit`
получает `data-kudo-clicked="1"` — ровно один клик; повторное чтение атрибута
после короткой паузы даёт то же значение «1», не «2» (инструментация —
инкрементный счётчик клика, не константа, см. `bugs/AT-BUG-035.md` критерий
Fixed после B2-фикса, иначе двойной клик неотличим от одинарного)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `framework/data/works.py::LOVED` (900000001), рейтинг не задан |
| Устанавливаемый рейтинг | Kudosed (LIKE), через листинговый bottom-sheet |
| Открытые вкладки | Tab A (листинг), Tab B (work-страница W) |

## Заметки для автоматизации
- **БЛОКЕР (test_debt):** узел `#kudo_submit` отсутствует ВО ВСЕХ текущих replay-
  фикстурах — `render_work_page_html` (`framework/data/recording_builder.py:546-585`)
  не рендерит его вовсе (сверено чтением: единственные упоминания «kudos» в модуле —
  статичный счётчик `<dd class="kudos">0</dd>`, не интерактивный узел). Без узла
  `document.getElementById('kudo_submit')` в приложении вернёт `null`, `if(b)b.click()`
  молча не выполнится НЕЗАВИСИМО от того, сработал ли level-предикат — то есть Then
  этого и всех остальных кейсов области (TC-139..144) был бы либо невозможен
  (позитив), либо вакуумно-истинен (негативы) без узла. Заведено `bugs/AT-BUG-035.md`
  тем же ходом (`test_cases: [TC-138..TC-144]`) — единый блокер на всю область, не
  по кейсу. `automated_by` пуст, кейс не диспатчится в автоматизацию до Fixed.
- **Механика чтения Tab B — reduce-to-one, НЕ «активировать Tab B перед switch_to.context»
  (исправлено на critic attempt2, 2026-07-31; прежняя формулировка противоречила
  задокументированной эмпирике репо).** Факт: `browser_screen.py:319-329` —
  при >1 живой `android.webkit.WebView` chromedriver экспонирует РОВНО ОДИН контекст
  `WEBVIEW_<pkg>`, и он ПРИЛИПАЕТ к вкладке-0 (первый когда-либо созданный WebView =
  здесь Tab A, листинг); «ни переключение активной вкладки в UI, ни повторный
  `switch_to.context()` не переключают его на другую вкладку, пока вкладка-0 жива»
  (дословно докстринг). Подтверждения: `bugs/AT-BUG-022.md`,
  `test_tap_zone_guard.py:50-56`, `test_reading_ux.py:27-30`. Установленная идиома
  (образец TC-026, `browser_steps.swipe_close_tab`): единственный способ читать
  WebView НЕ-нулевой вкладки — свести число живых вкладок к одной. Здесь: сначала
  читаем бейдж на Tab A (штатный sticky-контекст, свитчить не нужно — это ДЕФОЛТНОЕ
  состояние chromedriver), ЗАТЕМ закрываем Tab A (`browser_steps.swipe_close_tab(driver,
  position=0)`) — Tab B остаётся единственной живой WebView, уничтожение прилипшей
  цели форсирует chromedriver переподключиться к ней (эмпирически подтверждено тем
  же докстрингом); только после этого `contexts.in_webview` читает `#kudo_submit` на
  Tab B без риска попасть в DOM листинга.
- Открытие Tab B в фон — готовый `browser_steps.long_press_work_link` (TC-026).
  Rate-кнопка листинга и выбор рейтинга — готовые `browser_steps.tap_rate_button` +
  `rating_steps.rate_via_listing_overlay(driver, "LIKE")`.
- **Позитивный контроль листингового пути (S3, critic attempt2).** Этот кейс —
  единственный в области, где клик ОЖИДАЕТСЯ фактом; зелёный TC-138 в ТОМ ЖЕ
  прогоне, что и негативы TC-139/140/142/143 (все читают `#kudo_submit` той же
  reduce-to-one механикой), — необходимое условие доверия к их негативным Then:
  подтверждает, что узел фикстуры, счётчик клика и chromedriver-реконнект
  работоспособны. Без зелёного TC-138 в прогоне негативы неотличимы от «узел/
  механика чтения сломаны» (см. также TC-139 «Наблюдаемость негативного Then»
  про дискриминатор для evalJs на отсоединённой фоновой WebView).
- **Батарея правил-реакций** (место вызова `:856-861`, входит в листинговый путь
  `applyRating`):
  - edge vs level — этот кейс закрывает EDGE; LEVEL (ядро BUG-015) — TC-139.
  - ретроактивность включения — **н-п**: у kudos-автоклика нет управляющего тумблера
    (в отличие от auto-download), поведение безусловно завязано на значение
    сохраняемого рейтинга — ретроактивности включения тут нечему быть.
  - off-инвариант — **н-п**: та же причина (нет выключаемой настройки); структурные
    негативы правила покрыты TC-140 (нет открытой вкладки) / TC-141 (панельный путь
    не кликает) / TC-142 / TC-143 (смена/снятие рейтинга).
  - идемпотентность — **н-п** отдельным сценарием: Then уже читает атрибут дважды
    (сразу и после паузы) и подтверждает «1», не «2», за ОДИН вызов `applyRating`;
    повторный вызов (пересохранение) — предмет TC-139, где ожидается «0», не «2».
  - propagation — **н-п**: kudos-клик целится в ОДНУ конкретную вкладку
    (`evalJs(workTab.id, ...)`), у эффекта нет множественных потребителей (не путать
    с `broadcastRatingChange`/бейдж-синком — отдельный механизм
    `bridge-badge-sync-multi`, уже покрыт своими кейсами).
