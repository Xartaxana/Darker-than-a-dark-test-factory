# TC-144 — Позитивная граница панельного пути: первое сохранение LIKE/SAVE через панель работы шлёт kudos один раз

## Предусловия
- Приложение запущено с чистыми данными, режим replay (`work_with_download.mitm`
  либо `listing_basic.mitm`, **после фикса `bugs/AT-BUG-035.md`** — до фикса
  кейс не может быть закодирован, см. «Заметки для автоматизации»).
- Работа W = `LOVED` (900000001) — В ROOM НЕТ НИ ОДНОЙ ЗАПИСИ для этой работы
  (чистые данные, сидинг НЕ применяется намеренно: любой сидинг создал бы
  строку `WorkRating` и увёл бы сценарий в ветку `savePanelRating`/`existing !=
  null`, предмет TC-141, а не `pendingPanelSave`, предмет ЭТОГО кейса).
- Открыта ОДНА вкладка — work-страница W, открытая IN-PLACE
  (`rating_steps.open_work_page`) — сценарий одновкладочный, sticky-context
  блокер B1 (см. TC-138/139/142/143) здесь не возникает по построению.
- Узел `#kudo_submit` на этой странице ещё НЕ несёт атрибут `data-kudo-clicked`
  (baseline инструментированного узла фикстуры).

## Сценарий (Given-When-Then)

**Given** приложение в replay-режиме; открыта единственная вкладка — work-страница
W; в Room нет ни одной записи для W (первое касание этой работы); узел
`#kudo_submit` без `data-kudo-clicked`

**When** пользователь раскрывает встроенную панель `RatingMenu` (BottomNav
разворачивается тем же механизмом, что и панель) и выбирает рейтинг «Kudosed»
(LIKE) — `rating_steps.rate_current_work(driver, "LIKE")`; это ПЕРВОЕ в жизни
работы сохранение через панель (ветка `onRateWorkRequested`/`pendingPanelSave`,
`:1053-1054`, НЕ `savePanelRating`)

**Then** рейтинг сохранён: панель показывает «Kudosed» выбранным без
перезагрузки страницы, работа появляется на вкладке Kudosed экрана Library
(новая строка `WorkRating` создана — это и есть переход «записи не было →
запись появилась», отличающий эту ветку от TC-141)
**And** на ТОЙ ЖЕ (единственной) work-вкладке узел `#kudo_submit` получает
`data-kudo-clicked="1"` — ровно один клик; повторное чтение атрибута после
короткой паузы даёт то же значение «1», не «2» (инструментация — инкрементный
счётчик клика, та же механика, что TC-138 после B2-фикса `bugs/AT-BUG-035.md`)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа W | `framework/data/works.py::LOVED` (900000001), в Room записи нет |
| Устанавливаемый рейтинг | Kudosed (LIKE), через встроенную панель work-страницы |
| Открытые вкладки | одна — work-страница W (in-place) |

## Заметки для автоматизации
- **БЛОКЕР (test_debt) — общий для области:** `bugs/AT-BUG-035.md` (узел
  `#kudo_submit` отсутствует во всех фикстурах); `automated_by` пуст.
  Обоснование общее для всех семи кейсов области — см. TC-138
  (`test_cases: [TC-138..TC-144]`, тикет расширен ЭТИМ кейсом при заведении).
- Открытие work-страницы IN-PLACE — `rating_steps.open_work_page(driver,
  work_id)` (см. `framework/screens/browser_screen.py::open_work` —
  `driver.get()` внутри уже открытого WebView, новой вкладки не создаёт,
  единственная вкладка остаётся единственной). Раскрытие панели и выбор
  рейтинга — готовый `rating_steps.rate_current_work(driver, "LIKE")`
  (используется TC-007/TC-114/TC-117).
- Чтение `#kudo_submit` — `contexts.in_webview` на единственной открытой
  вкладке; здесь НЕТ риска sticky-context залипания `AT-BUG-022` (в отличие от
  TC-138/139/142/143, где живут ДВЕ WebView-вкладки одновременно) — reduce-to-one
  не требуется, эта граница нарочно спроектирована одновкладочной.
- **Критично для воспроизводимости: НЕ сидить работу W заранее.** Любой сидинг
  (`app_steps.seed_library`) создаёт строку `WorkRating` до When, и тогда
  сохранение уйдёт веткой `savePanelRating`/`existing != null` (TC-141), а не
  `pendingPanelSave` — сценарий этого кейса перестанет существовать. Работа
  должна быть буквально нетронутой в Room на момент When.
- **Позитивный контроль TC-141 (B3, critic attempt2).** Этот кейс и TC-141 бьют
  по ДВУМ ВЕТКАМ ОДНОГО механизма сохранения через панель work-страницы:
  TC-144 — `pendingPanelSave` (запись отсутствует, первое сохранение, kudos
  кликает), TC-141 — `savePanelRating`/`existing != null` (запись уже есть,
  правка тега, kudos НЕ кликает). Зелёный TC-144 в ТОМ ЖЕ прогоне, что и
  негатив TC-141 (оба читают `#kudo_submit` на панельной work-странице той же
  инструментацией), — необходимое условие доверия к негативу TC-141: без него
  зелёный TC-141 неотличим от «панель физически не может кликнуть узел/
  инструментация не читается со страницы работы» (тот же принцип, что связка
  TC-138↔TC-139/140/142/143 для листингового пути).
- **Батарея правил-реакций** (место вызова `:1053-1054`, панельный путь,
  ветка `pendingPanelSave` — ДРУГОЕ место вызова, чем `:856` у TC-138..143 и
  `:743-758` у TC-141):
  - edge vs level — **н-п для LEVEL-половины**: этот call site структурно
    исполняется ТОЛЬКО когда записи в Room ещё нет — по построению это ВСЕГДА
    edge (первое сохранение), второе сохранение той же работы уходит ДРУГИМ
    call site'ом (`savePanelRating`, `existing != null`, TC-141), который
    структурно не содержит kudos-вызова вовсе. «Level» здесь не непроверен, а
    неприменим — на этом месте вызова ему неоткуда взяться. Кейс закрывает
    EDGE (единственно возможный режим этого call site).
  - ретроактивность включения — **н-п**: см. TC-138 (нет управляющего
    тумблера у kudos-автоклика).
  - off-инвариант — **н-п**: та же причина; структурный негатив ЭТОГО
    механизма (панельный путь) покрыт TC-141.
  - идемпотентность — **н-п**: этот call site физически исполняется РОВНО
    ОДИН раз за жизнь записи (как только строка `WorkRating` появляется,
    дальнейшие сохранения идут другим call site'ом) — повторного вызова
    ЭТОГО места в принципе не бывает; проверка «что будет при повторном
    сохранении» — предмет TC-141, другой call site.
  - propagation — **н-п**: одна вкладка, один потребитель, тот же довод, что
    TC-138.
