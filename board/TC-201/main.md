# TC-201 — Баннер отсутствует при обоих флагах false (off-инвариант)

## Предусловия
- Приложение запущено, `seeded_library` (в т.ч. `DISLIKED`, `rating=DISLIKE`).
- В Settings тумблер «Hide Disliked works» ВЫКЛЮЧЕН ДО навигации на листинг
  (`hiddenRatings` пуст) — тот же порядок, что TC-015/199. Display mode = Hide
  (не важно при пустом hidden-set).
- Фильтр-профиль не выбран (`activeFilterId=null`, дефолт) — `ao3FilterActive=false`.
- Открывается листинговая страница (replay `listing_basic.mitm`).

## Сценарий (Given-When-Then)

**Given** приложение запущено с `seeded_library`, тумблер «Hide Disliked works»
выключен, фильтр-профиль не выбран

**When** пользователь открывает листинговую страницу, содержащую блёрбы всех
эталонных работ

**Then** узел `#ao3-companion-hidden-notice` ОТСУТСТВУЕТ в DOM — гейт создания
`ratedHidden || filterActive` (`ao3_bridge.js:479`) ложен при обоих флагах false
**And** ни один блёрб (в т.ч. DISLIKED) не скрыт и не затемнён — `display`/`opacity`
не изменены фильтрацией

**Инвариант:** условие создания баннера — строго дизъюнкция `ratedHidden ||
filterActive`; при обоих `false` узел не создаётся НИ РАЗУ за время жизни
страницы (гейт проверяется на каждом вызове `updateHiddenBanner`, включая
init при загрузке) — это **off-инвариант** правила-реакции банера: выключенное
состояние даёт ЯВНЫЙ негативный факт «узла нет в DOM», а не «просто не
проверяли» (наблюдаемость негативного Then — прямая DOM-проверка отсутствия
элемента, не сетевой эффект, поэтому обоснование «Replay не требуется» здесь
неприменимо иначе как в контексте: это НЕ сетевой Then, вопрос
наблюдаемости решён самим локатором).

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Работа | `DISLIKED` из `framework/data/works.py` — остаётся видна |
| `ratedHidden` | false |
| `ao3FilterActive` | false |
| Баннер | отсутствует |

## Заметки для автоматизации
- Не блокер: метод чтения баннера — см. заметку TC-197.
- `settings_steps.set_hide_rating(driver, "Disliked", False)` — существующий шаг.
- **Батарея правил-реакций (полная оценка применимости для области
  `bridge-hidden-works-banner`, зафиксирована здесь и переиспользуется
  ссылкой сиблингами TC-197..200/203/204, чтобы не дублировать по кейсам):**
  - **off-инвариант** — ПРИМЕНИМО, это ядро настоящего кейса (явный негативный
    Then выше).
  - **propagation** — ПРИМЕНИМО (код `BrowserScreen.kt:161-168` рассылает
    `setHiddenBanner` на ВСЕ открытые WebView разом, `for (wv in
    webViews.values)`) — покрыто отдельным кейсом TC-204 (класс BUG-012).
  - **edge vs level** — н-п: у баннера нет «сохранения без семантического
    перехода» — `updateHiddenBanner()` не персистентный побочный эффект (не
    пишет в БД/сеть), а идемпотентный DOM-рендер, вызываемый и на КАЖДОЙ
    загрузке страницы, и на каждом live-push; лишний вызов с теми же
    значениями просто перезаписывает тот же `textContent` тем же значением —
    предиката состояния, который мог бы неверно сработать на "нейтральном"
    save-пути (класс BUG-014), здесь просто нет по конструкции.
  - **ретроактивность** — н-п: нет персистентного per-объектного состояния,
    к которому применялась бы ретроактивность (в отличие от auto-download/
    auto-kudos, привязанных к конкретной строке Room) — баннер полностью
    производный от ДВУХ live-флагов, пересчитывается заново на каждом
    триггере, истории не хранит.
  - **идемпотентность** — н-п по той же причине, что edge-vs-level: замена
    `textContent`/`remove()` идемпотентны по построению (перезапись, не
    накопление/дублирование), в отличие от auto-kudos/auto-download, где
    повторный вызов рискует продублировать сетевой эффект.
