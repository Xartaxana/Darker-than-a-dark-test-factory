# TC-165 — Формат экспортированного backup-файла: ровно контрактные ключи, без настроек

## Предусловия
- Приложение запущено, в Room засеяна 1 работа с непустыми
  `comment`/`tags`/`fandom`/`wordCount` (обычные, не экстремальные, значения)
  и 1 filter-профиль (`seed_db.seed_filter_profiles`).
- Несколько настроек приложения изменены относительно дефолта (например,
  тема Dark, `tap_to_scroll` ON) — специально, чтобы Then мог убедиться в их
  ОТСУТСТВИИ в файле, а не в случайном совпадении с дефолтом.
- SAF file picker доступен.

## Сценарий (Given-When-Then)

**Given** в Room есть 1 работа с заполненными полями и 1 filter-профиль;
несколько настроек приложения отличаются от дефолта

**When** пользователь выполняет «Back up data» и выбирает файл через SAF

**Then** появляется диалог «Backup created» с корректными счётчиками
**And** ФАКТИЧЕСКОЕ содержимое файла (`adb shell cat` или чтение через SAF),
распарсенное как JSON, имеет верхний уровень — множество ключей РОВНО
`{version, works, filterProfiles}` (ни одного лишнего, ни одного
недостающего)
**And** объект каждой работы в `works` несёт РОВНО набор полей `{ao3Id,
author, comment, downloadFile, fandom, rating, tags, timestamp, title, url,
wordCount}` — не больше и не меньше
**And** ни один ключ, соответствующий настройке приложения (`theme_mode`,
`tap_to_scroll`, `infinite_scroll`, `hidden_ratings`, `filter_display_mode`,
`download_folder_uri` и т.п.), НЕ встречается НИГДЕ в файле — ни на верхнем
уровне, ни вложенным

**Инвариант:** формат backup-файла — фиксированный КОНТРАКТ полей (не
«всё, что есть в приложении на момент экспорта»): множество ключей верхнего
уровня и множество полей объекта работы неизменны для ЛЮБОГО состояния
Room/настроек на момент экспорта — наличие/отсутствие данных в самих
работах не меняет НАБОР ключей, только их значения; поэтому кейс проверяет
СВОЙСТВО «набор ключей», а не единичный пример содержимого.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Верхний уровень JSON | `{version, works, filterProfiles}`, ровно 3 ключа |
| Поля объекта работы | `{ao3Id, author, comment, downloadFile, fandom, rating, tags, timestamp, title, url, wordCount}` |
| Поля объекта профиля | `{id, name, queryString, timestamp}` |
| Ключи настроек в файле | отсутствуют полностью |

## Заметки для автоматизации
- Не заблокировано инфраструктурой — SAF-экспорт + `adb shell cat`
  уже используются TC-021/CH-007 (образец `backup_steps.py`).
- Ассерт — МНОЖЕСТВО ключей через `set(json.loads(content).keys()) ==
  {"version", "works", "filterProfiles"}`, не подстрочный поиск и не
  «ключ присутствует» (иначе лишний непредусмотренный ключ прошёл бы
  незамеченным — именно этого требует «ассерт-якорь на содержимое файла»
  из формулировки кандидата).
- Настройки для негативной проверки — намеренно ОТЛИЧНЫЕ от дефолта
  (Dark/ON), чтобы отсутствие их значений в файле не могло быть случайным
  совпадением с тем, что дефолтное значение просто не сериализуется.
- Имя экспортируемого файла — детерминированное и своё для кейса (приём
  `saf_save_document(filename=...)`, образец CH-007 Data setup «Имя
  каждого экспорта бэкапа — СВОЁ и детерминированное»), `rm` до экспорта.
- Дельта к TC-021 (round-trip данных `works`/`filterProfiles` после
  restore) — этот кейс НЕ доходит до Restore вовсе, предмет — статический
  контракт СРАЗУ после экспорта, включая поле `downloadFile` (которое
  TC-021 не проверяет отдельно) и явное отсутствие настроек (которое ни
  один существующий кейс не ассертит).
- Область — контракт формата (статический снимок структуры), не round-trip
  множества записей — строка `Инвариант:` описывает свойство «набор
  ключей», не банковский инвариант backup/restore дословно; тем не менее
  добавлена, так как утверждение квантифицируется по ЛЮБОМУ состоянию
  данных, не по конкретному примеру.
- Батарея правил-реакций — н-п: экспорт запускается прямым явным действием
  пользователя, не авто-триггером на несвязанное событие.
