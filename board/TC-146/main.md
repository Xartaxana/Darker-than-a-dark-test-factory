# Слайдер яркости на экране Settings снижает реальную яркость и включает чёрный overlay ниже минимума (второй вход к жесту TC-055)

# TC-146 — Слайдер яркости в Settings: второй вход к жесту TC-055

## Предусловия
- Приложение запущено с чистыми данными, яркость на дефолтном уровне (как
  задаётся при старте — см. TC-055 Given), чёрного overlay нет.
- На вкладке Browse открыта страница AO3.
- Открыт экран Settings, виден слайдер «Brightness» (диапазон -0.3..1) и
  подпись текущего процента.
- Режим прогона: replay либо live-smoke; яркость экрана управляется
  приложением (тот же контекст среды, что TC-055).

## Сценарий (Given-When-Then)

**Given** на экране Settings слайдер «Brightness» в дефолтном положении,
чёрного overlay на Browse нет

**When** пользователь тянет ползунок слайдера от дефолтного положения к
нижней границе диапазона (-0.3), затем открывает вкладку Browse

**Then** реальная яркость окна снижается по мере движения ползунка (та же
наблюдаемая реакция, что двухпальцевый жест TC-055); при пересечении нуля
на Browse поверх экрана появляется полупрозрачный чёрный overlay,
дополнительно затемняющий изображение — тот же эффект, что TC-055 в ветке
v<0, вызванный ДРУГИМ входом (слайдер Settings, не жест)

**When** пользователь возвращается в Settings и тянет ползунок обратно к
верхней границе диапазона (1)

**Then** чёрный overlay на Browse исчезает и реальная яркость окна
восстанавливается — эффект воспроизводится в обе стороны через этот вход,
как через жест (TC-055)

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Контрол | `Slider` «Brightness» на экране Settings, диапазон -0.3..1 |
| Эффект в диапазоне v>=0 | снижение реальной яркости окна |
| Эффект при v<0 | чёрный overlay поверх Browse (тот же код-путь, что TC-055) |

## Заметки для автоматизации
- Тот же прокси, что реализован для TC-055: средняя яркость (luma)
  полноэкранного скриншота (`Pillow`, уже в `framework/requirements.txt`).
  Блокера нет.
- **Техническая оговорка по наблюдаемости (важно, унаследовано от TC-055)**:
  `Window.attributes.screenBrightness` не виден UiAutomator2 как UI-элемент
  (`framework/screens/browser_screen.py::screenshot_avg_luma`) — прокси видит
  ТОЛЬКО чёрный overlay (ветка `v<0`), реальное снижение яркости окна в
  диапазоне `v>=0` этим методом не различить от отсутствия изменения; фазы
  `v>=0`/`v<0` раздельно прокси не разделяет (та же граница, что
  `test-cases/browser/TC-055.md` «Техническая оговорка по наблюдаемости»).
  Автоматизатору проверять эмпирически наблюдаемый эффект (overlay/luma), не
  формулировку Then буквально про «реальную яркость».
- **Слайдер Settings — самостоятельный контрол, ни один существующий тест его
  не драйвит.** `BRIGHTNESS_SLIDER` (`framework/screens/settings_screen.py:72`)
  используется сейчас только на присутствие (`framework/steps/settings_steps.py:35`,
  font_scale-смоук) — не как источник ввода. CH-004
  (`exploratory-charters/PERTURBATIONS.md:17,236-238,282`) зафиксировал, что
  двухпальцевый W3C-жест яркости НЕ гарантированно регистрирует смену pref
  через Appium actions (pointerInput-классификатор не всегда срабатывает) —
  механизм #4 CH-004 остался непрогнанным по этой причине. Штатный Compose
  `Slider` (drag или программная установка через accessibility-action) —
  вероятно более устойчивый вход для нижнего диапазона яркости, чем жест;
  автоматизатору стоит рассмотреть его не только как «второй вход» для
  полноты, а как основной путь покрытия. Код для драйва слайдера предстоит
  написать — примитив (`drag`/`execute_script` по accessibility-action)
  существующий, не отсутствующая фикстура.
- LaunchedEffect реагирует на `settingsUiState.brightnessValue` независимо от
  того, что именно его изменило (Settings slider или side panel жест) — один
  и тот же код-путь, поэтому Then кейса дословно повторяет TC-055 (не
  разные assert'ы для разных входов).
- Не путать с TC-055 (там вход — двухпальцевый жест над контентом Browse) и
  с TC-054 (та проверяет темы/шрифт, не яркость). Кейс независим от порядка:
  состояние яркости приводится слайдером внутри самого кейса.
- Кейс НЕ комбинаторной C4-семьи (непрерывный range-контрол одного пользователя,
  тестируется в обе стороны одним сценарием, тот же паттерн, что TC-055,
  у которого тоже нет строки `Инвариант:`), строка `Инвариант:` не требуется.

## Дефекты-собратья / находка гранулярности реестра (для test-strategist)
- `docs/feature-registry.yaml` запись `settings-brightness-slider`
  (`docs/feature-registry.yaml:373-376`) несёт TITLE «Слайдер яркости
  (overlay при v<0, reset-on-start)» — бандлит ДВЕ разных наблюдаемых
  поверхности с разными Then: (1) сам слайдер/диапазон/overlay — закрыто
  этим кейсом; (2) переключатель `resetBrightnessOnStart` («Reset brightness
  on start», `SettingsScreen.kt:688-693`, `SettingsViewModel.
  setResetBrightnessOnStart` :461-464) — САМОСТОЯТЕЛЬНЫЙ persistence-тумблер
  с собственной семантикой (ON, дефолт: яркость на каждом старте берётся из
  системы, сохранённое значение игнорируется; OFF: сохранённое значение
  переживает kill+relaunch), с НУЛЕВЫМ покрытием (grep по `framework/` на
  `reset_brightness_on_start`/`resetBrightnessOnStart` пуст, кроме
  разведческих чартеров CH-004/PERTURBATIONS.md, которые сами называют его
  «остаток миссии», механизм #5 непрогнан). §9-пункт `settings-brightness-slider`
  дословно называет только «второй вход… включая диапазон ниже системного
  минимума» — про `resetBrightnessOnStart` не упоминает, поэтому эта грань
  ВНЕ явного скоупа текущего needs-design-прохода (диспатч ограничивал owns
  тремя названными под-областями, non-goals запрещали расширение). Итог:
  этот Then кейса закрывает часть TITLE реестровой записи, не весь; по
  правилу гранулярности (docs test-designer, урок hide/dim 2026-07-17) —
  **докладываю, не расширяю scope сам**: запись `settings-brightness-slider`
  нуждается либо в дроблении (например, `settings-brightness-reset-on-start`
  отдельной записью), либо в отдельном needs-design-пункте §9 на сам
  тумблер — решение за test-strategist/владельцем реестра.
