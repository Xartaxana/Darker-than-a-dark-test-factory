# TC-171 — Restore в непустую базу: локальная версия побеждает при совпадении id, удалённая — возвращается

## Предусловия
- Приложение запущено, в Room засеяны ТРИ работы (`seed_db.seed_with_comment`,
  образец TC-021):
  - **W_KEEP** — рейтинг + комментарий, контроль (остаётся нетронутой на
    всём протяжении сценария, кроме самого факта Backup/Restore).
  - **W_EDIT** — рейтинг + комментарий "Original comment".
  - **W_DELETE** — только рейтинг, без комментария/тегов/скачанного файла
    (минимальная строка, чтобы её можно было удалить дверью Library
    целиком, без остатка).
- Filter-профилей в этом кейсе нет (0) — дальнейший дизайн сознательно
  держит дилог простым («0 filters» неизменно на всём протяжении), чтобы
  не размывать assert на скип-семантику работ; filter-профильная ветка
  этой же семьи уже закрыта TC-166.
- SAF file picker доступен.
- Папка загрузок ПУСТА (ни одна из W_KEEP/W_EDIT/W_DELETE не имеет
  скачанного файла) — точный текст диалога в Then без суффикса
  «Also relinked … added …» зависит от этого; ветка с непустой папкой
  (скип по ao3Id + релинк файла одновременно) — TC-172.
- Для локальной правки W_EDIT нужна навигация на Browse и replay-запись,
  открывающая листинг с Rate-кнопкой для её ao3Id (тот же класс
  инфраструктуры, что уже используют Automated TC-114/TC-115 для правки
  комментария ранее оценённой работы).

## Сценарий (Given-When-Then)

**Given** в Room засеяны W_KEEP (рейтинг+комментарий), W_EDIT
(рейтинг+"Original comment"), W_DELETE (только рейтинг) — три РАЗНЫЕ
работы с разными ao3Id

**When** пользователь в Settings выполняет «Back up data», выбирает файл
F через SAF — файл F содержит все три работы с ИСХОДНЫМИ полями
**And** переходит на Browse, открывает bottom-sheet рейтинга W_EDIT и
меняет комментарий на "LOCAL EDIT should survive restore" (рейтинг
W_EDIT не трогается, тот же ao3Id)
**And** переходит в Library, long-press по карточке W_DELETE, выбирает
«Delete work» — строка W_DELETE полностью удаляется из Room (её ao3Id
больше не существует)
**And** возвращается в Settings, выполняет «Restore from backup», выбирает
ТОТ ЖЕ файл F

**Then** появляется диалог «Backup restored» с ТОЧНЫМ текстом «Restored 1
works, 0 filters (2 works already existed).» — ровно W_DELETE
реимпортирована (1), W_KEEP и W_EDIT скипнуты как уже существующие (2);
текст НЕ называет ни одного имени работы и не предлагает выбор
«перезаписать/оставить» — регрессионный замок фактического поведения
**And** после закрытия диалога прямое чтение Room
(`seed_db.read_work_ratings()`) показывает: W_KEEP — поля идентичны
исходным (контроль не задет); **W_EDIT — комментарий остаётся "LOCAL EDIT
should survive restore"** (НЕ откатился на бэкапное "Original comment" —
скип отбрасывает версию из бэкапа целиком, локальная правка не
перезаписывается ни одним полем); **W_DELETE — строка существует снова**,
все поля (rating/comment=None/tags=None/fandom/word_count) совпадают с
исходными значениями из бэкапа (реконструирована целиком, так как её
ao3Id отсутствовал в снимке `existingIds` на момент импорта)
**And** множество ao3Id в Room после Restore имеет мощность 3 (W_KEEP,
W_EDIT, W_DELETE) — ни дублей, ни лишних строк

**Инвариант:** разрешение конфликта по КАЖДОЙ строке Restore определяется
ИСКЛЮЧИТЕЛЬНО присутствием её `ao3Id` в снимке `existingIds`, взятом ДО
цикла импорта — если id присутствует (независимо от ТОГО, что именно
изменено локально: комментарий, тег, рейтинг), бэкапная версия
отбрасывается целиком, ни одно поле не применяется; если id отсутствует
(строка была удалена локально после бэкапа — независимо от способа
удаления), работа реконструируется из бэкапа ПОЛНОСТЬЮ. Оба исхода —
следствие ОДНОГО вызова Restore над ОДНИМ снимком `existingIds`, не двух
независимых операций; множество ao3Id после Restore равно {id локально
не удалённых} ∪ {id локально удалённых, но бывших в бэкапе}, без
дублирования.

## Проверяемые данные
| Параметр | Значение |
|---|---|
| W_KEEP до/после | без изменений (контроль) |
| W_EDIT комментарий до Backup | "Original comment" |
| W_EDIT комментарий после локальной правки | "LOCAL EDIT should survive restore" |
| W_EDIT комментарий после Restore | "LOCAL EDIT should survive restore" (== локальный, не бэкапный) |
| W_DELETE после локального удаления | строки нет |
| W_DELETE после Restore | строка восстановлена, поля == исходным (из бэкапа) |
| Диалог Restore | «Restored 1 works, 0 filters (2 works already existed).» |
| Мощность множества ao3Id после | 3 |

## Заметки для автоматизации
- Не заблокировано инфраструктурой: SAF backup/restore — TC-021 (Automated),
  `seed_db.seed_with_comment`/`read_work_ratings` — TC-021, «Delete work» из
  Library — `library_steps.delete_via_overlay(driver, title, "Delete work")`
  (уже используется существующими downloads-кейсами, Compose-native, БЕЗ
  WebView), правка комментария ранее оценённой работы через листинговый
  bottom-sheet — `rating_steps.rate_via_listing_overlay`/
  `add_note_via_listing_overlay` + replay-запись листинга с Rate-кнопкой
  для конкретного ao3Id (тот же класс, что уже использует Automated
  TC-114/TC-115 для похожего сценария «правка заметки ранее оценённой
  работы»; какая конкретно запись `framework/data/recordings/*.mitm`
  покрывает нужный листинг/ao3Id — решает test-automator по каталогу
  записей, не блокер дизайна: инфраструктура класса уже существует).
- Сверка после Restore — прямым чтением Room
  (`seed_db.read_work_ratings()`), НЕ через текст карточки Library (та же
  причина, что TC-021/TC-166: локале-независимость и полнота полей).
- Текст диалога — точная строка, не подстрока (в отличие от TC-167/168, где
  текст ошибки парсера подстрочно сверяется из-за экранирования): формула
  `Restored ${imported} works, ${importedProfiles} filters
  (${skipped} works already existed).` (`SettingsScreen.kt:1186-1191`)
  детерминирована при 0 filterProfiles в кейсе — подставить точные числа
  1/0/2.
- Дельта к TC-021 (round-trip БЕЗ локальных изменений — Restore идёт в
  ПУСТУЮ базу после Clear all) и TC-166 (та же комбинаторная семья
  edit-survives/delete-returns, но для filter-профилей через дверь
  Settings UI, не работ через дверь Browse/Library) — этот кейс первый,
  открывающий ветку коллизии `ao3Id` именно для `work_ratings`.
- Порядок W_KEEP/W_EDIT/W_DELETE в Given — три РАЗНЫЕ работы
  (`framework/data/works.py`), не переиспользование одного id под разными
  состояниями — не путать со сценариями edge-vs-level (BUG-014 класс), это
  разные объекты.
- **Батарея правил-реакций** — н-п: Restore — явное прямое действие
  пользователя, не авто-триггер на несвязанном событии (тот же довод, что
  TC-166/167/168).
- Дефект-собрат / направление для test-strategist: seam «merge ×
  downloads» (ветка Б чартера CH-007, Г3) этим кейсом НЕ покрыт (в
  W_DELETE/W_EDIT/W_KEEP нет скачанных файлов) — решён ОТДЕЛЬНЫМ кейсом
  TC-172 (см. запись §9), чтобы не смешивать инфраструктуру SAF/download в
  одном сценарии.
