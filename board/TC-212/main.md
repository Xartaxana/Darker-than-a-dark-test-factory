# TC-212 — LWW-слияние фильтр-профилей

## Предусловия
- Синхронизация настроена. Локально сохранён фильтр-профиль P (`name="Local
  Name"`, `queryString="q=local"`) — `seed_filter_profiles` возвращает его
  сгенерированный `id`.
- Удалённый снимок (мок) несёт профиль с ТЕМ ЖЕ `id`, но `name="Remote
  Name"`, `queryString="q=remote"`, `timestamp` заведомо позже локального.

## Сценарий (Given-When-Then)

**Given** локальный профиль P и удалённая более свежая версия того же `id`
настроены как выше

**When** пользователь запускает «Sync now»

**Then** в списке фильтр-профилей Settings профиль P теперь показывает
«Remote Name»
**And** в панели фильтров листинга (Browse) применение P использует
`queryString="q=remote"` — обе поверхности синхронно отражают победителя

## Проверяемые данные
| Параметр | Значение |
|---|---|
| Профиль P | Local Name / q=local (более старый timestamp) |
| Удалённая версия | Remote Name / q=remote (более новый timestamp) |

## Заметки для автоматизации
- Sync-фикстура отсутствует (тот же класс, что TC-207..211) — информация
  для test-automator, не блокер.
- `id` профиля для мок-снимка берётся из возврата `seed_filter_profiles`
  (функция уже генерирует `uuid4`, но не возвращает его вызывающей стороне —
  потребуется небольшое расширение сигнатуры/новый хелпер, чтобы тест мог
  подставить ТОТ ЖЕ `id` в мок; тоже информация для test-automator).
- Риск области ниже, чем у слияния работ (R-09, не R-01) — по коду это та же
  форма LWW, но без файлов и без риска потери контента, отсюда P2.
