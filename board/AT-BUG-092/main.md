## Суть долга

TC-286 (branch 2в правила-реакции `fulfillSendRequests`: сбой закачки
оставляет `sendRequestedAt`/`sendHandledAt`-запрос неотработанным, следующий
проход синхронизации повторяет попытку) требует, чтобы ОДИН и тот же URL
(GET work-страницы работы `W`, `DownloadRepository.fetchDownloadUrl`) отдал
**разный** HTTP-ответ в двух последовательных прогонах `syncNow()` внутри
**одного** теста: `404` на первом проходе (закачка проваливается,
`fetchDownloadUrl` возвращает `null` немедленно —
`DownloadRepository.kt:215-218`, код `>=400` вне диапазона 500-599, ретраев
нет), затем `200` + валидная download-ссылка на втором (закачка
проходит). Ни один существующий примитив фреймворка это не даёт сделать
безопасно:

1. **`sync_replay` (`framework/tests/conftest.py:1077-1145`) рассчитан РОВНО
   на один вызов `start(...)` за тест.** `assert not started["value"]`
   (`:1120-1125`) роняет тест немедленно при попытке переконфигурировать —
   намеренная защита от осиротевшего mitmdump-процесса на порту 8080
   (класс AT-BUG-043), но она же и запрещает сам приём. Grep этим ходом по
   всему `framework/` (`sync_replay(`/`start_replay(`/`mitm.stop(`) — 6
   изолированных вызовов `sync_replay(` в `framework/tests/test_sync.py`,
   КАЖДЫЙ в своей тестовой функции, ни одного повторного вызова внутри
   одной; вне области `sync` внутри `framework/` — ни одного вхождения.
   **Исправление (критик-вход, T2, 2026-08-21):** формулировка «прецедента
   нет нигде в репозитории» опиралась на грep, СУЖЕННЫЙ до `framework/` —
   overclaim по границе охвата. Grep ПО ВСЕМУ репозиторию (этим ходом)
   находит ЕЩЁ ОДИН файл с реальными вызовами `sync_replay(` вне
   `framework/`: `runs/reference/test_bug078_verify_temp_REFERENCE.py:172,255`
   — ДВА вызова, но КАЖДЫЙ в СВОЕЙ тестовой функции (`test_receiving_
   device_downloads_and_shows_snackbar` / `test_local_row_wins_but_send_
   request_still_merges`), НЕ повторный вызов внутри одной — вывод по
   существу НЕ меняется (прецедента реконфигурации ВНУТРИ одного теста
   по-прежнему нет), но граница охвата поиска называется честно: «нет
   прецедента» проверено по `framework/` + `runs/reference/` (единственный
   живой код за пределами `framework/`, ссылающийся на эту фикстуру), а не
   буквально «нигде в репозитории» (остальные попадания repo-wide grep —
   `bugs/*.md`/`board/*/main.md`/`state/escalations.md`/`runs/*/allure/*`/
   тест-кейсы — не код, комментарии/артефакты/зеркала).
2. **Низкоуровневые примитивы `mitm.start_replay`/`mitm.stop`
   (`framework/core/mitm.py:381-455,571`) технически МОГУТ быть вызваны
   дважды подряд напрямую, в обход фикстуры** (teardown одного `_proc`
   корректен по фиксу AT-BUG-043) — но: (а) НЕТ ни одного живого прогона,
   доказывающего, что это действительно работает на устройстве (порт
   освобождается вовремя, второй `start_replay` реально подхватывает новый
   `.mitm` без гонки); (б) `server_replay_extra=forward`
   (`mitm.py:442`) — **безусловный**, без параметра отключения: любая
   ошибка в ручной пере-конфигурации (например, устройство успевает
   отправить запрос в окне между `stop()` и вторым `start_replay()`) уходит
   не в контролируемый отказ теста, а в **живой archiveofourown.org** —
   прямое нарушение правила проекта «никогда не грузить живой AO3».
3. **Альтернатива без реконфигурации прокси** — `server_replay_reuse`
   (сейчас безусловно `true`, `mitm.py:441`) позволила бы записать ДВЕ
   флоу-записи под один URL и «расходовать» их по очереди (первый матч —
   404, второй — 200) в рамках ОДНОГО подъёма mitmdump — но
   `mitm.start_replay` не имеет параметра, отключающего
   `server_replay_reuse`; это требует правки самой функции.

Ни (2), ни (3) не являются существующим проверенным приёмом — писать тест
на основании догадки «наверное сработает» означает реальный риск
случайного live-forward на archiveofourown.org (`docs/01-test-strategy.md`
§9 «sync/downloads», TC-280 «Обоснование объёма» — именно поэтому дизайн
TC-280 сознательно вынес эту ветку за скобки, а TC-283 независимо
подтвердил отсутствие прецедента).

Смежная, уже проверенная живьём часть: синтетический `404` на GET
work-страницы сам по себе — безопасный, доказанный приём
(`rb.make_html_get_flow(url, body, status=404)`, precedent AT-BUG-061,
`framework/data/recording_builder.py:937-942`,
`METADATA_FETCH_WORK_B_AO3_ID`, другой HTTP-клиент — `HttpURLConnection`,
но server-replay матчит только по scheme+method+path+query+host+port,
клиент-агностично). Долг — ИМЕННО в переключении ответа МЕЖДУ двумя
проходами внутри одного теста, не в генерации 404 самой по себе.

## Критерий готовности (Fixed)

- Один из приёмов (2) или (3) реализован в `framework/core/mitm.py`/
  `framework/tests/conftest.py` и доказан живым прогоном НА МЕНЕЕ
  рискованном сценарии, чем `sync` (любой существующий `replay`-тест с
  двумя последовательными HTTP-подменами разного содержимого одного URL,
  например в области `downloads`) — снимает саму технику с «предположения»
  на «проверенный факт», не рискуя live-forward-инцидентом на первом же
  использовании внутри `sync`.
- TC-286 доведён до зелёного прогона на replay ЭТИМ приёмом (доказательство
  пригодности именно для сценария retry).
- Smoke без регресса.

**Исправление (критик-вход, T2/B2, 2026-08-21):** приём (3) выше
(«Альтернатива без реконфигурации прокси» — `server_replay_reuse`)
корректно назван в «Суть долга» пункт 3 как требующий правки самой
функции, НО этот критерий Fixed не называл явно риск: `server_replay_reuse`
(`mitm.py:441`) — ГЛОБАЛЬНЫЙ флаг ЦЕЛОГО процесса mitmdump, поднятого нужен
он ради повторных запросов АССЕТОВ device-wide (см. комментарий у
`start_replay`, `mitm.py:388-389`). Отключение `server_replay_reuse`
process-wide отправило бы ЛЮБОЙ повторный запрос ЛЮБОГО URL после
исчерпания его собственного флоу на живой archiveofourown.org
(`server_replay_extra=forward`) — то есть РАСШИРЯЕТ риск live-forward, ради
предотвращения которого баг заведён, а не сужает его. Если бы приём (3)
когда-либо понадобился для ДРУГОГО сценария этой области — правильная форма
не «глобально отключить», а point-in-time/per-flow расходование ЛИБО связка
«reuse off + `server_replay_extra=kill`» с явной оговоркой о риске ассетов
(kill вместо forward убирает именно возросший риск, ценой падения на любом
незаписанном ассете — приемлемый компромисс для контролируемого теста, НЕ
для общего device-wide прокси). Приём (2) (низкоуровневый `stop`/
`start_replay` дважды в обход фикстуры) остаётся ВОЗМОЖНЫМ путём для
будущего сценария, если такой найдётся — критерий Fixed выше не переписан
целиком (баг рекомендован к закрытию, не к продолжению работы), но
исправление зафиксировано для читателя, который решит переоткрыть.

## Анализ

фикстуры), но уже AT-BUG-073 (`sync_replay`) — доведённый механизм не
покрывает МНОЖЕСТВЕННУЮ реконфигурацию внутри одного теста, только
однократный подъём с локально зависимым содержимым. Чинит фабрика по
правилу «Устранить test debt» (B4). Fixed не ждёт сборку приложения —
