# TC-191 — Save note с листинга по существующей строке сохраняет локальные title/фандом/word count нетронутыми

## Предусловия
- Работа W (`ao3_id 900000001`) — Room засеяна (`seed_db.seed_with_comment`)
  строкой с ЛОКАЛЬНО РАСХОДЯЩИМИСЯ метаданными: `title="ЛОКАЛЬНЫЙ заголовок"`,
  `author="Локальный автор"`, `fandom="Мой фандом"`, `wordCount=777777`,
  `rating=SAVE`, `comment="note A"` (тот же класс baseline, что TC-151/TC-152,
  без `downloadPath`/тегов — они не в скоупе этого кейса, уже покрыты теми
  кейсами).
- ТЕМ ЖЕ вызовом `seed_db.seed_with_comment` дополнительно засеяны ДВЕ
  БРАКЕТИРУЮЩИЕ референсные работы, рейтинг Favorite (`SAVE`), без
  заметки/тегов: `PENDING` (`framework/data/works.py`, `ao3_id 900000004`,
  `wordCount=12000`) и `KUDOSED` (`ao3_id 900000002`, `wordCount=1500`).
  Их word count окружает ПОТЕНЦИАЛЬНЫЙ канонический fallback листинга
  `wordCount=4200` (`12000 > 4200 > 1500`) — критик-вход rework (B2): с
  ЕДИНСТВЕННОЙ работой в Library любая позиция единственного элемента
  тривиальна и не может опровергнуть ничего; с этими соседями позиция
  становится РАЗЛИЧИМЫМ оракулом (см. Then).
- Открыт листинг (replay `listing_basic.mitm`, `recording_builder.LISTING_BASIC_URL`),
  содержащий блёрб работы W — карточка на листинге показывает КАНОНИЧЕСКИЕ
  значения фикстуры (`title="A Loved Test Work"`, `fandom="Fandom Alpha"`,
  `wordCount=4200`), листинг статичен и не знает о локальных данных в Room.
- Rate-кнопкой блёрба открыт нативный overlay (`RatingOverlay`) — Favorite
  показан выбранным (соответствует засеянному `SAVE`); превью существующей
  заметки раскрыто тапом (`tap_comment_preview`, приём TC-088), заметка
  `"note A"` видна.

## Сценарий (Given-When-Then)

**Given** работа W имеет ЛОКАЛЬНО РАСХОДЯЩИЕСЯ со страницей `title`/`fandom`/
`wordCount`, рейтинг Favorite, заметку `"note A"`; на листинге overlay
рейтинга раскрыт с превью заметки, Favorite показан выбранным

**When** пользователь нажимает «Save note» БЕЗ правки текста заметки (рейтинг
Favorite остаётся выбранным) — код-путь `applyRating(rating=SAVE,
comment="note A", dismiss=false)` → `existing.backfillMetadata(work).copy(...)`
(`BrowserViewModel.kt:891-919`, применяет ветку `:897`); overlay сам НЕ
закрывается (`dismiss=false` — `applyRating(dismiss=false)` пишет Room, но
держит overlay открытым независимо от того, какая именно кнопка вызвала
сохранение, см. `app-under-test/CLAUDE.md` «Rating entry points», пункт 1) →
пользователь явно закрывает overlay тапом вне карточки (`RatingOverlay.
dismiss()`) → переключается на вкладку Library

**Then** `title`/`author`/`fandom`/`wordCount` строки ОСТАЮТСЯ ЛОКАЛЬНЫМИ
расходящимися значениями — НЕ заменены скрейпом канонической страницы
листинга (`read_work_ratings_full()`)
**And** `timestamp` строки ИЗМЕНИЛСЯ относительно baseline (различающий
оракул CH-008: подтверждает, что запись реально прошла через upsert-путь
`applyRating`, а не что тап не дошёл до обработчика)
**And** сортировка Library «Word count (high to low)» размещает три карточки
СТРОГО в порядке `W(777777) → PENDING(12000) → KUDOSED(1500)` — Y-координата
карточки W МЕНЬШЕ (выше на экране) Y-координаты карточки PENDING
(`LibraryScreen.visible_card_y`), подтверждая, что `wordCount` остался
ЛОКАЛЬНЫМ `777777`. Если бы поле тихо откатилось к каноническому `4200`
(BUG-048-класс), карточка W оказалась бы МЕЖДУ PENDING и KUDOSED — бракет
референсными работами делает эту разницу различимой, а не тривиальной
позицией единственного элемента списка
**And** (ПОСЛЕДНЯЯ проверка кейса, после сортировочной) Library фильтр-панель
по фандому продолжает показывать локальный `"Мой фандом"` (выбор этого
фандома находит карточку работы W); канонический `"Fandom Alpha"` для работы
W НЕ появляется в списке фандомов

**ПОРЯДОК КЛАУЗ Then ОБЯЗАТЕЛЕН (критик-вход rework, B4):** проверка
сортировки трёх карточек идёт ДО проверки фандом-фильтра, а фандом-фильтр —
ПОСЛЕДНЯЯ проверка кейса и НЕ сбрасывается. Причина: применение фильтра
МУТИРУЕТ видимый список — работы других фандомов скрываются (эмпирика
`framework/tests/test_library_filters.py:87-95`, `assert_work_not_in_tab`), а
бракетирующие соседи несут ДРУГИЕ фандомы (PENDING — `Fandom Delta`,
KUDOSED — `Fandom Beta`), поэтому после применения `"Мой фандом"` на экране
остаётся ТОЛЬКО карточка W: проверка порядка трёх карточек дала бы ЛОЖНЫЙ
КРАСНЫЙ («карточки не видны», `visible_card_y` → `None`), не вычислив сам
оракул word count. Сброса фильтра существующим примитивом нет:
`LibraryScreen.open_fandom_picker` тапает `by_text("All fandoms")`, а после
применения триггер пикера показывает выбранный фандом (`LibraryScreen.kt:630`
— `draftFandom ?: "All fandoms"`). Перестановка этих клауз обратно ломает
кейс — автоматизатору менять их порядок нельзя.

## Заметки для автоматизации
- **Анти-ловушка (задокументированная ГРАНИЦА, не покрыта этим кейсом):**
  ветка `pendingPanelSave` (`onRateWorkRequested:1088-1101`) — отдельный
  писатель со странице work-page панели — по-прежнему конструирует строку
  напрямую, а не через `backfillMetadata`; проверка пустоты там выполняется в
  `savePanelRating` (`:707`/`:753`) в момент ЗАПРОСА, а сама запись — ПОСЛЕ
  JS round-trip, что признано гонкой в комментарии кода `:1085-1087` (R2,
  ESC-026). Этот кейс использует ТОЛЬКО дверь-пересборщик листинга
  (`applyRating`/`backfillMetadata`, :897) — гонка панели кейсом НЕ
  покрывается, граница явно названа, не молчание.
- Раскрытие overlay с уже выбранным рейтингом и превью заметки —
  существующие методы `rating_overlay.py` (`RatingOverlay.tap_comment_preview`,
  использован TC-087/TC-088); листинг открывается
  `browser_steps.open_listing(driver, recording_builder.LISTING_BASIC_URL)`,
  Rate-кнопка — `browser_steps.tap_rate_button(driver, work_id)`; «Save note»
  — `RatingOverlay.save_note()` (bottom-sheet сам не закрывается — докстринг
  метода) → закрытие overlay явным `RatingOverlay.dismiss()` (тап вне
  карточки, метод уже существует и используется, см. `rating_overlay.py`)
  ПЕРЕД переключением на вкладку Library.
- Baseline строится `seed_db.seed_with_comment` (Work с локальными
  title/author/fandom/word_count, rating="SAVE", comment="note A", tags=None)
  — блокера нет, функция уже существует и уже используется TC-014/TC-155;
  тем же вызовом (список из 3 кортежей) сеются бракетирующие соседи
  `PENDING`/`KUDOSED` (rating="SAVE", comment=None, tags=None).
- Оракул — `seed_db.read_work_ratings_full()` (AT-BUG-046, уже Fixed) до/после
  действия; сверка фильтр-панели — `library_steps.apply_fandom_filter`/
  `LibraryScreen.open_fandom_picker`; сортировка — `LibraryScreen.
  open_sort_menu`/`select_sort_option` (образец TC-030/TC-031), позиция трёх
  карточек — `LibraryScreen.visible_card_y(title)` на каждый из трёх
  заголовков (W/PENDING/KUDOSED), сравнение Y напрямую (не
  `topmost_visible_title` — та функция отдаёт только САМЫЙ верхний из
  кандидатов, не относительный порядок всех трёх, а именно порядок и есть
  бракетирующий оракул этого кейса).
- **Бракетирующие референсные работы (критик-вход rework, B2):** `PENDING`
  (`wordCount=12000`) и `KUDOSED` (`wordCount=1500`) взяты готовыми из
  `framework/data/works.py` (уже существуют, использовались TC-030/031 и
  соседями) — окружают канонический fallback `4200` (`12000 > 4200 > 1500`),
  делая позицию W (локально `777777`) различимым индикатором: правильное
  поведение — W выше PENDING; тихий откат к канонической странице — W МЕЖДУ
  PENDING и KUDOSED. С единственной работой в списке (было в attempt 1)
  позиция тривиальна независимо от значения — блокер устранён добавлением
  соседей, не заменой Then на прямой ассерт значения (второй вариант из
  B2 не выбран: список из трёх карточек ближе к пользовательскому наблюдению
  «работа осталась на своём месте в отсортированной библиотеке», чем чтение
  текста на карточке).
- **Границы `backfillMetadata` (две точки вызова, критик-вход rework):**
  метод применяется в `BrowserViewModel.kt:849` (ветка `rating == null`,
  deselect/save-note-only с уже существующей строкой) и `:897` (ветка
  `rating != null`, дверь ЭТОГО кейса). Этот кейс покрывает ТОЛЬКО `:897`;
  негативная сторона `:849` (непустые локальные метаданные не перезаписываются
  при deselect) уже покрыта `TC-152`; позитивная сторона `:849` (пустые поля
  stub-строки заполняются при save-note/deselect БЕЗ выбора рейтинга) этим
  проходом НЕ покрыта — граница названа явно, не молчание.
- **Наблюдаемость Then про фильтр/сортировку:** оба эффекта — прямые Room-
  read-производные UI-элементы (fandom-пикер строится из `distinct(fandom)`
  засеянных строк, `LibraryViewModel.kt:76-78`; сортировка — по колонке
  `wordCount`), не сетевой эффект — класс `AT-BUG-029`/калибровки Lead
  2026-07-30 неприменим, наблюдение прямое.
- Область НЕ комбинаторная в смысле банка CLAUDE.md: кейс — точечный сценарий
  ОДНОЙ двери/точки кода (`backfillMetadata` при `Save note` без правки
  текста), фильтр/сортировка используются как ОБСЕРВАБЕЛЬНЫЙ оракул
  правильности ОДНОЙ записи, а не проверка самого механизма
  фильтрации/сортировки на множестве входов (тот же прецедент рассуждения,
  что TC-151/TC-152/TC-155) — строка `Инвариант:` не требуется.
- Правило `backfillMetadata` НЕ является правилом-реакцией в смысле батареи
  CLAUDE.md (авто-скачивание/авто-kudos/broadcast/уведомление): дозаполнение
  — часть ОДНОЙ и той же записи рейтинга (нет отдельного побочного эффекта
  на условие), выполняется одинаково при КАЖДОМ вызове ветки `existing != null`
  (нет отдельного "edge" и "level" пути), не переключаемо сеттингом (нет
  off-состояния), детерминированно идемпотентно по построению (`ifBlank`/`?:`
  не заменяют уже непустые значения повторным вызовом) — батарея н-п.
  Ретроактивность (третий бank-пункт) содержательно покрыта companion-кейсом
  TC-192 (строка, созданная ДО первой оценки, ведёт себя по текущей семантике
  при первом касании).
- **Companion-кейс TC-192** — положительная сторона того же правила (пустое
  поле заполняется), тот же файл/строки кода, другой Given (orphan-строка с
  пустыми полями вместо расходящихся).
- Блокеров автоматизации не обнаружено — все использованные примитивы
  (`seed_with_comment`, `read_work_ratings_full`, `open_listing`,
  `tap_rate_button`, `RatingOverlay`, `library_steps`/`LibraryScreen`
  фильтр/сортировка) уже существуют в фреймворке.
