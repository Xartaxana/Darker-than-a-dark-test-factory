## 1. Объект тестирования

Android-приложение ao3-wrapper (minSdk 26, targetSdk 36): WebView-обёртка над
archiveofourown.org + нативные Compose-экраны (Library, Settings) + локальная БД Room +
JS-bridge (`ao3_bridge.js`), инжектируемый в каждую страницу.

**Иерархия источников истины (обязательна для всех агентов, особенно
test-designer — не читать её как формальность):**

1. **Код `app-under-test`** — единственная надёжная истина о фактическом
   поведении. Место реализации, а не описания: `BrowserScreen.kt`,
   `MainActivity.kt`, `*ViewModel.kt`, `ao3_bridge.js` и т.д. Приёмочные
   критерии кейсов должны опираться на прочтение кода, а не на пересказ в
   доках, когда есть расхождение или сомнение.
2. **`app-under-test/CLAUDE.md`** — вторичный, но обычно более детальный и
   актуальный источник, особенно для хрупких/часто ломающихся зон (пример:
   раздел "Dark mode — fragile area" документирует инварианты и чек-лист
   проверки точнее, чем PROJECT.md). Хорошая отправная точка перед чтением
   кода, но не заменяет его при формулировке критерия приёмки.
3. **`app-under-test/PROJECT.md`** — только черновой ориентир и карта
   функциональности верхнего уровня. Уже подтверждён случай, когда он
   расходится с реальным кодом (см. §10, side panel / dark mode). Перед тем
   как класть факт из PROJECT.md в критерий приёмки теста — обязательно
   перепроверять по коду, не полагаться на него как на финальную истину.

При обнаруженном расхождении PROJECT.md ↔ код: верить коду, фиксировать
расхождение как находку для человека в §10, **не редактировать сам
PROJECT.md** (он находится в `app-under-test/`, действует запрет проекта на
изменения кода/доков приложения — это ответственность разработчиков
приложения, не QA).

API у AO3 нет — живая спецификация = код приложения (в первую очередь) +
CLAUDE.md + фактическое наблюдаемое поведение; PROJECT.md используется только
как отправная точка для навигации по функциональности, не как источник
истины при конфликте.

**Сборки и версии (сверено по коду 2026-08-09, коммит 6f884d97).** Пачка
коммитов этой сборки принесла конвейер поставки в сам проект приложения —
для QA это меняет ТОЛЬКО одно: как читается версия тестируемого артефакта,
поэтому фиксируем факты здесь, а не в реестре фич (наблюдаемого поведения
приложения они не добавляют):

- `app/build.gradle.kts:21-24` — `versionCode = CI_PIPELINE_IID + 12` (без CI —
  `12`), `versionName` = тег без ведущего «v», иначе `dev-<CI_PIPELINE_IID>`,
  иначе `dev-local`. То есть **у любой не-тегированной сборки имя вида
  `dev-6`/`dev-local`, а `versionCode − 12` = номер пайплайна**, по которому
  `found_in:` бага возвращается к коммиту.
- `.gitlab-ci.yml` — `build:debug` на push в `main`/MR (артефакт
  `ao3-debug-<short-sha>`, 30 дней), `build:release` только на теги `^v\d`
  (артефакт `ao3-<tag>-<pipelineIID>-<sha>`, 1 год); release подписан тем же
  debug-ключом (`build.gradle.kts:42-44`), поэтому ставится поверх
  sideload-установки.
- Следствие для конвейера, требующее внимания координатора (не моя правка):
  `state/app-under-test.yaml` для сборки 6f884d97 всё ещё несёт
  `version_name: "1.10"` / `version_code: 11`, чего эта схема версий выдать уже
  не может; `found_in:` новых багов должен браться из фактического APK, иначе
  ссылка «версия → пайплайн → коммит» рвётся.

## 2. Ограничения и следствия для стратегии

| Ограничение | Следствие |
|---|---|
| Нельзя менять код приложения | Только black-box UI-тестирование через Appium/UiAutomator2; никаких testTag, никаких unit-тестов внутри приложения |
| Нет API у AO3, весь контент через WebView | Гибридное тестирование: нативный слой (Compose) + web-слой (DOM внутри WebView) |
| Живой сайт AO3: Cloudflare bot-check, нестабильная сеть, изменяющийся DOM | Два режима прогона: **live** (минимальный smoke) и **replay** (детерминированная регрессия на записанных страницах через mitmproxy) |
| Compose-экраны без testTag | Локаторы: content-description, текст, иерархия accessibility tree; хрупкость закладываем в дизайн локаторов (один локатор — одно место в коде) |
| Данные только локально (Room, SharedPreferences) | Управление состоянием через adb (`pm clear`, seed через restore-flow или `run-as` на debug-сборке) |

## 3. Уровни тестирования

| Уровень | Что проверяет | Инструмент | Доля |
|---|---|---|---|
| E2E UI (нативный + WebView) | Основные пользовательские сценарии | Appium + UiAutomator2 | ~70% |
| Web-слой (bridge-канарейки) | Живой DOM AO3 всё ещё соответствует селекторам `ao3_bridge.js` | Отдельный canary-suite (live) | ~10% |
| Данные | Целостность Room после операций: backup/restore, clear, scan for downloads | E2E + проверка экспортированного JSON | ~15% |
| Нефункциональные | Четыре области §9 «Нефункциональные»: performance/stability smoke (E2), accessibility smoke (E1), compatibility (E3), security/privacy smoke (E4-min); плюс восстановление после kill, offline | E2E-сценарии + инспекция манифеста/logcat | ~10% |

## 4. Режимы прогона

### live (smoke, canary)
Настоящий AO3, залогиненная тестовая учётка (cookie WebView). Только P0-смоук
(5–10 тестов) и canary-suite селекторов. Падения здесь чаще всего = изменение сайта
или bot-check, а не баг приложения — триаж это учитывает.

### replay (регрессия, по умолчанию)
Эмулятор + mitmproxy в режиме replay: записанные страницы AO3 (листинги, страница
работы, форма Sort&Filter) версионируются в `framework/data/recordings/`. Детерминизм,
скорость, независимость от Cloudflare. Требование: AVD-образ без Google Play (root)
для установки CA mitmproxy в системное хранилище — WebView не доверяет user-CA.

## 7. Критерии качества прогона (gate)

## 9. Области, требующие тест-дизайна (`needs-design`)

**Конвенция сопровождения (машиночитаемо, не декоративно).** Метка
`needs-design` у пункта/области — это триггер правила `state/rules.yaml`
«Спроектировать кейсы для области без покрытия» (диспатч `test-designer`).
Область (или пункт) считается **designed** и метка снимается, когда по её
пунктам созданы тест-кейсы в любом из статусов `Review`/`Approved`/`Automated`
(дизайн уже существует). Статус `Draft` НЕ засчитывается — это ещё не готовый
дизайн. Снятие метки происходит в том же ходе, что и закрытие области, иначе
правило диспатчит `test-designer` вхолостую. Пункт, покрытый лишь частично,
остаётся `needs-design` с явным описанием того, что именно не покрыто (а не
всей области).

Третий режим — **отложенный минорный остаток**: не покрытая под-функция
пункта, помеченного `designed`, которую сознательно НЕ выносят в `needs-design`
и НЕ триггерят `test-designer`. Критерий отличия от `needs-design`: под-функция
лежит вне рискового ядра пункта (вне привязанного к пункту риска §5) и её
дизайн не блокирует закрытие области; решение о дозакрытии — за человеком.
Трекается прозой в самом пункте §9 с явной пометкой «отложенный минорный
остаток» (находится Grep'ом, видим человеку при ревью §9), а не машиночитаемой
меткой `needs-design`.

**Форма токена в пунктах (конвенция 2026-07-28; класс «токен в отрицании» —
находка CH-005 п.3 отчёта §10 + доклад test-strategist).** Внутри ПУНКТОВ §9
буквальная подстрока `needs-design` пишется ТОЛЬКО как действующая метка.
Отрицания, история и ссылки на снятую метку формулируются описательно, БЕЗ
буквального токена: «дизайн-метка снята», «отдельная дизайн-метка не
требуется», «остаток из дизайн-очереди закрыт», «прежний текст помечал её
меткой дизайна». Причина: правило `state/rules.yaml` ищет пункт §9 с меткой,
и токен в отрицании внутри пункта неотличим от метки без семантического
разбора (4 предсуществующих экземпляра переписаны 2026-07-28 этой
конвенцией). Заголовок §9, текст конвенции и комментарии §10 — вне пунктов,
как и раньше. Детектор утечки: false-диспатч test-designer на покрытую
область → его штатный no-op со снятием метки (комментарий правила в
rules.yaml) + строка orchestrator-log; разбор no-op'ов — чек калибровки.

    человеку. Метки §9 не требует: инструмент чартерный, не кейсовый.
  - **механическая половина — ЭТА область**: числовые пороги, которых модельное
    зрение не меряет, в кейсах, воспроизводимых на каждой сборке.
  Граница честности зафиксирована в ОБЕ стороны (в шаблоне чартера — своей
  строкой): тур не измеряет пороги, свип не судит «красиво/некрасиво» и глаза
  не заменяет.

  **Три оракула (названы решением владельца; каждый — отдельный род Then,
  дробление на кейсы за test-designer):**
  - **(а) touch-target >= 48dp (гайдлайн Android) для НАТИВНОГО хрома** —
    панели, тумблеры, чипы `TabStrip`, кнопки диалогов: `bounds` берутся из
    a11y-дерева UiAutomator2 (тот же примитив инспекции без взаимодействия, что
    у TC-106). Порог — Android-гайдлайн, НЕ WCAG; поимённый список целей —
    часть дизайна.
  - **(б) контраст DOM-контента WebView через `getComputedStyle`** (`color`
    против эффективного `background-color`), WCAG-порог **4.5:1** для обычного
    текста и **3:1** для крупного: применяется к ИНЖЕКТИРОВАННЫМ элементам
    bridge (Rate/Note-кнопки, бейджи — палитра `BADGE` в `ao3_bridge.js`
    зеркалит `MaterialTheme.ao3Colors`, то есть дрейф палитры приложения виден
    только сверкой обеих сторон) и к ключевым узлам НАШИХ replay-фикстур.
  - **(в) пересечения bounding-rect'ов интерактивных элементов (перекрытия)** —
    как минимум нативный слой, где `bounds` достоверны из a11y-дерева.

  **Границы, которые дизайн ОБЯЗАН назвать (без них кейс недостоверен, а не
  просто хрупок):**
  - **dp против px.** `bounds` a11y-дерева — в device px; порог 48dp =
    48 × density, и density ИЗМЕРЯЕТСЯ (`adb shell wm density`), а не берётся
    из памяти. Записанная в этом документе плотность эталонного AVD —
    **dpr 2.625** (замер CH-005 на 1080×2400, 420 dpi ⇒ 48dp = 126 px), не 2.5;
    расхождение названо здесь явно, чтобы константа не разошлась с фактом. Для
    WebView `getComputedStyle`/`getBoundingClientRect` отдают CSS px — связка с
    device px идёт через `window.devicePixelRatio` и текущий viewport-масштаб
    (его меняет `textZoom` side panel!), это отдельная строка Given, а не
    мелочь.
  - **чужая вёрстка вне скоупа (граница §8).** Живой AO3 — не наш продукт:
    свип идёт по НАШИМ инжектированным элементам и по replay-фикстурам, чей
    HTML порождаем мы (`scripts/build_replay_recordings.py`), а не по вёрстке
    archiveofourown.org. Контраст чужого текста AO3 — не наш дефект и не наша
    находка.
  - **динамические состояния** (раскрытая нижняя панель, fullscreen, открытый
    диалог/оверлей, живой снекбар): либо ОТДЕЛЬНЫЕ точки свипа с поимённым
    списком, либо ЯВНЫЙ non-goal первой итерации — дизайн обязан выбрать и
    записать. Умолчание запрещено: именно в динамике живёт `bugs/BUG-017.md`
    (парад снекбаров), и молчаливое исключение прочтётся как «свип это
    покрывает».
  - **перечень точек свипа — воспроизводимый и поимённый** (по образцу маршрута
    TC-107: Library → Browse (work page) → Settings), иначе «свип» не
    повторяется от прогона к прогону и его красный не сравним с прошлым.

**Находка code-vs-docs (2026-07-02, разведка test-strategist по коду перед
дизайном side panel) — требует внимания человека, TC-048 нужно пересмотреть:**

Прямое чтение кода (`BrowserScreen.kt`, `MainActivity.kt`, `BrowseSidePanel.kt`,
`app-under-test/CLAUDE.md`) показывает, что предпосылка «WebView dark mode

  is necessary because ALGORITHMIC_DARKENING only takes effect on next page
  load" — то есть `reload()` УЖЕ выполняется программно при переключении темы,
  без участия пользователя и без cold start приложения.
