## 1. Объект тестирования

Android-приложение ao3-wrapper (minSdk 26, targetSdk 36): WebView-обёртка над
archiveofourown.org + нативные Compose-экраны (Library, Settings) + локальная БД Room +
JS-bridge (`ao3_bridge.js`), инжектируемый в каждую страницу.

**Иерархия источников истины (обязательна для всех агентов, особенно
test-designer — не читать её как формальность):**

1. **Код `app-under-test`** — единственная надёжная истина о фактическом
   поведении. Место реализации, а не описания: `BrowserScreen.kt`,
   `MainActivity.kt`, `*ViewModel.kt`, `ao3_bridge.js` и т.д. Приёмочные
   критерии кейсов должны опираться на прочтение кода, а не на пересказ в
   доках, когда есть расхождение или сомнение.
2. **`app-under-test/CLAUDE.md`** — вторичный, но обычно более детальный и
   актуальный источник, особенно для хрупких/часто ломающихся зон (пример:
   раздел "Dark mode — fragile area" документирует инварианты и чек-лист
   проверки точнее, чем PROJECT.md). Хорошая отправная точка перед чтением
   кода, но не заменяет его при формулировке критерия приёмки.
3. **`app-under-test/PROJECT.md`** — только черновой ориентир и карта
   функциональности верхнего уровня. Уже подтверждён случай, когда он
   расходится с реальным кодом (см. §10, side panel / dark mode). Перед тем
   как класть факт из PROJECT.md в критерий приёмки теста — обязательно
   перепроверять по коду, не полагаться на него как на финальную истину.

При обнаруженном расхождении PROJECT.md ↔ код: верить коду, фиксировать
расхождение как находку для человека в §10, **не редактировать сам
PROJECT.md** (он находится в `app-under-test/`, действует запрет проекта на
изменения кода/доков приложения — это ответственность разработчиков
приложения, не QA).

API у AO3 нет — живая спецификация = код приложения (в первую очередь) +
CLAUDE.md + фактическое наблюдаемое поведение; PROJECT.md используется только
как отправная точка для навигации по функциональности, не как источник
истины при конфликте.

## 2. Ограничения и следствия для стратегии

| Ограничение | Следствие |
|---|---|
| Нельзя менять код приложения | Только black-box UI-тестирование через Appium/UiAutomator2; никаких testTag, никаких unit-тестов внутри приложения |
| Нет API у AO3, весь контент через WebView | Гибридное тестирование: нативный слой (Compose) + web-слой (DOM внутри WebView) |
| Живой сайт AO3: Cloudflare bot-check, нестабильная сеть, изменяющийся DOM | Два режима прогона: **live** (минимальный smoke) и **replay** (детерминированная регрессия на записанных страницах через mitmproxy) |
| Compose-экраны без testTag | Локаторы: content-description, текст, иерархия accessibility tree; хрупкость закладываем в дизайн локаторов (один локатор — одно место в коде) |
| Данные только локально (Room, SharedPreferences) | Управление состоянием через adb (`pm clear`, seed через restore-flow или `run-as` на debug-сборке) |

## 3. Уровни тестирования

| Уровень | Что проверяет | Инструмент | Доля |
|---|---|---|---|
| E2E UI (нативный + WebView) | Основные пользовательские сценарии | Appium + UiAutomator2 | ~70% |
| Web-слой (bridge-канарейки) | Живой DOM AO3 всё ещё соответствует селекторам `ao3_bridge.js` | Отдельный canary-suite (live) | ~10% |
| Данные | Целостность Room после операций: backup/restore, clear, scan for downloads | E2E + проверка экспортированного JSON | ~15% |
| Нефункциональные | Четыре области §9 «Нефункциональные»: performance/stability smoke (E2), accessibility smoke (E1), compatibility (E3), security/privacy smoke (E4-min); плюс восстановление после kill, offline | E2E-сценарии + инспекция манифеста/logcat | ~10% |

## 4. Режимы прогона

### live (smoke, canary)
Настоящий AO3, залогиненная тестовая учётка (cookie WebView). Только P0-смоук
(5–10 тестов) и canary-suite селекторов. Падения здесь чаще всего = изменение сайта
или bot-check, а не баг приложения — триаж это учитывает.

### replay (регрессия, по умолчанию)
Эмулятор + mitmproxy в режиме replay: записанные страницы AO3 (листинги, страница
работы, форма Sort&Filter) версионируются в `framework/data/recordings/`. Детерминизм,
скорость, независимость от Cloudflare. Требование: AVD-образ без Google Play (root)
для установки CA mitmproxy в системное хранилище — WebView не доверяет user-CA.

## 6. Приоритеты покрытия

- **P0 (smoke, гоняется на каждой новой сборке):** запуск и загрузка AO3; выставление
  каждого из 5 рейтингов со страницы работы и из листинга; бейдж появляется без
  перезагрузки; работа попадает в нужную вкладку Library; скрытие Disliked при
  включённой фильтрации; Clear all ratings с подтверждением; backup → clear → restore
  возвращает данные.
- **P1 (регрессия):** мультитаб (создание, лимит 10, undo-закрытие, фоновые табы,
  персистентность после рестарта); фильтры Library (фандом, word count, теги,
  downloaded-only) и все 5 сортировок; download-flow (авто при Loved, ручной из
  Library, открытие file://, удаление, scan for downloads); фильтр-профили
  (сохранение из формы AO3, применение, удаление); заметки и личные теги; error page +
  Retry; **side panel в Browse (тема/шрифт/яркость) и темы Light/Dark/System в Settings**.
  - *Важность области (решение человека 2026-07-02):* **side panel в Browse — более
    важный пользовательский путь, чем экран Settings** (по факту продукта это основной
    вход в тему и размер шрифта). Это ранжирование области, а не тег кейса: сами
    тест-кейсы остаются **P1** (регрессия), но при секвенировании работ и дизайна
    покрытие side panel идёт впереди settings-экрана. См. §9 «browser: side panel».
- **P2:** длинный хвост: поворот экрана, kill/restore процесса, offline-переходы,
  граничные значения (пустая Library, работа без word count, blank author в
  сортировке), restore старого bare-array формата бэкапа.
- **P3:** косметика: цвета бейджей в dark/light, иконки сортировки, snackbar-тексты.

## 7. Критерии качества прогона (gate)

- P0 100% pass → сборка пригодна к использованию.
- P1 ≥ 95% pass, все падения оттриажены (см. docs/03, роль failure-analyst).
- Любое падение обязано получить вердикт: `APP_BUG | TEST_BUG | SITE_CHANGED | ENV_ISSUE | FLAKY` — «просто красный» прогон не закрывается.

## 9. Области, требующие тест-дизайна (`needs-design`)

**Конвенция сопровождения (машиночитаемо, не декоративно).** Метка
`needs-design` у пункта/области — это триггер правила `state/rules.yaml`
«Спроектировать кейсы для области без покрытия» (диспатч `test-designer`).
Область (или пункт) считается **designed** и метка снимается, когда по её
пунктам созданы тест-кейсы в любом из статусов `Review`/`Approved`/`Automated`
(дизайн уже существует). Статус `Draft` НЕ засчитывается — это ещё не готовый
дизайн. Снятие метки происходит в том же ходе, что и закрытие области, иначе
правило диспатчит `test-designer` вхолостую. Пункт, покрытый лишь частично,
остаётся `needs-design` с явным описанием того, что именно не покрыто (а не
всей области).

Третий режим — **отложенный минорный остаток**: не покрытая под-функция
пункта, помеченного `designed`, которую сознательно НЕ выносят в `needs-design`
и НЕ триггерят `test-designer`. Критерий отличия от `needs-design`: под-функция
лежит вне рискового ядра пункта (вне привязанного к пункту риска §5) и её
дизайн не блокирует закрытие области; решение о дозакрытии — за человеком.
Трекается прозой в самом пункте §9 с явной пометкой «отложенный минорный
остаток» (находится Grep'ом, видим человеку при ревью §9), а не машиночитаемой
меткой `needs-design`.

Прямое чтение кода (`BrowserScreen.kt`, `MainActivity.kt`, `BrowseSidePanel.kt`,

**не соответствует фактическому поведению кода уже сейчас**:

- `BrowserScreen.kt` содержит `LaunchedEffect(darkTheme)` (строки ~151–159),
  который на КАЖДОЕ изменение `darkTheme` немедленно (а) пушит
