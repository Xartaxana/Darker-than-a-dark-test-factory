# Политика маршрутизации моделей (routing MVP)

Источник дисциплины: D:\Improving_AI\Operating-System-for-LLMs
(DELEGATION_TABLE.md, решения D-00xx). Назначения estimated —
корректируются еженедельной калибровкой OS по журналу. **Компактная
редакция (диета 2026-08-15, минус внешней критики «конституция 67КБ»):
правило + enforcement + детектор; полные нарративы, прецеденты и
даты-истории — docs/09-history.md §«CLAUDE.md-диета 2026-08-15»
(VERBATIM-архив прежней редакции). Правило сжатия: вырезать можно
ТОЛЬКО то, у чего есть код-гейт ИЛИ явно названный дом в
скилле/агенте — здесь остаются «что + где enforcement»; норма без
кода-гейта и named-дома из конституции НЕ вырезается (урок
критик-входа самой диеты: класс L1-L14).**

## Ярусы

- **scout** (Haiku) — разведка: поиск/чтение по репо, сбор контекста.
  Возвращает дайджест, не дампы.
- **builder** (Sonnet) — реализация по готовой спеке, тесты, рутина.
  Не изобретает требования — возвращает вопросы.
- **critic** (Opus) — ревью кода/архитектуры, отладка неясных багов,
  вход приёмки. Не для рутинных проверок формата.
- **Lead-сессия** (Lead-привязка: Opus 5 — `delegation.config.yaml`
  roles.lead, читают mechanism_gate/log_append; порт D-0099 OS, слово
  оператора 2026-08-15; **Fable — резерв ВЫШЕ Lead**, зовётся словом
  оператора, все права Lead) — декомпозиция, спеки, приёмка,
  архитектура. Только Lead решает, что и кому делегировать.

QA-агенты конвейера — `model` во frontmatter `.claude/agents/*.md`.
**Задача под when-условием state/rules.yaml диспатчится ТОЛЬКО
проходом /qa-loop** (очередь фабрики — полигон конвейера; слово
оператора 2026-07-10). Ручные диспатчи Lead — для НЕ-конвейерной
работы (механизмы, промпты, OS-репо, критик-вход приёмки, разведка,
эскалации). Уже запущенного вручную воркера не убивать — принять
штатно, новых не запускать. Детектор: чек 15 калибровки OS. Имена scout/builder/critic/
Lead — имена ФУНКЦИЙ, не моделей; привязка функция→модель —
frontmatter агентов и delegation.config.yaml. Грейды OS
(intern/junior/…) — их словарь учёта, в правилах не участвует.

## Правила маршрутизации

1. **Разведка → scout ПО УМОЛЧАНИЮ** (чтение >1-2 заранее известных
   файлов ИЛИ любой поиск по репо). Точечная сверка до ~4 ИЗВЕСТНЫХ
   целей может остаться у Lead — ТОЛЬКО с `dispatch_skipped`
   (молчаливый пропуск = нарушение, F-9). Приёмка дайджеста — по
   следу (D-0046): scout прилагает, где искал; Lead сверяет ≥1
   несущее утверждение (негатив «нигде нет X» — обязательно); без
   следа → rejected; сверка отмечается в accepted-событии. Обзор
   ВНЕШНЕГО репо — двухпроходный (D-0066): карта scout + точечный
   второй проход координатора, след второго прохода в записи обзора
   (без dispatch_skipped — это координаторская работа).
2. **Реализация по готовой спеке → builder.** Приёмка — по witness
   (D-0052/D-0053): фактический вывод проверочного прогона в поле
   `witness`, не пересказ; отчёт без witness → rejected. UI-задача —
   прогон включает вождение UI (скриншот/запись «до/после»).
3. **critic — ОБЯЗАТЕЛЬНЫЙ вход приёмки** для: (а) builder-класс
   диффов ЛЮБОГО воркера (по классу работы, не имени агента) —
   заметный размер (>~100 строк) или схема данных/ядровая логика;
   (б) непонятных багов ДО самостоятельной отладки Lead. Первый
   фильтр — само-прогон исполнителя по DoD; critic начинает поверх.
   Денежный/численный дифф критик начинает ЭМПИРИКОЙ (прогоном
   контрольных значений). Вердикт критика — вход; приёмка за Lead
   (D-0037). Мелкие диффы — льгота «critic: skipped, <причина>» в
   accepted, ТОЛЬКО у принимающего ярусом выше исполнителя (D-0058).
   **Двухслойный вход** (порт №14): механический слой (перепрогоны,
   контрольные значения, смоки) исполняется и прикладывается
   ДОСЛОВНЫМ выводом ДО вердикта; зона критика — вердиктный слой;
   слой не приложен — критик возвращает запрос, не исполняет сам.
   **Критик-на-план** (t-159): recon/спека, служащая планом работ
   дороже ~30 мин, получает критик-вход на ПЛАН до старта кода.
   Гейты самой фабрики (fix-verifier по D1, test-reviewer по F1) это
   НЕ отменяет — critic закрывает шов «крупный дифф принимается до
   достижимости фабричного гейта».
4. **Независимые части → параллельные субагенты**, каждый со своей
   спекой; спеки объявляют владение путями, Lead проверяет
   пересечение до запуска. Параллельные СЕССИИ в одном репо — тот же
   класс (чужие незакоммиченные пути не трогать). **Сверка пересечения
   — НЕ ТОЛЬКО ПО ПУТЯМ (2026-08-19):** проверяются и ОБЩИЕ РЕСУРСЫ С
   ГЛОБАЛЬНЫМ ПОБОЧНЫМ ЭФФЕКТОМ — устройство, порт, сервис и особенно
   функции-жнецы процессов (`Stop-NodeProcesses` и родня). Инцидент
   класса: параллельный узел с непересекающимися путями и device-free
   по построению убил живой Appium чужого device-замера, потому что его
   DoD ТРЕБОВАЛ вызвать жнеца, чтобы доказать исключение из него. Если
   DoD воркера вызывает нечто, гасящее процессы/порты хоста, — это
   коллизия, даже когда файлы не пересекаются: либо развести по времени,
   либо потребовать dry-run вместо живого вызова. task_id
   описательные, подлинно новые; повторные delegated/ретраи/reopen —
   enforce'ит scripts/log_append.py (см. Журнал). Замеченная позже
   коллизия — пометка в notes, счёт как две задачи (D-0060).
   **Worktree ≠ полное дерево (2026-08-20):** $root обвязки резолвится
   от файла (детектор: scripts/tests/test_root_resolution_worktree.py),
   но untracked `tools/` в worktree ОТСУТСТВУЕТ — adb/эмулятор/JDK-
   зависимые шаги из worktree не исполняются (FileNotFoundError), а
   wiring-тесты там красные ШТАТНО (hooksPath главного чекаута). DoD
   worktree-воркера — device-free; device-witness снимает координатор
   из главного чекаута.
   4а. Задача ≥5 событий ИЛИ ≥2 сессий — markdown-DAG в docs/tasks/
   (D-0080); статус узла — тем же ходом, что его журнальное событие;
   ПИШУЩИЙ узел DAG объявляет owns-пути.
   4б. **Кросс-деплойный пункт живёт в носителе ЦЕЛИ** (D-0082):
   для OS — их CURRENT_CONTEXT.md кросс-коммитом; для нас —
   docs/HANDOFF.md. Notes журнала/FINDINGS — НЕ носитель. Детекторы:
   чек 3 session-handoff + чеки 0/5 калибровки OS (F-48).
   4в. **Ярусное требование закрывается замером** (D-0083):
   log_append сверяет заявленную model с транскриптом воркера
   (worker_ref async:/agent:); MISMATCH-предупреждение разбирается ДО
   использования результата как слова требуемого яруса (перезапуск /
   честная запись с basis / эскалация). Детектор: чек 5 калибровки OS.
5. **Плоское делегирование (D-0037):** субагенты не запускают
   субагентов; разложимая задача возвращается Lead'у событием
   `decomposable`.
6. **Эскалация:** агент не справился — 2 `rejected` одного яруса на
   одном task_id ИЛИ явный сигнал «не хватает уровня» → ярус выше
   ОБЯЗАТЕЛЕН (`escalated`, model = новая); третья попытка на
   том же ярусе — нарушение. Неудачная попытка = отклонённый на
   приёмке результат; каждое отклонение — `rejected` (attempt,
   failure_class: spec/capability/recon/tooling). Enforcement:
   log_append. Для lead-яруса эскалация = ОПЕРАТОРУ; со 2-го подряд
   rejected на task_id notes несёт строку «оператор в петле».
   Стоимостной кроссовер меряет калибровка.
7. **Фоновый запуск по умолчанию (D-0040):** `run_in_background`;
   синхронное ожидание — только когда следующий шаг зависит от
   результата И другой работы нет (строго последовательные шаги
   /qa-loop — легитимный случай, но и там завершай ход между шагами,
   чтобы очередь сообщений оператора обрабатывалась). Приёмка по
   завершении обязательна.
   Лейбл диспатча начинается с модели воркера («sonnet: …») —
   сверка чеком 5 калибровки (D-0042).
8. **Универсальное правило пропуска (F-9):** тип задачи отображается
   на дешёвый ярус, а Lead делает сам — законно ТОЛЬКО с
   `dispatch_skipped` (причина обязательна). **Батчинг мелочей**
   (D-0081): мелкая builder-правка, НЕ блокирующая следующий шаг,
   поштучно не исполняется — копится и уходит одним пакетным
   диспатчем на границе этапа (маркер «батч мелочей» в notes);
   самоисполнение со skip-событием легально только для правки,
   блокирующей текущий ход, — причина обязана называть блокировку.
   Lead-tier работа событий пропуска не требует.
8а. **Отсрочка готовой работы (2026-08-03):** ГОТОВАЯ пара
   «правило/обязанность × артефакт» (без лока, не Blocked/wip, не
   ждёт человека; экземпляры: срабатывание rules.yaml, follow-up
   Done-чартера found_bugs/followup_tc/new_risks, эскалация с
   названным исполнителем, разбор вердикта воркера) откладывается
   ТОЛЬКО по: (1) лимит срабатываний
   прохода; (2) конфликт путей с работающим воркером; (3) занятое
   устройство — только device-класс. Каждая отсрочка — явной строкой
   с причиной из списка, в ЛЮБОМ режиме координации. Поимённо
   нелегальны: «следующим проходом», «исторический бэклог»,
   «пересекается с известной очередью». Детекторы:
   `charter_followup_unprocessed` (sla_sweep, pre_step 2), секция
   «отложено» сводки, чек 3а session-handoff, чек 5 калибровки OS.
9. **Чини класс, а не экземпляр (D-0043):** дефект — экземпляр
   класса, пока не доказано обратное. Назови класс; пройди по КАРТЕ
   ОСЕЙ D:\Improving_AI\Operating-System-for-LLMs\docs\SIBLING_MAP.md
   (точечный lookup; внутренние оси AO3 — скилл ↔ state/rules.yaml ↔
   schemas/ ↔ scripts/, промпты агентов; класс шире карты → scout);
   почини сейчас или ЯВНО поставь остаток в очередь; правило — на
   самый верхний связывающий уровень. Новая ось — коммитом в OS
   сразу либо явной строкой HANDOFF («новая ось для SIBLING_MAP»).
   Молчаливо оставленный аналог = нарушение. Воркеры ДОКЛАДЫВАЮТ
   аналоги (не расширяя scope), critic проверяет классовую полноту,
   Lead владеет обходом.
10. **Четыре вопроса к каждому механизму (F-11):** прежде чем
   коммитить, Lead ПИСЬМЕННО отвечает; нет ответа — механизм не
   готов. (а) стоимость соблюдения и кто платит; (б) оси — ПЕРЕЧИСЛЕНИЕМ (D-0055): строка
   на КАЖДУЮ ось карты; enforcement — commit-msg-хук (.githooks/ +
   scripts/mechanism_gate.py): механизменный коммит несёт осевой блок
   + строку «tier: <модель>» не ниже привязки (HEAD-резолюция
   конфига; конфиг в неводе; skip-строка «оси: не-механизм
   (<причина>)» — для не-механизмов, при staged-конфиге запрещена
   кодом); (в) ГДЕ зарегистрирован детектор отказа — инвариант ВСЕХ
   механизмов (чек калибровки или named внешний детектор; без
   детектора — пожелание, обнаружение такого — находка); (г) что не
   даёт механизм ПРОПУСТИТЬ (код на пути исполнения, D-0063; «на
   дисциплине» — только явной строкой с named-детектором утечки;
   продвижение в код-гейт — по evidence, не ради симметрии).
   Распознавание (D-0065): механизм = правка, меняющая обязанность
   будущих сессий/агентов либо машинную проверку; сомнение =
   механизм. Детектор утечки — чек 8 калибровки OS. Вопросы
   оператора, вскрывшие пробел, — findings в OS-репо.
11. **DoD в каждом диспатче (D-0054):** builder — критерии приёмки +
   проверочный прогон-witness; интерактивная поверхность (CLI/UI) —
   адверсариальная мини-батарея (величина, вложенность, кодировка,
   пустой/битый ввод); каждый введённый лимит — тест НА границе и ЗА
   ней (класс M6); потолок скоупа = ключи приёмки + батарея +
   границы. scout — явный вопрос + критерий полноты («нигде нет X» —
   валидный итог со следом). critic — против чего ревьюить
   (спека/DoD прилагается). Диспатч без DoD воркер возвращает
   вопросами (аварийная сетка; частые возвраты — дефект
   спек-дисциплины координатора). Рядом с DoD — МАНИФЕСТ КОНТЕКСТА
   (D-0073): «дано»; пишущий диспатч — также owns/non-goals/handoff;
   декларативен по чтению, нормативен по записи (выход за корзину —
   строка отчёта «понадобилось сверх манифеста», не нарушение); для
   точечного read-only диспатча манифест = явное перечисление
   вложенного в самом тексте, без полей. Самопроверка диспетчера ДО
   отправки включает сверку исполнимости DoD-шагов с `tools:`
   frontmatter воркера (калибровка №4): шаг, требующий отсутствующего
   инструмента, либо явно переносится на приёмку координатора, либо
   меняет исполнителя.
11а. **Маршрутизация вопросов (D-0077):** вопросы ходят ВВЕРХ, работа
   — ВНИЗ; вершина — ОПЕРАТОР (выше Lead). Недоопределённые
   ТРЕБОВАНИЯ — вопрос оператору, участок стоит до ответа; решать за
   оператора запрещено любому ярусу. Скип-льгота — только вниз;
   вопрос выше своего уровня поглотить нельзя — только эскалация.
   Самоисполненное после `dispatch_skipped` проходит ту же приёмку,
   что builder-дифф; сдача оператору непринятого — нарушение.
   Headless-среда без оператора — только явной строкой условий с
   прокси-эскалацией (протокол экзамена OS).

## Журнал маршрутизации — logs/routing-log.jsonl

Запись ТОЛЬКО через `python scripts/log_append.py` — он enforce'ит
формат, обязательные поля, матрицу приёмки, ретраи и фантомы; текст
ниже — справка, носитель правил — код гейта и его тесты.

**События:** delegated, accepted, rejected, escalated, decomposable,
dispatch_skipped, defect_found (поздний дефект ПРИНЯТОЙ работы, `ref`
= task_id исходного accepted; НОВЫЕ баги приложения — артефакты
bugs/, НЕ события журнала — смешение портит false-accept-метрику),
lead_degraded, lead_restored.

**Факты, не намерения (D-0076):** delegated/escalated пишутся ПОСЛЕ
фактического запуска, `worker_ref` обязателен (хэндл существует
только после запуска). Открытые диспатчи — `log_append.py
open-dispatches` (Session Start и чек 2 handoff); фантом закрывается
токеном `closes-phantom:<task_id>` в notes следующего события.
Пропущенное событие чинится РЕТРО-парой (append-only, пометка
«retroactive», фактические границы в notes; вставка в прошлое
запрещена).

**Поля:** `model` обязательна для delegated/escalated/accepted/
rejected (самодекларация; сверка с транскриптами — калибровка);
`task_id` сквозной; `attempt`+`failure_class` на rejected; `witness`
на accepted по builder; `ref` на defect_found; `category`
факультативна (признанное отличие от D-0053 OS); `lead_binding` —
ставится log_append АВТОМАТИЧЕСКИ и только на accepted, легализованных
веткой lead-binding (D-0099; поток финальных приёмок счётен, внешний
слой истинности by — чек 6 калибровки OS).

**Приёмка (`--by` обязателен для accepted/rejected):** accepted
легален при tier(by) СТРОГО выше tier(agent)
(haiku<sonnet<opus<fable; QA-агенты — model из frontmatter), ЛИБО
веткой lead-binding (by ЛИТЕРАЛЬНО == семейству привязки,
tier(agent) <= tier(привязки), basis пуст — финальная приёмка
Lead-сессией), ЛИБО с `--basis` по ПОЛНОЙ ПАРЕ (калибровка №4):
haiku/sonnet-класс — только `critic`; opus-класс и выше — только
`queued-to-lead`. Пол by<sonnet безусловен при любой привязке.
agent=lead — матрица не применяется; неизвестный агент —
предупреждение, by достаточно. rejected несёт by без tier-проверки.
rejected(agent=lead) — вердикт критик-раунда по Lead-итерации (см.
правило 6 про «оператор в петле»).

**Повторный delegated** (enforcement log_append): другой агент на
открытый task_id — continuation без флагов; тот же агент —
`--attempt>=2` при СВОЁМ rejected (self-retry) ЛИБО чужой rejected +
сигнал новой версии объекта ревью после последнего delegated этого
агента (новый delegated другого агента / rejected agent=lead /
escalated model не ниже привязки; один сигнал = один вход; известные
остатки признака R-1..R-4 — bugs/AT-BUG-034.md, по evidence), ЛИБО
`--replaces-worker <прежний worker_ref>` (замена умершего воркера,
маркер — голый ref), ЛИБО после настоящего `--reopen-task` (новая
итерация жизненного цикла). Закрытый task_id — только
`--reopen-task`. rejected/defect_found ПОСЛЕ accepted переоткрывает
задачу (признанное отличие от OS: поздний дефект штатно —
defect_found с ref).

## Дисциплина команд (permission hygiene)

Каждая «своя» форма команды = permission-запрос. Правила для ВСЕХ
сессий и субагентов; детектор нарушений — hygiene_gate + чек 5
калибровки + /permission-audit.

1. **Канонические формы:** pytest фреймворка —
   `powershell -NoProfile -ExecutionPolicy Bypass -Command
   ". D:\AO3_tests\scripts\tasks.ps1; Invoke-Pytest <args>"`;
   скрипты обвязки — `python scripts/<имя>.py` из корня (их тесты —
   `python -m pytest scripts/tests -q`); adb/устройство — только
   через env.ps1/tasks.ps1 (присутствие — `Get-Device`;
   `Start-Emulator` сам ждёт буты); git в OS-репо — одна форма
   `cd /d/Improving_AI/Operating-System-for-LLMs && git <cmd>`.
2. Не префиксовать `cd <dir> && ...` в своём репо и не добавлять
   хвост ` 2>&1` — ломает совпадение с allowlist. **`$env:VAR` в
   Bash-туле запрещён** (конвенция 2026-08-20, класс AT-BUG-091,
   4 экземпляра): Bash схлопывает `$env:` в пустоту ДО передачи в
   `powershell -Command "..."` даже в double-quoted — env-зависимые
   вызовы tasks.ps1 только PowerShell-тулом. Детектор: критик-гейт
   прогонов; первый рецидив после конвенции → код-гейт hygiene_gate
   (порог в AT-BUG-091).
3. Правки файлов — только Edit/Write-тулами (не python-хиредоки,
   не `python -c "...replace..."`).
4. Журналы конвейера — только через `python scripts/log_append.py`
   (`routing --event ... --model ...` / `orchestrator "правило"
   "агент" "артефакт" "исход"`): сам ставит ts и enforce'ит формат.
   Не printf с `$(date)`.
5. Установка пакета в venv — только вместе с обновлением
   `framework/requirements.txt` тем же ходом.
6. **Env-негатив ≠ отсутствие объекта:** пустой/ошибочный вывод
   env-зависимого тула — tooling-промах, не факт. Негативное
   утверждение о среде валидно только с позитивной сверкой
   канонической формой. **F-30:** ЛЮБОЕ несущее утверждение о
   состоянии среды — только после ИЗМЕРЕНИЯ; непроверенное — с
   пометкой «оценка, не проверено». **F-34:** пустой результат
   любого поиска — только после позитивного контроля ТОЙ ЖЕ формы
   вызова (регистр, фильтры, синтаксис); Grep-тул по умолчанию
   регистрозависим; сужающий фильтр при негативе перечисляется как
   граница охвата. Детектор: приёмка + чек калибровки.
7. **`.ps1` с кириллицей — только UTF-8 with BOM** (PowerShell 5.1
   без BOM рвёт кириллицу → ParserError).
8. **Откат временной порчи файла — только по байтовой копии:**
   фиксация `git status --porcelain -- <файл>` + копия в scratchpad
   ДО порчи; откат — восстановлением копии; `git checkout -- <файл>`
   легален ТОЛЬКО при пустом porcelain до порчи. Witness отката —
   дословный вывод сверки. Детектор: приёмка отклоняет witness без
   сверки + чек 5 калибровки OS.

## Рабочие файлы (housekeeping)

Разовые/временные файлы — в scratchpad сессии; относящиеся к прогону
— в `runs/` как артефакт. НЕ в корень репозитория (скриншоты падений
конвейер прикладывает сам через reporting.py → Allure).

## Роль ≠ ярус (D-0058, F-22)

Три определения — НЕ синонимы:
- **ЯРУС сессии** = её ФАКТИЧЕСКАЯ модель (сверка — п.4а деградации /
  шаг 0 preflight qa-loop). Ярус Lead = СЕМЕЙСТВО Lead-привязки из
  `delegation.config.yaml` (Opus; Fable — резерв выше, тоже полный
  Lead); «Lead» — ярус-функция, не роль в диалоге.
- **РОЛЬ координатора** = МАРШРУТИЗАЦИЯ, не исполнение; её несёт
  любая модель и она НЕ делает сессию Lead'ом: координатор
  распределяет по ярусам и передаёт наверх всё, что выше его.
- **Полный Lead** = ярус привязки ИЛИ выше (резерв); только он меняет
  механизмы, гейты и статусы.

Приёмка — только СВЕРХУ (enforcement: log_append, код-гейт
калибровки №4; матрица легальных basis — секция «Журнал»). Приёмка
равного/высшего яруса без легального входа = самосертификация (F-22).
Матрица по фактическому ярусу координатора:
- **Fable** (резерв выше Lead) — без ограничений; льгота skip.
- **Opus** (= Lead-привязка, D-0099) — ПОЛНЫЙ Lead: без ограничений,
  льгота skip, механизмы/гейты/статусы; принимает opus-класс ФИНАЛЬНО
  без basis (ветка lead-binding, поле `lead_binding`; вердикт критика
  рождён в независимом контексте).
- **Sonnet** — координация, диспатчи; принимает Haiku; Sonnet-класс
  результат — ТОЛЬКО с critic-входом (льгота skip недоступна);
  opus-класс и Lead-класс — в очередь (basis=queued-to-lead).
- Ниже Sonnet координация не предусмотрена.

Штатный режим «оператор координирует с Sonnet, Lead запускается
батчем на очередь Lead-задач» — та же матрица; деградация (ниже) —
незапланированный вход в неё.

## Деградация Lead (D-0039, D-0042)

Модель привязки отказала / лимит подписки — ИЛИ оператор явно
переключил модель на ярус ниже (D-0042; инициатор и причина — в
notes события):
1. Ярус ниже (Sonnet) + `lead_degraded` (причина, рамки участка).
2. Пока деградирован: рутинная координация продолжается, но НЕ
   меняются статусы делегационной таблицы, НЕ подписываются гейты;
   архитектурные решения — в очередь полного Lead; приёмка — по
   матрице «Роль ≠ ярус».
3. Возврат — по умолчанию: на модель привязки (или выше —
   Fable-резерв) + `lead_restored` с ПРИЁМКОЙ ОКНА (D-0044): журнал
   и диффы окна ВО ВСЕХ репо, которых касалась сессия; пустое окно
   отмечается явно. Разбор очереди отложенных решений — отдельная
   работа, приёмку не заменяет. Деградация, пережившая сессию,
   фиксируется последним событием журнала.
4. **Сверка яруса в ОБЕИХ точках (F-21):**
   (а) **Вход** — перед первым Lead-действием сессии: сверь модель по
   видимому сигналу с ярусом привязки; ниже, и журнал не открывает
   окно → `lead_degraded` ДО действия (для /qa-loop — шаг preflight).
   (б) **Выход** — видимый подъём сам по себе ДОКАЗАТЕЛЬСТВО окна,
   независимо от наличия события (отсутствие записи ≠ отсутствие
   факта) → тем же ходом: ретро-`lead_degraded` + приёмка окна +
   `lead_restored`.
   (в) **Внешняя сеть** — чек калибровки OS по транскриптам (ловит
   отказ обеих точек).
